# 热成像功能 - 经验总结

## 一、项目目标

在所有游戏模式（非仅Nano6）下实现热成像透视效果。

## 二、核心困难

### 困难1：IL2CPP的MethodInfo*隐藏参数

IL2CPP编译后，每个方法调用都需要一个隐藏的 `MethodInfo*` 参数，它不是函数逻辑参数，而是IL2CPP运行时的元数据指针。

- **影响**：直接用NativeFunction调用游戏函数时，少传这个参数就会崩溃（access violation at 0x4）
- **获取方式**：可通过 `il2cpp_class_get_method_from_name` 导出函数获取，但需要先拿到正确的klass指针
- **教训**：IL2CPP逆向中，任何函数调用都必须考虑MethodInfo*，否则必崩

### 困难2：模式锁定的初始化逻辑（根本原因）

`CameraManager.Awake()` 中有 `if (gameMode == 5)` 条件判断，仅在Nano6模式下初始化：

| 字段 | Nano6 | 其他模式 |
|------|-------|----------|
| thermalVision | ✅ 有值 | ✅ 有值（VolumeProfile共享） |
| fwdRenderData | ✅ 有值 | ❌ NULL |
| humanCatchFeature | ✅ 有值 | ❌ NULL |

**关键发现**：ThermalVision组件本身存在且参数可写，但 `fwdRenderData` 和 `humanCatchFeature` 为NULL，导致渲染管线断裂——组件参数改了，但渲染器不知道要执行热成像的RenderPass。

### 困难3：Unity URP渲染管线的运行时限制

即使通过补丁或手动设置修复了指针，仍面临：

- URP在启动时根据RendererFeatures列表创建ScriptableRenderer
- 运行时修改Feature列表，已创建的Renderer不会自动重建
- 可能需要调用 `InvalidateRenderer()` 才能生效，但该方法是否暴露给IL2CPP不确定
- **这是最大的不确定性**：指针层面可以补全，渲染管线是否响应是另一回事

## 三、尝试过的方案及结果

| 方案 | 思路 | 结果 |
|------|------|------|
| A: SetThermalVision | 直接调用游戏原生函数 | Nano6 ✅ / 其他模式 ❌（内部依赖humanCatchFeature） |
| B: 直接改组件参数 | 写ThermalVision的active/Duration | 参数写入成功，但无视觉效果（管线断裂） |
| C: Mode_Nano6方法 | 调用Nano6模式专用方法 | ❌ 仅Nano6可用，不符合全模式需求 |
| D: TryGet组件 | VolumeProfile.TryGet<ThermalVision> | 组件能找到，但同样无法解决渲染管线问题 |
| E: 手动初始化+补丁 | NOP条件跳转+URP管线获取 | 待验证，可行性约60% |

## 四、不可行性分析

### 为什么"改参数"不等于"有效果"

```
热成像渲染链路：
VolumeProfile → ThermalVision组件 → ScriptableRendererFeature → ScriptableRenderPass → GPU渲染
                                      ↑
                                   这一步断裂
                                   fwdRenderData=NULL → 无法找到Feature → 无法创建RenderPass
```

组件参数只是数据，真正让画面变化的是RenderPass在每帧渲染时读取这些数据并执行Shader。没有RenderPass，参数再正确也不会有任何视觉效果。

### 为什么补丁Awake()条件跳转可能不够

1. Awake()在场景加载时执行一次，补丁时机可能已过
2. 即使补丁成功，后续代码可能依赖其他仅在Nano6模式下创建的对象
3. Unity渲染管线可能需要完整的初始化流程，而非仅设置几个指针

### 为什么从URP管线获取fwdRenderData存在风险

- 写入fwdRenderData指针 ≠ 渲染器重新初始化
- ScriptableRenderer在管线启动时已创建，运行时添加Feature不会自动注册到渲染循环
- 可能需要触发管线重建，但这在运行时可能引发渲染异常

## 五、结论

**热成像在非Nano6模式下的可行性：约40-60%**

- 数据层（组件、参数）：✅ 可控
- 指针层（fwdRenderData、humanCatchFeature）：⚠️ 可补全
- 渲染层（RenderPass注册与执行）：❓ 最大不确定性

核心矛盾：**Unity URP是"启动时构建渲染图"的架构，运行时修改需要管线配合重建**，这不是简单的指针修补能解决的。

## 六、如果继续尝试

优先级从高到低：
1. 测试v2.3补丁+URP方案，观察实际效果
2. 如果无视觉效果，尝试调用 `UniversalRenderPipeline.InvalidateRenderer()` 强制重建
3. 如果仍不行，考虑Hook渲染循环，在FrameEnd之前手动注入热成像Shader
4. 最后手段：替换整个渲染管线资产为包含热成像Feature的版本

## 七、游戏修改的难易度分层

从IL2CPP游戏修改的通用经验来看，不同层面的修改难度差异巨大：

### ✅ 容易修改（成功率高，95%+）

| 类型 | 原因 | 典型例子 |
|------|------|----------|
| 数值型字段 | 内存中是float/int，直接读写 | 血量、弹药、移动速度、伤害倍率 |
| 布尔型开关 | 单字节0/1翻转 | 无后座力、无限弹药、穿墙开关 |
| 静态数据引用 | 指针已存在，替换即可 | 武器属性、角色数据 |
| 条件判断补丁 | NOP掉跳转指令即可 | 跳过校验、解锁功能 |
| 调用已有函数 | 函数本身完整，只需正确传参 | SetThermalVision（Nano6下） |

**共同特点**：数据已存在于内存中，或代码路径已存在，只需改值/改跳转/正确调用。

### ⚠️ 中等难度（成功率50-80%）

| 类型 | 难点 | 典型例子 |
|------|------|----------|
| 跨模式调用 | 初始化逻辑不同，依赖对象可能缺失 | 非Nano6调SetThermalVision |
| 单例获取 | 需要找到正确的静态字段偏移 | CameraManager.instance |
| MethodInfo* | 隐藏参数，需要额外查找 | IL2CPP函数调用的第三个参数 |
| 运行时创建对象 | 需要调用构造函数并正确初始化 | new一个游戏对象 |
| Hook时机 | 需要在正确的生命周期节点介入 | 补丁Awake()的条件跳转 |

**共同特点**：逻辑链路存在但断裂，需要补全中间环节；或需要理解运行时结构才能正确操作。

### ❌ 难以修改（成功率低，20-40%）

| 类型 | 难点 | 典型例子 |
|------|------|----------|
| 渲染管线注入 | URP启动时构建渲染图，运行时修改不生效 | 热成像RenderPass注册 |
| 运行时添加Feature | ScriptableRenderer不会自动重建 | humanCatchFeature注入 |
| 跨系统联动 | 多个子系统需要同时正确初始化 | 热成像=组件+Feature+Pass+Shader |
| Shader/材质操作 | 需要理解GPU管线和资源绑定 | 自定义后处理效果 |
| 网络同步逻辑 | 修改会被服务端校验或导致不同步 | 位置、伤害等网络数据 |

**共同特点**：不是"改一个值"的问题，而是"让一个系统重新初始化"的问题；或涉及多系统协作，任何一环断裂都导致失败。

### 难度递增规律

```
改数据 →  改流程 →   补逻辑 →   重建系统
  ↑         ↑         ↑         ↑
容易        中等      较难       极难
```

- **改数据**：内存中已存在，直接读写
- **改流程**：代码路径存在，修改跳转让代码走不同分支
- **补逻辑**：代码路径不存在，需要手动补全缺失的初始化步骤
- **重建系统**：整个子系统需要重新初始化，运行时几乎不可能完美还原

### 本项目的位置

热成像功能卡在 **补逻辑 → 重建系统** 的边界：

- ThermalVision组件（改数据）✅ 已解决
- 条件跳转补丁（改流程）✅ 已实现
- fwdRenderData/humanCatchFeature补全（补逻辑）⚠️ 指针可设，效果未知
- URP渲染管线重建（重建系统）❌ 运行时无法完美重建

**教训**：选择修改目标时，优先选择"改数据"和"改流程"层面就能生效的功能，避免需要"重建系统"的目标。

## 八、"重建系统"能否从IDA和dump.cs重构？

以热成像为例，分析信息是否全面、重构是否可行。

### IDA能告诉我们的（信息充分）

从 `CameraManager.Awake()` 的完整反编译，Nano6初始化路径的每一步都清晰可见：

```
步骤1: Volume.get_profile() → 获取VolumeProfile
步骤2: CameraManager.static_fields.volumeProfile = profile
步骤3: VolumeProfile.TryGet<GhostBladeOneShine>() → oneShine
步骤4: VolumeProfile.TryGet<ThermalVision>() → thermalVision
步骤5: this.fwdRenderData.m_RendererFeatures → 获取Feature列表
步骤6: 创建 Predicate<ScriptableRendererFeature> (lambda: Awake_b__19_0)
步骤7: List<ScriptableRendererFeature>.Find(predicate) → humanCatchFeature
步骤8: this.humanCatchFeature = 查找结果
```

**结论：初始化逻辑100%可还原，IDA信息充分。**

### dump.cs能告诉我们的（信息充分）

| 信息 | 是否可获取 | 示例 |
|------|-----------|------|
| 类定义与字段偏移 | ✅ | CameraManager.thermalVision at 0x18 |
| 方法签名 | ✅ | SetThermalVision(float, bool) |
| 继承关系 | ✅ | ForwardRendererData : ScriptableRendererData |
| 泛型实例化 | ✅ | List<ScriptableRendererFeature> |
| 嵌套类型 | ✅ | CameraManager.<>c (lambda容器) |

**结论：类型结构100%可还原，dump.cs信息充分。**

### 信息充分但仍不可行的原因

**问题不在"不知道怎么做"，而在"做了不生效"。**

```
我们知道要做什么：                    但运行时无法生效：
                                   
1. 获取fwdRenderData    ✅ 能做到    → 指针写入成功
2. 找到humanCatchFeature ✅ 能做到    → 指针写入成功  
3. 设置thermalVision    ✅ 能做到    → 参数写入成功
4. 让URP执行RenderPass  ❌ 做不到    → 渲染器已创建，不读新数据
```

关键断裂点：`ScriptableRenderer` 在管线启动时从 `ScriptableRendererData` 创建，之后只执行已注册的 RenderPass 列表。运行时修改 Data 不会更新 Renderer 的 Pass 列表。

### 具体缺失的"重建"能力

| 需要的能力 | IDA中是否存在 | 说明 |
|-----------|-------------|------|
| InvalidateRenderer() | ❌ 未找到 | 强制URP重建渲染器的方法不存在 |
| ScriptableRenderer重建入口 | ❌ 未导出 | 构造函数存在但无法安全调用 |
| AddRenderPasses动态注入 | ❌ 架构不支持 | 该方法是Renderer调Feature，不是外部调Renderer |
| 运行时Feature注册 | ❌ 非标准流程 | Unity设计上不支持运行时添加Feature |

### 可行性评估

```
信息层面：  ████████████████████ 100%  （IDA+dump.cs完全够用）
逻辑层面：  ██████████████████░░  90%  （初始化步骤可完整还原）
指针层面：  ████████████████░░░░  80%  （所有指针可手动设置）
渲染层面：  ████░░░░░░░░░░░░░░░░  20%  （URP不响应运行时修改）
```

**综合可行性：约30-40%**

### 核心结论

**IDA和dump.cs提供的信息是充分的，"重建系统"不可行的原因不是信息不足，而是架构限制：**

1. **信息问题可以解决** — 逆向工具能完整还原初始化逻辑
2. **架构问题无法绕过** — URP渲染管线是"启动时构建、运行时只读"的设计
3. **类比**：就像你知道发动机怎么组装（信息充分），但车已经在高速上跑了，你没法停车重新组装发动机（架构限制）

### 如果一定要突破

唯一可能绕过架构限制的路径：

1. **Hook渲染循环** — 在 `ScriptableRenderer.AddRenderPasses` 中注入代码，直接将 ThermalVisionPass 添加到每帧的渲染队列（不依赖Feature注册机制）
2. **替换管线资产** — 修改内存中的 UniversalRenderPipelineAsset，让它的 RendererData 包含热成像Feature，然后触发场景重新加载
3. **直接操作CommandBuffer** — 绕过URP的Feature/Pass机制，用 Camera.AddCommandBuffer 在渲染的特定阶段注入热成像Shader

这三条路都超出了"从IDA重构"的范畴，属于**自己写渲染代码**而非**还原游戏逻辑**。
