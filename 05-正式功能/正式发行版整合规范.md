# 正式发行版整合规范

这份文档专门给“把单功能整合进 `04-正式发行版`”时使用。

核心目的只有一个：新增功能可以进来，但不能把整合包越改越乱。

## 1. 一句话原则

正式发行版不是试验田。

新功能必须先在 `06-测试` 或 `05-正式功能` 跑通，再进入 `04-正式发行版`。整合时只迁移成熟逻辑，按整合包架构接入，不把测试代码、临时代码、独立 UI 逻辑直接复制进去。

## 2. 整合前先确认

整合前先问清楚这几件事：

- 这个功能在单功能版本里是否已经跑通。
- 是否已经确认 Hook 点、RVA、字段偏移。
- 是否已经用 IDA MCP 或 IDA 索引看过真实逻辑。
- 是否清楚功能开启、关闭、退出清理分别要做什么。
- 是否会影响已有功能，比如武器、时间、角色状态、回合、UI 快捷键。
- 是否需要 UI 控件，是开关、按钮、滑块、下拉框，还是独立页面。
- 是否需要保存配置，比如倍率、快捷键、武器 ID、开关状态。
- 是否需要 RPC 导出，Python 是否要主动调用 JS。
- 是否需要 JS 主线程调度，比如调用 Unity API。

如果这些没确认，不要直接改整合包。

## 3. 复制新版，不直接覆盖旧版

整合新功能时，优先复制一份最新整合包作为新版本：

```text
04-正式发行版/全功能整合包1.8
  -> 04-正式发行版/全功能整合包1.9
```

不要直接在旧稳定版本上大改。

好处：

- 旧版本随时可回退。
- 新旧版本可以对比差异。
- 出问题时能确认是新功能的问题，还是历史问题。

## 4. 目录职责

整合包里每层只做自己的事。

```text
game_modifier/
├── core/          基础能力、服务、配置、状态、日志、外部适配
├── features/      功能注册和功能元数据
├── scripts/       Frida JS Hook 逻辑
├── ui/            界面、控制器、视图
├── data/          用户配置和运行配置
├── resources/     图片、音效、图标等资源
└── tests/         代码层面回归测试
```

更细一点：

| 目录 | 应该放什么 | 不应该放什么 |
| --- | --- | --- |
| `ui/views/` | 创建控件、布局、文案、返回控件句柄 | Frida 调用、JSON 读写、Hook 逻辑 |
| `ui/controllers/` | 按钮点击、滑块变化、事件响应、UI 状态编排 | RVA、内存地址、文件读写细节 |
| `ui/state/` | 界面状态对象 | 游戏 Hook 逻辑 |
| `core/services/` | 功能启停、连接游戏、RPC 调用封装 | 具体控件布局 |
| `core/repositories/` | JSON 读写、默认值、旧配置兼容 | UI 控件、Frida Hook |
| `core/adapters/` | 外部事件转成程序内部事件 | 业务决策 |
| `features/` | 功能 ID、名称、分类、JS 文件绑定 | 复杂业务逻辑 |
| `scripts/` | Frida Hook、NativeFunction、内存读写、RPC 边界 | Python UI 逻辑 |

一句话：UI 不懂 Hook，JS 不懂界面，Repository 不懂业务，Service 不懂布局。

## 5. 解耦原则

### 5.1 单一职责

一个文件只负责一类事情。

如果一个方法同时做 UI、读 JSON、调用 Frida、更新日志，它就该拆。

判断标准：

- 控件创建放 `view`。
- 用户操作流程放 `controller`。
- 游戏动作封装放 `service`。
- 配置读写放 `repository`。
- 运行状态放 `state`。
- Frida Hook 放 `scripts`。

### 5.2 UI 不能直接操作 Frida

不推荐在 UI 里直接写：

```python
self._frida.call_export(...)
self._frida.send_toggle(...)
```

推荐路径：

```text
UI 控件
  -> controller
  -> service
  -> frida_manager
  -> JS RPC / toggle
```

这样以后换 UI 框架、改 RPC 名称、换日志处理时，不用到处找散落的调用。

### 5.3 JS 模块必须有生命周期

每个 JS 功能模块尽量统一提供：

```js
enable()
disable()
cleanup()
isEnabled()
```

含义不要混：

- `enable()`：用户要开启功能。
- `disable()`：用户手动关闭功能，尽量恢复游戏效果。
- `cleanup()`：程序退出、断开连接、重新注入前强制清理。
- `isEnabled()`：返回当前模块运行状态。

`cleanup()` 必须安全、强制、幂等。多调用几次不能崩。

### 5.4 用户意愿和运行效果分开

用户保存的配置是一回事，当前 Frida 会话里的实际效果是另一回事。

例子：

- 用户上次开启了快刀，这个状态可以保存在 JSON。
- 程序退出时清理快刀效果，不应该把 JSON 里的“用户想开启快刀”改成关闭。

退出清理是清理本次注入，不是修改用户选择。

### 5.5 不做无目标大拆

解耦不是把代码拆得越碎越好。

可以顺手拆：

- 正在改的功能边界已经很清楚。
- 旧代码正好挡住新功能接入。
- 拆完能减少重复、降低风险、方便测试。

不要硬拆：

- 只是为了减少行数。
- 拆出来只有一层薄薄转发。
- 功能还不稳定，边界没想清楚。
- 用户只是要小修，结果牵动几十个文件。

## 6. 标准化命名

新增功能必须有稳定的英文 ID。

建议格式：

```text
feature_id: snake_case
Python 文件: feature_22_xxx.py
JS 文件: 22-xxx.js 或 xxx.js，按当前整合包风格来
RPC 名: lowerCamelCase 或现有风格，不能混乱
UI 文案: 中文给用户看
日志模块名: 和 feature_id 对齐
```

同一个功能不要出现多个叫法。

例如不要一会儿叫：

```text
weapon_giver
give_weapon
weaponGive
武器赋予功能
```

应该绑定清楚：

```text
weapon_giver（赋予武器）
```

文档、代码、日志、配置都尽量用同一个 ID。

## 7. 新功能必须接入的位置

常见新增功能至少要检查这些点：

| 文件/目录 | 作用 |
| --- | --- |
| `core/config.py` | 功能信息、路径、资源、常量 |
| `features/feature_xx_name.py` | 功能定义 |
| `features/__init__.py` | 导入功能，触发注册 |
| `scripts/xx-name.js` | Frida Hook 和 RPC |
| `core/frida_manager.py` | RPC 导出、JS 消息处理、日志路由 |
| `core/services/` | Python 对 JS 的调用封装 |
| `core/repositories/` | 需要持久化时读写 JSON |
| `ui/views/` | 控件布局 |
| `ui/controllers/` | 用户操作流程 |
| `ui/app.py` | 只做接线和生命周期入口 |
| `data/` | 默认配置或用户配置 |
| `新增内容.md` | 记录本次改动 |

不是每个功能都要改全部文件。原则是：需要哪层能力，就接入哪层；不要把所有东西塞进一个文件。

## 8. Feature 注册规范

功能注册要完整，否则容易出现“UI 看得到，但 JS 没加载”或者“Python 调不到功能”。

检查项：

- `features/feature_xx_name.py` 存在。
- 继承现有 `FeatureBase` 或当前版本使用的功能基类。
- 使用现有注册方式，不要发明新的注册系统。
- `feature_id` 和配置、UI、JS 模块名一致。
- `js_filename` 指向正确脚本。
- `features/__init__.py` 已导入这个 Feature。
- 启动程序时没有“未知功能”或“模块未加载”错误。

## 9. JS 脚本整合规范

不要把单功能 JS 整个复制进整合包就完事。

必须迁移：

- Hook 地址、RVA、字段偏移。
- 核心判断逻辑。
- 内存读写逻辑。
- NativeFunction 定义。
- 玩家/人机/模式判断。
- 必要的主线程调度逻辑。

必须改成整合包规范：

- 日志 API。
- RPC 入口。
- `enable / disable / cleanup` 生命周期。
- 错误返回格式。
- 状态变量命名。
- 模块注册方式。

不应该迁移：

- 临时调试按钮。
- 大量刷屏日志。
- 独立版 Python UI 适配逻辑。
- 测试阶段的硬编码临时参数。
- 已经被整合包公共模块提供的重复工具。

## 10. RPC 规范

Python 主动调用 JS 时，走 RPC。

原则：

- RPC 名称稳定，不要频繁改。
- 每个 RPC 都要有参数校验。
- 返回值统一用对象，至少包含 `ok`。
- 失败时返回 `msg`，开发细节进日志。
- Python 侧不要假设一定成功。

推荐返回：

```js
return {
  ok: true,
  data: {}
};
```

失败：

```js
return {
  ok: false,
  msg: "请先进入房间"
};
```

Python 侧：

```python
result = service.do_action(...)
if not result.get("ok"):
    show_user_message(result.get("msg", "操作失败"))
```

不要在 UI 里直接拼 RPC。

## 11. 日志规范

日志分两类：用户日志和开发日志。

用户日志给玩家看，要简短、能行动：

- “请先进入房间后再试”
- “功能暂未就绪，请重新连接游戏”
- “已开启，下回合生效”

开发日志给排查用，可以包含：

- RVA
- 指针地址
- Hook 名称
- NativeFunction
- GameAssembly
- 异常堆栈
- taskId
- 当前模式和对象状态

不要把开发细节刷到 UI。

JS 里优先用现有日志函数：

```js
sendUserLog(...)
sendDevLog(...)
sendBothLog(...)
```

旧 `sendLog(...)` 不要继续扩散。

## 12. UI 整合规范

先判断功能适合哪种 UI：

| 功能类型 | UI 形式 |
| --- | --- |
| 一个开关 | 普通功能卡片 |
| 开关 + 1 到 2 个参数 | 宽功能卡片或带滑块卡片 |
| 一次性动作 | 按钮卡片 |
| 多个输入、列表、复杂配置 | 独立页面 |
| 特定模式专用功能 | 放进对应模式页面 |

UI 只负责让用户操作舒服，不负责业务细节。

要求：

- 文案说人话，不堆技术名词。
- 操作失败要告诉用户下一步。
- 控件状态要和真实状态同步。
- 未连接、未进房间、功能未就绪时，要禁用或给提示。
- 不要为一个简单功能新建复杂页面。
- 不要把复杂配置硬塞进小卡片。

## 13. 配置和数据规范

需要保存的东西统一进 `data/`，通过 repository 读写。

适合保存：

- 功能开关意愿。
- 滑块倍率。
- 快捷键绑定。
- 武器 ID。
- 用户选择的模式或配置。

不适合保存：

- 本次 Frida 会话里的对象指针。
- Hook 是否已经安装。
- 当前房间里的临时玩家对象。
- 本次运行里的任务队列。
- 当前 NativeFunction 引用。

配置文件要考虑：

- 文件不存在时用默认值。
- 旧版本字段缺失时能兼容。
- JSON 坏了时不要让程序直接崩。
- 写文件失败要有开发日志。

## 14. 主线程和 Hook 安全

Unity API、GameManager、GiveWeapon、Transform 等很多逻辑必须注意线程。

原则：

- 不确定线程安全时，不要在任意 Hook 回调或 RPC 里直接调用 Unity API。
- 可以通过 `ModeBase.Update` 等主线程 Hook 做任务队列调度。
- 不要在初始化时立刻调用危险 NativeFunction。
- 不要在 `onLeave` 里乱调游戏函数。
- Hook 回调里要做空指针检查。
- 切房间、复活、退出房间后，旧对象指针可能失效。

能不缓存指针就不缓存。必须缓存时，要有有效性检查和清理时机。

## 15. 功能冲突处理

多个功能可能改同一个地方。

常见冲突：

- 多个功能 Hook 同一个函数。
- 多个功能都修改武器射速、后座、子弹。
- 多个功能都改时间或回合状态。
- 多个功能都依赖玩家对象或 GameManager。
- `Interceptor.replace` 互相覆盖。
- 一个功能关闭时把另一个功能需要的状态恢复掉。

处理原则：

- 同一个 Hook 点尽量集中管理。
- 能用共享 Hook 分发，就不要多个模块各装一遍。
- 修改同一个字段时，要明确优先级。
- 关闭一个功能时，只恢复自己改过的内容。
- 整合后必须做组合测试。

## 16. 错误处理原则

不要静默吞异常。

不推荐：

```python
except Exception:
    pass
```

推荐：

```python
except Exception as exc:
    dev_log.exception("xxx failed")
    user_log("操作失败，请稍后重试")
```

JS 也一样：

- 用户知道结果。
- 开发日志知道原因。
- 失败要返回，不要假装成功。

## 17. 测试和验收

AI 负责代码层面验证，用户负责游戏效果验证。

AI 至少检查：

- Python 文件能编译。
- JS 文件语法通过。
- 相关单元测试通过。
- 新功能注册完整。
- RPC 名称能对应。
- UI 调用路径存在。
- 没有把旧功能无关代码改掉。
- 中文没有乱码。
- 用户日志没有出现 Hook、RVA、指针等开发细节。

用户重点测试：

- 游戏是否闪退。
- 功能是否真的生效。
- 开启、关闭是否正常。
- 切房间、重进房间是否正常。
- 多模式是否正常。
- 多个功能同时开启是否冲突。
- 打包后 EXE 是否能启动和连接。

## 18. 整合完成检查清单

整合完至少过一遍：

- [ ] 新版本目录已复制，不是在旧稳定版上直接大改。
- [ ] 新功能 ID 统一。
- [ ] Feature 已注册。
- [ ] JS 脚本已接入。
- [ ] RPC 已导出，Python 侧调用路径正确。
- [ ] UI 已接入，控件状态能同步。
- [ ] 配置需要保存的已进 repository。
- [ ] `enable / disable / cleanup` 边界清楚。
- [ ] 用户日志和开发日志已区分。
- [ ] 没有新增旧式 `sendLog(...)`。
- [ ] 没有把业务逻辑继续堆进 `ui/app.py`。
- [ ] 没有直接在 UI 里散落 `call_export`。
- [ ] 没有修改无关旧功能。
- [ ] 旧功能的文件差异已经看过。
- [ ] Python 编译检查通过。
- [ ] JS 语法检查通过。
- [ ] `新增内容.md` 已记录本次改动。
- [ ] 需要用户手动测试的点已经列出来。

## 19. AI 整合时的禁区

AI 不要做这些：

- 不要为了“看起来更整洁”重写旧功能。
- 不要在没要求的情况下改 UI 风格。
- 不要改旧功能的 Hook 点。
- 不要把单功能独立 UI 直接塞进整合包。
- 不要凭空创造不存在的 `FridaManager` 方法。
- 不要把 `call_export` 写成另一个项目里的调用方式。
- 不要把开发日志刷进用户界面。
- 不要把 JSON 状态和运行期状态混在一起。
- 不要把程序退出清理当成用户关闭功能。
- 不要删除特殊处理逻辑，除非能解释它为什么已经没用。

## 20. 推荐给 AI 的固定提示词

整合新功能前，可以直接把下面这段给 AI：

```text
请先阅读：
1. 05-正式功能/AI快速上手.md
2. 05-正式功能/正式发行版整合规范.md
3. 04-正式发行版/最新整合包/AI协作开发操作文档.md
4. 04-正式发行版/最新整合包/game_modifier/docs/程序规范.md

本次任务是把单功能整合到正式发行版。

要求：
- 先判断这个功能属于 view / controller / service / repository / state / adapter / feature / script 哪几层。
- 不要把业务逻辑继续堆进 ui/app.py。
- 不要修改无关旧功能。
- JS 必须有清楚的 enable / disable / cleanup 边界。
- Python 调 JS 优先走 service，再由 service 调 Frida RPC。
- 用户日志和开发日志分开。
- 整合后列出改了哪些文件、为什么改、如何验证。
- 如果需要用户进游戏手动测试，请列出具体测试点。
```

## 21. 最后提醒

整合不是“把代码复制进去能跑就行”。

真正好的整合应该满足：

- 新功能能生效。
- 旧功能不受影响。
- 目录职责仍然清楚。
- 状态不会互相污染。
- 出问题时日志能定位。
- 下一个 AI 接手时能看懂。

能做到这些，整合包才会越做越稳，而不是越做越重。
