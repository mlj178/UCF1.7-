# Unity IL2CPP 时间加速 - 经验总结

## 一、方法概述：与传统 Hook 的区别

### 传统做法（Hook 函数）
- Hook 某个函数，在函数执行时拦截修改参数或返回值
- 依赖目标函数被调用才能生效，不调用就不生效
- 适合：修改函数参数、过滤返回值

### 本次做法（icall 解析 + 机器码分析 + 直接写内存）
- 不 Hook 任何函数，而是**定位变量地址，直接写内存**
- 定位方式：`il2cpp_resolve_icall` → 引擎函数指针 → 反汇编机器码 → 提取变量地址
- 不依赖函数调用时机，配合定时刷新可持续生效
- 适合：修改全局状态/属性值，尤其是没有 setter 的情况

### 为什么不用 Hook？
- `Time.timeScale` 没有 `set_timeScale` icall（dump.cs 确认），无法通过 Hook setter 实现
- 即使 Hook `get_timeScale`，也只能改返回值，游戏内部读取的值不变，效果不完整
- 直接写内存修改源数据，游戏所有读取该值的地方都会受影响

## 二、完整流程

```
1. il2cpp_resolve_icall("UnityEngine.Time::get_timeScale()")
   → 返回引擎DLL中的真实函数地址（不是GameAssembly.dll中的桩）

2. 调用引擎函数验证可用性，获取当前值

3. 反汇编引擎函数机器码，提取变量地址信息
   → 全局变量模式：直接得到地址
   → 结构体成员模式：得到 helper 函数 + 偏移，调用 helper 获取指针再 +偏移

4. 直接 writeFloat() 修改变量值

5. 定时刷新（5s）防止游戏覆盖
```

## 三、遇到的问题与解决方案

### 问题1：unable to find method 'setTimeScale'

**原因**：Frida Python 绑定会自动将 `snake_case` 转为 `camelCase`：
- Python 调用 `script.exports.set_time_scale()` → Frida 内部查找 JS 的 `setTimeScale`
- 但 JS 定义的是 `set_time_scale`，找不到所以报错

**解决**：JS 的 `rpc.exports` 方法名必须用 **camelCase**：
```javascript
// 错误
rpc.exports = { set_time_scale: function() {} }

// 正确
rpc.exports = { setTimeScale: function() {} }
```

### 问题2：invalid abi specified

**原因**：Frida 不认识 `'cdecl'` 这个 ABI 字符串

**解决**：Windows 32位 Microsoft cdecl 的正确值是 **`'mscdecl'`**：
```javascript
// 错误
new NativeFunction(addr, 'pointer', ['pointer'], 'cdecl')

// 正确
new NativeFunction(addr, 'pointer', ['pointer'], 'mscdecl')
```

### 问题3：从 GameAssembly.dll 桩函数中找不到 fld [addr] 模式

**原因**：GameAssembly.dll 中的 `get_timeScale` 是**延迟解析桩**（lazy resolution stub），不是真正的引擎实现：
```asm
; GameAssembly.dll 中的桩函数
cmp  dword_10E64BDC, 0       ; 检查icall是否已解析
jnz  short loc_xxx            ; 已解析则跳转
push offset "UnityEngine.Time::get_timeScale()"
call il2cpp_resolve_icall     ; 解析icall
add  esp, 4                   ; cdecl清理栈
mov  dword_10E64BDC, eax      ; 保存函数指针
jmp  dword_10E64BDC           ; 跳转到引擎DLL中的真正实现
```
桩函数里只有 `cmp/jnz/push/call/add/mov/jmp`，没有 `fld` 指令。

**解决**：用 `il2cpp_resolve_icall` 直接获取引擎DLL中的真实函数地址，分析引擎函数的机器码。

### 问题4：引擎函数不是全局变量模式，而是结构体成员模式

**原因**：之前只匹配了 `D9 05`（`fld dword ptr [imm32]`，全局变量），但实际引擎函数是：
```asm
e8 bb d9 c9 ff       ; call GetTimeManager() → eax = 结构体指针
d9 80 ec 00 00 00    ; fld dword ptr [eax+0xEC] → 读取timeScale
c3                   ; ret
```
`D9 80` = `fld dword ptr [eax+disp32]`，timeScale 是结构体成员，偏移 0xEC。

**解决**：新增 `call + fld[eax+disp32]` 模式匹配：
1. 从 `E8` 指令提取 helper 函数地址
2. 从 `D9 80` 指令提取偏移 0xEC
3. 调用 helper 获取结构体指针
4. 结构体指针 + 0xEC = timeScale 变量地址

## 四、关键知识点

### 涉及的 DLL 及职责
- **GameAssembly.dll** — 读取 `il2cpp_resolve_icall` 导出函数
  - IL2CPP 运行时入口，只有它导出了 `il2cpp_resolve_icall`
  - 里面的 `get_timeScale` 只是延迟解析桩，没有真正的引擎实现
- **UnityPlayer.dll** — 读取引擎函数机器码，定位 timeScale 变量地址
  - `il2cpp_resolve_icall` 返回的函数指针指向这里
  - 真正的 `fld dword ptr [eax+0xEC]` 在这个 DLL 里
  - timeScale 变量（结构体成员）的内存也在这个 DLL 的数据段
- 简单说：**从 GameAssembly.dll 拿解析函数，解析后跳到 UnityPlayer.dll 找变量**

### IL2CPP icall 机制
- IL2CPP 将 C# 的 `[MethodImpl(MethodImplOptions.InternalCall)]` 方法编译为桩函数
- 桩函数首次调用时通过 `il2cpp_resolve_icall` 解析到引擎DLL中的真实实现
- `il2cpp_resolve_icall` 可以直接调用，无需等游戏触发桩函数

### 32位 Windows 调用约定
- `il2cpp_resolve_icall`：cdecl（调用者清理栈，IDA中可见 `add esp, 4`）
- 引擎函数（float返回）：cdecl（返回值在 FPU 栈 st(0)）
- Frida NativeFunction ABI：`'mscdecl'`（不是 `'cdecl'`）

### x86 浮点加载指令模式
| 指令 | 字节码 | 含义 |
|------|--------|------|
| `fld dword ptr [imm32]` | `D9 05 xx xx xx xx` | 全局变量 |
| `fld dword ptr [eax+disp32]` | `D9 80 yy yy yy yy` | 结构体成员 |
| `movss xmm0, [imm32]` | `F3 0F 10 05 xx xx xx xx` | SSE全局变量 |
| `movss xmm0, [eax+disp32]` | `F3 0F 10 80 yy yy yy yy` | SSE结构体成员 |

### Frida RPC 命名规则
- Python 端 `snake_case` 自动映射为 JS 端 `camelCase`
- JS 的 `rpc.exports` 必须用 `camelCase` 命名

### 恢复正常速度的实现
- 解锁时调用 `unlockTimeScale()`，做了三件事：
  1. `_locked = false` — 关闭锁定标志
  2. `stopRefresh()` — 停止定时刷新
  3. `setTimeScale(1.0)` — 直接写内存，将 timeScale 变量值改为 1.0
- 本质就是 `writeFloat(变量地址, 1.0)`，和加速时写其他值是同一个操作

### 定时刷新间隔（500ms vs 5s）为何不影响效果
- 定时刷新的作用：当 `_locked=true` 时，周期性检查 timeScale 是否被游戏改回，如果被改回则重新写入目标值
- 但实际上游戏并不会持续覆盖 timeScale。`Time.timeScale` 只在特定时机被游戏代码设置（如场景加载、暂停/恢复），不是每帧重写
- 所以一旦写入目标值，它会一直保持到游戏主动修改它为止，刷新间隔长短没有实质区别
- 刷新间隔的意义仅在于：如果游戏在某个时刻把 timeScale 改回 1.0，间隔越短恢复越快，但实际游戏中这种覆盖很少发生
