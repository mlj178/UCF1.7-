# AI 快速上手说明

这份文档给新开的 AI 会话用。先读这里，再动手分析功能。

## 0. 本文档职责

本文档只负责说明项目背景、游戏基础信息、逆向资料位置、常用判断入口和当前正式包结构。

它不重复写单功能开发流程，也不重复写正式发行版接入细节：

```text
单功能研发步骤：看《单功能开发-可复用流程.md》
单功能交付标准：看《01-单功能开发规范：面向正式发行版.md》
运行期安全规则：看《单功能开发-生命周期规范.md》
整合包2.1接入：看 04-正式发行版/00-正式发行版功能接入规范.md
```

如果本文档和上面专项文档冲突，以专项文档为准。

## 1. 这个项目是什么

项目是 `UnityCrossFire 1.7` 的游戏修改器。

- 游戏进程：`UnityCrossFire.exe`
- 游戏路径：`D:\BaiduNetdiskDownload\UnityCrossFire1.7.1\UnityCrossFire1.7.1\UnityCrossFire.exe`
- 游戏引擎：Unity 2020.3.30f1
- 编译方式：IL2CPP
- 位数：32 位 x86
- 核心 DLL：`GameAssembly.dll`
- Frida 调用约定：Windows x86 IL2CPP 通常用 `'mscdecl'`
- IDA 基址：`0x10000000`
- 实际地址：`IDA基址 + RVA`

一句话理解：这是一个用 Frida 改 IL2CPP 游戏逻辑的项目，Python/CustomTkinter 负责界面，JS 负责 Hook 和内存修改。

## 2. 先读哪些文件

每次新功能开始前，按这个顺序读：

1. 本文档
   - 先确认项目、游戏、资料路径和技术红线。
2. `05-正式功能/单功能开发-可复用流程.md`
   - 决定怎么从需求走到最小实现。
3. `05-正式功能/01-单功能开发规范：面向正式发行版.md`
   - 决定单功能目录、RPC、文档、测试、交付物怎么写。
4. `05-正式功能/单功能开发-生命周期规范.md`
   - 决定 Hook、指针、cleanup、切房间、进房后二次应用怎么做。
5. 同类成功功能目录
   - 写新功能时优先参考同类功能，不要自己发明一套新结构。
6. `04-正式发行版/00-正式发行版功能接入规范.md`
   - 只有准备迁移到整合包时再读。当前正式重点是 `全功能整合包2.1`。

## 3. 数据去哪里找

核心逆向资料都在：

`01-游戏逆向分析-相关信息/`

里面主要有三块：

### Il2CppDumper

路径：

`01-游戏逆向分析-相关信息/Il2CppDumper/`

常用文件：

- `dump.cs`：看类名、方法名、字段偏移、方法签名。
- `script.json`：看方法 RVA。
- `stringliteral.json`：查游戏字符串。
- `il2cpp.h`：看 IL2CPP 结构。

用法：先用 `dump.cs` 找类和字段，再用 `script.json` 找 RVA。

### IDA 汇编代码

路径：

`01-游戏逆向分析-相关信息/IDA-汇编代码/`

常用位置：

- `切分输出/`：IDA 导出的汇编代码，按 part 和 chunk 切分。
- `索引文件/ida_index_v3_1/`：IDA 索引。
- `索引文件/ida_index_v3_1/indexes/`：函数、类、方法、交叉引用等 JSON/JSONL 索引。
- `索引文件/ida_index_v3_1/IDA Index V3.1 最终报告.md`：索引说明和统计。

重要索引：

- `ida_functions.jsonl`：IDA 函数索引。
- `ida_methods.jsonl`：IDA 方法索引。
- `ida_classes.json`：IDA 类索引。
- `ida_xrefs.jsonl`：交叉引用。
- `ida_dumpcs_map.jsonl`：IDA 和 dump.cs 的对应关系。
- `dumpcs_methods.jsonl`：dump.cs 方法索引。
- `dumpcs_fields.jsonl`：dump.cs 字段索引。

如果索引查询脚本不存在，就直接用 `rg` 搜索 JSONL，或者用 IDA MCP 查询。

### AssetStudio

路径：

`01-游戏逆向分析-相关信息/AssetStudio/`

用途：

- 查资源、武器名、角色名、UI 名、MonoBehaviour 导出内容。
- 不要一上来全量读取，文件很多，按关键词搜索。

## 4. 查一个新功能的推荐流程

不要直接写代码。先把游戏逻辑查清楚。

1. 用大白话确认目标
   - 例如：只让玩家无限子弹，不影响人机。

2. 在 `05-正式功能/` 找同类成功案例
   - 武器类功能看无限子弹、无后座力、快速换弹、射速。
   - 近战类功能看快刀、攻击范围。
   - 玩家状态看移动速度、跳高失重、金刚不坏。
   - 模式/回合类看无限时间、跳过回合。

3. 在 `dump.cs` 搜索关键词
   - 类名、方法名、字段名都要搜。
   - 记录类、字段偏移、方法 RVA。

4. 用 `script.json` 或索引确认 RVA
   - 不要只靠记忆写地址。

5. 用 IDA MCP 反编译关键函数
   - 必须看真实逻辑。
   - 不要只靠 `dump.cs` 猜。

6. 选 Hook 点
   - 能 Hook 基类就优先 Hook 基类，方便全模式生效。
   - 注意区分玩家、人机、武器归属、游戏模式。

7. 先在 `06-测试/` 做测试功能
   - 跑通后再整理到 `05-正式功能/`。
   - 最后才考虑整合到 `04-正式发行版/`。

## 5. 写新功能放哪里

开发顺序：

```text
05-正式功能/XX-功能名称
  -> 单功能验证稳定
  -> 按 04-正式发行版/00-正式发行版功能接入规范.md 迁移到全功能整合包2.1
```

不要跳过单功能验证直接改整合包。

`05-正式功能/` 里每个功能都是一个独立目录，格式类似：

```text
05-正式功能/
├── 01-无限子弹/
├── 02-无后座力/
├── 03-全模式-无限时间/
├── ...
└── 21-第三人称视角/
```

新功能命名建议：

```text
05-正式功能/22-功能名称/
├── AAAAA-功能名_probe.js       # 可选，只探测
├── AAAAA-功能名_min.js         # 最小核心 JS
├── AAAAA-功能名_ui.py          # 单功能测试 UI
├── manifest.release-draft.json # 面向2.1的接入草稿
├── 功能名-最小实现步骤.md
├── 功能名-生命周期说明.md
└── 经验总结.md
```

这里的单功能 UI 只用于验证，不直接进入 `全功能整合包2.1`。

## 6. 最重要的技术红线

这些不要犯：

- 不要只看 `dump.cs` 就下结论，关键逻辑必须用 IDA MCP 反编译确认。
- 不要自己随便换 Hook 点，先解释为什么选它。
- 不要缓存容易失效的对象指针，切房间、换模式、重生后可能崩。
- 不要高频定时器硬写内存，容易卡顿或闪退。
- 不要在不确定线程安全时乱调 Unity API。
- 不要整合新功能时顺手改旧功能。
- 不要把正确的旧代码重构成另一套写法。
- 不要省略日志，测试阶段日志要能看出 Hook 是否命中、对象是否有效、玩家/人机是否识别正确。

## 7. 常用判断点

常用函数：

| 名称 | RVA | 用途 |
| --- | --- | --- |
| `Weapon.get_isMyWeapon` | `0xB6E1D0` | 判断武器是否属于玩家 |
| `Player.get_isMyPlayer` | `0xB55FD0` | 判断 Player 是否是本地玩家 |
| `ModeBase.Update` | `0xAF6A00` | 主线程 Update，常用于安全调度 |
| `WPN_Gun.ConsumeAmmo` | `0xB61140` | 消耗子弹 |
| `PlayerWeapons.get_isInfinityAmmo` | `0xB17120` | 无限子弹判断 |
| `PlayerWeapons.get_KnifeSpeed` | `0xB170A0` | 刀速 |
| `PlayerWeapons.get_ReloadSpeed` | `0xB170E0` | 换弹速度 |
| `WPN_Knife.GetKnifeAttackData` | `0xB63EC0` | 近战攻击数据 |
| `Entity.OnEntityHurt` | `0x10B3F470` | 实体受伤 |

常用字段：

| 字段 | 偏移 | 用途 |
| --- | --- | --- |
| `Entity.team` | `0x20` | 队伍 |
| `Weapon.data` | `0x68` | 武器数据 |
| `PlayerWeapons.owner` | `0x8` | PlayerWeapons 所属玩家 |
| `PlayerWeapons.Modifier_KnifeSpeed` | `0x44` | 刀速倍率 |
| `WPN_Knife.owner` | `0x30` | 近战武器所属玩家 |
| `Il2CppString.length` | `0x08` | 字符串长度 |
| `Il2CppString.chars` | `0x0C` | UTF-16 字符内容 |

这些地址和偏移只是快速入口。真正写代码前，仍然要用当前文件确认。

## 8. 和用户沟通时怎么输出

用户偏好：简洁、说人话、结构化。

建议输出格式：

```text
目标：
我理解你要做的是...

我查了什么：
1. ...
2. ...

目前判断：
...

推荐方案：
...

风险：
...

下一步：
...
```

如果还没查 IDA，就明确说“这里只是初步判断，还没用 IDA MCP 确认”。

如果需要用户手动测试，就说清楚测试点，不要说“应该没问题”。

## 9. 整合到正式发行版时

当前重点适配 `04-正式发行版/全功能整合包2.1/game_modifier/`。

2.1 是插件式功能目录：

```text
features/<feature_dir>/
├── __init__.py
├── manifest.json
├── feature.py
├── panel.py
├── script.js
└── events.py
```

整合原则：

```text
完整复制已经验证的核心 JS 到插件 script.js
不直接接入单功能 UI
不把 JS 放进 scripts/
不恢复 features.json 或 core/feature_registry.py 这类旧注册表
不为了单个功能修改中心架构
只做 manifest、feature.py、panel.py、events.py、RPC、配置和生命周期适配
```

具体字段、模板、状态恢复、`sync_enabled_from_config`、`room_ready_reapply` 等要求，以：

```text
04-正式发行版/00-正式发行版功能接入规范.md
```

为准。本文档不重复维护接入细节，避免和 2.1 规范互相打架。
