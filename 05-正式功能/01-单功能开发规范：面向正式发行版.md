# 单功能开发规范：面向正式发行版2.1低改造接入

这份规范用于 `05-正式功能/XX-功能名/` 下的所有新功能。

目标不是只让单功能单独跑通，而是让它从开发第一天起就符合正式发行版结构。

## 0. 本文档职责

本文档只规定单功能目录应该交付什么、RPC 怎么统一、文档和测试要补齐到什么程度。

它不重复维护开发顺序、运行期细节、整合包具体字段：

```text
开发顺序：看《单功能开发-可复用流程.md》
运行期生命周期：看《单功能开发-生命周期规范.md》
项目背景：看《00-游戏信息背景-AI快速上手.md》
整合包2.1最终接入：看 04-正式发行版/00-正式发行版功能接入规范.md
```

如果本文档和正式发行版接入规范冲突，以正式发行版接入规范为准。

最终要求：

```text
单功能目录 = 一个可迁移功能包
正式发行版2.1 = 完整复制核心 JS + 补插件壳 + 接 UI
不允许后期重写核心 JS
不允许后期重写 RPC
不允许后期重写状态管理
不允许后期为了整合大改旧功能
不允许恢复旧 scripts/、features.json、core/feature_registry.py 接入方式
```

------

## 1. 核心原则

### 1.1 单功能必须按发行版标准写

以前的错误做法：

```text
05 单功能能跑就行
用自己的 launcher
用自己的 UI 调用方式
用自己的 JS 函数名
后期合并到 04 时再慢慢改
```

新的标准做法：

```text
05 单功能阶段就按 04 发行版接口写
单功能 UI 只是测试壳
JS、RPC、配置、日志、生命周期全部按发行版标准
后期合并只移动文件，不重写逻辑
```

------

## 2. 每个功能必须有唯一 feature_id

每个功能从创建开始就必须确定一个永久 ID。

格式：

```text
snake_case 小写英文
不能用中文
不能随版本变化
不能因为 UI 名称变化而变化
```

例子：

```text
infinite_ammo
no_recoil
fast_reload
third_person_camera
fast_stock
```

这个 `feature_id` 必须同时用于：

```text
核心 JS 注释和日志
manifest.release-draft.json
日志前缀
RPC 调用
配置项 key
2.1 正式 manifest.feature_id
UI 控件绑定名
测试文件名
```

错误例子：

```text
JS 叫 fast_stock.js
Python 叫 jisu_qiangtuo.py
UI 里叫 极速枪托
配置里叫 stockSpeed
RPC 里叫 enableFastButt
```

正确例子：

```text
feature_id: fast_stock
单功能核心 JS: AAAAA-fast_stock_min.js
2.1 插件 JS: features/<feature_dir>/script.js
2.1 Python: features/<feature_dir>/feature.py
配置 key: fast_stock
RPC: enable / disable / status / cleanup / setConfig
日志前缀: [fast_stock]
UI 显示名: 极速枪托
```

------

## 3. 标准单功能目录结构

每个功能目录必须使用这个结构：

```text
05-正式功能/XX-功能名/
├── AAAAA-功能名_probe.js          # 可选，只探测
├── AAAAA-功能名_min.js            # 必须，最小核心 JS
├── AAAAA-功能名_ui.py             # 必须，单功能测试 UI
├── manifest.release-draft.json     # 必须，面向2.1的接入草稿
├── 功能名-最小实现步骤.md
├── 功能名-实现原理.md
├── 功能名-生命周期说明.md
├── 经验总结.md
├── tests/
│   ├── test_功能名_static.py
│   └── check_功能名.js
├── dev/
├── probe/
├── archive/
└── README.md
```

说明：

```text
AAAAA-功能名_min.js        放已经验证的核心 JS，迁移2.1时优先完整复制
AAAAA-功能名_ui.py         只作为单功能测试壳，不直接接入2.1
manifest.release-draft.json 提前记录2.1 manifest 草稿
功能说明文档                放目标、原理、生命周期、经验
tests/                      放静态检查和语法检查
dev/probe/archive/           放临时探测、失败方案、旧版本
```

2.1 正式接入后的目标目录是：

```text
04-正式发行版/全功能整合包2.1/game_modifier/features/<feature_dir>/
├── __init__.py
├── manifest.json
├── feature.py
├── panel.py
├── script.js
└── events.py
```

单功能阶段不要求提前生成完整 2.1 插件目录，但必须保证核心 JS、RPC、配置、生命周期已经按可迁移标准写好。

临时文件不允许参与发行版接入。

## 4. manifest.release-draft.json 是必须文件

每个功能必须提供 `manifest.release-draft.json`。

它的作用是提前记录未来接入 2.1 所需的信息：

```text
功能叫什么
UI 怎么显示
RPC 有哪些
配置项有哪些
依赖哪些 RVA / 字段偏移
生命周期是否需要进房后二次应用
是否同步上一次 enabled 状态
测试怎么跑
```

单功能阶段用草稿文件，不直接冒充 2.1 正式 manifest。正式接入时再按 `04-正式发行版/00-正式发行版功能接入规范.md` 生成：

```text
features/<feature_dir>/manifest.json
```

草稿模板：

```json
{
  "feature_id": "fast_stock",
  "canonical_id": "fast_stock",
  "display_name": "极速枪托",
  "category": "weapon",
  "tab": "weapon_tab",
  "icon": "*",
  "desc": "一句话说明功能效果。",
  "version": "1.0.0",
  "status": "single_feature_verified",

  "single_feature_files": {
    "core_js": "AAAAA-fast_stock_min.js",
    "test_ui": "AAAAA-fast_stock_ui.py"
  },

  "rpc": [
    "enable",
    "disable",
    "status",
    "cleanup",
    "setConfig"
  ],

  "config": {
    "enabled": false,
    "multiplier": {
      "type": "float",
      "default": 1.5,
      "min": 1.0,
      "max": 5.0,
      "label": "倍率"
    }
  },

  "reverse_info": {
    "module": "GameAssembly.dll",
    "arch": "x86",
    "calling_convention": "mscdecl",
    "rva": [],

  },

    "cleanup": true,

  }

```

要求：

```text
manifest.release-draft.json 必须跟代码同步更新
不能等到整合正式版时再补
正式接入时以草稿为输入，生成2.1正式 manifest.json
没有 manifest.release-draft.json 的功能不得标记为 release_ready
```

## 5. JS RPC 必须统一

每个 JS 必须导出同一套 RPC。

固定接口：

```js
rpc.exports = {
    enable() {},
    disable() {},
    status() {},
    cleanup() {},
    setConfig(config) {}
};
```

允许额外增加：

```js
reset(reason) {}
debugDump() {}
```

但正式发行版只依赖固定接口。

### 5.1 enable

职责：

```text
安装 Hook，如果已安装则跳过
设置 Runtime.enabled = true
读取当前配置
记录 enable 日志
```

不允许：

```text
重复 attach Hook
重复启动定时器
缓存 Player/Weapon 后一直用
直接依赖单功能 UI
```

------

### 5.2 disable

职责：

```text
Runtime.enabled = false
停止功能效果
恢复当前 generation 内可安全恢复的原值
清理运行期缓存
清理普通定时器
```

------

### 5.3 cleanup

职责：

```text
关闭功能
清理 Hook
清理定时器
清理缓存
清理原值记录
允许重复调用
```

要求：

```text
cleanup 调用 1 次不能崩
cleanup 调用 10 次也不能崩
UI 退出时必须调用 cleanup
游戏断开时必须调用 cleanup
```

------

### 5.4 status

必须返回结构化状态。

标准返回：

```js
{
    feature_id: "fast_stock",
    enabled: true,
    initialized: true,
    generation: 3,
    hook_hits: 120,
    error_count: 0,
    last_error: "",
    last_reset_reason: "weapon_changed"
}
```

不要只返回字符串。

------

### 5.5 setConfig

正式发行版通过这个接口传配置。

标准：

```js
setConfig(config) {
    Runtime.config = Object.assign(Runtime.config, config || {});
    return true;
}
```

要求：

```text
JS 不能直接读 UI 控件
JS 不能假设配置只在 enable 前设置
配置变化后必须可以实时生效，或者明确写明需要重新 enable
```

------

## 6. JS 内部必须有 Runtime 状态对象

每个 JS 必须有统一 Runtime。

模板：

```js
const Runtime = {
    feature_id: "fast_stock",
    enabled: false,
    initialized: false,
    generation: 0,

    hooks: [],
    timers: [],

    config: {},

    cache: {
        localPlayer: ptr(0),
        currentWeapon: ptr(0)
    },

    originals: {},

    stats: {
        hookHits: 0,
        errorCount: 0,
        cleanupCount: 0,
        lastError: "",
        lastResetReason: ""
    }
};
```

要求：

```text
不要把状态散落成一堆全局变量
不要长期相信 Player* / Weapon*
不要跨房间使用旧指针
必须实现 resetRuntime(reason)
```

------

## 7. Python feature 文件按 2.1 插件适配器写

单功能阶段可以有 `AAAAA-功能名_ui.py` 作为测试壳，但不能把只能自己用的 Python 调用方式当成交付标准。

正式迁移到 2.1 后，每个插件目录的 `feature.py` 必须继承 `PluginFeatureBase`。

2.1 目标模板：

```python
from core.plugin.plugin_base import PluginFeatureBase


class PluginFeature(PluginFeatureBase):
    feature_id = "fast_stock"
    js_filename = "script.js"
    name = "极速枪托"
    icon = "*"
    category = "weapon"
    desc = "一句话说明功能效果。"
```

重点：

```text
不要在单功能 UI 里发明和2.1不同的 RPC 名称
不要写死旧 call_export / scripts 路径作为正式接口
正式版 feature.py 只做插件元数据和通用基类适配
真正游戏逻辑留在 script.js
```

重点：

```text
单功能 UI 必须模拟 enable/disable/status/cleanup/setConfig 调用
不要 UI 直接乱调 script.exports.xxx
不要 launcher.py 绕过标准 RPC
发行版整合时按 2.1 插件模板生成 feature.py
```

------

## 8. 单功能 UI 必须模拟正式发行版调用方式

单功能 UI 只是测试壳。

它必须模拟正式发行版流程：

```text
启动 UI
attach 游戏
加载 JS
创建 Feature 类
调用 feature.enable()
调用 feature.disable()
调用 feature.status()
退出时调用 feature.cleanup()
```

不允许：

```text
UI 直接写死 JS 路径但正式版路径不同
UI 直接调 enableFastStock 这种临时 RPC
UI 没有 cleanup
UI 没有 status
```

------

## 9. 文件命名必须稳定

单功能阶段文件名要稳定，迁移到 2.1 时再映射到插件标准文件名。

标准：

```text
AAAAA-功能名_probe.js
AAAAA-功能名_min.js
AAAAA-功能名_ui.py
manifest.release-draft.json
tests/test_功能名_static.py
```

2.1 目标文件名固定为：

```text
features/<feature_dir>/manifest.json
features/<feature_dir>/feature.py
features/<feature_dir>/panel.py
features/<feature_dir>/script.js
features/<feature_dir>/events.py
```

错误：

```text
极速枪托最终版.js
极速枪托测试2.js
fast_stock_new_ok.js
launcher_fixed.py
最终可用.py
```

临时版本必须放入：

```text
dev/
archive/
```

正式可迁移文件必须永远保持固定名字。

## 10. 日志必须统一

JS 日志前缀：

```text
[feature_id]
```

Python 日志前缀：

```text
[feature_id]
```

必须记录：

```text
load
enable
disable
cleanup
resetRuntime
hook installed
hook hit
pointer invalid
config changed
error
```

日志必须限频，不能刷屏。

## 11. 逆向信息必须写入文档和 manifest

每个功能必须写清：

```text
用到哪些 RVA
用到哪些字段偏移
来源是 dump.cs 还是 IDA
是否已经看过 IDA 汇编/反编译
Hook 点为什么选它
备选 Hook 点是什么
```

不允许：

```text
只在 JS 里写一个 0xB61140
文档不解释地址来源
后期整合时没人知道这个地址干什么
```

## 12. 功能完成前必须通过标准检查

单功能进入“可合并”状态前，必须通过：

```text
manifest.release-draft.json 存在
feature_id 全文件一致
JS 有 enable/disable/status/cleanup/setConfig
JS 有 Runtime
JS 有 cleanupTimers / cleanupHooks / resetRuntime
单功能 UI 通过标准 RPC 调用
node --check 通过
python -m py_compile 通过
静态测试通过
经验总结写完
生命周期说明写完
```

## 13. 单功能状态分级

每个功能必须标注状态。

允许状态：

```text
researching              研究中
probe_done               探测完成
single_feature_min       最小实现
single_feature_verified  单功能已验证
release_ready            可进入正式版
released                 已进入正式版
deprecated               废弃
```

只有 `release_ready` 才允许进入 `04-正式发行版`。

------

## 14. release_ready 标准

满足这些条件才可以标记为 `release_ready`：

```text
1. 单功能 UI 能正常开启/关闭
2. JS RPC 完整
3. cleanup 可重复调用
4. 反复开关不会重复 Hook
5. 切房间不会继续用旧指针
6. 死亡/重生不崩
7. 退出游戏不刷异常
8. manifest.release-draft.json 完整
9. 已明确 2.1 插件 feature.py / panel.py / script.js 映射方式
10. UI 调用方式和发行版一致
11. 不依赖 launcher.py
12. 文档写清 RVA / 字段 / Hook 点
13. 如果依赖房间内对象，已实现 pendingApply / room-ready reapply
```

## 16. 文件编码规范

### 16.1 基本要求

所有新建和修改的文本文件必须使用 UTF-8 编码。

默认使用 UTF-8 无 BOM。

禁止使用 GBK、ANSI、Windows 默认编码保存源码或文档。

### 16.2 适用范围

以下类型的文件必须统一 UTF-8：

```text
.md     文档文件
.py     Python 源码
.js     JavaScript 源码
.json   配置文件
.txt    文本文件
.bat    批处理脚本
.ps1    PowerShell 脚本
.yaml   YAML 配置
.yml    YAML 配置
.ini    配置文件
.cfg    配置文件
.toml   配置文件
```

所有包含中文、emoji、特殊符号的文件，必须确认保存为 UTF-8。

### 16.3 Python 读写规范

Python 读取文本文件时必须显式写：

```python
with open(path, "r", encoding="utf-8") as f:
    content = f.read()
```

Python 写入文本文件时必须显式写：

```python
with open(path, "w", encoding="utf-8") as f:
    f.write(content)
```

### 16.4 JSON 读写规范

Python 写入 JSON 时必须使用：

```python
import json

with open(path, "w", encoding="utf-8") as f:
    json.dump(data, f, ensure_ascii=False, indent=2)
```

Python 读取 JSON 时必须使用：

```python
import json

with open(path, "r", encoding="utf-8") as f:
    data = json.load(f)
```

### 16.5 日志规范

`logging.FileHandler` 必须指定 `encoding="utf-8"`：

```python
import logging

handler = logging.FileHandler(log_path, encoding="utf-8")
```

不允许因为 Windows 中文环境而使用默认编码读取文件。

### 16.6 乱码禁止

不允许出现以下情况：

```text
????    问号代替中文
       Unicode 替换字符
乱码中文
emoji 丢失
```
