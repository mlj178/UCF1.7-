# 增加血量 - 简要说明

## 功能目标
开启开关后，每触发一次快捷键（F3）或点一次「加血一次」按钮，就为本地玩家加一次血。只对玩家自己生效，不影响 BOT / 队友。

## 功能类型
玩家状态类（一次性动作 + 开关门控）。

## 实现原理
1. Hook `Player.Update`（主线程），每帧拿到 `Player*` 参数。
2. `addhp` RPC 只设置 `pending.addHp = true`，不直接写游戏对象（遵守 RPC 线程与主线程分离）。
3. `Player.Update` 命中本地玩家（`get_isMyPlayer`）后，读 `healthData`，调用原游戏
   `HealthData.AddHealthMax(add_amount, heal=1)`，并立即清 pending。
   同时提升 `currentHealth` 和 `maxHealth`，满血也能往上加，可无限叠加。
4. 不直接写 `currentHealth`/`maxHealth` 字段——都是 `ObscuredInt`（加密值），走游戏原生方法最安全。

## 关键 RVA / 字段
| 项目 | 值 | 说明 |
|---|---|---|
| `Player.Update` | `0x00B551D0` | 主线程执行点，参数0 = Player* |
| `Player.get_isMyPlayer` | `0x00B55FD0` | 判断是否本地玩家 |
| `HealthData.AddHealthMax(int, bool)` | `0x00AE4260` | 原游戏加上限+回血方法（探测实测生效） |
| `Entity.healthData` | `0x1C` | HealthData* 字段 |

调用约定 `mscdecl`，进程 ia32 / pointerSize 4。

## Hook 点
- 仅一个 `Player.Update`（`Interceptor.attach`，不用 replace）。
- 开关分离：`enable` 安装 Hook、`disable` 只关 enabled、`cleanup` 才 detach。

## RPC
`enable` / `disable` / `status` / `cleanup` / `setConfig`(`set_config`/`setconfig`) / `addhp`

配置项：`add_amount`（单次加血量，默认 10，范围 1~100，整数）。

## 生命周期
- 不缓存 Player 指针，每帧用 `Player.Update` 的 `args[0]` 并即时 `isMyPlayer` 校验，切房 / 死亡 / 重生无旧指针风险。
- pending 在 `resetRuntime` / `disable` / `cleanup` / 命中本地玩家后清除。
- `manifest.lifecycle.requires_room_ready_reapply = false`：加血是一次性动作，无持续生效状态需进房后二次应用。

## 测试方式
1. 连接游戏 → 开启开关 → 点按钮 / 按 F3（接入后）→ 观察 cur血 增加 `add_amount`。
2. 关闭开关后点按钮 → 应被 reject（`feature_disabled`）。
3. 反复开关 5 次 → 不重复安装 Hook。
4. 切房间 / 死亡重生 → 不崩、不加到 BOT 身上。
5. 退出游戏 / 关闭 UI → `cleanup` 被调用，无异常刷屏。

## 2026-09-09 游戏内实测问题与排查

### 现象
独立 UI 测试：日志显示 `player healed +10`（调用未抛异常），但游戏内血量毫无变化。

### IDA 手动解码结论（Heal 被封顶）
对 `HealthData.Heal(int)`（0x10AE44F0，IDA part3.chunk006）逐字节手动解码汇编：

```text
cur = 解密(currentHealth)          // ObscuredInt 解密辅助函数
max = 解密(maxHealth)              // 加载 [edi+0x1C] 后同样解密
newVal = value + cur               // add eax, esi
result = Math.Min(newVal, max)     // call3(newVal, max, 0) —— 封顶！
currentHealth = 加密(result)
```

**结论：满血状态下 Heal 无论加多少都无效果**，与实测"毫无效果"吻合。
脚本日志 `healed +N` 只代表调用没抛异常，不代表数据变了——以后不能只看调用成功就下结论。

### 备选方案
`HealthData.AddHealthMax(int addHP, bool heal)`（RVA `0xAE4260`，生化模式 `GiveLevelUpBonusHp` 就用它）
同时操作 currentHealth 和 maxHealth，是"真正把血量加上去（提升上限）"的候选。

### 探测工具（dev/）
- `dev/AAAAA-hp_boost_probe.js`：主线程状态机探测（BEFORE 快照 → 执行动作 → 等 5 帧 → AFTER 快照 → 对比）。
  - 快照内容：healthData 指针（字段 vs get_healthData() 交叉验证）、team、rate、isMaxHP、isDead、
    currentHealth/maxHealth/tempHealth 三个 ObscuredInt 的原始 20 字节、invinsibleEndTime。
  - 三种动作：`readonly`（只读对照，检测自然回血干扰）/ `heal` / `addmax`。
- `dev/AAAAA-hp_boost_probe_ui.py`：探测 UI，自动连接、自动 enable、三个探测按钮、数值滑条；
  **所有日志持久化到 `dev/logs/hp_boost_probe_YYYYMMDD_HHMMSS.log`**。

### 探测结论判读
| 情况 | 判读 |
|---|---|
| 满血 + heal 无变化 | 符合封顶预期，先受伤再测 |
| 未满血 + heal 后 rate 上升 | Heal 数据层生效，问题解决 |
| addmax 后 maxHealth 原始字节变化 | AddHealthMax 生效，可切换实现方案 |
| 未满血 + heal 完全无变化 | 需查 healthData 对象归属/线程/加密，看 hdField vs hdGetter 是否 match |

## 2026-09-09 探测结论与方案切换（已完成）

### AddHealthMax 探测结果（日志 hp_boost_probe_20260909_170301.log）
通过 ObscuredInt 解码（明文 = dword[0] XOR dword[1]，密钥 0x6C81C）验证：

| 时机 | maxHealth 明文 | 验证 |
|---|---|---|
| 初始 | 100 | 满血基线 |
| AddHealthMax(+10) 后 | 110 | ✓ |
| 再 AddHealthMax(+56) 后 | 166 | ✓ |

- maxHealth 精确 +N 上涨，currentHealth 同步跟上（rate 恒 1.0），tempHealth 不受影响。
- 两次探测期间加密密钥稳定，对象操作干净。

### 最终方案
正式 `script.js` 已从 `HealthData.Heal(int)` 切换为 `HealthData.AddHealthMax(addHP, heal=1)`：
- RVA `0xAE44F0` → `0xAE4260`，NativeFunction 签名 `(ptr, int, int, ptr)`。
- bool 参数必须声明 `'int'` 并传 `1`（本版 Frida x86 mscdecl 不接受 JS true/false，
  否则抛 `expected an integer`——探测时踩过 8 次的坑）。
- pending 状态机、生命周期、RPC 接口全部不变，`addhp` 语义不变。
