# 开火直伤（direct_damage）— 简要说明

> 位置：`05-正式功能/40-开火直伤/`（05 单功能阶段）
> 定位：第一版最小可用实现，跑通后再整目录迁移到 `04-正式发行版/全功能整合包x.x/game_modifier/features/40_direct_damage/`

## 1. 功能是什么

功能分成**两条完全不同的路线**：

### A. 常规枪械 —— 直伤（不走子弹）

开火时**不再走子弹射线**，直接把伤害结算到「选中的敌人」身上。
全程**不修改镜头、不修改准星、不控制射线方向**。

```
原版：开火 -> Recoil.GetShootRay 生成射线 -> WPN_Gun.Damage(Ray)
           -> RaycastAll 找命中体 -> 构造 DamageEventData -> 结算伤害
本功能：开火 -> WPN_Gun.Damage 被接管(attach) -> 选目标 -> 构造 DamageEventData -> 结算伤害
```

### B. 榴弹 / 手雷 / RPG / 榴弹枪 / 特殊技能弹 —— 弹体追踪（**不做直伤**）

这些武器的**原版逻辑本来就是**「弹体飞到 → 命中判定 → `WPN_GRENADE.CreateExplosion`
做范围伤害」，伤害数值、爆炸半径、距离衰减、`wpnIndex`、击杀归属全都是对的。
所以本功能对它们**不注入任何伤害**，只把弹体掰向敌人（会拐弯追踪），伤害 100% 交给原版。

```
本功能：开火 -> ProjectMissile 生成弹体 -> 登记"这颗弹要追踪"
           -> FixedUpdate 每个物理步把 velocity 掰向敌人 -> 弹体拐弯撞上去
           -> 原版 CreateExplosion 结算伤害（我们完全不插手）
```

> 为什么不做直伤：给它们额外注入直伤等于「打两遍」，而且绕过了爆炸范围判定，
> 手感很怪。用户的需求是「弹体可以追踪、可以拐弯」，不是「开火瞬间就掉血」。

## 2. 打谁 —— 目标选择设计（重点）

### 2.1 候选集

来源：`GameManager.allPlayers`（Il2Cpp 数组）+ `playersBL` / `playersGR`（两个 List）
合并去重（`allPlayers` 实测不全，必须三处合并，与自瞄同口径）。

逐个过滤：

| 过滤 | 条件 |
|---|---|
| 不是自己 | 指针 != 本地玩家 |
| 敌对 | `isEnemyTeam(myTeam, team)`，team==2 视为自由混战，所有人都算敌人 |
| 存活 | `Entity.get_isDead` 为 false |
| 位置有效 | transform 位置可读，且坐标绝对值 < 5000 |
| 距离 | `max_distance`（默认 80 米，0 = 不限） |
| 准星锥 | 夹角 <= `max_angle_deg`（默认 30°，仅 `nearest` 模式跳过） |

### 2.2 方向基准（准星方向）

读取本地玩家 `Player.cameraRotation`（+0x4C 的 yaw、+0x50 的 pitch），**只读**。
角度约定与游戏/自瞄一致：

```
yaw   = atan2(dx, dz)
pitch = atan2(dy, sqrt(dx^2 + dz^2))
夹角  = sqrt(yawDiff^2 + pitchDiff^2)
```

### 2.3 目标命中点

优先胸部骨骼 `currentCharacter.spine1`（+0x60），退化到 `spine`（+0x5C），
最后退化到「玩家坐标 + 身高偏移(`chest_fallback_height`=1.1)」。
命中点同时写入 `DamageEventData.hitPos`，用于命中反馈/飘字定位。

### 2.4 排序策略 `target_mode`

| 值 | 含义 | 说明 |
|---|---|---|
| `nearest`（**默认**） | **全场最近的敌人，完全不看准星方向** | 对应"打空气/不瞄准/看不到人/隔着墙，开火就要有伤害" |
| `angle_then_distance` | 先卡准星锥（`max_angle_deg`），再在锥内取距离最近 | 只想打准星方向的人时用 |
| `weighted` | `score = 夹角(度) x angle_weight + 距离(米) x distance_weight`，取最小 | 兼顾"更正对"与"更近"，权重可调 |

> `nearest` 模式下 `max_angle_deg` **完全不起作用**，`max_distance` 默认 0 = 不限距离。
> 默认值改成 `nearest` 是需求驱动的：原先默认 `angle_then_distance`（锥 30°），
> 结果对着空气/墙开火时锥内没人 -> 没有目标 -> 不掉血，被判定为"功能没生效"。

> 目标结果带 `target_cache_ms`（默认 25ms）短缓存，
> 避免霰弹/多段命中在同一帧里反复重扫全场。

### 2.5 弹体追踪的"打谁"策略（**独立于 `target_mode`**）

`target_mode` / `max_angle_deg` / `max_distance` **只作用于枪械直伤**。
弹体追踪（RPG / 手雷 / 榴弹枪 / 奥术手雷 / 火球）走的是另一套 `scanEnemies` + 准星锥，
只认这两个键：

| 键 | 默认 | 含义 |
|---|---|---|
| `homing_cone_deg` | `30` | `0` = 关闭准星锥，退回旧的"全场最近"；`>0` = 先只保留「锥轴 与 参考点->目标 夹角 <= 该值」的敌人，**锥内再比距离取最近的那个** |
| `homing_cone_fallback` | `true` | 锥内一个敌人都没有时：`true` = 回退成"全场最近"（保住"对着空气扔雷也能追到人"）；`false` = 这颗弹不追踪、按原弹道直飞 |

**锥轴 / 锥心**：

| 时机 | 锥轴 | 锥心 |
|---|---|---|
| 发射时（`SetWeaponData` -> `pickEnemyForLaunch`） | 本地玩家相机朝向 `Player.cameraRotation` | **眼睛位置** = 玩家坐标 + `local_eye_height`(1.55) |
| 飞行途中换目标（目标死亡/失效 -> `pickEnemyForMissileRetarget`） | **弹体当前速度方向** | 弹体当前位置 |

> 为什么发射时用眼睛而不是脚底：准星锥必须从相机位置量，用脚底量在几何上不成立。
>
> 为什么换目标时用「弹体速度」而不是玩家准星：弹体已经飞出去了，玩家可能早就看别处，
> 用玩家准星会让弹体在半空突然大幅掉头；用速度天然避免 180 度掉头，观感更自然。

排序依据 = 到参考点的 3D 直线距离，量到**胸口**（`getAimPoint`，取不到才退到脚底 +1.1）。
硬过滤永远只有两条：**敌对阵营 + 存活**，永远不打自己人。
夹角算法与枪械直伤完全一致（`calculateTargetAngles` + `angleDistanceDeg`），
所以「准星锥」在两条路径上的含义不会漂移。

> 默认 `30 度 + 回退开` = 优先追我瞄的那个方向里最近的人；没瞄到人时仍然追最近的。
> 想变成严格「只追我瞄的人」，把「锥内没人时回退全场最近」关掉即可。

## 3. 伤害怎么打进去 `damage_entry`

`DamageEventData` 是 **0x48 字节、按值压栈** 的 struct（x86 cdecl）。
Frida 的 `NativeFunction` 不支持"按值结构体"参数，因此本实现把 72 字节拆成
**18 个 4 字节标量参数**依次压栈（cdecl 下栈连续，逐 4 字节完全相同），
`MethodInfo*` 统一传 `ptr(0)`（与项目其它 NativeFunction 一致）。

| 值 | 调用 | 说明 |
|---|---|---|
| `gamemanager`（**默认**） | `GameManager.TakeDamage(DamageEventData)` 0xAFC1C0 | **唯一会真正把敌人打死的入口**，见下方证据链 |
| `hurt` | `Player.OnEntityHurt(DamageEventData)` 0xB516B0 | 只扣血、**不走死亡广播** -> 敌人 HP 归零但站着不死（无敌） |
| `health` | `HealthData.Hurt(int)` 0xAE45B0 | 同上，只扣血不走死亡/击杀流程 |
| `dry_run` | 不调用 | 只选目标 + 打日志，安全验证用（配合 `fallback_to_original` 即探针模式） |

**为什么默认必须是 `gamemanager`（三段反汇编证据）**：

1. `DamageEventData.TakePlace()`（0xB3D0D0）是**游戏自己的结算函数**，反汇编出来就是：

   ```c
   if (victim == null) return;
   if (victim.healthData == null) return;
   if (victim.healthData.isDead) return;      // 已死就不重复结算
   GameManager.TakeDamage(this);              // 0xAFC1C0
   ```

2. `GameManager.TakeDamage`（0xAFC1C0）内部依次调用：

   ```
   +0x246  GameManager.PlayHitFxAndSnd      // 命中特效/音效
   +0x51a  HealthData.get_isDead            // 判定是否死亡
   +0x6b4  GameManager.DeathEventBroadcast  // ★ 真正把敌人打死
   ```
   （另外 `GameManager.DamageEvent$$Invoke` 被调用 6 次 = InvalidCheck/PreCal/PostCal/Post/... 观察者链）

3. `Entity.OnEntityHurt`（0x40 字节）的全部逻辑只是：

   ```c
   if (type == 4 /*Infect*/) return;
   if (healthData == null) return;
   HealthData.Hurt(healthData, (int)damage);   // 只做 HP 相减
   ```

   它**完全不碰 `DeathEventBroadcast`**；`HealthData.Hurt` 也没有任何无敌/死亡判定
   （`HealthData.isDead` 就只是 `currentHealth <= 0`）。

   **==> 用 `hurt`/`health` 的后果：敌人 HP 归零、`isDead=true`，
   但死亡广播从未触发 -> 敌人不会死、后续还被我们的选目标逻辑当成死人跳过，
   画面上就是敌人站着打不死，即敌人无敌。**

### 3.1 自动降级保险 `entry_fallback`

`GameManager.TakeDamage` 会先过 `DamageEvent_InvalidCheck_Observers`，理论上存在被否决的可能。
所以加了一条保险：如果调用后**目标 HP 完全没变**，自动再补一次 `Player.OnEntityHurt`，
保证至少掉血，并在日志里写清楚：

```
[probe:hp] GameManager.TakeDamage 未生效（HP 没变），自动降级用 Player.OnEntityHurt 兜底
           —— 注意这条兜底不会走死亡广播
```

`entry_fallback`（默认 `true`）可以关掉。降级次数看 status 的 `entry_fallback_count`。

结构体字段（`DamageEventData`）：

```
+0x00 attacker      +0x04 victim        +0x08 damage(float)
+0x0C origin(Vec3)  +0x18 hitPos(Vec3)  +0x24 hitTag
+0x28 hitSndName    +0x2C hitEffect     +0x30 wallThrough
+0x34 type          +0x38 damageTag     +0x3C wpnIndex
+0x40 wpnSprIndex   +0x44 ignoreDmgRate          (size 0x48)
```

`type`：`Gun=1 / Knife=2 / Grenade=3 / Infect=4 / Other=5`。

字符串字段（hitTag / hitSndName / hitEffect）：

1. 优先使用**只读观察钩子**从真实伤害事件（`Entity/Player.OnEntityHurt`）里抓到的原版字符串指针；
2. 没抓到就现场用本地玩家 `ClientData.nickname` 的 klass 构造一个**空 IL2CPP String**；
3. 再不行才传 null。

### 3.2 `wpnIndex` 必须是合法字典 key（本轮修复：敌人死了不复活 / 多人生化闪退）

`DamageEventData` 里有个 `wpnIndex`（+0x3C），早期手工合成事件时把它填了 **0**。
这个 0 会一路传到死亡链路里去做**字典查找**：

```
GameManager.TakeDamage
  -> GameManager.DeathEventBroadcast(DeathEventData)      // 只在 victim 已死时才会走到
    -> GameManager_DeathEvent$$Invoke                     // 广播给 HUD / Player / 模式
      -> HUD_KillMark -> DeathEventData.get_wpnName() / get_killMsgIcon()
        -> GameManager.WpnDataDictionary[wpnIndex]        // Dictionary<int, WeaponData>
```

IDA 反汇编（`DeathEventData.get_wpnName` / `get_killMsgIcon` / `get_isVVIP` 三个函数完全同构）：

```c
WpnDataDictionary = GameManager_TypeInfo->static_fields->WpnDataDictionary;
if ( !WpnDataDictionary
  || (Item = Dictionary<int,WeaponData>.get_Item(WpnDataDictionary, wpnIndex)) == 0 )
    il2cpp_raise_exception();          // 字典里没有这个 key -> KeyNotFoundException
```

后果（和实测日志完全对上）：

| 后果 | 原因 |
|---|---|
| 敌人 HP 归零、`isDead=true`，但**永远不复活** | 异常从 HUD 订阅者冒出来，**打断了整条死亡广播链**，复活调度根本没跑 |
| 打完一波后 `enemies` 掉到 0 再也不涨 | 上一条的必然结果：`isDead=true` 被选目标逻辑当死人跳过 |
| **多人生化模式闪退** | 同一条异常在联网/生化模式下把游戏带崩 |

> 日志指纹：`[probe:apply] EXCEPTION entry=gamemanager: system error`，而且**只在击杀时出现**
> （`DeathEventBroadcast` 只在 `HealthData.get_isDead` 为真时才被调用）。
> Frida 把 IL2CPP 抛出的托管异常（MSVC C++ 异常 0xE06D7363）归类成 `GUM_EXCEPTION_SYSTEM`，
> 所以 `error.message` 就是 `system error`。

**修复**：

1. `wpnIndex` 改为读当前武器的 `Weapon.data(+0x68) -> WeaponData.wpnIndex(+0x0C)`。
   这个 `Weapon.data` 是游戏自己在用的（`WPN_Gun.Damage` 反汇编第一句就是 `if (this->fields.data)`），
   里面的 `wpnIndex` 与游戏填进伤害事件的值同源。
2. 读不到就退回**原版事件底板**：挂 `DamageEventData.TakePlace`（原版每次开火都会走到，
   `this` 就是结构体指针）与 `GameManager.TakeDamage` 入口，把**不是我们自己合成**的真实事件里的
   `wpnIndex` 抄下来（**只抄这一个标量**，不抄字符串指针 —— 那些指针的生命周期不归我们管，
   缓存下来会有 use-after-free 风险）。
3. 两个候选都要过一遍**游戏自己的武器表实查**：调用 `GameManager.GetWpnData(idx, out data)`
   （0x00AFB130）。反汇编确认它内部是 `Dictionary.TryGetValue`：**key 不存在只返回 false，不会抛异常**，
   所以可以安全地当校验器用。查不到的候选直接丢掉，并在日志写
   `[probe:tpl] wpnIndex=N（来源 X）不在 GameManager.WpnDataDictionary 里 -> 丢弃这个候选`。
4. 候选全丢光 -> **放弃这次注入**，走原版弹道，日志写 `[probe:tpl] refuse to inject`。
   宁可这一枪不打，也绝不把不合法的 `wpnIndex` 丢进死亡广播。
   （只有"拿不到 `GetWpnData` / 调用异常"时才跳过校验，避免误杀功能。）
5. `wpnSprIndex` 保持 0 是安全的：`WeaponData.GetKillMsgIcon(int index)` 反汇编是
   `return this->spriteAsset.killMsgIcon;`，**根本没用这个参数**。
6. `hitTag` / `hitSndName` 改成传 **null**（原版 `WPN_Gun.Damage` 自己就是先 `memset(event, 0, 0x48)`
   再按需填，null 正是原版默认值）；`hitEffect` 用 `WeaponData.hitEffectName(+0xA8)`
   （挂在常驻 ScriptableObject 上，生命周期足够长）。

### 3.3 复活无敌 & "半死敌人"陷阱（本轮修复：复活后打不动 / 掉血却不死）

实测日志（`logs/direct_damage_ui_20261013_092708.log`）把两件事分得很清楚。

**现象 A：复活之后 `GameManager.TakeDamage` 打不动。** 复活后每一枪都是这样：

```
[probe:gmTakeDamage] damage=105.00 type=1 [ours]     <- 我们传进去的确实是 105
[probe:playerHurt]   damage=0.00   type=1 [ours]     <- 观察者链把它抹成了 0
[probe:healthHurt]   value=0                         <- Hurt(health, 0) 自然不掉血
```

`DamageEvent_InvalidCheck_Observers` 那一环按目标的**减伤/无敌状态**把 `data.damage` 归零了。
dump.cs 里对应：

| 字段 | 偏移 | 作用 |
|---|---|---|
| `Entity.damageRate` | +0x14 | `SetDamageRate()` 产生的减伤倍率 |
| `Entity.isInvincible` | +0x18 | `InvincibleBuff` 通过 `RefBool` 写的无敌标记 |
| `HealthData.invinsibleEndTime` | +0x44 | 复活无敌的结束时间戳 |
| `DamageEventData.ignoreDmgRate` | +0x44 | **游戏自己留的"忽略目标减伤"开关** |

修复：

1. 合成事件时把 `ignoreDmgRate` 置 **1**（语义就是"这次伤害忽略目标的减伤"）。
2. 注入前把目标的 `isInvincible(+0x18)` 与 `invinsibleEndTime(+0x44)` 清 0；
   它们非零时打 `[probe:inv]`，日志里能直接看到是不是它在挡。

**现象 B：`entry_fallback` 造出"半死敌人"—— 这才是"复活后打不到"的真正原因。**

复活后第一枪被观察者归零 -> 旧版 `entry_fallback` 自动降级调 `Player.OnEntityHurt`，
而那条路**只扣血、不走 `DeathEventBroadcast`**：

```
[probe:hp] GameManager.TakeDamage 未生效（HP 没变），自动降级用 Player.OnEntityHurt 兜底
[probe:playerHurt] damage=105.00  ->  [probe:healthHurt] value=105  ->  HP 归零
[probe:hp] rate=1.000->0.000 dead=false->true => HP DROPPED
（注意：这一段完全没有 deathIn / deathOut）
```

于是敌人变成 `HP=0 / isDead=true`、但永远不会死也不会复活的幽灵；
选目标逻辑按 `isDead` 过滤，之后每一枪都是：

```
[probe:cand1] 0x249318a0 -> dead, skip
[probe:gunNoTarget] no direct-damage target; original ray RESTORED
```

打满 8 个敌人后场上全是这种幽灵 -> `enemies=0` -> 用户看到的"复活后打不到、也不掉血"。

修复：**`entry_fallback` 不再退回 `hurt`，改成"清一次无敌状态 + 用完整入口重试"**。
重试走的是同一条 `GameManager.TakeDamage`，所以打死就是真死（有死亡广播、有复活），
**再也不可能产生半死敌人**。

> 结论：`damage_entry = hurt/health` 只适合单次调试；**任何"自动降级到 hurt"的设计都必须删掉**。

### 3.4 2.7 实测：击杀时仍会抛托管异常 -> "死了不复活"（death_diag 诊断）

2.7 整合包实测日志（`game_modifier/logs/game_modifier.log`）里，直接开火击杀敌人时仍然出现：

```
[ERROR] [direct_damage] [fail:applyDamage:gun] applyDamage:gun: system error (x1..x5)
```

`system error` = Frida 把 IL2CPP 抛出的托管异常（MSVC C++ 异常 `0xE06D7363`）归类成
`GUM_EXCEPTION_SYSTEM`。**它发生在"这一枪把目标打死的时刻"**（异常前后 HP 已经归零、
`dead=false->true`），也就是 `DeathEventBroadcast` 那一段。

> 注意：05 单功能环境（`05-正式功能/40-开火直伤/logs`）里的枪械直伤击杀 **没有** 这个异常，
> 只有 2.7 整合包（当时跑的是 `Nano4 + Terminator`，日志里 `mode=6`）里才复现 ——
> 说明触发器很可能是"多人生化终结者模式"特有的死亡处理。
> 这与用户报的"终结者 / 超级终结者死亡后不复活、模型卡在原地"完全吻合。

**为什么"异常 = 不复活"**：见 §3.2。`DeathEventBroadcast` 一旦被打断，
`ModeBase_Nano.DeathEvent -> ModeBase_Nano.RespawnPlayer` 这条"复活调度"就不会跑，
但 `HealthData` 已经是 `isDead=true`，于是目标变成"HP=0、站着、永不复活的半死幽灵"。
复活时机上，终结者/高阶终结者还会走 `Mode_Nano4_Terminator.RespawnPlayer` 的
**墓碑复活**分支（`attribute_Nano.id==9` 不死契约 + `Nano4T_Data.graveCount/canUseGrave`），
这一条同样要经过基类 `ModeBase_Nano.RespawnPlayer`，所以一起被打断。

**已加的诊断（§7.2 新增前缀，默认开启，全部只读）**

| 前缀 | 回答什么问题 |
|---|---|
| `[deathDiag]` | 击杀后的观察结果：`目标已复活` / `*** 击杀后未复活（半死/幽灵）***` |
| `[deathDiag:deathIn]` / `[deathDiag:deathOut]` | 死亡广播进出（进了没出 = 异常现场），并打出 killer / dead / type / wpnIndex / wpnSprIndex / headShot / damageTag |
| `[deathDiag:respawnPlayer]` | `ModeBase_Nano.RespawnPlayer` 有没有被调用（复活调度），含 dead / respawnTime / isNormalRespawn / clearExp / role / respawnType / isRespawning / grave |
| `[deathDiag:playerRespawn]` | `Player.Respawn` 有没有被调用 |
| `[deathDiag:abort]` | **上一次死亡广播"进了没出"**（= 被打断的那一次），直接打出它全部的 12 个字段 |
| `[deathDiag:raise]` | 托管异常现场：类名 + `inBroadcast=YES/no` + 现场字段 + 调用栈 RVA 列表 |
| `[deathFix]` | 复活兜底动作（补发 `RespawnPlayer`）以及兜底后是否真的活了 |
| `[probe:beat] deathDiag:` | 每 5 秒汇总：`death=in->out aborted=... rescued=... respawnPlayer=... playerRespawn=... raises=... watch[active/recovered/noRevive]` |

相关配置（`setConfig` 可改；改完建议 disable/enable 一次让钩子重装）：

| key | 默认 | 说明 |
|---|---|---|
| `death_diag` | `true` | 诊断总开关（关掉后连这 4 个只读钩子都不装） |
| `death_diag_ms` | `20000` | 击杀后观察窗口；超过这个时间还没活过来就判"不复活" |
| `death_diag_detail` | `false` | true = 每次死亡广播/复活调度都逐条打印（很吵） |
| `death_fix_wpn` | `false` | 死亡广播入口把字典里查不到的 wpnIndex 换成合法 key。**§3.6 已证伪，默认关闭**，只影响击杀提示武器名 |
| `death_fix_respawn` | `true` | **复活兜底**：确认某次死亡广播"进了没出"、目标过了 grace 还 `isDead` 时，由我们补一次 `ModeBase_Nano.RespawnPlayer`（见 §3.6.4） |
| `death_respawn_grace_ms` | `6000` | 兜底前等多久（毫秒）。正常死亡 1~2 秒就复活，所以 6 秒还没动静基本就是被打断了 |

**另外一处硬化**：`applyDamage` 的异常现在会带上"发生在哪一步"的阶段名：
`[fail:applyDamage:gun@takeDamage]` / `@buildEvent` / `@snapshot` / `@clearInvincible` …
—— 下次复现可以直接看出是 `GameManager.TakeDamage` 抛的，还是读血量快照抛的。

> 已确认的一个**现存代码隐患**（尚未改动，等实测确认再定）：
> `resolveWpnIndex` 用 `GameManager.GetWpnData` 校验 `wpnIndex`，而 `GetWpnData` 查的是
> `GameManager.WpnDictionary`（静态 +0x18，`Dictionary<int, Weapon>`）；
> 死亡广播里的 `DeathEventData.get_wpnName/get_killMsgIcon/get_isVVIP` 查的是
> `GameManager.WpnDataDictionary`（静态 +0x1C，`Dictionary<int, WeaponData>`）。
> **两个是不同字典**，所以现在的"合法性校验"并没有校验到真正会抛 KeyNotFoundException 的那个字典。

### 3.5 2026-10-14 实测复盘（death_fix_wpn；**该假设已被 §3.6 证伪，默认关闭**）

按 §3.4 开诊断后又跑了一局，日志给出了决定性证据：

| 项 | 值 |
|---|---|
| 死亡广播进入 `deathIn` | 41 |
| 正常返回 `deathOut` | 38 |
| **进了没出** | **3**（09:10:17.918 wpnIndex=938、09:10:21.686 wpnIndex=183、12:33:42.625 wpnIndex=2759） |
| 复活调度 `RespawnPlayer` / `Player.Respawn` | 38（**只等于 deathOut**） |

结论：**3 次死亡广播被打断，并且这 3 次目标一个都没排上复活**；其余 38 次全部正常。
每次打断的同一毫秒都伴随 `[fail:WPN_Gun.Damage replacement] system error`，
说明异常就是从死亡广播里冒出来、一路穿过 `WPN_Gun.Damage` 的。

对照反汇编：死亡广播里 `HUD_KillMark` 会调
`DeathEventData.get_wpnName()/get_killMsgIcon()/get_isVVIP()`，三者都是
`GameManager.WpnDataDictionary[wpnIndex]`；**key 不存在就 `il2cpp_raise_exception`**。
3 个坏 key 938 / 183 / 2759 当时推断是字典里没有的。

> ⚠️ **这段推论已被 §3.6 证伪**：反汇编本身没问题（确实查 `WpnDataDictionary[eventData.wpnIndex]`、
> key 缺失确实抛 `KeyNotFoundException`），但"这 3 次打断是因为 key 不在字典里"只是当时的推断 ——
> 下一局出现了**同一个 wpnIndex 一次炸、一次正常**的反例。所以这几次打断的**真实触发点仍未定案**，
> 要靠 §3.6.3 的 `[deathDiag:raise]` / `[deathDiag:abort]` 定案。

> 注意：这一局 `localFires=0/2`、`damage=0`、`hpDrop=0/0`、`[ours]=0`，
> 说明**这一局枪械直伤几乎没真正打出去**；3 次打断全是 `[game]`（人机的原版枪线）。
> 所以这不是"我们合成的事件不合法"，而是**任何 wpnIndex 不在字典里的死亡广播都会炸**；
> 我们合成事件时同样可能撞上这种 key，所以修复做在广播入口最稳、覆盖面最大。

**当时的修复：`death_fix_wpn`（**现在默认关闭** —— 下一局的日志（§3.6）里同一个 wpnIndex
既炸过又正常过，说明它根本没打中病根，只在击杀提示上留了副作用）**

在 `GameManager.DeathEventBroadcast` 的 `onEnter`：

1. 读 `DeathEventData.wpnIndex`（结构体按值压在 `[esp+4]`，字段在 `+0x30`）；
2. 扫一遍 `GameManager.WpnDataDictionary`（静态 `+0x1C`，`Dictionary<int,WeaponData>`；
   布局 `+0x0C entries / +0x10 count / +0x14 version`，Entry 16 字节、key 在 `+0x08`），
   把合法 key 缓存进 JS 对象（`version` 不变不重扫）；
3. key 不在里面 -> 把 `[esp+4+0x30]` 改写成「最近一次确认合法的 key」，
   没有就用字典里最小的合法 key；
4. 打 `[deathFix] ... 已改为 N` 日志。

这样死亡广播不会再抛 `KeyNotFoundException`，`ModeBase_Nano.DeathEvent -> Respawning`
就能跑完，目标正常复活。唯一代价：这几次击杀提示显示的武器名会变成兜底武器的名字。

> `death_diag=false` 会连带关掉这个修复；只想关修复就设 `death_fix_wpn=false`。
> `wpnFix` 在真实对局里始终是 0 —— 见 §3.6：这条假设不成立，
> "模型卡在原地不复活"另有原因，真正的止血手段是 `death_fix_respawn`。

### 3.6 2026-10-14 二轮实测：§3.5 的假设被证伪 + 复活兜底（death_fix_respawn）

第二份 2.7 日志（13:29:38 ~ 13:35:23）给出了 §3.5 的反例，也带来了更硬的取证手段。

#### 3.6.1 决定性反例：同一个 wpnIndex 一次炸、一次正常

| 时间 | `dead` | `wpnIndex` | 结果 |
|---|---|---|---|
| 13:29:53.235 | `0x4781d730` | **341** | 进了没出（`death=14->13`），目标不复活 |
| 13:29:54.231 | `0x4786ab80` | **341** | 正常返回，`RespawnPlayer` 正常调用 |

整局 `wpnFix=0`：按 §3.5 自己的判定，341 也是字典里的合法 key。
**"wpnIndex 非法"不成立**，`death_fix_wpn` 在真实对局里一次都没触发，只改过击杀提示的武器名。
所以它的默认值改回 `false`（代码留着，方便复现旧实验）。

#### 3.6.2 "进了没出 -> 目标不复活"这条因果链仍然成立

这一局 `death=322->318`：4 次广播进了没出，并且**这 4 次都没有 `ModeBase_Nano.RespawnPlayer`**；
被抓到细节的两个受害者（`0x4781d730` / `0x4781dcf0`）直到 4.5 分钟后（局末重开）
才被复活 —— 这就是玩家看到的"终结者模型卡在原地、不复活"。

两次抓到细节的打断都是 `damageType=1`、`damageTag=0x40`，且受害者在 `08_gather`
的 `NANO_INFECT` 诊断里都是"幽灵"（ghostRole 8/9）。但光靠这几个字段还分不出
**到底是哪个字段、哪个字典**触发的异常 —— 于是有了下面三件取证装备。

#### 3.6.3 新增取证（默认开）

1. **整份 `DeathEventData` 打平**：`[deathDiag:deathIn]` 现在打出全部 12 个字段，
   并对 4 个"看着像索引"的字段逐个用 `WpnDataDictionary` 实查一遍
   （`| dict: wpn=341:MISS wpnSpr=0:MISS ...`）。`wpn:OK` 却仍然炸 -> 异常不在武器名这条线上。
2. **`[deathDiag:abort]`**：`onEnter` 记下"当前这次"，下一次 `onEnter` 时若上一次还没出来，
   就把**上一次的完整字段**以 error 级打出来。不依赖任何异常钩子，是"进了没出"的稳定证据。
3. **`[deathDiag:raise]`（★2026-10-14 起默认关闭，`death_diag_raise=true` 才装）**：
   IDA 确认 `il2cpp_raise_exception` 与所有托管 `throw` 最终都收敛到
   `sub_1013FF10(Il2CppException*, MethodInfo*)`（RVA `0x13FF10`）。
   钩它即可在异常抛出的那一毫秒拿到：异常类名（`klass+0x08` 指向类名字符串）、
   是否正在死亡广播里（`inBroadcast=YES`）、现场字段、以及调用栈 RVA 列表 `bt=+0x...,+0x...`。
   把 `bt` 里的 RVA 加上 `0x10000000` 丢给 IDA，就能定位是哪个 observer 抛的。
   **为什么默认关**：`sub_1013FF10` 是 noreturn 的 C++ throw 漏斗；Frida 内联钩子挂在抛出点上
   时，Frida 自己的异常处理器会把 `0xE06D7363` 先抓走（同 26 手雷模式 v2.13 注释里的根因），
   游戏异常帧收不到 -> `RaiseException` 直接返回 -> 落到调用点后编译器填的 `int 3` ->
   `0x80000003 @ GameAssembly+0x1401A6` 秒退。2026-10-14 18:26 多人生化（终结者）实测：
   探针 `[deathDiag:raise]` 与崩溃同一毫秒，见 `06-测试/_crash18_26/崩溃分析-2026-10-14-1826.md`。
   “广播有没有被打断”仍由 `deathIn/deathOut` 计数 + `[deathDiag:abort]` 判定，不需要碰异常漏斗。

#### 3.6.4 顺带做的"复活兜底" `death_fix_respawn`（默认开）

* 每一笔 `DeathEventBroadcast` 都登记进观察窗口（`Runtime.deathWatch`，key = 玩家指针）；
* `ModeBase_Nano.RespawnPlayer` / `Player.Respawn` 命中即标记 `scheduled`；
* 在**游戏主线程**（死亡广播 `onLeave` + 每 5 秒一次的心跳 `checkDeathWatch`，内部 1 秒最多一次）检查：
  死亡超过 `death_respawn_grace_ms`、没观察到复活调度、且现在仍然 `isDead=true`
  -> 由我们补一次 `ModeBase_Nano.RespawnPlayer(mode, victim, 1, 1, 0)`
  （`mode` 从 `RespawnPlayer` / `DeathEvent` 钩子的 `[esp+4]` 抓；没抓到就退化成 `Player.Respawn`）；
* 每次都写 `[deathFix] 复活兜底：...`，`[probe:beat] deathDiag:` 里看 `rescued=`。

> 这是"补最后一脚"，不是修根因：它跳过的是游戏自己的死亡记账，
> 所以只在"这一次死亡确实没排上复活"时才动手（正常对局 `rescued=0`）。
> 作用窗口只有 **`death_respawn_grace_ms`(6s) ~ `death_diag_ms`(20s)**：
> 超过观察窗口就结案删掉，不会去"复活很久以前死的人"。
> 关闭：`death_fix_respawn=false`；`death_diag=false` 会连带关掉它。

#### 3.6.5 下一局应该看到什么

| 看什么 | 期望 |
|---|---|
| `[probe:beat] deathDiag: death=in->out aborted=` | `in > out` 说明异常还在；`aborted` 与之差一致 |
| `[deathDiag:abort]` | 打出来的就是**触发异常的那次死亡**的全部 12 个字段 |
| `[deathDiag:raise]` | **默认不装（防闪退）**；显式 `death_diag_raise=true` 才有：异常类名 + `inBroadcast=YES` + `bt=` |
| `[deathFix] 复活兜底` | 卡住的目标约 6 秒后被补一次复活，玩家侧不再看到"一直躺着" |
| 兜底后仍出现 `*** 击杀后未复活 ***` | `RespawnPlayer` 也救不回来 -> 要换兜底入口（例如走 `Mode_Nano4_Terminator` 的重写版） |

### 3.7 2026-10-14 三轮实测：真凶抓到 —— `WPN_Gun.Damage` 的 `replace + 回call`

§3.5 / §3.6 一直把这次异常当成"游戏自己的疑难 bug"，直到把一局的日志按 **死者角色 × 凶手** 切开，才看清：

| 组合 | 死亡次数 | 死亡广播被打断 |
|---|---|---|
| 终结者（NanoRole 8-17）**被 Bot 打死** | 9 | **8** |
| 终结者**被我们**（直伤）打死 | 7 | **0** |
| 非终结者被 Bot 打死 | 33 | 0 |
| 非终结者被我们打死 | 38 | 1 |

再按时间对齐：**每一个 `[deathDiag:abort]` 之前 0~40ms 都有一条
`[fail:WPN_Gun.Damage replacement] ... system error (xN)`，9 对 9 全部对应。**

结论（与 `26_grenade_mode` v2.13 注释里那条根因完全同源）：

1. Bot 打死终结者时，游戏自己的"伤害 -> 死亡广播"链内部会抛一个托管异常
   （il2cpp 用 C++ EH，Windows 异常码 `0xE06D7363`）。这种异常游戏一直自己在抛、
   也一直由游戏自己的异常帧消化（19:21 那局 `raises=14`，全部被游戏自己收掉，没有任何后果）。
2. 但 `WPN_Gun.Damage` 当时是 `Interceptor.replace` + 在 JS 里用 `NativeFunction`
   **回call 原函数** —— 异常一跨回 JS 边界就被 Frida 抢先捕获（JS 只看到 `system error`），
   游戏自己的异常帧再也收不到，死亡广播从抛出点直接断掉：
   `deathIn` 有、`deathOut` 没有、`ModeBase_Nano.RespawnPlayer` 一次都没被调用。
3. 所以"终结者躺尸不复活"**不是**游戏 bug，而是**我们的挂法**造成的。

**修复**：`WPN_Gun.Damage` 从 `replace` 改成 `Interceptor.attach`（只挂 `onEnter`）：

* **别人的开火（Bot）**：`onEnter` 里 `isLocalWeapon` 为假就 `return`，
  原函数完全原生执行、Frida 不在调用链上留任何帧 -> 托管异常照常交给游戏自己处理；
* **我自己的开火**：自己结算直伤，再用"模拟 ret"跳过原函数
  （mscdecl 参数由调用方清栈：读 `[esp]` 的返回地址 -> `esp += 4` + `pc = 返回地址`）；
* 跳过前校验"当前 `[esp]` 里的返回地址必须指向可执行页"，校验不过就**不跳过**
  （原函数照跑，最多这一发多打一遍，绝不乱跳栈），失败计数 `gun_skip_failed`；
  顺带一提：如果同一地址上还有别的 `attach(onLeave)` 监听者（例如 29 子弹穿墙），
  `[esp]` 会是 Frida 的返回 thunk —— 照跳，这样别人的 `onLeave` 链也照常会跑。

配置开关 `gun_hook_mode`：`attach`（默认）/ `replace`（旧行为，仅对照/回退排障用）。
旧 `replace` 分支保留在代码里，但启用时会打 `warn` 提醒它会重现"终结者不复活"。

> 兜底 `death_fix_respawn` 先留着当保险：修复生效后正常对局应该看到 `rescued` 不再增长、
> 没有任何 `[deathFix]`；那一刻就可以把它关掉，死亡完全回到游戏自己的流程。

## 4. 独立开关

| 开关 | config key | 默认 | 作用 |
|---|---|---|---|
| 常规枪械直伤 | `enable_guns` | 开 | 接管 `WPN_Gun.Damage`（attach + 模拟 ret 跳过原函数），自己做锥内直伤 |
| 枪械挂法 | `gun_hook_mode` | `attach` | `attach`=Bot 开火完全原生（推荐，见 3.7）；`replace`=旧行为，会重现"终结者不复活" |
| **弹体追踪(拐弯) 总开关** | `enable_homing` | 开 | 投射物追踪的总闸；关掉后下面两个子开关都不生效 |
| 榴弹/手雷/RPG 追踪 | `enable_explosives` | 开 | RPG / 手雷投掷 / 榴弹枪的**弹体**朝敌人拐弯（**不注入伤害**，见 4.1） |
| 特殊技能弹 追踪 | `enable_skill_projectiles` | 开 | 奥术手雷 / 地狱终结者火球的**弹体**朝敌人拐弯（**不注入伤害**，见 4.1） |
| 追踪锁定强度 | `homing_turn` | 1.0 | 每个物理步把方向掰向目标的力度；1.0=立刻拐弯，0.4=保留弧线慢慢拐 |
| 无目标时保留原版弹道 | `fallback_to_original` | 开 | 没有目标时回退原版射线（见下，只影响枪械） |
| **真实事件底板** | `use_event_template` | 开 | 抄原版伤害事件的 `wpnIndex` 等标量来校准合成事件（**见 3.2，关掉会导致敌人不复活/闪退**；只对枪械直伤有用） |

**枪械**：`Interceptor.attach(WPN_Gun.Damage)`（`onEnter` only）；非本地武器、或开关关闭时
直接返回，原函数由游戏自己原生调用，保证人机/关闭状态完全透明；
本地武器时我们结算完直伤，再用"模拟 ret"（弹返回地址 + 跳回调用方）跳过原函数，等价于原来的 replace 效果。
为什么不用 `replace`：见 §3.7（会把游戏自己的托管异常抢走 -> 死亡广播断掉 -> 终结者不复活）。

**`fallback_to_original`（默认 `true`）**：准星锥内没有可选目标时，是否回退原版射线。

| 值 | 无目标时 | 说明 |
|---|---|---|
| `true`（默认） | 原版弹道照常走 | 墙上照常有弹孔/着弹特效，手感自然 |
| `false` | 什么都不做 | 子弹凭空消失，**看起来像功能没生效** |

> 这个默认值是被实测纠正的：第一版用 `false`，用户打完 8 个敌人后开了 62 枪，
> 每一次都因为"无目标 + 不回退"而没有任何可见反馈，于是判断"功能完全没效果"。

**爆炸物 / 技能弹**：**不做任何直伤**，只做弹体追踪（见 4.1）。
它们开火时的那 5 个钩子只负责「记下这颗弹属于哪个类别」，然后立刻返回。

### 4.1 弹体追踪（制导）—— 本轮重做

让 RPG / 手雷 / 榴弹枪 / 奥术手雷 / 地狱终结者火球的**弹体自己朝敌人拐弯**。
**这一路完全不注入伤害**，伤害仍由原版 `WPN_GRENADE.CreateExplosion` 结算。

#### 4.1.1 先纠正一个上一版的错误挂点

上一版把「登记制导」挂在 `WPN_Missile.SetOwner`（0xB66390）上，**永远不会触发**。
证据（对 GameAssembly.dll 的 `il2cpp` 段做全量 `E8` 相对调用扫描）：

| 目标函数 | 全二进制直接调用点数量 |
|---|---|
| `WPN_Missile.SetOwner` 0x00B66390 | **0** |
| `WPN_Missile.Recycle` 0x00B66240 | 0（虚函数，走 vtable） |
| `UnityEngine.Rigidbody.set_velocity` 0x00ABC060 | 10（对照组，扫描方法本身是对的） |

owner 其实是在 **`Weapon.ProjectMissile`（0x00B6D080）里直接写字段**的：

```asm
mov  eax, [ebx+30h]        ; weapon.owner
lea  esi, [edi+30h]        ; &missile.owner
mov  [esi], eax            ; missile.owner = weapon.owner   <-- 直接写，不调 SetOwner
call write_barrier
mov  eax, [esi]
mov  eax, [eax+20h]
mov  [edi+34h], eax        ; missile.ownerInitalTeam = owner.team
```

所以「追踪不生效」的根因是**挂点选错了**，不是算法问题。

#### 4.1.2 投射物的完整生成链路（反汇编确认）

`Weapon.ProjectMissile`（0x00B6D080）是所有投射物的统一生成入口，
5 个开火路径都会走到它：`WPN_RPG.Fire` / `WPN_Throw.Throw` / `WPN_GrenadeGun.GunShootFunction`
/ `WPN_Arcane.Throw` / `WPN_EvilTerminator.ThrowFireBall`。

```
missile = EffectManager.GetEffect(prefab)                 ; 从对象池取一颗
missile.owner          = weapon.owner                     ; +0x30 直接写字段
missile.ownerInitalTeam = owner.team                      ; +0x34
... 位置 / 朝向（Transform.set_position / set_rotation）...
if (callback != null) callback.Invoke(missile)
      -> WPN_Missile.SetWeaponData(missile, weapon.data, sprIndex)   ; +0x38 / +0x3C
RecyclableObject.Active(missile) -> Work()
      -> Rigidbody.velocity = transform.forward * shootSpeed          ; +0x4C
```

两个可依赖的事实：

1. **进入 `SetWeaponData` 时 `owner` 已经写好，而且还没发射** —— 正好用来登记；
2. **弹体是标准物理刚体**：`Work()` 用 `Rigidbody.set_velocity` 发射，
   `WPN_Missile.FixedUpdate`（0x10B660C0）反汇编只有一句实质操作：
   `Rigidbody.AddForce(rigidBody, extraGravity, 5)`。
   所以「改写 velocity」就能拐弯，不需要碰任何游戏逻辑。

#### 4.1.3 新实现（挂点 / 拐弯 / 清理）

| 步骤 | Hook | 做什么 |
|---|---|---|
| 0 | 5 个开火函数（`WPN_RPG.Fire` 等） | **只记类别**：`Runtime.pendingMissile = {category, label, weapon, at}`，然后立刻返回。不注入伤害 |
| 1 | `WPN_Missile.SetWeaponData` 0xB663C0 | **登记**：先无条件清掉该指针的旧记录（对象池复用防串味），再用 `owner` 判断是不是自己发射的，用 `pendingMissile` 判断类别，然后记「这颗弹 → 最近的敌人」 |
| 2 | `WPN_Missile.FixedUpdate` 0xB660C0 的 **onLeave** | **拐弯**：读 `Rigidbody.get_velocity` + 弹体 `shootSpeed`，算目标方向，按 `homing_turn` 插值后 `Rigidbody.set_velocity`，同时用 `Quaternion.LookRotation` 掰 `Transform.rotation` |
| 3 | `WPN_Missile.Recycle` + `RecyclableObject.Recycle` | **清理**：只在「弹体真的回对象池」时删记录 |
| 4 | `WPN_Missile.Work` / `WPN_GRENADE.Work` 的 **onLeave** | 计数（`launch`）+ **补一次拐弯**：游戏在 `Work` 里写初速，必须等它写完再覆盖 |
| 5 | `WPN_Missile.OnCollisionEnter` / `WPN_GRENADE.OnCollisionEnter` / `WPN_GRENADE.OnTriggerEnter` | **只记账**（`touch[...]`），**绝不删记录** |
| 6 | 心跳（每 5s） | 清理超过 `homing_max_ms`（默认 20s）的残留记录 |

为什么第 5 步绝对不能删记录（本轮修复的头号 bug，见 §7.4 坑 5）：
`WPN_GRENADE.OnTriggerEnter` 是**近炸引信**（`expWhenTouchSth` +0x74 为真时，任何「敌人」
进入触发体就会调 `TryExplosion`）。弹体刚出膛那几帧身上还挂着各种碰撞体，一进去就把记录删了 ——
结果是**每颗弹只拐了 1 帧**，之后整段飞行都是原版直线，肉眼看到的就是「完全不拐弯」。
而 `Recycle` 一定会在爆炸/回收时触发，所以清理只需要挂在 `Recycle` 上。

为什么还要挂 `RecyclableObject.Recycle`：`WPN_Missile.Recycle` 是重写版本，
但有些路径直接调基类那一份，两边都挂才能保证一定清掉。

为什么用 `onLeave`：`FixedUpdate` 内部会自己 `AddForce`，`Work` 会自己写初速，
必须**等它们算完**再改写才有效。

记录不会「拐错人」的三重保险：
1. `armMissileHoming` 一进来就先 `forgetMissile(missile, 'reused')`（对象池复用防串味）；
2. 记录里存了 `owner` + `rigidBody` 两个**身份指纹**，每帧拐弯前复核，不一致立刻丢弃（`ident`）；
3. 心跳里按 `homing_max_ms` 超时清理。

拐弯算法（`steerMissile`）：

```
d = normalize(敌人瞄准点 - 弹体当前位置)      ; 瞄准点优先胸部骨骼 spine1
speed = homing_speed > 0 ? homing_speed : missile.shootSpeed   ; 缺省用弹体自身速度
if (homing_turn < 1)                          ; 保留一部分原弹道
    d = normalize(normalize(velocity) * (1-turn) + d * turn)
Rigidbody.set_velocity(rb, d * speed)
Transform.set_rotation(rb.transform, LookRotation(d))
```

配置：

| key | 默认 | 说明 |
|---|---|---|
| `enable_homing` | `true` | 总开关 |
| `enable_explosives` / `enable_skill_projectiles` | `true` | 两个类别子开关 |
| `homing_turn` | `1.0` | 0.05~1.0。1.0 = 每个物理步直接锁定目标方向（立刻拐弯，命中率最高）；0.4 = 保留弧线慢慢拐 |
| `homing_speed` | `0` | 0 = 用弹体自身的 `WPN_Missile.shootSpeed`(+0x4C)；否则用指定速度 |
| `homing_retarget` | `true` | 原目标死了自动改追**离弹体最近**的敌人 |
| `homing_max_ms` | `20000` | 超过这个时间放弃制导 |
| `homing_pending_ms` | `800` | 「开火记录 → 弹体生成」的最大时间差（配对窗口） |

设计取舍：

- **开关只影响登记，不影响开火计数**。这样 `trig` / `spawn` 这两个数字永远代表
  「钩子有没有命中」，不会因为开关关着变成 0 而让人误判成 RVA 不匹配。
- 登记时用 `homing_turn` 直接把速度设成固定大小（不再叠加重力），
  所以追踪中的弹体会平飞；这是为了命中率，也避免抛物线下坠打不到人。
- **没有寻路**：弹体只会沿直线朝敌人飞，中间隔墙就会打在墙上爆炸（原版行为），
  这是刻意保留的 —— 不改变原版的命中判定规则。

## 6. 生命周期

- 只安装固定 RVA Hook，命中时按 `enabled/config` 实时判断，
  因此 `requires_room_ready_reapply = false`（无需进房后二次应用）。
- `cleanup` 可重复调用：`Interceptor.revert` 还原替换、detach 全部 attach 钩子、
  清空缓存与指针。
- 切换房间不缓存跨房间的游戏对象（每次开火重新读 GameManager）。

| `[probe:homingSteer]` | 实际改写了弹体速度（拐弯） |

HP 对照怎么做的：`HealthData.get_rate()`（HP 百分比）前后对比，
同时把 `currentHealth`（`ObscuredInt`）的原始字段 `key/hidden/fake/inited` 也前后对比，
即使 `get_rate` 取不到也能证明血量有没有被改写。

### 7.4 已踩过的坑（务必保留这段，别再犯）

**Frida 的 `NativeFunction` 对 `'bool'` 返回值给的是 JS `number(0/1)`，不是 JS `boolean`。**

实测（frida **17.9.1**，ia32 与 x64 结果一致）：

```js
new NativeFunction(IsProcessorFeaturePresent, 'bool', ['int'])(10)
// -> 1            typeof === "number"
// -> (1 === true) === false     <-- 恒为 false！
```

早期版本本功能写的是 `native.isMyWeapon(weapon, ptr(0)) === true`，
于是 `isLocalWeapon()` **恒返回 false**：被接管后的 `WPN_Gun.Damage`
每一次都把调用原样转给原函数，**任何武器、任何入口都不会有任何效果**，
而且不报错、日志上也看不出异常（唯一线索是 `[probe:gunDamage#N] isMyWeapon=false`）。

正确写法（与整合包 2.7 的 `26_grenade_mode` 一致）是真值判定：

```js
native.isMyWeapon(weapon, ptr(0)) ? true : false      // 或 Boolean(...)
```

本文件已统一收敛到 `toFlag()` 辅助函数，凡是 `bool` 返回值一律走它，
并且探针会把**原始返回值**一起打出来（`true(raw=1)`），以后再遇到类型问题一眼可见。

> 顺带一提：`29_bullet_wall_penetration/script.js:370` 里也有一处
> `native.isMyWeapon(...) === true`，但那个辅助函数没被任何地方调用（死代码），
> 它钩子内部用的是 `if (!native.isMyWeapon(...))`，所以那个功能不受影响。

> **坑 2（本轮修复）：合成伤害事件时 `wpnIndex` 填了 0。**
>
> 后果不是"伤害变小"，而是**敌人死了不复活 + 多人生化模式闪退**。
> 链路与证据链见 §3.2。一句话记住：
>
> `wpnIndex` 是 `GameManager.WpnDataDictionary` 的 key，**必须**来自 `WeaponData.wpnIndex`，
> 绝不能填 0；拿不到就宁可不注入。
>
> 诊断工具：`[probe:deathIn]` / `[probe:deathOut]` 两个数字不相等 = 死亡广播被异常打断。

**坑 3：给"只在基类出现的方法"挂钩子，不代表子类会走到它。**

`WPN_GRENADE : WPN_Missile`，而 `OnCollisionEnter` / `Work` 都是**虚函数且被手雷重写**。
只挂基类 `WPN_Missile.OnCollisionEnter` 对手雷**永远不会触发** ——
表现是制导记录永远清不掉，弹体回收后指针被复用，下一次可能是**敌人的手雷被掰到我们的目标上**。
所以：手雷重写的虚函数必须单独挂（`WPN_GRENADE.OnCollisionEnter` 0xB5D0F0 / `OnTriggerEnter` 0xB5D270）。

**坑 4：不要在"看起来该被调用"的方法上挂钩子，先确认它真的被调用。**

`WPN_Missile.SetOwner`（0x00B66390）在 dump.cs 里是个正常的 `public void`，
但在整份二进制里**一个直接调用点都没有** —— owner 是 `Weapon.ProjectMissile` 直接写字段的。
挂它等于挂了个死钩子，`homingArmed` 永远是 0，看起来就像"追踪算法不生效"。
**验证方法**：对 `il2cpp` 段做 `E8` 相对调用扫描，数目标地址的调用点个数。
（`Rigidbody.set_velocity` 有 10 个调用点，说明扫描方法本身是可靠的。）

**坑 5：不要用「碰到东西」当作清理制导记录的条件。**

上一版把 `OnCollisionEnter` / `OnTriggerEnter` 也当成清理点。看起来合理（弹体撞到东西就该结束制导），
实际上是致命的：弹体**刚出膛那几帧**身上还挂着各种碰撞体，`WPN_GRENADE.OnTriggerEnter`（近炸引信）
立刻触发，记录在第 1 帧就被删掉，制导只写了一次速度，之后整段飞行都是原版直线。

日志上的特征非常明确（实测数据）：
`arm=38`、`forget=38`、`drop=0`、`steer=123` —— **123 / 38 ≈ 3**，
也就是说「每颗弹平均只拐了 3 次」。一颗飞 100 单位、速度 50 的弹至少要拐几十帧。
**看到 steer / arm 只有个位数，就是记录被提前删了**，去 `清理原因[...]` 里找是谁删的。

正确做法：清理只挂在**回对象池**（`Recycle`）上；「碰到东西」只记账。
对象池复用的安全由「登记时先清旧记录 + 身份指纹复核」保证。

**验证方法**：写一个能加载 script.js 的桩环境（stub `Interceptor` / `NativeFunction` / `Process`），
手动按顺序调 `SetWeaponData -> Work -> FixedUpdate x N -> OnTriggerEnter -> FixedUpdate x N`，
断言 `steer_wrote` 在 `OnTriggerEnter` 之后**继续增长**。本轮 31 项断言全过；
把「trigger 之后记录还在」改回旧行为会立刻挂 5 项 —— 这就是回归测试的价值。

## 9. 已知限制

- 爆炸物 / 技能弹**不做直伤**（本轮改的）：只在弹体上做追踪，伤害完全由原版爆炸结算。
- 跳过射线后，原版「墙上弹孔 / 着弹特效」由 `WPN_Gun.Damage` 内的
  `EffectManager.CreateBulletHole` 生成，本功能不再产生。
- 找不到目标时默认**回退原版弹道**（`fallback_to_original = true`），
  避免出现"打完敌人后开枪毫无反馈、看起来功能没生效"的错觉；
  想只保留纯直伤（无目标时子弹彻底不飞）就把它关掉。
- 伤害部位倍率 / 距离衰减不会复刻，固定使用武器基础伤害 x 倍率。
- **只有 `gamemanager` 会真正杀死敌人**；`hurt`/`health` 只扣血，敌人会变成 HP 0 但站着不死，
  只在需要不触发击杀/死亡流程的特殊场景才用。
- 弹体追踪**没有寻路**：只把速度/朝向掰向目标，目标在厚墙后面时会撞墙爆炸（原版行为）。能否绕墙的评估见 §10（结论：凸障碍可做，走廊/房间需要真寻路）。
- 弹体追踪把速度设成固定大小（不再叠加重力），所以追踪中的弹体是平飞的，不再有抛物弧线；
  想要弧线手感就把 `homing_turn` 调小（例如 0.4）。
- 弹体在飞行中**不会**换目标，除非原目标死亡/失效（`homing_retarget`）。
- 登记依赖「开火钩子 → `SetWeaponData`」在同一次调用栈内配对，窗口 `homing_pending_ms`（默认 800ms）。
- `nearest` 模式下永远是"离自己最近的敌人"，与你朝哪打无关；
  想恢复"只打准星方向"就把 `target_mode` 改回 `angle_then_distance` 并设 `max_angle_deg`。

## 10. 「弹体绕墙」可行性评估

> 本节是**调研结论，没有写任何代码**。现有实现仍然没有避障。

### 10.1 结论先给

| 目标 | 可行性 | 成本 | 建议 |
|---|---|---|---|
| 绕开**柱子 / 墙角 / 凸台 / 薄墙**（凸障碍） | **可行**，1~2 次射线/帧 | 低（约 60 行） | **推荐先做** |
| 绕开**窄缝 / 复杂凸形组合** | 可行 | 中（约 120 行，8~16 条射线/帧） | 有需要再做 |
| 绕开 **L 形 / U 形走廊、进房间**（凹形，要绕远路） | 技术上可行，但**必须真寻路** | 高 | **不建议现在做** |
| 干脆**穿墙**（不绕，直接穿过去） | 最省事 | 极低（改 layer / 关碰撞，1~2 行） | 备选，但观感是弹体穿墙 |

### 10.2 为什么凸障碍可行、凹形不行

贪心避障（local avoidance）的本质是**只看眼前**：

- **遇到柱子**：射线打到柱子 -> 把速度投影到柱面切向 -> 弹体贴着柱子滑过去 -> 柱子后面重新看见目标 -> 恢复直追。**成功**。
- **遇到 U 形槽**：弹体沿一面墙滑进去，到尽头被另外两面墙夹住，各个方向都被挡住，只能原地蹭到撞墙爆炸。**失败**。

要解决凹形，必须有「全局地图」概念，也就是真寻路（A* / navmesh）。
这也是商业 FPS 里「会拐弯的火箭」通常只做**凸障碍避让 + 沿墙滑动**的原因。

### 10.3 三层实现方案（如果要做的话）

**T1 —— 单射线 + 沿墙滑动（最推荐）**

每个物理步（`FixedUpdate` 的 onLeave）：

1. `Physics.Linecast(弹体位置, 目标瞄点, layerMask)` 判断直线通不通；
2. 通 -> 走现有的直追目标逻辑（完全不变）；
3. 不通 -> 用 `Physics.Raycast(..., out RaycastHit)` 拿**碰撞点法线**，把朝目标的方向投影到法线所在的切平面上，得到沿墙滑的方向；
4. 把这个方向限制在与当前速度夹角 <= 60 度之内（防止突然掉头），再按 `homing_turn` 插值写入 velocity。

- 射线数：1~2 条/帧
- 起点必须**前移 0.3~0.5m**，否则会打到弹体自己的 collider
- `maxDistance` 取 `到目标距离 - 0.6`，否则会把目标自己的 collider 当成障碍

**T2 —— 多方向采样（绕更复杂的凸形）**

被挡住时，以目标方向为轴心，在 20~60 度偏角上采 8~16 条 `Linecast`，对每条候选方向打分 `score = 与目标方向的夹角 + 被挡惩罚`，取最优先通过的方向。仍然会卡凹形。

**T3 —— 真寻路（NavMesh / A*）**

`NavMesh.SamplePosition` 找起终点 + `NavMesh.CalculatePath` 出路径点，弹体追「下一个路径点」而不是直接追目标。四个问题：

1. **依赖场景里有烘焙 navmesh**（`AstarPathfindingProject.dll` 的存在是好兆头，但没验证过地图里有 graph）；
2. 弹速 50 m/s、50Hz 物理步 = 每步飞 1m，需要至少 8~10m 的前瞻点，否则来不及拐；
3. 弹体是 Rigidbody 物理驱动，路径点和物理碰撞同时驱动会互相打架；
4. 工作量大（路径缓存、失败回退、每颗弹独立状态）。

### 10.4 必须注意的风险

| 风险 | 说明 |
|---|---|
| 打到弹体自己 | 射线起点前移，或排除弹体 layer（用 `Physics.DefaultRaycastLayers` = `~IgnoreRaycast`） |
| 打到目标自己 | `maxDistance = 到目标距离 - 0.6`；或读 `RaycastHit.collider` 比对目标实体 |
| 墙会动 / 可破坏 | 每帧重测，缓存不要超过 1 个物理步 |
| 绕墙降低命中率 | 只在被挡住时才避障，并限制单帧最大偏转角（<=60 度） |
| 凹角死循环 | 贪心避障的固有限制，无法根治；可加「原地停留超时 -> 放弃避障直飞」兜底 |
| 多人模式 | 弹体若在各客户端各自模拟，绕墙轨迹会不一致（视觉上无所谓，伤害仍由碰撞决定）；若服务器权威，则只有本地看到绕墙 |
| 性能 | 50Hz x 每弹 16 条射线，6 颗弹同时存在约 4800 次/秒 raycast；Unity 世界小，单次约 1~3us，总量约 1.5% CPU，**可接受** |

### 10.5 如果要做，第一步只做 T1

T1 的收益/成本比最高，而且**失败时不会比现在更差**（通不了就退回现有直追逻辑）。
T2/T3 建议等 T1 实测确认「绕柱子真的有效、观感可接受」之后再决定。
