# 游戏模式切换-简要说明

## 1. 目标

提供一个最小化的游戏模式替换功能。玩家在 CustomTkinter UI 中选择模式，点击游戏原本的“开始游戏”后自动生效。

第一版不支持对局中热切换，不做复杂界面，不增加独立“应用”按钮。

## 2. 文件

```text
AAAAA-game_mode_override_min.js
AAAAA-game_mode_override_ui.py
游戏模式切换-简要说明.md
```

## 3. UI

UI 只提供：

1. “启用模式替换”开关。
2. 单选模式下拉框。
3. 当前连接和生效状态文本。

选择变化通过 `setConfig` 发送给 JS。选择只更新下一局配置，真正覆盖发生在游戏原本的开始流程中。

## 4. 模式映射

| UI 选项 | GameMode | WeaponLimited |
| --- | ---: | ---: |
| 团队竞技 | `TeamDeath = 0` | `None = 0` |
| 特殊战 | `Special = 2` | `None = 0` |
| 个人竞技 | `DeathMatch = 1` | `None = 0` |
| 生化3 | `Nano3 = 3` | `None = 0` |
| 多人生化（生化4） | `Nano4 = 4` | `None = 0` |
| 生化6 | `Nano6 = 5` | `None = 0` |
| 生化4终结者 | `Nano4_Terminator = 6` | `None = 0` |
| 狙击战 | `TeamDeath = 0` | `Sniper = 3` |
| 手枪战 | `TeamDeath = 0` | `HandGun = 2` |

狙击战和手枪战不是独立 `GameMode`，而是团队竞技规则加 `WeaponLimited` 武器限制。

## 5. 拦截流程

流程入口：

```text
UI_GameRoom.OnStartGameBtnDown
RVA: 0xB25F40
```

正常流程中，`UI_GameRoom.OnStartGameBtnDown` 会先调用当前 `MapAsset` 的虚方法 `ApplyGameSetting`，再启动场景加载协程。

实际 Hook：

```text
MapAsset.ApplyGameSetting
RVA: 0xAE82B0
```

该方法会正常写入：

```text
GameManager.gameMode
GameManager.gameModePrefab
GameManager.weaponLimited
```

JS 在 `MapAsset.ApplyGameSetting` 的 `onLeave` 执行一次最终覆盖。此时地图基础配置已经完成，派生实现和场景加载流程尚未结束。

`MapAsset_DeathMatch`、`MapAsset_Nano` 和 `MapAsset_TeamDeath` 的派生实现都会先调用这个基础方法；基础方法返回后，派生实现只继续设置比分、时间、回合等规则参数，不再覆盖 `GameManager.gameMode`、`GameManager.gameModePrefab` 或 `GameManager.weaponLimited`。

## 6. 目标规则预制体

不能只覆盖 `GameManager.gameMode`，否则游戏可能仍实例化原模式规则。

JS 从当前 `UI_GameRoom.mapDatas` 中扫描 `MapAsset.gameMode`，找到目标模式对应的 `MapAsset`，读取其默认 `gameModePrefab`，然后一起写入 `GameManager.gameModePrefab`。

不假定 `mapDatas` 的数组顺序固定。

## 7. 失败处理

出现以下情况时放弃本次覆盖，让游戏继续使用原始设置：

- 找不到 `UI_GameRoom` 或 `mapDatas`。
- 找不到目标模式对应的 `MapAsset`。
- 目标 `gameModePrefab` 为空。
- 游戏进程或脚本已断开。

JS 记录失败原因，但不阻断游戏正常开始。

## 8. 第一版范围

第一版只实现：

- 自动连接 `UnityCrossFire.exe`。
- 模式替换开关和 9 项单选下拉框。
- 开始游戏时进行一次模式、规则预制体和武器限制覆盖。
- RPC 配置、状态查询和 cleanup。

第一版不实现：

- 对局中途热切模式。
- 后台定时锁值。
- 复杂地图兼容性修复。
- 模式专属时间、比分、回合数的额外配置。
- 测试文件或复杂交付物。

跨模式使用某张地图时，地图是否具备目标规则需要的出生点和场景对象，仍由游戏原始地图资源决定。第一版只做个人竞技中立出生点兜底，不为不兼容地图补场景资源。

## 9. 个人竞技模式特殊处理

根因判断：个人竞技不是“没有 bot 生成”，而是进入生成/出生阶段后，个人竞技会强制走 `Neutral` 阵营，依赖地图里的 `SP_Netural` 出生点；如果把个人竞技强行套到其他模式地图上，而那个地图没有中立出生点，bot 就会看起来没有正常加载。

个人竞技的关键特殊点：

- `UI_GameRoom.GenerateBotClient` 仍会按 bot 数量生成 bot 的 `ClientData`，并写入 `UI_GameRoom.players`。
- bot 初始 `joinTeam` 仍然是 `0/1` 交替，不是在生成阶段直接变成中立。
- `GameManager.AddPlayer` 在 `GameMode.DeathMatch = 1` 时，会无视传入的 `joinTeam`，强制把玩家和 bot 的队伍改成 `Team.Neutral = 2`。
- `MapManager.GetSpawnPoint` 在队伍为 `Neutral = 2` 时会读取 `SP_Netural`。缺少 `SP_Netural` 的地图无法稳定支持个人竞技出生。

第一版采用最小修法：不改变个人竞技的 `Neutral` 阵营规则，只在 `SP_Netural` 为空或不可用时，临时把当前 `MapManager.SP_Netural` 指向已有的 `SP_BL` 或 `SP_GR` 出生点数组。这样玩家和 bot 仍然属于中立阵营，只是借用两队出生点完成出生。

该兜底只解决“没有中立出生点导致无法出生”的问题，不补地图专属物件、场景触发器或模式规则参数。验证个人竞技时，仍应优先使用原本支持个人竞技的地图；如果在团队、生化、特殊战等地图中强制切换到个人竞技，需要重点观察借用出生点后是否有重叠、卡点或出生位置不合理。

## 10. 实施步骤

1. 参考现有最小功能模板，确定 Frida 自动连接、RPC、日志和 cleanup 写法。
2. 编写 `AAAAA-game_mode_override_min.js`：安装 `MapAsset.ApplyGameSetting` Hook，扫描目标 `MapAsset`，覆盖模式、规则预制体和武器限制。
3. 为个人竞技增加 `MapManager.SP_Netural` 兜底：捕获 `MapManager.Awake` 的实例，在 `MapManager.GetSpawnPoint(Neutral)` 前检查中立出生点，必要时借用 `SP_BL` 或 `SP_GR`。
4. 编写 `AAAAA-game_mode_override_ui.py`：自动连接游戏，提供启用开关、9 项模式下拉框和状态文本。
5. 执行 JS 语法检查、Python 编译检查和 RPC/地址静态核对，不创建测试文件。
6. 游戏实测时依次验证团队、个人、生化、狙击和手枪，再验证 Nano6 与 Nano4_Terminator；不兼容地图只记录现象，不在第一版补资源。
