# 游戏模式切换-简要说明-整合版2.2

本文按 `全功能整合包2.2/game_modifier/features/27_game_mode_override/script.js` 的当前逻辑整理。

## 1. 总体规则

模式切换只在游戏房间开始流程中生效，不做对局中热切换。脚本通常会在 `MapAsset.ApplyGameSetting` 后覆盖 `GameManager.gameMode`、`GameManager.gameModePrefab`、`GameManager.weaponLimited`，并在开始按钮流程末尾同步胜利条件、时间、回合等规则字段。

例外：个人竞技图切到普通生化、剑客模式或多人生化时，会先保留个人竞技模式给 `GenerateBotClient` 生成 bot，再在 `GenerateBotClient.leave` 后套用目标生化模式；如果该回调没有按预期命中，`GameManager.AddPlayers.enter` 会作为兜底时机。多人生化还会额外补 `SupplyBox` / attribute 链路，用于触发升级箱。

UI 当前提供 7 个选项：团队竞技、刀战、生化4、生化6、生化4终结者、狙击战、手枪战。

生化类判断范围是 `GameMode=3..6`。虽然 UI 不提供生化3和个人竞技选项，但源地图仍可能是这些模式。

代码依据：

- 模式选项来自 `MODES`：团队竞技 `gameMode=0`，普通生化 `4`，剑客 `5`，多人生化 `6`；刀/手枪/狙击是 `weaponOnly` 分支。
- 生化类源图判断来自 `isNanoGameModeValue(gameMode)`，范围是 `3..6`。
- 刀战、狙击战、手枪战在个人/团队图只走 `applyWeaponOnlyMode` 写 `GameManager.weaponLimited`，并由 `applySelectedModeRules` 跳过规则同步，所以胜利条件沿用原地图。
- 刀战、狙击战、手枪战在生化类图会走 `applyTeamDeathWeaponOnlyMode`，把 `GameManager.gameMode` 和 `gameModePrefab` 改成团队竞技，再叠加武器限制。
- 团队规则来自 `buildTeamRule`：普通场景读团队下拉框；生化类源图转团队规则时由 `shouldUseFixedTeamTimeLimit` 固定写 12:00。
- 生化规则来自 `buildNanoRule`：目标回合读 `Nano.RoundDatas`，普通/剑客读 `Nano.GameTime_Nano4`，多人生化读 `Nano.GameTime_Nano4Terminator`。
- 多人生化升级箱链路来自 `ModeBase_Nano.OnStartNewGameRound` 和 `StartGenerateSupplyBox`：只在目标模式是 `nano4_terminator`，并且实例精确校验为 `Mode_Nano4_Terminator` 时写入。

## 4. 胜利条件和时间

团队规则使用 `buildTeamRule`：

- 选择“团队竞技”时，如果源地图是生化类 `GameMode=3..6`，固定按限时胜利处理，`targetScore=0`，比赛时间固定为 12:00。
- 选择“刀战 / 狙击战 / 手枪战”时，如果源地图是生化类 `GameMode=3..6`，脚本会先转团队规则，也同样固定限时 12:00。
- 其他团队规则仍按房间下拉框读取：限时胜利读取团队时间数组；击杀胜利读取团队击杀数组和击杀条件时间。
- 团队规则会写 `revengeEnable=1`、`targetRound=0`、`respawnTime=3.0`。

生化规则使用 `buildNanoRule`：

- `targetRound` 从生化回合数组读取，兜底为 9/11/13/15/17，默认偏向 13。
- `targetScore=0`，`revengeEnable=0`，`respawnTime=3.0`。
- 多人生化时间优先读终结者静态时间，兜底 3:30；普通生化/剑客时间优先读普通生化静态时间，兜底 2:30。

## 5. 静态配置/兜底值

脚本会优先读取游戏里的 `MapAsset` 静态配置；读不到时使用下面的兜底值。生化类地图切到团队规则这个场景例外，会固定写入 12:00。

| 配置项 | 读取来源 | 兜底值 |
| --- | --- | --- |
| 生化类地图转团队规则 | 固定写入 | 12:00 |
| 团队限时胜利时间 | `TeamDeath.TimeDatas` | 5:00 / 8:00 / 10:00 / 12:00 |
| 团队击杀胜利人头 | `TeamDeath.KillDatas` | 40 / 60 / 80 / 100 / 150 |
| 团队击杀胜利时间 | `TeamDeath.KillConditionTime` | 20:00 |
| 生化目标回合 | `Nano.RoundDatas` | 9 / 11 / 13 / 15 / 17，默认索引用 13 |
| 普通生化/剑客单回合时间 | `Nano.GameTime_Nano4` | 2:30 |
| 多人生化/终结者单回合时间 | `Nano.GameTime_Nano4Terminator` | 3:30 |
| 团队/生化复活时间 | 写入 `ModeBase.respawnTime` | 3.0 秒 |
| 团队复仇开关 | 写入 `GameManager.revengeEnable` | 1 |
| 生化复仇开关 | 写入 `GameManager.revengeEnable` | 0 |
| 团队目标回合 | 写入 `ModeBase.targetRound` | 0 |
| 生化目标分数 | 写入 `ModeBase.targetScore` | 0 |

下拉框默认索引也有固定兜底：团队胜利类型默认按击杀胜利处理；击杀数默认取第 4 档，也就是 100 人头；限时胜利默认取第 1 档，也就是 5:00；生化回合默认取第 3 档，也就是 13 回合。

## 6. 武器和 bot 兼容

刀战、狙击战、手枪战会改 `GameManager.weaponLimited`。为了避免 bot 首次发枪仍拿到不符合限制的主武器，脚本保留 bot 发枪兜底：

| 限制模式 | bot 兜底武器索引 |
| --- | ---: |
| 刀战 | 244 |
| 狙击战 | 2568 |
| 手枪战 | 20 |

团队规则套到个人竞技图时，脚本会在 bot 生成后把 bot 交替分到 BL/GR，并在 `MapManager.Awake` / `GameManager.AddPlayers` / `GetSpawnPoint` 阶段处理出生点兜底。个人竞技图切到普通生化、剑客模式或多人生化时，脚本会先让个人竞技流程生成 bot，再参考团队竞技修复只把 bot 交替分到 BL/GR，并把个人竞技图已有的 `SP_Netural` 借给 `SP_BL/SP_GR`，避免 bot 因队伍/出生点不匹配进不了场。

出生点兜底是通用的：请求 Neutral 出生点时，如果 `SP_Netural` 为空，会尝试借用已有 `SP_BL` 或 `SP_GR`；请求 BL/GR 出生点时，如果对应数组为空，会尝试借用 `SP_Netural`。

这些兜底只解决队伍和出生点数组缺失，不补地图专属机关、触发器或场景资源。

## 7. 补给箱和升级箱

脚本不手动创建箱子坐标，也不直接实例化箱子 prefab。箱子仍走游戏自己的 `StartGenerateSupplyBox` / `UpgrandeBoxGenerator` / `GenerateUpgradeBox` 链路。27 只在目标模式是多人生化时补齐下面内容：

- 从 `attributeAsset.attributes` 加载多人生化特性表。
- 把 `attribute_Nano` 写成 ID 8：`终结者出现`，对应额外红色补给箱。
- 把 `attribute_Human` 写成 ID 18：`英雄出现`，对应额外蓝色补给箱。
- 如果地图缺补给点，会把已有出生点或普通补给点临时借给 `SP_SupplyBox`、`SP_RedBox`、`SP_BlueBox`。
- 同时补齐 `IDList_SupplyBox`、`IDList_RedBox`、`IDList_BlueBox`，内容按对应 `SP_*` 长度填 `0..N-1`，让原生 `MapManager.GetSupplyBoxPoint` 能正常随机取点。
- 监听原生 `UpgrandeBoxGenerator` 是否已经启动；如果游戏没有启动，则在 `StartGenerateSupplyBox.leave` 用同一个原生 generator 兜底启动 `UpgrandeBoxGenerator(62, 0)` 和 `UpgrandeBoxGenerator(91, 1)`。

你说的特殊箱、超级箱、变身箱，本质上都属于多人生化 `SupplyBox` / `UpgradeBox` 这条链路；代码里可确认的名字是 `UpgradeBox`、`SupplyBox.Type.Red`、`SupplyBox.Type.Blue`、`attribute_Nano`、`attribute_Human`、`终结者出现`、`英雄出现`。

| 源地图类型 | 选择普通生化/剑客 | 选择多人生化 |
| --- | --- | --- |
| 个人竞技图 | 不补多人生化升级箱；普通补给箱是否出现取决于游戏原生生化补给流程和地图补给点。 | 补红箱/蓝箱特性；若补给点为空，`SP_SupplyBox/SP_RedBox/SP_BlueBox` 会借用 `SP_Netural`；并补 `IDList_*`；随后按原生延迟启动红/蓝升级箱 generator。 |
| 团队竞技图 | 不补多人生化升级箱；普通补给箱是否出现取决于游戏原生生化补给流程和地图补给点。 | 补红箱/蓝箱特性；若补给点为空，普通箱优先借 `SP_Netural`，没有中立点时继续借 `SP_BL/SP_GR`；红箱优先借 `SP_BL`，蓝箱优先借 `SP_GR`；并补 `IDList_*`；随后按原生延迟启动红/蓝升级箱 generator。 |
| 生化类图 | 普通生化/剑客按原生生化补给逻辑生成普通补给箱。 | 保留原生普通箱；如果红/蓝专属点缺失，红箱优先借 `SP_BL`，再借 `SP_SupplyBox`，蓝箱优先借 `SP_GR`，再借 `SP_SupplyBox`；并补 `IDList_*`；随后按原生延迟启动红/蓝升级箱 generator。 |

代码依据：`MapManager` 字段里有 `SP_SupplyBox=0x1C`、`SP_RedBox=0x20`、`SP_BlueBox=0x24`，也有 `IDList_SupplyBox=0x28`、`IDList_RedBox=0x2C`、`IDList_BlueBox=0x30`。IDA 里 `MapManager.Awake` 只有在地图字典存在对应补给点 key 时才创建并填充 `IDList_*`；`MapManager.GetSupplyBoxPoint` 实际先从 `IDList_*` 随机取索引，再到对应 `SP_*` 取点。多人生化 `StartGenerateSupplyBox` 在非 battle round 分支启动 `UpgrandeBoxGenerator(62, 0)` 和 `UpgrandeBoxGenerator(91, 1)`；该协程内部再调用 `GenerateUpgradeBox`。

## 8. 已知问题修复记录

问题：个人竞技图切到普通生化、剑客模式或多人生化时，进入地图后没有 bot。

原因：如果在 `MapAsset.ApplyGameSetting.leave` 立刻把 `GameManager.gameMode` 改成生化，后续 `UI_GameRoom.GenerateBotClient` 会在生化模式上下文里运行。个人竞技图原本依赖这个阶段生成 bot，模式提前变成生化后，bot 生成可能被跳过，后续再修队伍和出生点也没有 bot 可处理。

二次原因：`UI_GameRoom.OnStartGameBtnDown.leave` 不能代表 bot 已经生成完成。如果在这里消费延迟标记，某些流程里仍会早于 `GenerateBotClient` 改写成生化模式，导致个人竞技图的人机生成继续被跳过。

三次原因：把玩家和 bot 全部写成 Neutral 并不能复用个人竞技图切团队竞技时已经验证过的出生链路，部分生化目标规则下 bot 仍可能因为队伍/出生点不匹配进不了场。

解决方案：仅针对“个人竞技源图 `GameMode=1` -> 生化 `GameMode=4/5/6`”延迟套用目标模式。脚本在 `ApplyGameSetting.leave` 只标记延迟，不在 `OnStartGameBtnDown.leave` 消费；等 `GenerateBotClient.leave` 后再写入目标生化模式和 prefab，`GameManager.AddPlayers.enter` 作为兜底再次尝试。随后参考个人竞技图切团队竞技的修法，只把 bot 交替分到 BL/GR，并确保 `SP_BL/SP_GR` 可借用 `SP_Netural`，不再强制把玩家和 bot 写成 Neutral。

问题：个人/团队/生化类地图选择多人生化时，没有多人生化专属升级箱，或只有普通补给箱。

原因：27 之前只切 `GameManager.gameMode/gameModePrefab` 和规则字段，没有补 `Mode_Nano4_Terminator` 的补给箱与 attribute 链路。多人生化红/蓝升级箱需要本回合 `attribute_Nano/attribute_Human` 配合；个人竞技图/团队竞技图还可能没有 `SP_SupplyBox/SP_RedBox/SP_BlueBox`。另外 `MapManager.GetSupplyBoxPoint` 不是只看 `SP_*`，还要 `IDList_*` 随机索引列表；如果只补 `SP_*`，原生生成器仍然取不到点。

解决方案：目标模式为多人生化时，在精确校验 `Mode_Nano4_Terminator` 实例后写入 `attribute_Nano=终结者出现(8)`、`attribute_Human=英雄出现(18)`；补 `SP_SupplyBox/SP_RedBox/SP_BlueBox`，并用原生 `List<int>` 补齐 `IDList_SupplyBox/IDList_RedBox/IDList_BlueBox`。最后监听原生 `UpgrandeBoxGenerator`，如果游戏没有启动，则用原生 generator 按 `62秒/team=0`、`91秒/team=1` 兜底启动。

## 9. Hook 范围

2.2 整合版保留的是开局和出生/发枪相关 Hook：开始按钮、`MapAsset.ApplyGameSetting`、bot 生成、加玩家、`MapManager.Awake`、取出生点、发枪、Spawn/Respawn。为多人生化升级箱额外使用 `ModeBase_Nano.OnStartNewGameRound`、`StartGenerateSupplyBox` 和 `UpgrandeBoxGenerator`，但只在目标模式是多人生化且实例精确为 `Mode_Nano4_Terminator` 时写入 attribute、补给点数组引用，并按原生 generator 链路兜底。未恢复死亡事件、回合结束、CheckRoundOver 等高风险 Hook。

补充记录：2026-07-22 日志显示，多人生化进入生化类地图时，原生红/蓝升级箱 generator 已启动，且 `MapManager.GetSupplyBoxPoint(Red/Blue)` 已被调用，但调用现场 `SP_RedBox/SP_BlueBox` 数量为 0、`IDList_RedBox/IDList_BlueBox` 不可用，所以红/蓝箱卡在取点阶段。整合版 2.2 已把最终兜底前移到 `GetSupplyBoxPoint.enter`：每次原生取补给点前刷新当前 `MapManager`，并补齐 `SP_SupplyBox/SP_RedBox/SP_BlueBox` 与 `IDList_*`，然后再交给原生函数随机取点。

二次补充：后续日志显示该局只出现 `Yellow(0)` 普通箱取点，未出现 `Red(1)` / `Blue(2)` 取点；同时红/蓝升级箱原生 generator 计数已增加，说明生成器启动过，但本局日志窗口还没等到原生 62 秒/91 秒红蓝升级箱取点，游戏对象就已销毁。另一个代码问题是 `IDList_RedBox/IDList_BlueBox` 可能存在“非空但不是有效 `List<int>`”的旧指针，旧逻辑只在空指针时新建列表，导致红/蓝索引表无法补齐。整合版 2.2 已改为：`getListSize(listPtr) === null` 时直接重建干净的 `List<int>` 并写回 `IDList_*`；同时 `GetSupplyBoxPoint.enter` 诊断先于兜底执行，便于确认原生实际请求的是普通箱还是红/蓝箱。

三次补充：最新日志已经出现 `Red(1)` / `Blue(2)` 取点，说明距离箱子出现已经推进到最后的取点阶段。卡点是 `GetSupplyBoxPoint` 的参数布局不是普通实例方法布局：`args[0]` 表现为 out `SpawnPoint` 临时地址，`args[1]` 才是 `SupplyBox.Type`。旧逻辑在 `GetSupplyBoxPoint.enter` 把 `args[0]` 写成 `Runtime.mapManager`，导致缓存被临时地址污染，后续读取 `SP_RedBox/SP_BlueBox` 时出现 `0x1/0x5` 这类明显不是托管数组的指针，并触发 `access violation accessing 0xc`。整合版 2.2 已修复为：`GetSupplyBoxPoint` 不再覆盖 `Runtime.mapManager`，只使用 `MapManager.Awake` / `GetSpawnPoint` 缓存的真实对象；补点前还会检查缓存对象的 SP 字段形状，字段值必须是 null 或像托管数组的指针，避免把错误对象当 MapManager 写入。

四次补充：团队竞技地图切多人生化时，地图可能本来没有 `SP_SupplyBox/SP_RedBox/SP_BlueBox`，但有 `SP_BL/SP_GR`。补点前的 MapManager 校验不能把待补目标字段也当成必须有效，否则团队图会直接跳过补箱。整合版 2.2 已改为只校验可借用来源点 `SP_BL/SP_GR/SP_Netural/SP_SupplyBox`，只要其中一个是有效数组就允许继续补 `SP_SupplyBox/SP_RedBox/SP_BlueBox` 和 `IDList_*`。
