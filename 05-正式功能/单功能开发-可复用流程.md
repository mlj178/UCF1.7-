# 单功能开发可复用流程

这份流程用于以后开发新的单独功能。

目标是：少走弯路。所有新功能第一版都先做最小可用闭环，不需要复杂设计；核心效果验证稳定后，再考虑是否增加扩展或整合正式版。

## 0. 本文档职责

本文档只规定“开发一个单功能时按什么顺序推进”。

它不重复维护目录标准、生命周期细节、2.1 接入字段：

```text
目录和交付物标准：看《01-单功能开发规范：面向正式发行版.md》
运行期生命周期：看《单功能开发-生命周期规范.md》
整合包2.1接入：看 04-正式发行版/00-正式发行版功能接入规范.md
```

如果要改正式整合包，不在本文档里找旧路径，直接以 2.1 接入规范为准。

## 1. 先说清楚功能目标

先用人话写清楚：

```text
我要实现什么？
在哪些场景必须生效？
哪些场景先不管？
成功标准是什么？
```

例子：

```text
实现无限背包。
远离出生点、开枪时，也能打开背包并切换武器。
先只管玩家自己，不管 BOT。
先做单功能测试，不急着进正式发行版。
```

## 2. 先查资料，不急着写代码

优先查这些地方：

```text
01-游戏逆向分析-相关信息/Il2CppDumper/dump.cs
01-游戏逆向分析-相关信息/IDA-汇编代码/索引文件
01-游戏逆向分析-相关信息/IDA-汇编代码/切分输出
```

要确认：

```text
相关类
相关方法
RVA 地址
字段偏移
调用链路
字段类型是不是普通类型
```

不要只凭名字猜。

## 3. 写最小实现步骤

可以在功能文件夹里先写一个简要说明文档：

```text
05-正式功能/XX-功能名/功能名-简要说明.md
```

内容不用长，但要写清楚：

```text
目标
调用链路
关键 RVA
关键字段偏移
推荐方案
备选方案
测试方式
失败后怎么继续查
```

这一步不是强制交付物，作用是让后面的代码有方向。

## 4. 先解释原理

写代码前，AI 必须先停下来，用人话说清楚原理。

必须说清楚：

```text
Hook 哪个方法？
改哪个字段？
调用哪个原游戏方法？
为什么这样风险更低？
哪些东西暂时不改？
如果这个方案失败，下一步查哪里？
```

如果原理说不清，先别写代码。

这一段要尽量简洁，不要堆术语。

推荐格式：

```text
实现原理：
1. 入口是 xxx 方法。
2. 关键限制是 xxx 字段。
3. 最小实现只改 xxx，不改 xxx。
4. 风险是 xxx，所以先用 Hook 验证。

请你确认这个方案。
你确认后，我再继续写最小实现代码。
```

## 4.5. 必须等待确认

这是流程里的强制暂停点。

AI 解释完原理后，不能继续写代码，必须等用户明确回复。

可以继续的回复例子：

```text
确认
继续
按这个方案写
执行编写代码
```

没有确认前，不要进入下面这些步骤：

```text
不要写 JS
不要写 launcher
不要写测试
不要改正式发行版
```

这一步的目的不是拖慢开发，而是避免方向错了还一路写到底。

## 5. 优先做最小实现

用户确认原理后，再进入这一步。

这是所有新功能的默认起点：第一版只做核心功能，不做复杂设计。

优先原则：

```text
能 Hook 就先 Hook
能走游戏原逻辑就走游戏原逻辑
能少改字段就少改字段
需要替换函数时可以使用 Interceptor.replace，但要写清楚原因和恢复方式
生命周期函数禁止 replace，只允许用 Interceptor.attach 监听
能不主动调用危险函数就不主动调用
```

不要第一版就做：

```text
正式版整合
复杂 UI
快捷键配置
大量恢复逻辑
重写游戏完整流程
```

## 6. 代码文件放在功能目录

推荐结构：

```text
05-正式功能/XX-功能名/
├── AAAAA-功能名_min.js         # 唯一核心 JS
├── AAAAA-功能名_ui.py          # 唯一 CustomTkinter UI
└── 功能名-简要说明.md          # 可选
```

注意：

```text
单功能标准入口是 UI，不是 launcher.py。
launcher.py 只能作为临时调试工具，不作为正式单功能交付标准。
单功能 UI 只用于验证，不直接接入全功能整合包2.1。
迁移到2.1时优先完整复制核心 JS，再补插件壳。
manifest.release-draft.json、生命周期说明、经验总结、tests、README 默认不需要补。
```

如果功能还没跑通，先不要放进正式发行版。

### 6.1 用户指定的轻量开发方式

默认只写两个代码文件：

```text
AAAAA-功能名_min.js
AAAAA-功能名_ui.py
```

分工固定为：

```text
JS：Hook、内存读写、Runtime 状态、RPC、cleanup、setConfig
PY：CustomTkinter UI、自动连接 UnityCrossFire.exe、加载 JS、显示状态和日志
```

不要再额外写：

```text
launcher.py
多个 JS 变体
多个 Python 辅助脚本
单独的命令行启动器
```

## 7. 按需要写可自动检查的测试

测试文件默认不需要。

功能风险高、容易写错地址、需要长期复用时，可以临时做自动检查，但不要把测试文件当成默认交付物：

```text
JS 文件是否存在
关键 RVA 是否写对
字段偏移是否写对
是否用了 Interceptor.attach
Interceptor.replace 是否有明确理由
生命周期函数是否没有使用 Interceptor.replace
RPC 接口是否导出
UI 是否使用 customtkinter
UI 是否加载正确 JS
UI 是否调用 enable/disable/status/cleanup
UI 是否有日志区
```

如果写测试，推荐用标准库 `unittest`，不用依赖额外包。

运行例子：

```powershell
python -m unittest "05-正式功能\XX-功能名\test_功能名_static.py" -v
node --check "05-正式功能\XX-功能名\AAAAA-功能名_min.js"
python -m py_compile "05-正式功能\XX-功能名\AAAAA-功能名_ui.py"
```

## 8. 写 Frida 脚本

脚本里固定写清楚：

```text
功能目标
实现原理
RVA
字段偏移
Hook 点
RPC 接口
日志
cleanup
```

### 8.1. 读写静态字段的正确方式

**用 TypeInfo RVA，不要用 il2cpp 反射 API。**

### 8.2. 必须阅读生命周期规范

写 JS 前必须阅读《单功能开发-生命周期规范.md》，所有功能都要实现 enable/disable/status/cleanup，并按 generation 机制清理旧指针。

常用 RPC：

```text
enable()
disable()
status()
cleanup()
```

日志不要刷屏，只记录关键点。

## 9. 写 CustomTkinter UI

UI 负责：

```text
等待游戏进程
自动连接 UnityCrossFire.exe
attach 游戏
加载当前功能目录下的唯一核心 JS
开关调用 enable/disable
可配置项调用 setConfig
定时调用 status()
显示日志
退出时 cleanup()
```

UI 推荐保持简单：

```text
标题
连接状态栏
功能开关
必要参数控件
状态数据显示
运行日志
```

常用控件：

```text
开关：CTkSwitch
倍率/数值：CTkSlider
枚举选择：CTkOptionMenu
日志：CTkTextbox
按钮：CTkButton
```

第一版 UI 只做能测试功能的东西，不要塞复杂设置页。

UI 控件展开原则：

```text
能让用户选择的布尔项，尽量展示为 CTkSwitch
需要调倍率、距离、速度、时间、范围等数值的项，使用 CTkSlider
滑块旁边必须显示当前数值
UI 不直接读写游戏内存，所有配置变化都通过 setConfig 传给 JS
默认配置写在 JS Runtime.config；UI 文件顶部可以写 DEFAULT_CONFIG 作为界面默认值
```

## 9.5. launcher 只能临时使用

如果排查问题时需要命令行快速注入，可以临时写 `launcher.py`。

但交付时要有 UI：

```text
AAAAA-功能名_ui.py
```

不要只交付 launcher。

## 10. 可选简要说明文档

如果需要保留上下文，可以在功能目录下写一个简要说明文档：

```text
功能名-简要说明.md
```

写清楚：

```text
当前实现原理
改了什么字段
Hook 了什么方法
怎么运行
怎么测试
目前边界
如果失败下一步查哪里
```

这份文档是可选的，给以后的自己和 AI 看。

## 11. 验证顺序

能自动验证的先自动验证：

```text
node --check（如果有 JS）
py_compile（如果有 Python UI）
文件清单
```

再进游戏验证：

```text
正常场景
边界场景
反复开关
切房间
退出游戏
```

自动验证通过不等于游戏内一定成功。

如果写了简要说明文档，进游戏实测结果可以写回 `功能名-简要说明.md`。

## 12. 失败时怎么处理

不要马上重写。

按顺序查：

```text
Hook 有没有命中
参数是不是对的
字段指针是不是空
字段类型是不是加密/结构体
返回值在哪里变成失败
是不是还有 UI 层限制
是不是调用线程不对
```

优先加日志和探测脚本。

确认问题后再改代码。

## 13. 什么时候整合正式发行版

满足这些条件后再整合：

```text
单功能脚本能稳定运行
核心场景测试通过
失败边界已经记录
cleanup 不会破坏游戏
RPC 接口稳定
字段和 RVA 来源清楚
```

整合时再参考：

```text
04-正式发行版/00-正式发行版功能接入规范.md
```

当前整合包2.1使用插件目录 `features/<feature_dir>/`。本文档不维护 2.1 的具体接入字段，避免和正式接入规范重复。

## 一句话流程

```text
说清需求 -> 查 dump/IDA -> 可选写简要说明 -> 讲清原理 -> 停下等确认 -> 写唯一核心 JS -> 写唯一 CustomTkinter UI -> 自动验证语法 -> 进游戏实测 -> 稳定后再整合正式版
```
