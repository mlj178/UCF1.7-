## 七、多人生化模式 (Nano) 游戏逻辑通俗讲解

### 7.1 一局生化模式从头到尾发生了什么

```
① 加载地图 → ② 所有人出场(都是人类) → ③ 倒计时 
→ ④ 随机选几个人变幽灵 → ⑤ 每一回合开始选特性 
→ ⑥ 人类开枪打幽灵 / 幽灵抓人感染 → ⑦ 回合结束 → 回到⑤
```



**你当前玩的 Nano4+Terminator** 是普通生化的升级版，比普通生化多了：

- **回合特性**（每回合抽卡：不死契约、致命一击...）
- **终结者进化链**（普通终结者 → 高级终结者 → 魔王）
- **升级箱**（红色/蓝色特殊补给箱）
- **墓碑复活**（不死契约对应功能）

### 7.3 回合特性是怎么抽出来的

用大白话说就是：**每回合开始，游戏从两个奖池里各抽一张卡。**

```
幽灵方奖池 (normalRound.nano)      人类方奖池 (normalRound.human)
┌──────────────────────┐         ┌──────────────────────┐
│ 🔴 不死契约  权重=10  │         │ 🔵 致命一击  权重=10  │
│ 🔴 硬化      权重=10  │         │ 🔵 致命攻击  权重=10  │
│ 🔴 沸血      权重=10  │         │ 🔵 英雄出现  权重=10  │
│ 🔴 末日降临  权重=5   │         │ 🔵 救世主    权重=10  │
│ ...            ...    │         │ ...            ...    │
└──────────────────────┘         └──────────────────────┘
        ↓ 随机抽一张                      ↓ 随机抽一张
   attribute_Nano                   attribute_Human
  (存到 0xE0 字段)                 (存到 0xE4 字段)
        ↓                                ↓
  "本回合幽灵方获得 不死契约"      "本回合人类方获得 致命一击"
```

**但还有隐藏规则（IDA 反编译发现的！）：**

- 每 5 回合是"决战回合"（`isBattleRound = true`），用 `battleRound` 池代替 `normalRound`
- 如果场上**活人少于 8 个**，禁止出现"末日降临"和"英雄出现"
- 权重高的特性被抽中的概率更大

### 7.4 一个人被感染后发生了什么

```
人类被幽灵挠了一下 → 
  InfectEvent(nanoGhost, soldier) 被调用 →
    soldier 变成 NanoGhost(role=1) →
      幽灵经验 +10（感染成功加分）→
        检查是不是所有人都被感染了（CheckRoundOver）→
          如果是 → 幽灵胜利(GhostWin)
          如果不是 → 游戏继续
```

### 7.5 一个人变成英雄是什么流程

```
人类按 E 键 → 
  TryBecomeHero(player, keyState) 被调用 →
    检查条件：死掉的队友够不够？→
      GetHeroRole(player) 决定变成哪个英雄 →
        BecomeHero(player, role, showTip) →
          UpdateNanoRole(player, newRole)  ← 核心！切换角色身份 →
            更换模型、更换武器、刷新 HUD
```

## 八、BUFF选择器的设计哲学：临时变量 vs 实际生效变量

### 8.1 核心设计理念

**问题**：如何让用户"看到上次的选择"，但"不自动生效"？

**答案**：**双变量体系** - 临时变量（UI显示） + 实际生效变量（Hook控制）

```
┌─────────────────────────────────────────────────────────┐
│  变量体系架构                                            │
├─────────────────────────────────────────────────────────┤
│  临时变量 (_temp_ghost/human)                           │
│  ├─ 作用：记录用户的选择偏好                             │
│  ├─ 取值：幽灵方 0-9，人类方 10-19                      │
│  ├─ 保存：写入配置文件（Nano-4T-selector.json）         │
│  └─ 用途：UI显示、记住用户偏好                          │
│                                                          │
│  实际生效变量 (_wanted_ghost/human)                     │
│  ├─ 作用：控制Hook是否拦截                              │
│  ├─ 取值：-1（未激活）或 0-9/10-19（已激活）            │
│  ├─ 保存：不保存到配置文件                              │
│  └─ 用途：运行时状态，决定是否干预游戏                  │
└─────────────────────────────────────────────────────────┘
```

### 8.2 为什么需要-1哨兵值？

**-1的含义**：**"用户未明确确认，不要干预游戏"**

#### JavaScript Hook逻辑：
```javascript
onLeave: function(retval) {
    if (!NANO4T_ACTIVE) return;  // 未激活，透传
    var id = this._isNano ? NANO4T_WANTED_GHOST : NANO4T_WANTED_HUMAN;
    if (id < 0) return;  // id=-1，透传（游戏正常运行）
    // id>=0，替换返回值（干预游戏）
    retval.replace(NANO4T_ATTR_PTR[id]);
}
```

**关键点**：
- `-1` 是哨兵值，表示"未激活"
- `>= 0` 表示"已激活"，Hook会拦截并替换buff

### 8.5 配置文件的作用

**配置文件保存什么？**
```json
{
  "ghost": 5,
  "human": 15
}
```

**答案**：保存**临时变量**（用户偏好），不保存实际生效变量。

**为什么？**

| 变量类型 | 是否保存 | 原因 |
|----------|----------|------|
| 临时变量 | ✅ 保存 | 记住用户的选择偏好，下次打开显示 |
| 实际生效变量 | ❌ 不保存 | 运行时状态，每次启动都应该重置为-1 |

**类比**：
```
配置文件 = 浏览器的"记住密码"
临时变量 = 密码输入框显示的内容
实际生效变量 = 是否已点击"登录"按钮
-1 = 还没点击"登录"
实际值 = 已点击"登录"
```

### 8.6 设计优势总结

#### 1. 用户体验优势

| 优势 | 说明 |
|------|------|
| **记住偏好** | 下次打开程序，UI显示上次的选择 |
| **明确确认** | 必须点击"应用"才生效，不会误操作 |
| **状态清晰** | [未激活]/[已激活]状态标签一目了然 |
| **安全可靠** | 不会在用户不知情的情况下干预游戏 |

#### 2. 技术实现优势

| 优势 | 说明 |
|------|------|
| **变量分离** | UI显示与实际生效分离，逻辑清晰 |
| **哨兵值设计** | -1表示未激活，避免混淆 |
| **状态重置** | 退出房间自动重置，不会残留状态 |
| **异常防护** | 配置文件无效值自动修正 |

#### 3. 防止的问题

| 问题 | 传统设计 | 本设计 |
|------|----------|--------|
| 程序启动自动生效 | ❌ 会发生 | ✅ 不会发生 |
| 用户未确认就生效 | ❌ 会发生 | ✅ 不会发生 |
| 退出房间状态残留 | ❌ 会发生 | ✅ 不会发生 |
| 配置文件无效值 | ❌ 程序崩溃 | ✅ 自动修正 |

```
│  实际生效=-1 → Hook透传 → 游戏随机buff                   │
│  临时变量不变 → UI保持上次选择                           │
└─────────────────────────────────────────────────────────┘
           ↓
┌─────────────────────────────────────────────────────────┐
│  用户再次进入                                            │
├─────────────────────────────────────────────────────────┤
│  实际生效=-1 → Hook透传 → 游戏随机buff                   │
│  UI显示临时变量 → 提示：请点击「应用」                   │
└─────────────────────────────────────────────────────────┘
```

### 8.8 核心设计原则

**原则1：用户意图优先**
- 用户必须明确点击"应用"才生效
- 不会在用户不知情的情况下干预游戏

**原则2：状态清晰可见**
- [未激活]/[已激活]状态标签
- UI显示与实际状态同步

**原则3：记住用户偏好**
- 配置文件保存临时变量
- 下次打开显示上次的选择

**原则4：安全重置机制**
- 退出房间自动重置实际生效变量
- 临时变量保持不变

**原则5：异常防护**
- 配置文件无效值自动修正
- 所有操作都有验证和异常捕获

---

**总结**：这个设计完美解决了"记住用户偏好"和"不自动生效"之间的矛盾，通过临时变量和实际生效变量的分离，实现了用户体验和技术实现的平衡。
