## 一、项目概述

本项目是一个 **DirectX ImGui 注入框架**，用于在 DirectX 游戏中叠加 ImGui 界面。

**适用场景**：
- 32位 DirectX 9/10/11/12 游戏
- 需要在游戏内显示自定义菜单/调试界面

**本项目已适配**：
- UnityCrossFire（32位 Unity IL2CPP 游戏，DirectX 11）

**核心功能**：
- ✅ ImGui 菜单（INSERT 键打开/关闭）
- ✅ DirectX 11 Hook（拦截 Present 函数）
- ✅ ESP 透视方框（CharacterController Bounds 主方案 + hitbox fallback）
- ✅ 管道通信（DLL ↔ Python 客户端，控制 ESP 开关）
- ✅ 玩家检测（GameManager.allPlayers + Bot.Update Hook 补充）
- ✅ 坐标转换（WorldToScreen 投影）
- ✅ 跨局清理（Session Epoch + Hook回调）
- ✅ 线程同步（CRITICAL_SECTION）
- ✅ 指针过期机制（5秒超时自动清理）
- ✅ 方框合理性校验（宽高比、面积、异常值过滤）

## 五、常见问题

### Q1：注入后游戏崩溃

**原因**：
- DLL 位数与游戏不匹配
- DirectX 版本不匹配
- 缺少运行时依赖

**解决**：
```
1. 确认游戏位数，编译对应位数的 DLL
2. 确认游戏使用的 DirectX 版本
3. 安装 Visual C++ Redistributable
```

### Q2：注入成功但无菜单

**原因**：
- DirectX Hook 未生效
- 游戏使用了非标准渲染方式

**解决**：
```
1. 检查游戏是否加载了 d3d11.dll/d3d9.dll
2. 尝试不同的 Hook 顺序
3. 使用 Process Hacker 确认 DLL 已加载
```

### Q3：注入器报错 "未找到 LoadLibraryA"

**原因**：注入器位数与游戏不匹配

**解决**：
```
32位游戏 → 使用 32位注入器（/platform:x86）
64位游戏 → 使用 64位注入器（/platform:x64）
```

### Q4：模块数很少（7个）正常吗？

**正常！**

```
64位 Windows 查看器无法直接看到 32位进程的真实模块
这是 WOW64 模拟层的正常现象
只要注入成功且菜单出现，就说明一切正常
```

### Q5：编译报错 LNK1104: 无法打开文件

**原因**：DLL 被游戏进程占用

**解决**：
```
关闭游戏进程，重新编译
```

## 六、技术原理

### 6.1 注入原理

```
┌─────────────────────────────────────────────────────────┐
│ 注入流程                                                 │
├─────────────────────────────────────────────────────────┤
│ 1. 找到目标进程                                          │
│ 2. 获取 kernel32.dll 在目标进程中的基址                  │
│ 3. 计算 LoadLibraryA 的 RVA（相对虚拟地址）              │
│ 4. 在目标进程分配内存，写入 DLL 路径                     │
│ 5. 创建远程线程，执行 LoadLibraryA                       │
│ 6. DLL 加载，DllMain 执行 Hook 初始化                    │
└─────────────────────────────────────────────────────────┘
```

### 6.2 关键技术点

**RVA 计算**（解决跨位数问题）：
```csharp
// 本地 kernel32.dll 地址
IntPtr localKernel32 = GetModuleHandle("kernel32.dll");
// 本地 LoadLibraryA 地址
IntPtr localLoadLibrary = GetProcAddress(localKernel32, "LoadLibraryA");
// 计算 RVA
long rva = localLoadLibrary.ToInt64() - localKernel32.ToInt64();
// 目标进程的 LoadLibraryA
IntPtr remoteLoadLibrary = new IntPtr(remoteKernel32.ToInt64() + rva);
```

**DirectX Hook**：
```cpp
// Hook Present 函数
oPresent = (Present_t)SwapChain->lpVtbl[8];  // DXGI SwapChain 虚函数表
MH_CreateHook(oPresent, hkPresent, reinterpret_cast<LPVOID*>(&oPresent));
MH_EnableHook(oPresent);
```

### 7.1 ESP 代码位置

```
├── transform_helper.h/cpp # Transform 组件访问（坐标获取）
├── coord_converter.h/cpp # 坐标转换（3D → 2D）
└── esp_renderer.h/cpp    # ESP 渲染器（方框绘制）
```

### 7.2 ESP 功能原理

```
┌──────────────────────────────────────────────────────────────┐
│ ESP 渲染流程（三层优先级方案）                                 │
├──────────────────────────────────────────────────────────────┤
│ 0. Python 客户端发送 set_feature 命令 → ESPState 开启         │
│ 1. GameManager.GetAllPlayers() - 获取所有玩家                │
│ 2. TransformHelper.GetHitboxData() - 获取方框数据            │
│    ├─ 【主方案】CharacterController Bounds                    │
│    │   Entity+0x2C → CharacterController                     │
│    │   → Collider.get_bounds_Injected → Bounds(center,extents)│
│    │   → 8角点投影 → 2D包围盒                                │
│    ├─ 【Fallback 1】hitbox transforms                        │
│    │   CharacterModel.hitboxes[] + neck/spine/spine1         │
│    │   + helmet collider → min/max包围盒                     │
│    └─ 【Fallback 2】characterContainer + 固定身高1.65m       │
│ 3. 方框合理性校验（宽高比、面积、异常值过滤）                  │
│ 4. ESPRenderer.DrawBox() - 绘制方框                           │
└──────────────────────────────────────────────────────────────┘
```

**当前实现方案**：CharacterController Bounds（主）+ Hitbox Fallback

| 优先级 | 方案 | 数据源 | method值 | 说明 |
|--------|------|--------|----------|------|
| **主方案** | CharacterController Bounds | Entity.characterController → Collider.get_bounds_Injected | 1 | 物理碰撞体AABB，不受动画影响 |
| **Fallback 1** | hitbox transforms | CharacterModel.hitboxes + neck/spine/helmet | 2 | 骨骼Transform数组，受动画过渡帧影响 |
| **Fallback 2** | 固定身高 | Player.characterContainer + 1.65m偏移 | - | 最简方案，精度最低 |

**三个方法是优先级链式调用，同一帧对同一个玩家只有一个方法生效**：

```
GetHitboxData(player)
  ├─ 尝试 GetBoundsData()        ← 第1优先
  │   成功 → 返回 (method=1)      ← 大多数情况走这里
  │   失败 ↓
  ├─ 尝试 GetHitboxFallbackData() ← 第2优先
  │   成功 → 返回 (method=2)      ← CharacterController为空时走这里
  │   失败 ↓
  └─ 返回 invalid                  ← 两层都失败

DrawPlayerESP(player)
  ├─ hitbox.valid == true → 用Bounds或Hitbox的方框绘制
  └─ hitbox.valid == false → 走 DrawPlayerESPFallback()  ← 第3优先
                             characterContainer + 1.65m固定身高
```

**实际运行时**：
- **正常玩家**：几乎都走第1优先（Bounds，method=1），因为每个玩家都有CharacterController
- **CharacterController为空的特殊情况**：走第2优先（hitbox，method=2）
- **前两层都失败**：走第3优先（固定身高fallback）

所以三个方法都写入了代码且都能生效，但不是同时参与——是**串行降级**，只有前面的失败才会用后面的。

**为什么 Bounds 是主方案**：
- CharacterController 是 Unity 物理组件，其 bounds 始终反映角色真实碰撞体大小
- 不受动画状态、模型切换、过渡帧影响（解决了多人生化模式异常方框问题）
- 8个角点取min/max天然消除离群点
- 性能优于遍历15+个hitbox Transform

**方框合理性校验**（esp_common.h config）：

| 参数 | 值 | 说明 |
|------|-----|------|
| BOX_MAX_WIDTH | 300.0f | 最大屏幕宽度（像素） |
| BOX_MAX_HEIGHT | 600.0f | 最大屏幕高度（像素） |
| BOX_MIN_ASPECT | 0.15f | 最小宽高比 |
| BOX_MAX_ASPECT | 5.0f | 最大宽高比 |
| HITBOX_MAX_REF_DIST | 5.0f | hitbox点与参考位置最大距离（米） |

**方框计算逻辑（Bounds主方案）**：
```cpp
// 1. 从Entity读取CharacterController
void* controller = *(void**)((char*)player + 0x2C);

// 2. 调用Collider.get_bounds_Injected获取AABB
UnityBounds bounds;  // center(12B) + extents(12B) = 24 bytes
Collider.get_bounds_Injected(controller, &bounds, nullptr);

// 3. 计算AABB的8个角点
bmin = center - extents;
bmax = center + extents;
corners[8] = { bmin/bmax的所有组合 };

// 4. 投影所有8个角点到屏幕空间
for (int i = 0; i < 8; i++) {
    WorldToScreen(corners[i], &screen);
    left = min(left, screen.x);
    right = max(right, screen.x);
    top = min(top, screen.y);
    bottom = max(bottom, screen.y);
}

// 5. 计算最终方框尺寸 + 合理性校验
width = right - left;
height = bottom - top;
// 校验: 宽高比、面积、最小尺寸
```

**方框计算逻辑（hitbox fallback）**：
```cpp
// 1. 从Player读取currentCharacter
void* currentCharacter = *(void**)((char*)player + 0x5C);

// 2. 遍历hitboxes数组
void* hitboxesArr = *(void**)((char*)currentCharacter + 0x74);
for (int i = 0; i < hitboxCount; i++) {
    Transform* tf = hitboxes[i];
    Vector3 worldPos = Transform.get_position(tf);
    // 离群点过滤: 与参考位置距离 > 5m 则跳过
    Vector2 screenPos = WorldToScreen(worldPos);
    left = min(left, screenPos.x);
    right = max(right, screenPos.x);
    top = min(top, screenPos.y);
    bottom = max(bottom, screenPos.y);
}

// 3. 强制加入neck/spine/spine1作为固定补充点
addTransformPoint(neck);    // 头部顶部
addTransformPoint(spine);   // 身体中轴
addTransformPoint(spine1);  // 身体稳定点

// 4. 加入helmet collider作为头部补充点
helmetCollider = helmet + 0x10;
addTransformPoint(helmetCollider.transform);

// 5. 计算最终方框尺寸 + 合理性校验
width = right - left;
height = bottom - top;
```

## 九、踩坑记录与解决方案

> 以下为实际开发中遇到的问题，按时间顺序排列，供后续排查参考。

### 9.1 注入器枚举模块数量极少（仅7个）

| 项目 | 内容 |
|------|------|
| **现象** | `EnumProcessModulesEx` 只返回 7 个模块，找不到 kernel32.dll |
| **根因** | 64位系统查看32位进程时，`LIST_MODULES_64BIT (0x02)` 无法枚举32位模块 |
| **解决** | 改用 `LIST_MODULES_32BIT (0x01)`，正确枚举32位进程模块 |
| **代码** | `inject.cs` 中 `private const int LIST_MODULES_32BIT = 0x02;` → 改为 `0x01` |

### 9.2 注入成功后游戏闪退（STATUS_HEAP_CORRUPTION 0xC0000374）

| 项目 | 内容 |
|------|------|
| **现象** | DLL注入后游戏立即崩溃，错误码 `0xC0000374` |
| **根因** | `FileLogger` 为静态全局变量，多翻译单元各自有独立实例，`CRITICAL_SECTION` 无效，并发写日志导致堆损坏 |
| **解决** | 将 `FileLogger` 改为单例模式，确保全局唯一实例和线程同步 |

### 9.3 中文路径导致 DLL 加载失败

| 项目 | 内容 |
|------|------|
| **现象** | DLL路径含中文（如"正式功能"、"盒子"）时，注入器显示成功但游戏无效果/闪退 |
| **根因** | `LoadLibraryA` 不支持 Unicode 路径；注入器用 `Encoding.Default`（ANSI）写入中文路径，目标进程无法正确解析 |
| **解决** | 1. 注入器改用 `LoadLibraryW` + `Encoding.Unicode` 编码路径<br>2. DLL 内部日志改用 `_wfsopen`/`CreateFileW`（宽字符API）<br>3. 用 `GetModuleFileNameW` 动态获取 DLL 路径，不依赖源文件编码 |
| **验证** | 英文路径测试通过，确认中文路径是根因 |

### 9.4 直接运行 inject.exe 无方框透视效果

| 项目 | 内容 |
|------|------|
| **现象** | 直接运行 inject.exe 注入后，游戏中无方框透视 |
| **根因** | `ESPState::m_boxEnabled` 默认 `false`，需要通过管道发送 `{"cmd":"set_feature","feature":"esp_box","enabled":true}` 才能开启 |
| **解决** | 必须通过 `main.py` 点击方框透视按钮，走完整流程：注入 → 连接管道 → 发送开启命令 |
| **注意** | inject.exe 只完成注入，不发送任何管道命令 |

### 9.5 方框透视开启后无法关闭（管道 ERROR_BROKEN_PIPE 232）

| 项目 | 内容 |
|------|------|
| **现象** | 点击开启按钮后方框出现，但再次点击关闭按钮无效，日志显示 `WriteFile failed: 232` |
| **根因** | Python 客户端用 `FILE_FLAG_OVERLAPPED`（异步I/O）打开管道，但 DLL 端用同步模式（`PIPE_WAIT`）创建管道。DLL 用同步 `WriteFile` 写回响应时，Python 的 overlapped `ReadFile` 还没准备好，导致管道断裂（ERROR_BROKEN_PIPE 232）。管道断裂后 DLL 跳出消息循环，客户端再也无法通信 |
| **解决** | Python 客户端去掉 `FILE_FLAG_OVERLAPPED`，改用同步模式：`CreateFileW(..., 0)` + 同步 `ReadFile`/`WriteFile`，与 DLL 端一致 |
| **关键代码** | `universal_hook_manager.py` 的 `_connect_pipe()` 和 `_send()` 方法 |

### 9.6 管道 ERROR_PIPE_BUSY (231) 重复注入

| 项目 | 内容 |
|------|------|
| **现象** | 日志持续输出 `CreateNamedPipe failed: 231`，管道无法创建 |
| **根因** | 上次注入的管道实例未清理，新注入时旧管道仍占用命名管道名称 |
| **解决** | DLL 端管道服务器在创建管道前先尝试以客户端身份连接旧管道并关闭，清理残留实例；`maxInstances` 从 1 改为 2 |

### 10.4 获取玩家坐标

**核心函数**：`TransformHelper::GetPlayerPosition()`

```cpp
Vector3 TransformHelper::GetPlayerPosition(void* player) {
    // 优先1: characterContainer (Player+0x58) → Transform.get_position()
    void* container = *(void**)((char*)player + 0x58);
    Vector3 pos = GetPosition(container);
    if (IsSanePosition(pos)) return pos;

    // 优先2: Component.get_transform() → Transform.get_position()
    void* transform = GetTransform(player);
    pos = GetPosition(transform);
    if (IsSanePosition(pos)) return pos;

    return Vector3();  // 失败
}
```

**函数地址**：RVA `0x3F42B0`（il2cpp_bridge.h）

**调用链**：

```
player (Player*)
  ↓ offset 0x58
characterContainer (Transform*)
  ↓ Transform.get_position()
Vector3 (x, y, z)
```
