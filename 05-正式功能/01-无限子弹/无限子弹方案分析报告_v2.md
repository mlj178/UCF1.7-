  # 先分清三个关键概念
  
  1. **GameAssembly.dll 基址**：`0x6ca30000`
  2. **RVA**：script.json 里的偏移（相对于 dll 开头）
  3. 字段分两种
     - 静态字段（全局管理器、静态变量）
     - 实例字段（玩家、武器 KnifeAttackData 里的 damage/range）
  

  

  

  

  ## 三、各方案详细分析

  ### 1. AAAAA_plan4_replace_consume.js (成功案例)

  #### 工作原理

  使用Frida的`Interceptor.replace`完全替换`ConsumeAmmo`函数，直接返回`true`，不修改.text段，零侵入性。
  
  #### 关键代码逻辑
  
  ```javascript
  Interceptor.replace(ADDR_CONSUME_AMMO, new NativeCallback(
      function (thisPtr, methodInfo) {
          return 1; // 直接返回true，不消耗子弹
      },
      "bool", ["pointer", "pointer"]
  ));
  ```
  
  #### 优势分析
  
  - **无状态设计**：不缓存任何指针，无需清理
  - **零性能开销**：纯Frida层拦截，不涉及内存读写
  - **生命周期完美**：房间切换时自动保持有效
  - **安全性高**：不修改游戏代码段，避免反外挂检测

  ------

  ### 2. infinite_ammo_all_weapons.js (失败案例)
  
  #### 问题诊断

  - **严重内存泄漏**：没有房间切换清理机制，指针缓存持续增长
  - **生命周期管理缺失**：`playerWeapons`数组无限累积，最终导致闪退
  - **性能问题**：每50ms遍历所有武器，没有快速路径优化
  
  #### 核心问题代码
  
  ```javascript
  var playerWeapons = []; // 全局数组，永远不会清理
  var targetValues = {};  // 全局对象，永远不会清理
  
  // 没有房间切换清理逻辑
  setInterval(function() {
      for (var i = 0; i < playerWeapons.length; i++) {
          lockWeapon(playerWeapons[i], i); // 持续操作可能已释放的指针
      }
  }, 50);
  ```

  #### 闪退原因

  当切换房间时，旧武器指针被释放，但脚本仍尝试访问这些无效指针，最终导致访问违规异常。

  #### 改进建议

  必须添加房间切换清理逻辑，参考V6版本的`clearAll()`实现。

  ------

  ### 3. infinite_ammo_god.js (功能受限)
  
  #### 问题诊断

  - **单武器限制**：`playerGun`变量只能存储第一把武器
  - **身份判断缺陷**：没有验证是否为玩家武器，可能锁定BOT武器
  - **初始化依赖**：必须开火一次才能识别武器
  
  #### 核心问题代码
  
  ```javascript
  var playerGun = null; // 只能存储一把武器
  
  Interceptor.attach(addr, {
      onEnter: function(args) {
          if (playerGun === null) { // 只记录第一把枪
              playerGun = thisPtr;
              // 设置目标值为当前值
          }
      }
  });
  ```
  
  #### 功能限制

  - 副武器无法生效：脚本只hook了部分开火函数
  - 身份判断缺失：没有调用`isMyWeapon`验证
  - 首次开火依赖：必须先开火才能激活无限子弹
  
  #### 改进建议

  - 使用数组存储多把武器
  - 添加`isMyWeapon`验证
  - 预加载武器指针，不依赖首次开火

  ------

  ### 4. plan1_memory_lock.js (内存锁定方案)

  #### 工作原理

  锁定`ObscuredInt.hiddenValue`加密值，而不是裸数值，避免反作弊检测。
  
  #### 关键优化

  - **加密值锁定**：读取并写回原始加密值，不修改为9999
  - **房间清理**：切换房间时清空所有缓存指针
  - **黑白名单**：缓存玩家武器和BOT武器，避免重复验证
  
  #### 核心代码
  
  ```javascript
  // 读取加密值
  var cv = adPtr.add(0x0C).readInt();   // clip.hiddenValue
  var av = adPtr.add(0x20).readInt();   // ammo.hiddenValue
  
  // 写回加密值（不是9999）
  adPtr.add(0x0C).writeInt(d.cv);
  adPtr.add(0x20).writeInt(d.av);
  ```
  
  #### 优势

  - 兼容性好：适用于所有ObscuredInt加密字段
  - 反检测强：不修改为明显异常值
  - 稳定性高：有完善的清理机制
  
  #### 局限
  
  - 2秒定时器可能导致短暂弹药减少
  - 需要首次开火才能识别武器

  ------

  ### 5. plan2_nop_consume.js (代码段修改)

  #### 代码段地址来源分析
  
  根据脚本内容分析，地址`0xB61140`等硬编码偏移量**并非来自JSON或CS文件**，而是通过以下方式获得：

  1. **IDA Pro反汇编**：对`GameAssembly.dll`进行静态分析，定位`WPN_Gun::ConsumeAmmo`函数
  2. **Il2CppDumper工具**：从游戏的`global-metadata.dat`中提取函数签名和偏移
  3. **动态调试验证**：通过Frida或x64dbg在运行时验证函数地址的正确性

  这些地址是**IL2CPP编译后的Native函数偏移**，通常通过逆向工程工具链获得，而非配置文件。

  #### 工作原理

  直接修改`.text`代码段，将`ConsumeAmmo`函数入口patch为`mov eax, 1; ret`指令。
  
  #### 关键代码逻辑
  
  ```javascript
  // Patch: mov eax, 1; ret
  var patchBytes = [0xB8, 0x01, 0x00, 0x00, 0x00, 0xC3];
  
  Memory.protect(ADDR_CONSUME_AMMO, 6, 'rwx');
  ADDR_CONSUME_AMMO.writeByteArray(patchBytes); // 直接修改代码段
  ```
  
  #### 与Plan4的区别
  
  - **Plan2**：直接修改游戏代码段，效果持久化（关闭Frida后仍有效）
  - **Plan4**：Frida层拦截，关闭脚本即失效
  
  #### 风险警告

  - **反外挂检测**：修改代码段可能触发CRC校验或内存保护
  - **兼容性问题**：游戏更新后地址变化会导致崩溃
  - **调试困难**：需要处理内存保护和字节恢复

  ### 6. infinite_ammo_v6.js (优化版本)

  #### 缓存与快速路径详解
  
  **缓存机制设计**：
  
  ```javascript
  var wpnData = {};      // 白名单：已知玩家武器 {指针字符串 → {ptr, cv, av}}
  var notMine = {};      // 黑名单：已知非玩家武器 {指针字符串 → true}
  ```
  
  **快速路径实现**：
  
  ```javascript
  // 开火Hook中的极速路径
  onEnter: function (args) {
      var wpn = args[0];
      if (wpn === null || wpn.isNull()) return;
      var k = wpn.toString();       // 纯JS字符串操作，极快
      
      // 快速路径1：已知玩家武器 → 直接返回（定时器会处理）
      if (wpnData[k]) return;
      
      // 快速路径2：已知非玩家武器 → 直接跳过
      if (notMine[k]) return;
      
      // 慢速路径：只有全新指针才执行完整验证
      // （调用readable()和isMyWeapon()等系统调用）
  }
  ```
  
  **性能优化要点**：
  
  1. **纯JS操作优先**：`toString()`和Map查找都是纯JavaScript操作，速度极快
  2. **系统调用最小化**：只有未缓存的全新指针才调用`Process.findRangeByAddress`等昂贵操作
  3. **定时器零验证**：定时器只执行写入操作，不做任何地址有效性验证
  4. **黑名单机制**：BOT武器只需验证一次，后续直接跳过
  
  **架构优势**：
  
  - **无数量限制**：移除了V5的`MAX_WPN=4`限制
  - **极致性能**：99%的开火事件走快速路径，几乎零开销
  - **智能清理**：房间切换时自动清空所有缓存
  - **错误容忍**：写入失败时自动清理无效指针
  
  #### 完整生命周期管理
  
  ```javascript
  function clearAll() {
      var total = Object.keys(wpnData).length + Object.keys(notMine).length;
      wpnData = {};
      notMine = {};
      console.log("[ROOM] Cleared " + total + " cached refs");
  }
  ```

  ## 四、综合经验总结
  
  ### 最佳实践方案

  1. **首选Plan4**：`Interceptor.replace`方案，无状态、零开销、最稳定
  2. **次选V6**：内存锁定方案，功能全面，性能优化到位
  3. **避免Plan2**：代码段修改风险高，效果持久化难以控制
  
  ### 关键技术要点
  
  - **生命周期管理**：必须处理房间切换清理
  - **身份验证**：始终使用`isMyWeapon`过滤非玩家武器
  - **加密值处理**：ObscuredInt字段必须锁定原始加密值
  - **性能优化**：使用缓存和快速路径，避免频繁系统调用
  - **错误处理**：静默失败，避免异常导致脚本崩溃
  
  ### 穿越火线特定适配
  
  - **多武器支持**：主武器1/2、副武器1/2都需要覆盖
  - **切换房间**：CF房间切换频繁，清理机制至关重要
  - **反作弊规避**：避免明显异常值（如9999），使用原始加密值
  - **动画兼容**：Plan4方案会禁用换弹动画，需要权衡
  - **纳米模式支持**：需要同时处理`clip_nano`和`ammo_nano`字段
  
  ### 问题预防清单
  
  -  房间切换清理机制
  -  指针有效性验证
  -  玩家身份验证
  -  加密字段正确处理
  -  性能优化（缓存、快速路径）
  -  错误处理和静默失败
  -  反外挂规避策略（Plan2需特别注意）
  -  多武器类型支持（主/副/特殊）
  -  纳米模式弹药处理
