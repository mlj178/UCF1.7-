### 2.2 类型筛选：如何只取 `Skill_Common`？

数组中可能包含多种技能类型（`Skill_Common`, `Skill_ModeChange`, `Skill_SentryGun` 等）。需要筛选。

#### 方案 A：通过虚表比对（最可靠）
- 原理：每个 C# 对象的前 8 字节指向其类的虚表（vtable），同一类的实例虚表相同。
- 步骤：
  1. 通过 il2cpp-bridge 获取 `Skill_Common` 类的虚表地址（或硬编码 RVA）。
  2. 遍历技能数组时，读取每个对象的前 8 字节，若与目标虚表相等，则确定为 `Skill_Common`。
- 优点：100% 准确，不受字段偏移变化影响。
- 缺点：需要 il2cpp-bridge 支持（或手动寻找虚表 RVA）。

#### 方案 B：通过特征字段值猜测（快速但粗糙）
- 原理：`Skill_Common` 特有字段 `coldFinishTime` 通常为一个浮点数（0 或很大的未来时间）。
- 实现：读取每个对象 `+0x28`（猜测偏移）处的浮点值，若在合理范围（0~999999）内，则认为是 `Skill_Common`。
- 缺点：偏移不固定，且可能与其他类型的浮点字段混淆。

#### 最终选择：优先采用虚表比对，若无 bridge 则退化为特征值 + 运行时偏移校准。

# 方案对比：写内存 vs Hook 方法

| 维度             | 写内存 (`coldTime=0`)                                        | Hook 方法 (`replace`)                                        |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **地址依赖**     | ❌ **强依赖**实例地址变了（每回合/NoCd后）即失效，需重新计算。 | ✅ **无依赖**直接拦截函数入口，无视实例地址变化。             |
| **需周期性重扫** | ✅ **是**每回合或状态重置后，必须重新扫描并写入新地址。       | ❌ **否**只需在初始化时 Hook 一次，永久生效。                 |
| **代码复杂度**   | 🔵 **低**逻辑简单：`Memory.writeU32(addr, value)` (1行)。     | 🟠 **中**需编写 `Interceptor.attach` + 回调逻辑 + 参数处理。  |
| **稳定性**       | 🟡 **中**极易受游戏机制（如重生、换人）影响导致“断连”。       | 🟢 **高**只要函数名不变，不受运行时地址变动影响。             |
| **影响范围**     | ⚪ **单点**仅修改当前找到的那个实例对象数据。                 | 🔴 **全局**拦截所有调用该函数的行为，所有 `Skill_Common` 共享效果。 |

## 最终方案 `get_skill_common.js` 核心逻辑总结

### 一、目标
实现英雄技能无冷却（CD），采用 **主动调用游戏内部函数 `EndCold`** 的方式，而非直接修改 `coldFinishTime` 字段。

---

### 二、关键技术点

#### 1. 定位本地玩家实例（Player）
- **Hook 三个关键函数**，确保尽早捕获本地玩家指针：
  - `Player.get_isMyPlayer`（RVA `0xB55FD0`）—— 最可靠，通过 `Interceptor.replace` 在返回 `true` 时记录参数。
  - `Player.Update`（RVA `0xB551D0`）—— 附加检测，通过 `ClientData.isBot` 排除 Bot。
  - `ClientData.get_nickName`（RVA `0xB50810`）—— 作为补充，参数 `this` 即为 `ClientData`，再反推 `Player`。
- **防重复**：捕获到后存入 `myPlayerPtr`，后续不再覆盖。

#### 2. 定位技能数组与 `Skill_Common` 实例
- 路径：`Player + 0xB0` → `PlayerSkills` → `+0x08` → `Skill[]` 数组对象。
- 读取数组长度（`+0x0C`），遍历元素（`+0x10` 起，每元素 4 字节？这里代码有误，应为 8 字节但用了 4，可能是 32 位环境？不过不影响逻辑总结）。
- **类型识别**：通过读取 `+0x1C` 和 `+0x24` 两个浮点字段（推测为 `coldFinishTime` 和 `coldTime`），任一非空即视为 `Skill_Common`（简单特征值法）。

#### 3. 实现无 CD 的核心方法
- **放弃修改字段**，改为 **直接调用技能对象的 `EndCold()` 方法**（RVA `0xAE1BC0`，函数签名 `void EndCold(void*)`）。
- 定义 `_endColdFn = new NativeFunction(_base.add(0xAE1BC0), 'void', ['pointer'])`。
- 定时器每 200ms 执行 `scanAndEndCold()`：
  - 重新获取玩家 → PlayerSkills → 数组。
  - 遍历所有技能实例，对识别出的 `Skill_Common` 调用 `_endColdFn(sp)`。
- 优点：不依赖字段偏移，直接让游戏内部完成冷却清除，更稳定。

---

```
初始化
├── 定位 GameAssembly.dll
├── 创建 EndCold 函数指针
├── Hook 三个 Player/ClientData 函数 → 捕获 myPlayerPtr → 调用 scanSkillSteps（打印诊断）
└── 注册全局命令 & rpc

scanAndEndCold()
├── 检查 myPlayerPtr
├── Player +0xB0 → PlayerSkills
├── PlayerSkills +0x08 → Skill[]
├── 遍历元素，读取 +0x1C/+0x24 浮点值判断是否为 Skill_Common
└── 对每个匹配对象调用 _endColdFn(sp)

```

### 四、最终效果
- 玩家进入游戏后自动识别本地玩家。
- 开启无 CD 后，每 200ms 遍历当前技能列表，对所有 `Skill_Common` 实例调用 `EndCold()`。
- 技能冷却被强制清零，实现无 CD 效果，且无需维护字段偏移，适应性更强。
