## 一、结论（先给答案）

1. **异常性质**：`0x80000003`（STATUS_BREAKPOINT，执行到 `int 3`），
   地址 `GameAssembly.dll+0x1401A6`，主线程。**不是**访问违例、**不是**普通空指针，而是**托管异常抛出流程"没有抛出去"**。
2. **崩溃现场**：`+0x1401A6` 正好是 `sub_10140190`（"抛 System.NullReferenceException"的 noreturn 助手）
   里 `call sub_1013FF10`（`il2cpp::vm::Exception::Raise`）**之后的那条 `int 3`（0xCC）填充指令**：

   ```
   .text:10140190   push ebp
                    mov  ebp, esp
                    push 0
                    push [ebp+8]        ; 当前方法指针
                    call sub_10134610   ; 构造 System.NullReferenceException
                    add  esp, 4
                    push eax
                    call sub_1013FF10   ; Exception::Raise -> __CxxThrowException@8
   .text:101401A6   db 0CCh             ; <-- 崩溃点（编译器在 noreturn 调用后填的陷阱）
   ```

   正常情况这条指令**永远不可达**；它被执行 = **`Exception::Raise` 居然返回了**（C++ 异常没有 unwind，控制流落回调用点）。
3. **调用链**（转储 EBP 链 + IDA 交叉验证）：

   ```
   UnityPlayer.dll+0x6fbf77                       （引擎主循环调用托管方法）
     └─ il2cpp_runtime_invoke            @0x10108980，返回点 0x101089A6
          └─ sub_1013AC70               （Runtime::Invoke 内核，自带 SEH catch）
               └─ invoker_method = sub_10140190   （"抛 NullReferenceException"桩）
                    └─ Exception::Raise  @0x1013FF10   ← 应 noreturn，实际返回
                         └─ int 3 @+0x1401A6          ← 崩溃
   ```

   - 被调用方法上下文 `methodPointer = GameAssembly+0xB551D0 (Player$$Update)`；
   - 栈上还有玩家对象 `0x4354ab80` —— 正是崩溃前 43ms 那次死亡广播的 victim（见日志 `[deathDiag:deathIn] victim=0x4354ab80`）。
4. **触发关联**：本会话第一次跑**今天新加的「托管异常漏斗探针」**——「开火直伤」的 death_diag
   （默认 `death_diag:true`）用 `Interceptor.attach` 直接在 `Exception::Raise`（+0x13FF10）上打了 Frida 内联钩子。
   日志里这条探针在崩溃前 0.04 秒报出了**同一个异常**，backtrace 首帧就是崩溃地址：

   ```
   [2026-10-14 18:26:12.720] [ERROR] [game_modifier.direct_damage]
     [deathDiag:raise] ? inBroadcast=no bt=+1401a6,+1401c8,+b503ff,+7f9903,...
   [2026-10-14 18:26:19.299] [INFO]  [probe:beat] deathDiag: ... raises=1
   ```

   → **异常在"漏斗"处被改写后的执行路径吞掉（Raise 返回），进程撞上 int 3 立即结束。**
5. **定性**：这是**注入代码（修改器）造成的异常派发被破坏**，不是游戏自己"算错数"。
   首选嫌疑 = 「开火直伤」death_diag 的 `Exception::Raise` 钩子；
   次要嫌疑 = 方框透视 `Universal-ImGui-Hook.dll`（MinHook + 自认"用 SEH 吞访问违例"，
   10-11 那次同类闪退已定位到"双引擎重复挂钩 + 内存损坏"）。

## 七、第二现场（2026-10-14 三轮实测）：终结者被 Bot 打死 -> 死亡广播断掉 的**真正根因**与修复

### 7.1 现象与数据（测试会话 `7da632fc`，20:16:57–20:20:51，94 次死亡）

用户实测反馈："终结者被打死能复活了，但死了要等好几秒。" 把日志按 **死者角色 × 凶手** 切开：

| 组合 | 死亡次数 | 死亡广播被打断（进了没出） |
|---|---|---|
| 终结者（NanoRole 8-17）**被 Bot 打死** | 9 | **8** |
| 终结者**被玩家（开火直伤）打死** | 7 | **0** |
| 非终结者被 Bot 打死 | 33 | 0 |
| 非终结者被玩家打死 | 38 | 1 |

同一个终结者可以自对照：`0x49b0bcf0`（普通终结者 role 8）、`0x49b23b80`、`0x43909a10`（高阶终结者 role 9）
**玩家用直伤打死 -> 广播完整返回、游戏自己 0~1ms 就排好复活；Bot 打死 -> 广播从中间断掉**。

时间对齐（9 对 9，全部命中）：

```
20:17:25.386 [deathDiag:deathIn]  killer=0x49b46cf0 dead=0x351715c0   <- 广播进入
20:17:25.386 [fail:WPN_Gun.Damage replacement] ... system error (x1)  <- 同一毫秒被 Frida 捕获
20:17:26.316 [deathDiag:abort] 上一次死亡广播进入后没有返回            <- 没有 deathOut / 没有 RespawnPlayer
```

### 7.2 根因：`WPN_Gun.Damage` 的 `Interceptor.replace` + `NativeFunction` 回call

1. Bot 打死终结者时，游戏自己的"伤害 -> `GameManager.TakeDamage` -> `DeathEventBroadcast`"链内部
   会抛一个**托管异常**（il2cpp 用 C++ EH，码 `0xE06D7363`）。游戏本来就常在抛这种异常、
   也一直由游戏自己的异常帧消化（19:21 会话 `raises=14`，无任何后果）。
2. 但 `WPN_Gun.Damage` 被 `Interceptor.replace`，原函数又是从 JS 用 `NativeFunction` 回call 的 ——
   **异常一旦跨回 JS 边界就被 Frida 抢先捕获**（JS 只看到 `system error`），游戏自己的异常帧再也收不到，
   广播从抛出点直接断掉：`RespawnPlayer` 一次都没被调用 -> 终结者原地躺尸 ->
   只能等 `death_fix_respawn` 兜底（6s + 1s），这就是"要等好几秒"的来源。
3. 与 `26_grenade_mode` v2.13 注释里那条根因**完全同源**：
   "原函数内部一旦抛出托管异常，Frida 的异常处理器会先抓到它……游戏自己的异常处理帧就再也收不到了。"
   所以这不是游戏 bug，是**我们的挂法**。

### 7.3 修复：`WPN_Gun.Damage` 改 attach（只挂 onEnter）+ 模拟 ret 跳过原函数

* **别人的开火（Bot）**：`isLocalWeapon` 为假 -> `return`；原函数完全原生执行，
  Frida 不在调用链上留帧 -> 托管异常照常交给游戏自己处理（根因消除）。
* **我自己的开火**：JS 里自己结算直伤，然后"模拟 ret"跳过原函数
  （x86 mscdecl 参数由调用方清栈：取 `[esp]` 的返回地址 -> `esp += 4` + `pc = 返回地址`）。
* 安全阀：跳过前校验"当前 `[esp]` 里的返回地址必须指向可执行页"，校验不过就不跳过
  （原函数照跑，最多这一发多打一遍，绝不乱跳栈），失败计数 `gun_skip_failed`；
  另外若 `[esp]` 已被 Frida 换成返回 thunk（同一地址上还有别的 `attach(onLeave)` 监听者时会发生），
  照跳 —— 这样别人的 `onLeave` 链也照常会跑。
* 配置 `gun_hook_mode`：`attach`（默认）/ `replace`（旧行为保留，启用时打 warn）。
