## 一、结论（先给答案）

1. **崩溃性质**：`0xC0000005`，异常信息 `ExceptionInformation[0] = 8` = **执行违规**（CPU 跳到了一个不可执行地址），
   **不是** JS 抛异常、**不是** Frida 调用失败。
2. **崩溃现场**：游戏在主线程、**多人生化（终结者）模式**、**补给箱拾取**流程里做虚函数调用
   `ModeBase_Nano.OnPlayerPickUpSupplyBox`，读到一个**被写坏的方法指针**，于是 `call` 到了堆上的
   **模式实例对象**（0x48A7DF00）本身 → 执行违规。
3. **本质**：**内存损坏**（`Mode_Nano4_Terminator` 类的虚表槽/方法指针被写成了"游戏自己 GC 运行时的代码地址"），
   不是任何单个功能的"逻辑算错"。
4. **能往游戏内存里写"代码地址"的只有两类东西**：**Frida Hook（修改器）** 与 **MinHook（方框透视 DLL）**。
   本次会话里，这两者**同时**给同一批函数打补丁（见第四节），这是当前代码树里能查证的、唯一的代码指针写入源。

**链式还原**：

```
物理触发（游戏自己的代码，主线程）
  SupplyBox$$OnTriggerStay (0xB217E0)
    └─ 虚调用实例 = ModeBase_Nano$$get_instance2() ≠ 0
       push [klass+0x248] / eax = [klass+0x244] / call eax     ← klass = Mode_Nano4_Terminator
         └─ 实际跳到了 GC 运行时函数 GameAssembly+0x155170（= 0x6C0C5170）
              mov edi,[ebp+8] (= 被 call 时传进来的 this = 0x48A7DF00 = 模式实例)
              call edi                                             ← 执行违规 0xC0000005/8
```

即：**`Mode_Nano4_Terminator` 类的方法指针（`klass+0x244`）被写成了游戏 GC 的代码地址。**

## 四、代码层能查证的具体缺陷（按嫌疑排序）

### 1) 两种 Hook 引擎重复挂钩同一批"回合开始"函数（唯一能产生"代码指针写入"的地方）

| 目标函数 | Frida（修改器） | MinHook（方框透视 DLL） |
|---|---|---|
| `ModeBase$$OnStartNewGameRound` (GA+0xAF5B30) | `11_aim/script.js:1671`（**自瞄，开**） | `esp/game_manager.cpp:776` |
| `ModeBase_Nano$$OnStartNewGameRound` (GA+0xAF15D0) | `19_battle_round/script.js:455 / 288`（**脚本加载即挂钩，与开关无关**） | `esp/game_manager.cpp:792` |
| `GameManager$$OnDestroy` (GA+0xAFB6F0) | （未开的功能 03 才挂，且它写的是 0xAEBD40 = 实际是 `MapManager$$OnDestroy`，见下） | `esp/game_manager.cpp:813` |
| `Bot$$Update` (GA+0xB33370) | （未开） | `esp/game_manager.cpp:684` |

- 同一段 5 字节函数头被两个引擎先后改写/搬运（Frida 内联 trampoline + MinHook trampoline），属于未定义行为；
- **时间线吻合**：日志 20:37:13 正好是 `ModeBase_Nano$$OnStartNewGameRound` 被调用（BattleRound HOOK#1），
  且同一时刻出现 **12 秒卡顿**（PERF2 峰 11974ms）；37 秒后（20:37:50）在**同一模式**的补给箱虚调用上崩溃。
- 另外 `03_time` 把 `GameManager.OnDestroy` 写成 0xAEBD40，IDA 查证该地址是 `MapManager$$OnDestroy`
  —— 说明包内 RVA 有"对不上"的先例，需要系统核对。

### 2) 方框透视 DLL（18）本身的侵入面（此前几轮 P0 从未审计）

- 注入后 **MinHook** 内联挂钩游戏函数（写代码指针）；**自建线程** tid=24740 在非主线程调用
  `Component.get_transform` / `Transform.get_position` / `Animator.GetBoneTransform` /
  `Collider.get_bounds` / `WorldToScreenPoint_Injected` 等 Unity/IL2CPP API；
- DLL 自己承认会踩访问违例并靠 SEH 吞掉：
  `[ESP] DrawPlayerESP access violation for player 0x%p`、
  `[GameManager] get_isDead SEH exception for player 0x%p`、
  `Object recycled, klass invalid for 0x%p`；
- 在 IL2CPP 里从非主线程并发访问这些对象、并"故意触发+捕获"访问违例，是典型的**偶发**内存损坏来源。

### 3) 多人生化Buff选择（15，自动加载）——与崩溃路径最相关，但本次没有实际改写

- `15_nano4t/script.js:235` 挂 `Nano4T_AttributeAsset$$GetAttribute`(0xB4C420)，
  `onLeave: retval.replace(NANO4T_ATTR_PTR[id])` —— **正好是"终结者模式被选中的特性/护盾 Buff"路径**；
- 但日志里**没有**"已设置目标特性 g=/h="（`setWantedTraits` 每次都会打），
  即 `NANO4T_ACTIVE=false`，本次它只装了钩子、没有替换返回值。→ 本次不是它直接写坏的，但它是**同一条链路上唯一改写指针**的功能，必须一起复测。

### 4) 自瞄（11）写内存的面

- 每帧 `Player+0x4C/+0x50`（cameraRotation）、`Recoil+0x10/0x24/0x40/0x54` 清零、射击射线 +0x0C..+0x14，
  都是按 dump.cs 校验过的**边界内**写入，未发现越界；但它确实是"开着的会写游戏内存"的功能之一，
  且和 DLL 在 0xAF5B30 上重复挂钩。

## 五、建议的定位实验（一次只改一个变量）

1. **先关"方框透视"，其它保持**（或干脆不注入 `Universal-ImGui-Hook.dll`）→ 多人生化（终结者）房间 → 捡补给箱。
   若不再闪退，主因就在 DLL（MinHook + 非主线程 Unity 调用）。
2. 仍闪退：把 **19** 的"脚本加载即挂钩"改成"只有启用时才挂钩"，再试。
3. 仍闪退：关 **15**（不自动 init）再试；再关 **11**。
4. 复现时请保留：`logs/game_modifier.log`、`%LOCALAPPDATA%\CrashDumps\UnityCrossFire.exe.*.dmp`、
   WER 报告（本次已用 `06-测试/_crash20_37/*.py` 解析，可直接复用）。
