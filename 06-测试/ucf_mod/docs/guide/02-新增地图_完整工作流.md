# 新增地图 · 完整工作流（已实战验证）

> **类型：做**（照着敲就能复现的操作流程，不是查资料）
> **给谁看**：想给 UCF 1.7 加一张新地图的人。零基础能跟做，但需要装一次 Unity。
> **已验证案例**：`ForbiddenTD_Classic.GLB`（魔兽争霸3 紫禁城塔防图，562 个网格 / 52 张贴图）→ 团队模式第 3 项「测试地图」，**能进、能站、能走、HUD 正常**。
> **不回答什么**：路径点/寻路怎么改（见 [09-人机与路线设计.md](09-人机与路线设计.md)）；每张原版图的点位数据（见 [原始地图标准数据](原始地图标准数据/)）。
> **维护约定**：本文只写"怎么做"。具体地址/偏移查 `record/`。改动流程时同步更新"坑位清单"。

---

## 0. 这件事的目的

一句话：**把任意一个现成的 3D 模型（GLB / FBX / 从别的游戏扒的图），变成 UCF 里能选中、能进、能站住的一张新地图，并且不覆盖、不修改任何原版地图。**

要求：

| 编号 | 要求 | 现状 |
| --- | --- | --- |
| 1 | 不改原版 12 张地图的任何字节 | ✅ 新地图占第 13 个槽位 |
| 2 | 下拉框能选到，名字可控 | ✅ 注册表改两个字符串即可 |
| 3 | 进去能站住、能走、有碰撞 | ✅ 见第 9 步（出生点高度是命门） |
| 4 | 流程可复制，能批量做 | ✅ 第 10 节有检查表 |

---

## 1. 先给结论

**能加。已经跑通了。**

加一张新地图，本质只干四件事：

```
① 场景名册加一条      → 引擎允许加载这个索引
② 地图注册表加一项    → 下拉框能显示、能选中
③ 造一个 levelN       → 真正的地图内容
④ 造一个 sharedassetsN → 配套的网格/材质/贴图
```

① ② 是改两个现成文件的几十个字节；③ ④ 是整套流程里唯一的体力活。

**新手第一次做，按本文走大约 1 天**（其中一半时间花在装 Unity 和第一次构建）。
**熟练后一张 1~2 小时**，因为第 3、4 步的脚本可以复用，只改模型路径。

## 2. 为什么以前一直说"加不了"

这段必须留着 —— 因为当时的三条判断**全错**，错的原因比结论更有教学价值。

### 2.1 当时的判断 vs 实测结果

| 当时的判断 | 实测结果 | 错在哪 |
| --- | --- | --- |
| "名单写死，改不动" | ❌ 错。名册是**数据**不是代码常量，直接改字节即可 | 把"编辑器里没暴露"当成了"不可写" |
| "没有 type tree 所以改不了文件" | ❌ 错。知道布局就能直接怼原始字节 | 把"高层 API 解析不了"当成了"文件动不了" |
| "必须有注册文件/登记表" | ❌ 错。文件名是**算出来的**：`snprintf("level%d")`、`snprintf("sharedassets%d.assets")` | 没读二进制，凭直觉假设 |
| "外部挂载不行" | ✅ 对。运行时挂数据确实不行 | — |

**证据**：`ResourceManager`（1,529,056 字节）里搜不到任何 `levelN` / `sharedassets` 字符串 —— 文件系统里根本没有登记表。

### 2.2 真正卡住的是什么

当时说"加不了"，其实是被两堵**真墙**挡住了，只是我把墙的位置说错了：

| 真墙 | 表现 | 怎么绕过去的 |
| --- | --- | --- |
| **墙 1：没有同版本 Unity** | 只能手搓二进制，风险极高 | 装 **Unity 2020.3.30f1c1 (b9cd9c36f8f8)**，和游戏**完全一致**；命令行调用 |
| **墙 2：新场景缺游戏的管理器** | 场景能渲染，但游戏逻辑不启动、没有 HUD、没有出生点 | **不新建场景**，借原版地图的场景当骨架，只替换几何 |

第二堵墙是最关键的认知转变：

> 每张原版地图的 `levelN` 里，除了几何，还塞着 18 个管理对象 ——
> `A*`、`GameManager`、`MapManager`、`CameraManager`、`SoundManager`、`EffectManager`、`AssetManager`、`Main Camera`、`CM FreeLook`、`TopRig/MiddleRig/BottomRig`、`OneSide`、`TwoSide`、`Directional Light`、`MapShadow`、`cm`、`Light`、出生点容器……
>
> 这些 MonoBehaviour 的脚本编译在 `GameAssembly.dll`（IL2CPP）里，**外部 Unity 工程无法引用、也无法重建**。
>
> 所以正确做法不是"造一个完整场景"，而是**接管一个现成场景的渲染位**。

## 3. 前置环境（版本必须对齐，错一个都不行）

| 软件 | 要求版本 | 为什么 | 下载 |
| --- | --- | --- | --- |
| **Unity 编辑器** | **2020.3.30f1c1 (b9cd9c36f8f8)** | 必须和游戏**完全一致**。版本不同 → SerializedFile 格式/类型布局不同 → 引擎直接拒绝 | Unity Hub 里装 "2020.3.30f1c1" |
| **Unity Hub** | 任意较新版（3.x） | 用来登录、领许可证、装编辑器 | 官网 |
| **Blender** | 3.x / 4.x / 5.x 都行（实测 5.3） | 只做 GLB → FBX 和贴图导出，版本不敏感 | 官网 |
| **Python** | 3.10+ | 跑 `UnityPy` 读写 .assets | — |
| **UnityPy** | 1.25.x（实测 1.25.4） | 读写 SerializedFile / 解析对象 | `pip install UnityPy` |

### 3.1 三条硬约束

1. **Unity 版本必须等于游戏版本**。查游戏版本：游戏目录 `UnityPlayer.dll` 文件属性，或 `Player.log` 第一行。
2. **游戏是 32 位（x86）**。构建目标选 `StandaloneWindows`（不是 64 位）。BepInEx / MelonLoader 之类也必须用 x86 版。
3. **Unity 必须已激活许可证**，且编辑器能正常打开一次工程。

### 3.2 ⚠️ Unity 命令行最大的坑：不能用 `-batchmode`

```
❌ Unity.exe -batchmode -quit -executeMethod Xxx.Build      → 报 "BatchMode: Unity has not been activated with a valid License"
✅ Unity.exe -quit -executeMethod Xxx.Build                 → 正常
```

原因：Unity 中国版 2020.3 + Hub 3.x 的许可证客户端签名校验不兼容，`-batchmode` 走不通。
**去掉 `-batchmode` 照样能全自动**，只是会闪一个编辑器窗口（几十秒后自己关，别去点它）。

许可证状态自检：`%LOCALAPPDATA%\Unity\licenses\UnityEntitlementLicense.xml` 存在且 `IssueDate` 是最近的就对了。

## 4. 先懂三层结构（不懂必翻车）

引擎加载一张图要过三道门，**三层互相独立**，任何一层没打通都会失败，但失败现象完全不同：

| 层 | 文件 | 作用 | 没打通的症状 |
| --- | --- | --- | --- |
| ① 场景名册 | `globalgamemanagers` | 引擎**允不允许**加载这个索引；名字 → 索引 | 日志报 `couldn't be loaded because it has not been added to the build settings` |
| ② 地图注册表 | `sharedassets0.assets` | 下拉框**显示什么**；模式 → 地图列表 | 下拉框里看不到新图 |
| ③ 场景内容 | `levelN` + `sharedassetsN.assets`（+ `.resS`） | 实际的几何/碰撞/管理器 | 进去黑屏、掉出地图、无 HUD |

### 4.1 关键机制：文件名是算出来的

```
UnityPlayer.dll  0x10C07427   snprintf(buf, "level%d", index)
UnityPlayer.dll  0x1061D4F8   snprintf(buf, "sharedassets%d.assets", index)
```

**所以不需要"注册一个文件"，只需要"占住一个索引"。** 拿到索引 12，引擎自己就会去找 `level12`。

### 4.2 名册格式（BuildSettings.scenes）

```
int32  场景数量
[重复 N 次]
    int32  路径长度
    bytes  路径（ASCII，无结尾 \0）
    补零到 4 字节对齐
尾部 176 字节：16B GUID / 版本串 / buildGUID / 两个 int32
```

### 4.3 注册表格式（MonoBehaviour，注意有 `\0`）

每个模式一个 MonoBehaviour：

```
int32 len + 字符 + "\0" + 补零到 4 字节对齐     ← 模式名
...
int32  地图条数
每项：场景名 + 中文名 + ~48 字节固定字段（含预览图 PPtr）
```

### 4.4 原版 12 张图的索引（骨架选择参考）

| 索引 | 场景名 | 中文 | levelN 大小 |
| --- | --- | --- | --- |
| 0 | GameStart | 大厅/主菜单 | 209,276 |
| 1 | TransportShip | 运输船 | 354,420 |
| 2 | Factory | 小型工厂 | 76,876 |
| 3 | Cebu_City | 椰岛之巅 | 60,500 |
| 4 | NY_TM | 胜利广场 | 63,532 |
| 5 | Arena | 竞技场 | 47,772 |
| 6 | GrimReaperKM | 刀锋寨 | 50,364 |

### 4.5 新地图和"骨架地图"是什么关系（**必读**）

> 这一节回答一个新手最容易理解错的问题：我们到底是在"造一张新地图"，还是在"改一张旧地图"？
>
> **答案：都不是。我们是"接管"一个现成场景，只把外观换掉。**

#### ① 不会覆盖原图

| 对象 | 状态 |
| --- | --- |
| 原版 `level11`（死亡擂台） | **一个字节都没动**，还在原版游戏目录里（61,980 字节，md5 不变） |
| 用来当新图的 `level12` | 是 `level11` 的**字节级副本**：对象数 **478 → 478**，一个不多一个不少；文件 61,980 → 61,960 字节 |

所以"借骨架"= **复制一份，然后给这份副本换装**，原图毫发无伤。

#### ② 留了什么 / 换了什么

| 类别 | 内容 | 数量 |
| --- | --- | --- |
| **原样保留**<br>（游戏外壳） | `A*` `GameManager` `MapManager` `CameraManager` `SoundManager` `EffectManager` `AssetManager` `Main Camera` `CM FreeLook` `TopRig` / `MiddleRig` / `BottomRig` `OneSide` `TwoSide` `Directional Light` `MapShadow` `cm` `Light` | 52 个 MonoBehaviour + 相机 + 灯光 |
| | 出生点标记 `SpawnVel_BL` `SpawnVel_GR` | 2 个 |
| | A* 烘焙好的寻路图 | 1 份 |
| | BoxCollider（不可见碰撞盒） | 14 |
| | 粒子系统 / 光照设置 / NavMesh 设置 | 原样 |
| **替换**<br>（外观） | 渲染位的网格 `MeshFilter.m_Mesh` → 我们的网格 | 56 / 69 |
| | 渲染位的材质 `MeshRenderer.m_Materials` → 我们的材质 | 56 / 69 |
| | `MeshCollider.m_Mesh` → 我们的网格 | 52 |
| **修改** | Transform：位置归零 + 旋转单位 + 缩放 1 + **断开父级** | 56 |
| | 没被用到的渲染位：缩放 0 隐藏 + 网格置空 | 13 |
| | `MapManager` 里 16 个出生点的 **y：-1.85 → 3.0** | 16 个浮点数 |
| | `m_Externals[2]`：`sharedassets11.assets` → `sharedassets12.assets` | 1 处字符串 |
| | 悬空 PPtr 置空（天空盒材质 / 反射 Cubemap / 光照探针） | 3 |
| **新造** | `sharedassets12.assets` + `.resS`（56 网格 + 56 材质 + 52 贴图） | 1.96 MB + 2.52 MB |

#### ③ "白送"的能力（不用自己实现）

因为外壳整套留下来了，下面这些行为**直接继承**，一行代码都不用写：

| 能力 | 来源 |
| --- | --- |
| **弹力出场 / 弹进场** | 出生点标记 `SpawnVel_BL`(-1, 0, -75)、`SpawnVel_GR`(-1, 0, 75) —— 名字就是 **Spawn Velocity**，是**只有 Transform 的空物体**，原样复制；真正的弹入规则在 `GameAssembly.dll` 里，没碰 |
| **出生点位置与朝向** | `MapManager.pointDic` 里的 16 组 `SpawnPoint { Vector3 position; float rotation; }`，只改了 y |
| 寻路 / Bot 启动 | 场景里的 `A*` 组件，A* 图原样 |
| 第一人称相机、开镜、后坐力 | `Main Camera` + `CM FreeLook` 相机臂 |
| 观战 / 死亡视角 | `TopRig` / `MiddleRig` / `BottomRig` |
| 音量、特效、资源加载 | `SoundManager` / `EffectManager` / `AssetManager` |

> 本案例实测：紫禁城里玩家**同样是弹进场**的 —— 这就是继承来的，不是我们做的。

#### ④ 一句话类比

**换手机壳**：外观换成紫禁城，但里面的系统、主板、电源键全没动。
所以它开机就亮、能打电话（能进图、能站、能开枪），但也带着原厂的所有特性（寻路图还是死亡擂台的）。

#### ⑤ 代价

继承是有代价的，三条重点：**寻路图仍是原骨架的**、**出生点朝向沿用原图**、**下拉框里会顶掉一张原图**。详见 [§9 已知限制](#9-已知限制)。

## 5. 完整工作流

下面以一个 GLB 模型为例，最终要产出 4 个文件：

```
globalgamemanagers          13 条名册（第 13 条 = 新图）
sharedassets0.assets        注册表第 3 项改为新图
level12                     新图场景（= 死亡擂台骨架 + 我们的几何 + 抬高后的出生点）
sharedassets12.assets(.resS) 我们构建的资源（网格/材质/贴图）
```

---

### 第 1 步 · 准备模型

**要求**：

- 格式：`.glb` / `.gltf` / `.fbx` / `.obj` 都行（Blender 能开就行）
- 有贴图最好；没有也能做，用纯色兜底
- 单位尽量接近"1 单位 = 1 米"

**先量三件事**（后面判断"能不能用"就看这个）：

| 指标 | 怎么量 | 合格线 |
| --- | --- | --- |
| 包围盒尺寸 | Blender 里看 / 脚本算 | 几十~几百单位。太大要缩放，太小要放大 |
| 三角面数 | 同上 | < 50 万。几万面完全没问题 |
| 地面在哪里 | 看包围盒 min Y | 最好 ≈ 0；不是 0 也能改 |

**顺手也量一下"可走面积"**（本案例踩过的坑）：
从空中往下打射线采样，统计地面/屋顶/空洞的比例。本案例的紫禁城 58.7% 是屋顶、16.5% 是空的 —— 对 FPS 来说是"能看不能玩"。知道这一点才好决定要不要补地板。

---

### 第 2 步 · Blender 导出 FBX + 贴图

**为什么要过一道 Blender**：Unity 2020.3 不自带 glTF 导入器，但原生支持 FBX。

**关键点：GLB 里的贴图是内嵌的，Blender 直接导 FBX 会丢掉全部贴图。必须先落盘。**

Blender 无头模式脚本（`-b -P script.py`）：

```python
import bpy, os

GLB = "你的模型.glb"
TEX = "输出目录/textures"
os.makedirs(TEX, exist_ok=True)

bpy.ops.wm.read_factory_settings(use_empty=True)
bpy.ops.import_scene.gltf(filepath=GLB)

# ① 先把内嵌贴图全部存成 PNG
for im in bpy.data.images:
    w, h = im.size
    if w == 0 or h == 0:
        continue
    base = os.path.splitext(im.name)[0]
    safe = "".join(c if (c.isalnum() or c in "-_") else "_" for c in base)
    im.filepath_raw = os.path.join(TEX, safe + ".png")
    im.file_format = "PNG"
    im.save()

# ② 再导 FBX
bpy.ops.object.select_all(action='SELECT')
bpy.ops.export_scene.fbx(
    filepath="输出目录/model.fbx",
    use_selection=False,
    apply_unit_scale=True,
    apply_scale_options='FBX_SCALE_ALL',
    path_mode='COPY',
    embed_textures=False,
    mesh_smooth_type='FACE',
    bake_anim=False,
)
```

**检查点**：贴图文件夹里的 PNG 数量 == 模型里的材质数量（本案例 52 == 52）。

### 第 4 步 · 写构建脚本（核心）

用 `-executeMethod` 调一个静态方法，把"导入 → 合并 → 建场景 → Build"全自动跑完。

**必须做对的 6 件事**：

| # | 设置 | 写错会怎样 |
| --- | --- | --- |
| 1 | `ModelImporter.isReadable = true` | 网格不可读 → **MeshCollider 全部创建失败**，运行时掉出地图 |
| 2 | `ModelImporter.materialImportMode = ImportStandard` | 拿不到材质名 → 贴图配不上 |
| 3 | **按材质合并网格** | 模型碎成几百块，最后只能挂到几十个渲染位上 |
| 4 | 网格 → 贴图 **按名字配对** | 贴图全错位（本案例用 `GRP_xxx` / `M_GRP_xxx` 命名配对） |
| 5 | 地面要做成**实心盒子**，且三角形绕序正确 | 绕序反了 → 从上方看不见 + 单面碰撞体直接穿过去 |
| 6 | 构建目标 `StandaloneWindows`（32 位） | 和游戏位数不一致 |

**为什么必须合并**：骨架场景只有 69 个渲染位，你的模型可能有 562 个网格。按材质分组合并后 55 组，刚好塞得下。

核心代码骨架：

```csharp
// 1) 导入设置
var mi = (ModelImporter)AssetImporter.GetAtPath(fbxPath);
mi.isReadable = true;                          // ← 最重要
mi.materialImportMode = ModelImporterMaterialImportMode.ImportStandard;
mi.importAnimation = false; mi.importCameras = false; mi.importLights = false;
mi.importTangents = ModelImporterTangents.None;
mi.meshCompression = ModelImporterMeshCompression.Off;
mi.SaveAndReimport();

// 2) 按材质分组 + CombineMeshes
foreach (var group in groups) {
    var ci = group.Value.Select(mf => new CombineInstance {
        mesh = mf.sharedMesh,
        transform = mf.transform.localToWorldMatrix
    }).ToArray();
    var merged = new Mesh { indexFormat = IndexFormat.UInt32 };
    merged.CombineMeshes(ci, true, true);
    merged.name = "GRP_" + key;
    AssetDatabase.CreateAsset(merged, "Assets/Merged/GRP_" + key + ".asset");
    // 材质名必须是 "M_GRP_" + key，方便外部脚本按名字配对
}

// 3) 归一化：缩放到目标尺寸、把底面贴到 y=0、XZ 居中
// 4) 新场景里每个网格挂 MeshFilter + MeshRenderer + MeshCollider
// 5) BuildPipeline.BuildPlayer(...BuildTarget.StandaloneWindows...)
```

**材质用什么 shader**：

| shader | 在 UCF 里能用吗 | 结论 |
| --- | --- | --- |
| `Standard` | ❌ **不工作**（本案例实测全黑） | 不要用 |
| `Unlit/Color` | ✅ | 纯色兜底 |
| `Unlit/Texture` | ✅ | **推荐**，贴图原色，不受光照影响 |

### 第 5 步 · 构建

```powershell
$args = '-projectPath "D:\ucf_unity\UcfMap" -buildTarget StandaloneWindows ' +
        '-executeMethod UcfBuild.Build -quit -logFile "D:\ucf_unity\build.log"'
Start-Process -FilePath $unityExe -ArgumentList $args -Wait
```

```
sharedassets0.assets.resS    ← 变成 sharedassets12.assets.resS（有贴图时一定有）
```

### 第 6 步 · 产物改名（两个字节补丁，必做）

> ⚠️ 这是最容易漏的一步。**光改文件名不够，文件内部还写着旧名字。**

#### 补丁 A：`level0` 里的外部依赖名

构建出来的 level 文件里有 `m_Externals` 列表，其中一项指向 `sharedassets0.assets`。
不改的话，引擎会去加载**游戏自己的那个 70 MB 的 sharedassets0.assets**，你的网格全部错乱。

```python
data = bytearray(open("level0", "rb").read())
old, new = b"sharedassets0.assets", b"sharedassets12.assets"
i = data.find(old)
data[i:i+22] = new + b"\x00"      # 20 字符 → 21 字符，两者对齐后都是 24 字节，长度不变
open("level12", "wb").write(data)
```

#### 补丁 B：`sharedassets` 里的 `.resS` 路径（**漏了会看到彩虹噪点**）

**症状**：地图形状完全正确，但表面全是花花绿绿的噪点。

**原因**：贴图数据存在 `.resS` 里，每个贴图对象内嵌一个字符串 `"sharedassets0.assets.resS"`。你只改了文件名没改这个字符串 → 引擎去读游戏原版的 `.resS`，读出来全是垃圾。

**格式**：`int32 长度(25) + 25 字符 + \0 + 补零` → 对齐后 32 字节。
改成 26 字符后 `int32 长度(26) + 26 字符 + \0 + 补零` → **对齐后还是 32 字节**，所以可以原地替换。

```python
import struct
sa = bytearray(open("sharedassets0.assets", "rb").read())
oldp = b"sharedassets0.assets.resS"    # 25 字符
newp = b"sharedassets12.assets.resS"   # 26 字符
i = sa.find(oldp)
while i != -1:
    assert struct.unpack("<i", sa[i-4:i])[0] == 25   # 校验长度前缀
    sa[i-4:i-4+32] = struct.pack("<i", 26) + newp + b"\x00\x00"
    i = sa.find(oldp, i + 25)
open("sharedassets12.assets", "wb").write(sa)
```

贴图有几张就要改几处（本案例 52 处，脚本里循环处理）。

### 第 7 步 · 借原版场景当骨架

**这一步是整条流程的关键。** 不要用自己造的 `level0` 当 `level12`。

做法：**`level12` = 原版 `level11`（死亡擂台）的字节副本，改两处。**

#### 7.1 把外部依赖槽位换掉

`level11` 的 `m_Externals` 有 7 项，第 3 项（下标 2）是 `sharedassets11.assets`：

```
ext[0] globalgamemanagers.assets
ext[1] resources.assets
ext[2] sharedassets11.assets      ← 改成 sharedassets12.assets（21 字符对 21 字符，安全）
ext[3] Library/unity default resources
ext[4] sharedassets2.assets
ext[5] sharedassets1.assets
ext[6] sharedassets0.assets
```

```python
d = bytearray(open("level11", "rb").read())
i = d.find(b"sharedassets11.assets")
d[i:i+21] = b"sharedassets12.assets"
```

#### 7.2 把指向该槽位的 3 个 PPtr 置空（**漏了会崩溃**）

原版场景里有 3 个对象引用了 `sharedassets11.assets` 里的东西，槽位换掉后它们会指向**我们的网格**，类型对不上 → **直接崩溃**。

| 引用方 | 指向 | 处置 |
| --- | --- | --- |
| `RenderSettings.m_SkyboxMaterial` | Material | 置空 |
| `RenderSettings.m_CustomReflection` | Cubemap | 置空 |
| `LightmapSettings.m_LightProbes` | LightProbes | 置空 |

做法：遍历所有对象的 TypeTree，凡是 `m_FileID == 3` 的 PPtr 全部改成 `{0, 0}`（在我们重指几何之前做）。

> 借到的不只是"能跑"——**弹入出场、寻路图、观战相机、音效**这些能力都是从骨架图继承来的，交接清单见 [§4.5](#45-新地图和骨架地图是什么关系必读)。

### 第 8 步 · 替换几何

死亡擂台场景的渲染位统计（其他地图略有不同，需要自己数）：

| 组件 | 数量 |
| --- | --- |
| MeshRenderer | 69 |
| MeshFilter | 69 |
| Transform | 107 |
| **MeshCollider** | **52** |
| BoxCollider | 14 |

**做法**：把我们的 N 个合并网格，挂到这个场景的 N 个渲染位上。

对每个用到的渲染位（优先选**带 MeshCollider 的**，这样才有碰撞）：

```python
mf_tree["m_Mesh"] = {"m_FileID": 3, "m_PathID": 我们的网格 pid}
mr_tree["m_Materials"] = [{"m_FileID": 3, "m_PathID": 我们的材质 pid}]
mc_tree["m_Mesh"] = {"m_FileID": 3, "m_PathID": 我们的网格 pid}

tr_tree["m_LocalPosition"] = (0, 0, 0)
tr_tree["m_LocalRotation"] = (0, 0, 0, 1)
tr_tree["m_LocalScale"]    = (1, 1, 1)
tr_tree["m_Father"]        = {0, 0}       # 断开父级，否则会被原来的父物体带着跑
```

**没被用到的渲染位**：`m_Mesh` 置空 + `m_LocalScale` 设 0（隐藏）。

**注意两点**：

1. `m_FileID` 是 **1-based**：`m_FileID = 3` 对应 `m_Externals[2]`。
2. 断开父级后，记得从原父物体的 `m_Children` 里把它删掉。

### 第 9 步 · 修出生点高度（**最容易卡死在这里**）

#### 现象

地图能进、能看到几何、HUD 正常、ESC 能弹菜单，但**玩家一直在往下掉**，视野里是纯蓝的天空。

#### 原因

出生点**不在场景里的 `SpawnVel_*` 那些物体上**（那些只是编辑器辅助物）。

真正的位置存在 `MapManager` 这个 MonoBehaviour 的序列化数据里：

```csharp
public class MapManager : Singleton<MapManager> {
    [SerializeField] private SpawnPointDictionary pointDic;   // 出生点字典
    private SpawnPoint[] SP_BL, SP_GR, SP_Netural, ...;
}
public struct SpawnPoint {
    public Vector3 position;   // ← 就是这个 y
    public float rotation;
}
```

死亡擂台的 16 个出生点，**y 全是 `-1.85`**（因为死亡擂台的地面就在 -1.85）。
而我们的模型地面在 **y = 0** —— 于是出生点比地板低 1.85 米，一出生就在地板下面，直接掉出去。

#### 怎么改

MonoBehaviour 没有 TypeTree，不能按结构解析。但结构极简单，**按浮点数特征扫**即可：

```python
import struct

# 1) 找到 MapManager 的 MonoBehaviour
#    MonoBehaviour 前 12 字节固定是 m_GameObject: PPtr<int32 fileID, int64 pathID>
for pid, o in objs.items():
    if o.type.name == "MonoBehaviour":
        fid, gopid = struct.unpack("<iq", o.get_raw_data()[:12])
        if go_name.get(gopid) == "MapManager":
            mm = o
            break

# 2) 把 y == -1.85 的坐标全部抬高
raw = bytearray(mm.get_raw_data())
for off in range(0, len(raw) - 12, 4):
    x, y, z = struct.unpack("<fff", raw[off:off+12])
    if abs(y + 1.85) < 0.02 and -200 < x < 200 and -200 < z < 200:
        struct.pack_into("<f", raw, off + 4, 3.0)   # y = 3.0
mm.set_raw_data(bytes(raw))
```

本案例改了 **16 处**，改完玩家从空中 3 米落地，正好踩在石板地上。

> 💡 **通用公式**：出生点 y = 你的模型地面高度 + 2~3 米
> 换成别的地图骨架时，先用同样的方法把原图的出生点 y 打出来，照着改。

### 第 10 步 · 注册到下拉框

两件事：

#### 10.1 场景名册加第 13 条

`globalgamemanagers` 里 BuildSettings 对象（path_id = 11）的 `scenes` 字段：


## 9. 已知限制

| 限制 | 现状 | 可能的路 |
| --- | --- | --- |
| **没有室内空间** | 塔防图这类模型只有外壳，门是贴图，进不去 | 模型本身要有室内，或用碰撞体围出可走区域 |

| **渲染位数量固定** | 骨架只有 69 个位，最多 69 个材质组 | 合并到更少组，或自己造场景（需要解决管理器问题） |
