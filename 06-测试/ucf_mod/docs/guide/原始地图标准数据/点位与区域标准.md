## 0. 怎么读这份文档

### 0.1 面向人

1. 先看 **§3 模式 × 地图矩阵**，确定要查哪张图
2. 到 **§4** 找对应模式，按 `levelN · 英文名 · 中文名` 定位
3. 每张图固定四块：**来源 → 摘要 → 区域表 → 点表 → 线表 → 分组**
4. 坐标全部是**世界坐标**，单位米，3 位小数

### 0.2 面向机器（数据契约）

本文件是唯一数据源，**不附带任何 json**。解析规则：

| 规则 | 说明 |
|---|---|
| 图锚点 | `#### level{N} · {英文} · {中文}`，N 为 0~11 |
| 表识别 | 每个 `**××表**（N 条）` 后紧跟一张管道表 |
| 表结构 | 第 1 行表头，第 2 行 `|---|` 分隔 |
| 列序 | 固定，**按列序取值，不要按列名**（列名可能微调） |
| 空值 | `-` |
| 数值 | 定点十进制 3 位小数 |
| 分隔 | 单元格内不含 `\|` |

### 0.3 列定义

**区域表（12 列）**

```
# | 名称 | 类型 | 中心X | 中心Y | 中心Z | 尺寸X | 尺寸Y | 尺寸Z | 形状 | 父级 | 备注
```

- `形状`：`盒体` = 有 BoxCollider，尺寸为 collider size；`标记点` = 仅 Transform，无碰撞体

**标记点表（9 列）**

```
# | 名称 | 类型 | X | Y | Z | 父级 | 脚本 | 备注
```

**线表（12 列）**

```
# | 名称 | 类型 | 起点X | 起点Y | 起点Z | 终点对象 | 终点X | 终点Y | 终点Z | 父级 | 备注
```

## 2. 术语与分类

### 2.1 三层模型

口径与 [寻路全流程_从建图到蹲下.md](../寻路全流程_从建图到蹲下.md) §1 一致：**可走性层**只回答"能走到哪"，**目的层**只提供坐标，两层互不知道对方存在。

| 层 | 内容 | 由谁决定 |
|---|---|---|
| 可走性层 | `PointGraph` 节点（场景里 `tag == 20022` 的物体）／`NavMeshGraph` 三角面 | A\* Pathfinding 插件 |
| 连线层 | `NodeLink`（只加边）／`NodeLink2`（加 2 个端点 + 边）／`Bot_JumpLink`（只登记跳跃，不加点） | 插件 + 关卡 |
| 目的层 | `Bot_CrouchPos`／`Bot_GuardPos`／`Bot_NanoGuardPos`／`Bot_GuardArea`／`Bot_NanoGuardArea` | 游戏行为层 |

### 2.2 本文件的口径

| 术语 | 定义 | 数据在哪 |
|---|---|---|
| **路点** | `GameObject.tag == 20022（WayPoint）` | 附录 §9（全量坐标） |
| **标记点** | 挂目的层组件的对象（蹲点/守卫点/坠点/空点） | §4 每图「点表」 |
| **区域** | 盒体（有 `BoxCollider`）或按命名判定的区域对象 | §4 每图「区域表」 |
| **连线** | 挂 `NodeLink`／`NodeLink2`／`Bot_JumpLink` 的对象 | §4 每图「线表」 |

> **为什么分开**：路点决定"能走"，标记点决定"想去哪"。混在一张表里会把 3,070 个点图节点和 2 个蹲点并列，既难读也容易被误当成同一种东西。

> **2026-11-27 补：`zoomPos` 到底是什么**（UnityPy 直接解原版 `level2 / level7 / level8` 核实）
>
> 蹲点 / 守卫点的「朝哪看」存在 `zoomPos`（`Bot_GuardPos@0x10`、`Bot_NanoGuardPos@0x10`，`Vector3[]`），
> 元素是**世界坐标（要看向哪）**，不是单位方向向量：
>
> | 关卡 | 类 | 数量 | 实测 |
> |---|---|---|---|
> | level2 小型工厂 | `Bot_CrouchPos` | 8 | 每个 1 个方向，目标点离点位 7.3~39.7 m |
> | level7 沙漠要塞 | `Bot_NanoGuardPos` | 51 | **49 个为空**、2 个带 2 个方向；目标点 18~53 m |
> | level8 生化酒店 | `Bot_GuardPos`（旧，死数据） | 25 | 全部 1 个方向，多个点共用同一个目标点 |
>
> `Bot_NanoGuardArea.Init()` 会把 `entrancePos`（世界坐标的入口点）`AddRange` 进每个守卫点的
> `zoomPos` —— 所以**守卫点的张望方向多数来自守卫区的入口点**，自己带方向的很少。
> 反过来：改入口点 = 改这批守卫点的张望方向（这一条以前没人注意，2026-11-27 核实）。

#### 2.5.1 守卫点 vs 守卫区（最容易混的一对）

| 对比项 | 守卫点 `Bot_NanoGuardPos` | 守卫区 `Bot_NanoGuardArea` |
|---|---|---|
| 是什么 | 一个**坐标** | 一个**范围** + 一整套调度数据 |
| 管什么 | 人机**站在哪、朝哪看** | 人机**从哪进、去哪站、打不过往哪跑** |
| 场景形态 | 空物体，通常是守卫区的子物体 | Trigger 盒，带 `entrancePos[]` / `escapePos[]` / `neighborAreas[]` / `escapeAreas[]` |
| 生效条件 | **必须挂在守卫区下面**（区的 `Awake` 把子物体收进 `posList`），挂错父节点等于没挂 | 独立生效 |
| 数量关系 | 一个区下挂若干点 | 一个区 = 一组点 + 入口 + 逃跑路线 + 相邻区 |
| 行为优先级 | 守卫点 **6** | 被压时触发逃跑 **10**，盖过守卫点 |

一句话：**区是“房间”，点是“房间里站人的位置”。**
只放点不放区 → 点不会被收集，等于没摆；只放区不放点 → 空区，人机进去没地方站。

> 编辑器的对应行为（2026-11-27）：`F2 → 3 守卫区工具 → 2 加守卫点` **只在已有守卫区的 3 m 框里挂点**，
> 准星不在任何区里时按 5 会被拒绝（虚线框变灰 + 红字提示「先按 1 建区」）。
> 以前「加点」会顺手在同一个坐标再建一个区，现在不会了 —— 区和点是两步：先建区，再往区里加点。

#### 2.5.2 守卫区的四个数组

| 字段 | 含义 | 玩家看到什么 |
|---|---|---|
| `entrancePos[]` | 入口点 | 人机从固定门口 / 缺口鱼贯进区，不穿墙不卡门框 |
| `escapePos[]` | 逃跑点 | 你压进守卫区，人机不打了转身就跑 |
| `neighborAreas[]` | 相邻区 | 换区巡逻时的候选 |
| `escapeAreas[]` | 逃跑去向 | 脱战后换到哪个区 |
