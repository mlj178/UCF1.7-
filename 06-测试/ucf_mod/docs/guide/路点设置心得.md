# 路点设置心得（2026-11-24）

> 本文只写「踩出来、验证过」的结论，按现象 → 原因 → 规则三段写。
> 出现新坑就往下面加，别写成教程。

## 1. 1 m 内两个路点会抢吸附（最重要）

**现象**：人机走到跳点附近**来回转头、原地打转**，或者走到箱子边就停住不跳。

**原因**：游戏的跳链是**按「最近的路点」吸附**的 ——
`Bot_JumpLink.OnLatePostScan` 用组件自身坐标找最近节点，吸附半径 **1 m**；
而跳链的索引 `linkDic` 是**以起点节点为键**的。所以：

- 1 m 内如果有两个路点，路径排到的是 A、跳链挂的是 B，`GetLinkEndByGraphNode(nextNode)`
  就对不上，**跳链一次都不触发**；
- 就算对得上，A* 与"到达判定"会在两个几乎重合的点之间反复切换，
  人机表现为**原地转头、抽搐**（2026-11-24 运输船现场就是这个）。

**规则**：

1. **同层任意两个路点间距 ≥ 1.2 m**（比吸附半径 1 m 再留点余量）；
2. 跳链的**起跳点、落点必须各自唯一对应一个路点**，落点不要和下一跳的起跳点分成两个点；
3. 录制器已经自动处理：**同层 1.05 m 内的节点会合并成一个**（`ucf_rec.MERGE_NEAR`），
   合并后跳链端点也一起改写到合并后的点上。

## 2. 跳链的四个硬条件（不满足就不触发 / 跳不过去）

| 条件 | 数值 | 不满足会怎样 |
| --- | --- | --- |
| 两端各自吸附到路点 | 1 m 内 | 建出来但 `startNode/endNode` 为空，永不触发 |
| 两点之间要有 A→B 边 | 双向都不需要 | A* 不会把两点排成相邻，跳链永不触发 |
| 3D 长度下限 | ≥ 1.5 m | 游戏不认，人机"原地跳" |
| 3D 长度上限 | ≤ 3.0 m | 触发但跳不过去，起跳后掉回原地 |
| 人机当前最近路点 == 起点节点 | 精确相等 | 走到跳点也不跳（`nearN` 是旁边的点） |
| 朝向 / 速度 | `accuracy` / `needSpeed` | 站着、侧着、反着走都不跳（见 §7） |

文件里不写参数时默认是 `needSpeed=0 / accuracy=1.0`：不要求助跑，但**必须带速度朝跳链方向**，站着不跳。

体检：`python app/tools/data/check_jumps.py` 或看日志 `wpmenu: jump link ... startNode=... endNode=...`。

## 3. 高处落地用「单向边」，不要用跳链

**现象**：从地道口 / 箱子上跳下来，落地那里**没有连线**，人机不敢走、路线断掉。

**规则**：

- **平地跨越 / 往上跳** → `jump add A B`（跳链）+ `edge add A B`；
- **高处落地（往下）** → **只写 `edge add A B` 单向边**，不要建跳链。
  跳链会让人机起跳，从高往低不需要跳，走过去让重力把它带下去；
- 反向不要再补一条（人机爬不上来）。

录制器现在会**自动识别"离地→落到更低处"**（不管有没有按空格），补一条单向落地边。

## 4. 节点密度：默认 4 m，别让点堆在一起

> **2026-11-26 起**：不再是「每 N 米放一个点」。走路段先做 Douglas–Peucker
> （形状误差上限 `DP_EPS = 0.10 m`），再把超过 `step` 的段等分 —— `step` 现在是
> **最大段长**，不是固定间距。实测 09:07 风暴：最大偏差 25 cm → **8.7 cm**，
> 节点数基本不变（46）。下面几段是距离法时期的历史记录，结论（别堆点、别太小）仍然适用。

**现象**：包里有几百个点、密密麻麻，人机走起来一顿一顿、路线看着乱。

**原因（2026-11-24 抓到）**：重采样的累加写错了 —— 每个样本按"到上一个**节点**的距离"
累加，导致实际间距只有 ~1 m（270 m 的路线出了 287 个点）。

**规则**：走路重采样间距 `step` 用 **4 m**；窄道 / 拐角多的图用 **2.5 m**，
门框、走廊拐角、跳点助跑段这些地方再细一档用 **1.5 m**（2026-11-26 加）——
同一条 50.9 m 轨迹实测：2.5 m 时折线偏离真实脚步 p90 9 cm / 最大 40 cm，1.5 m 时
p90 4.5 cm / 最大 25 cm，节点数 25 → 35。**不要再往下**：1.05 m 是同层合并半径，
比它密会被去重成近点对（1.0 m 时 45 对），跳链端点也会被并到旁边的走路节点上。
同层点距不要小于 1.2 m；**跳点不算进重采样**，单独落。

### 4.0.1 跳点端点不参与吸附（2026-11-26）

录到的起跳点常常离最近的路点 0.4~0.7 m。以前它会被 1.05 m 合并半径吸过去，
3.00 m 的跳吸成 3.50 m、2.82 m 吸成 3.29 m，超过游戏 1.5~3.0 m 的窗口就整条丢掉
（08:48 风暴：4 跳只活 1 条，人机卡在塔第一层）。

现在 **`1.5 <= 3D <= 3.0` 的跳，两端坐标原样保留**，附近的走路节点反过来并到跳点上；
保存时 `dedupe_lines` 也不再吸跳点。只有真的超窗的跳会被标出来、不建链。

连带的一条经验：**两跳之间最好走开 1.5 m 再跳**。落点和下一起点如果只隔 0.5~0.7 m，
合并会超过 3 m、不合并又是两个近点，工具会提示一句「人机若来回转头，跳完先走开 1.5 m」。

**断口**：跳事件本身没结算出来（掉进虚空、录完马上停）才会有断口，复盘汇总写「断口 N」。
**长度不再拦**（2026-11-27 起跳链只保留下限 1.5 m）：链建出来只是「有机会」，
能不能过必须进游戏看；过不去就重录成两跳，或以后再研究 `needSpeed`。

## 4.1 跳链必须放在「必经之路」上（2026-11-24 现场结论）

**现象**：箱子堆上放了蹲守点，人机不来；日志里 63 条状态全是 `spd=0`、`tgt=(0,0,0)`，
没有任何一只靠近过箱子。

**原因**：A* 只会走"到目标的最短路"。箱子在角落、上面没有目标（蹲守点由游戏挑，
地图自带的 4 个蹲守点又在别处），所以**没有任何路径需要经过箱子** —— 跳链再正确也不会被用到。
原生地图（如新寂静村 58 条跳链）全都长在**主路线**上，就是这个道理。

**规则**：想让跳链生效，先让它"有用"——
- 箱子上面/后面要有**目的地**（另一条路、上层平台、包抄点），走跳链比绕路近；
- 或者把箱子做成**唯一通道**（把绕路封掉）。

## 4.2 编辑标记按地图分文件夹（2026-11-24 起）

- 旧：`<游戏目录>\ucf_mod\markers\markers.txt` —— **全图共用一份 + 放在游戏目录**，
  换图时别的图的蹲守点也会被加载（现场见过 y=+27 的悬空点，人机选中后原地"到达"）。
- 新：**工程端** `06-测试\ucf_mod\data\navdata\dev\markers\<包名>\markers.txt`
  例：`data\navdata\dev\markers\01_TransportShip运输船\markers.txt`。
  控制台启动游戏时注入 `UCF_MARKERS_DIR` 指过去；没走控制台才退回
  `<游戏目录>\ucf_mod\markers\<包名>\markers.txt`。换包/换图自动切换并重放。

## 4.3 地图自带的蹲守点是场景资产，不在点图里

`vis: ... crouch=4` 这类原生 `Bot_CrouchPos` 属于**地图场景**，
"空白点图"只清点图节点，不清这些组件。它们照样会被人机的 GoCrouchPos 选中。

## 5. 其他几条经验

- **别在悬空处放点**：落点必须真能站人（对着台面/箱子打），否则人机跳过去照样掉。
- **跳链越平越好**：跳高是定值（约 1.9 m，游戏 `JumpPower=10.5` 决定），
  水平距离才是"能不能过去"的关键；往上跳 1.8 m 的类型对助跑速度很敏感。
- **蹲守点（Bot_CrouchPos）不是"巡逻点"**：人机到了蹲守点会**蹲下不动**（这是它的设计），
  想让它继续走，别指望蹲守点；要"引它上去"得把目标放在上面。
- **验证顺序**：眼睛看（vis 黄块 = 跳链两端、白块 = 路点、蓝线 = 行走边）→
  看日志 `naved: N jump link(s) created ... startNode/endNode` →
  看人机 `beh: ... tgt=(...) ` 有没有目标 → 最后才调数值。

## 7. 跳跃触发的运行时条件（2026-11-25 反汇编确认）

> 之前只知道「路径里起点下一个节点 == endNode」会被 arm；这次把 `Bot.JumpCheck` 也反了，
> 站在跳点上不跳的原因找到了。地址相对 GameAssembly.dll（base 0x10000000）。

`Bot.JumpCheck`（0x10B2F300，480 字节）按顺序检查：

| 条件 | 反汇编 | 不满足 |
| --- | --- | --- |
| ① 人机「当前最近路点」就是跳链起点 | `[bot+0x88] == [bot+0xC8]` | 走到跳点也不跳（nearN 是旁边的点） |
| ② 朝向 / 速度 | `dot(ClearDirY(velocity), link.direction) >= 2*accuracy - 1`（阈值常量 0x10B99D68 = 1.0） | 站着（速度 0）、侧着、反着走都不跳 |
| ③ 沿跳链方向的速度 | `|Project(velocity, direction)| >= needSpeed`（+0xD4） | 助跑速度不够就不跳 |
| ④ 通过后 | `Player.Jump()`，`nextJumpTime = +inf` | — |

**accuracy 的含义（关键）**：

- `accuracy = 1.0` → 阈值 `2*1-1 = 1.0`：人机必须**带着速度朝跳链方向**（水平速度点积 ≥1.0）。
  台阶 / 箱子上跳时人机被挡住、速度降到 0，就**永远不跳**——2026-11-25 运输船北边地道卡住 60 秒就是这个。
- `accuracy = 0.5` → 阈值 `0`：站着（点积 0）也能过，只有**反着走**（点积 <0）才失败。
- `needSpeed = 0`：不要求助跑速度（投影 ≥0 恒成立）。

`Bot.OnPathComplete`（0x10B31950）：

- 遍历路径，只有「起点节点的下一个节点 == link.endNode」才 arm（`GetLink` 查 `linkDic` →
  `GetLinkEndByGraphNode` 比对）——**反方向 B→A 永远不 arm，跳链是单行道**。
- **匹配一条就直接 return**（0x10B31DCB → 0x10B31A15）：一条 A* 路径只会 arm 第一条跳链；
  后面连续的跳链要等下一次重算路径再 arm（人机 0.25~0.5 s 重算一次，长跳链会一顿一顿地跳）。

`Bot_JumpLink.OnLatePostScan`（0x10B2F8E0）：

- 起点 = 组件自身坐标的**最近节点**，每个 Link 的落点 = endTransform 坐标的最近节点；
- 最后 `linkDic[startNode] = 组件`——**同一个起点只能有一条跳链生效**（后建的覆盖先建的）。
  一个点要跳多个落点，必须把多个 Link 放进**同一个组件**的 `links[]`，不能建两个组件。

## 8. 竞技场原生跳链实测（2026-11-25，UnityPy 解 level5）

直接解 `UnityCrossFire_Data\level5` 里 21 个 `Bot_JumpLink` 组件的序列化数据
（`Link.needSpeed` / `Link.accuracy`），结果：

| 关卡 | 链接数 | needSpeed | accuracy |
| --- | --- | --- | --- |
| level5 竞技场 | 22 | **全部 0.0** | **全部 0.5** |
| level6 刀锋寨 | 18 | 全部 0.0 | 全部 0.5 |
| level10 新寂静村 | 58 | 0 / 3 / 5 / 6 / 7 | 0 ~ 0.85（按跳点难度区分） |

**结论**：竞技场的跳链就是「**不要求助跑 + 站着也能起跳**」（0 / 0.5）。
录制器 `ucf_rec.save_lines` 现在写 `jump add A B 0 0.5 0`，和竞技场一致。

竞技场跳链的几何特征（`native/05_Arena竞技场/map.json`）：

- 3D 长度 1.60~3.29 m，基本都 ≤3.0；**全部是往上跳**（+1.5 / +2.0 / +2.3 m）；
- 节点间距 1.6~3.7 m，**没有 4 m 平跳**——4 m 平跳既超长又在双向走廊上，
  只有正向会 arm，跳了也过不去。

## 9. 坑：游戏内保存会把 needSpeed / accuracy 抹掉

`src/editor.c` 的 `nav_save` 只写 6 个坐标：`jump add %.3f %.3f %.3f %.3f %.3f %.3f`，
不写可选参数。所以控制台录制 / 手改出来的 `0 0.5 0`，**进游戏后只要在游戏里保存一次就丢**，
参数回到默认 `0 / 1.0`（站着不跳）。

改法：`nav_save` 里参数非默认时按 9 个字段写回，然后重新构建 DLL。
（2026-11-25 已改：`nav_save` 遇到非默认参数会写 `%.2f %.2f %d`；需重新构建 / 部署 DLL 才生效。）

## 10. 案例：人机卡在「跳链落点」和「下一跳起点」之间（2026-11-25 运输船）

**现场**：`bot=44188390` 停在 `(15.1, -12.8, -17.8)`，10:53:12 ~ 10:53:27 连续采样 `spd=0.00`。

日志一行（10:53:27）：

```
p=(15.1,-12.8,-17.8) spd=0.00 acts=[BotAction.Saunter] over=1 reach=1
nearN=44182510  → (15.123, -13.515, -18.952)   跳 3 落点
nextN=44182510                                  路径下一节点也是它
njs=441824e0    → (15.124, -13.515, -20.155)   跳 4 起点（已 arm）
njend=441824b0  → (16.103, -11.803, -19.594)   跳 4 落点
njspeed=0.0  njacc=0.50  njtime=inf
```

**为什么卡**：

1. 跳 4 已被路径 arm（`njs` 非空），但 `JumpCheck` 第一关要求「人机最近路点 == 跳链起点」；
   它的最近路点是跳 3 落点 `44182510`，不是跳 4 起点 `441824e0` → **永远不跳**。
2. 人机实际站在 `y=-12.8`，比落点节点高 **0.7m**、水平差 **1.36m**（落在平台边缘/栏杆上），没站在点上。
3. 1.36m 在 Saunter 的到达半径（1.5m）以内，`reach=1` 认为「到了」就停；
   但路径下一段要它走到 1.2m 外的跳 4 起点，中间是台阶 / 空隙，走不过去；
   每 0.5s 重算一次路径，重复同一个死循环。

**根因**：跳 3 落点和跳 4 起点是**两个独立节点，只隔 1.2m**，中间只有一条走路边。
录制器的 `MERGE_NEAR = 1.05m` 没合并它们（1.20 > 1.05）；人机落地稍微偏一点就掉进两点之间，
既不在跳 4 起点（不能跳），也回不到落点（被几何挡住）。

**解决**：

- 删除 `node add 15.124 -13.515 -20.155`，让 `15.123 -13.515 -18.952` 同时作为跳 3 落点和跳 4 起点；
- 删除两点之间的双向边，跳 4 改为 `15.123 -13.515 -18.952 → 16.103 -11.803 -19.594`（2.07m），
  相关边一起改到 `15.123`；
- 结果：127 点 / 290 条边 / 14 条跳链，单连通，`check_jumps` 14 / 14 OK。
- 备份：`n786-57a46e3465c847cb.txt.bak-mergejump-20261125-105830`。

**规则（以后照这个做）**：

1. **连续跳链的落点 = 下一跳起点**，不要拆成两个点；水平 ≤1.5m、高差 ≤0.5m 就直接合并。
2. **两点之间没有真实可走面就不要加走路边**；宁可合并，也不要让 A* 以为能走过去。
3. 落点放在**平台中间**，不要放边缘 / 栏杆旁：人机会过冲 0.5~1.5m，而 Saunter 到达半径是 1.5m，
   放边缘就会出现「以为到了、其实悬空」。
4. 排查顺序：先看 `nearN` 和 `njs` 是不是同一个指针（不是 = 没站在起点）；
   再看 `spd` 是不是 0（0 = 被几何挡住，不是参数问题）；最后才看 `njacc / njspeed`。

**录制侧（2026-11-25 已实现）**：

- 落点 B 与下一跳起点 A 强制合并（水平 ≤1.5m、高差 ≤0.5m）；合并后下一跳仍要落在 1.5~3.0m，
  否则不合并（避免把两段 2.5m 平跳接成 4m）；
- 跨文件去重从 `0.35m` 提到 `1.05m`，并且被去掉的节点坐标会**改写**到保留的节点上，
  边 / 跳链端点一起改写（跳链的可选参数保留）。

**录制侧（待实现）**：

- B 保存前向下打射线吸附到可站面，打不到面就不写这条跳链——录制器是离线 Python，
  没有可走面查询；要么插件在录制时顺带校验，要么控制台接 navmesh；
- A 沿「远离 B」的方向回退 0.3m——单独挪 A 会和走路端点形成 0.3m 近点（抢吸附），
  要连走路段端点一起挪，暂缓；
- 着陆区（B 前后各 0.6m 各放一个着陆点）——会改变图拓扑，优先级低。
