# 控制台启动加速 2026-11-26

## 1. 原来慢在哪（实测）

| 阶段 | 耗时 |
|---|---|
| import | ~0.2 s |
| 建 11 个页面 | 4.4 – 7.6 s（人机路点 1.7–2.1 s、录制 0.4–0.8 s、车测 0.44 s…） |
| 首次绘制 | ~2 s |
| **合计** | **6.6 – 10 s** |

额外的：`find_map_doc` 每次都要 listdir + json.load（一次启动 768 次），滚动条/圆角每帧都走 Tk canvas。

## 2. 改了什么

1. **先显示窗口，页面后台逐页建**（`控制台.pyw`）
   - 建完外壳 + 当前页就先 `update()` 把窗口画出来；
   - 其余页放进队列，`after(250)` 起每 1 ms 建一页；
   - 点页签时若该页还没建，`_ensure_page` 立刻补建（数据/车测/录制/部署会先补「人机路点」）；
   - `refresh_status` 加保护，页面没建完时不炸。
2. **「人机路点」的成品页按需建**（`tabs/waypoint.py`）
   - 含对比表约 1 s，第一次切到「成品」才建。
3. **map.json 指纹缓存 5 s**（`ui/maps.py`）
   - 768 次 json.load → 每个指纹一次；部署/导出后最迟 5 s 生效。
4. Defender 排除：本机 Defender 服务不可用（0x800106ba），实际在跑的是火绒（HipsDaemon），
   排除要在火绒里加，脚本不改。

## 3. 效果（同一台机器，实测）

| | 改前 | 改后 |
|---|---|---|
| 窗口可交互 | 6.6 – 10 s | **1.9 s** |
| 全部页面建完 | 同上 | ~5.7 s（后台，期间可能有一次 1–2 s 的停顿） |

## 4. 注意

- 后台建页用的是主线程分时（不是真线程），所以建到「人机路点」那 1.7 s 里界面会顿一下；已经把它排在最前。
- 页面第一次点开若还没建，会现建（最多 ~2 s）。
- 16 个自检全过。

## 5. 折叠/展开卡死修复（同日）

**现象**：折叠再展开后程序像卡死，页面加载也慢。

**原因**：
1. 展开的 `update()` 正好撞上后台建页定时器 —— 一次建页最多 1.7 s，全算在展开这一下。
2. 后台建页原来 `after(1)` 一页接一页，几乎不给鼠标/键盘留时间。
3. 展开处又补排了一条建页链，和原来那条并存 —— 两条链互相抢，越跑越像卡死。

**修复**：
- 建页链改成**单实例**（`_start_pump` 去重，`_pump_on` 标记）。
- **折叠期间暂停建页**；折叠/展开前后 **1 s 内也不建**（`_pump_pause_until`）。
- 间隔 1 ms → **150 ms**，中间留出输入处理时间。
- 建页加 `_building` **重入保护**：`update()` 重入时不会把同一页再建一遍。
- 后台队列**当前组优先**（下一步最可能点的页排前面）。

**复测**（9 页还在队列里时）：

| | 修复前 | 修复后 |
|---|---|---|
| 折叠 | 34 ms | **20 ms** |
| 展开 | 2230 ms | **183–191 ms** |
| 启动可交互 | 3.5 s | **1.7 s** |
| 全部页建完 | — | 6–7 s（后台） |

## 6. 真正的卡死根因：状态定时链发散（同日晚补）

**现象（已复现）**：控制台折叠后放一边，几分钟后窗口「未响应」；Windows 事件日志里有
两次 `Application Hang / AppHangB1`（pythonw.exe，11:34、16:04）。抓到的进程 CPU
87% → 100%，`IsHungAppWindow = True`，点「展开」也回不来。

**定位**（py-spy 200 Hz 采样 8 s）：98.8% 的样本落在 `App.refresh_status` 里；
折叠状态下 60 s 内 `refresh_status` 被调 134 次，而且频率随时间线性上涨。

**原因**：
1. `refresh_status()` 结尾自己排了一条 `after(4000, self.refresh_status)`（旧代码的自我续命）；
2. 2026-11-26 启动加速又把入口换成 `_safe_status()`，它每 4 s 再调一次 `refresh_status()`。
3. 两条叠在一起 → 每个 tick 凭空多一条 4 s 链：4 s 后 2 条、8 s 后 3 条……
   10 分钟约 150 条，每秒几十次 `refresh_status`，主线程永远走不出这个函数，
   Windows 就判「未响应」。**折叠不是原因**，只是窗口收起来放一边、过几分钟才回来看，
   正好撞上链已经堆满。

**修复**（`app/控制台.pyw`）：
1. 排程只保留一处：`_safe_status()`；`refresh_status()` 不再自我排程。
2. 新增 `_start_status()` / `_stop_status()`：全程序只有一条状态链，可停可续。
3. 折叠时把两条后台链都停掉（状态 + 建页），展开时启动并立刻补一次刷新；
   建页链折叠时也不再每 500 ms 空转。
4. 关窗前先 `after_cancel` 两条链，`destroy` 之后不再有回调。

**复测**（同一台机器）：

| | 修复前 | 修复后 |
|---|---|---|
| 折叠 60 s 的 `refresh_status` 调用 | 134 次，且越跑越快 | **0 次** |
| 折叠 60 s 的进程 CPU | 87–100%（未响应） | **0.3–3%** |
| 展开后刷新频率 | 随时间上涨 | **0.2–0.5 /s 恒定** |
| 折叠 75 s → 展开 | —（已堆满） | 两条链都恢复，剩余 8 页 2 s 内建完 |
| 4 s 一次折叠/展开 ×7 + 反复调 `_start_status()` | — | 链数不增长 |

自检：新增 `app/tests/test_console_timers.py`，静态锁住「定时链只有一条 / 折叠停 /
展开续 / 关窗摘」；连同原有 16 个自检共 17 个全过。
