# 出生点：三个数组都能改 + 新增点优先（2026-11-27）

> 用户报告：**"出生点无用，不会有人机在我设立的出生点上复活出生。"**
> 本文= 结论 + 反编译证据 + 改了什么 + 怎么验证。
> 旧文 [出生点编辑与删除拆分_2026-11-25.md](出生点编辑与删除拆分_2026-11-25.md) 里
> 「人机不读这两个数组」这句是**错的**，以本文为准。

## 1. 结论（为什么"没用"）

### 1.1 人机是读出生点数组的

2026-11-27 用 IDA 清单 + capstone 复核（GameAssembly 基址 `0x10000000`）：

| 地址 | 函数 | 作用 |
| --- | --- | --- |
| `0x10B53760` | `Player.Spawn` | 内联了 `<Spawn>g__MoveToRespawnPos`，**直接 `call MapManager.GetSpawnPoint(team)`**（`+0x2C8`） |
| `0x10AEB6E0` | `MapManager.GetSpawnPoint` | team 0 → `SP_BL`(+0x10)、1 → `SP_GR`(+0x14)、**其他 → `SP_Netural`(+0x18)** |
| `0x10B736F0` | `<Respawn>g__WaitForRespawn` 协程 | 等 `respawnTime` → 虚调用 `Player.Spawn`（vtable slot 10 = `+0x10C`） |
| `0x10B40390` / `0x10B4A400` / `0x10AF2670` | `Mode_DeathMatch/TeamDeath.DeathEvent`、`ModeBase_Nano.RespawnPlayer` | 对**每个**死亡玩家（含人机）调 `Player.Respawn` |

所以人机重生 = `DeathEvent → Player.Respawn → 协程 → Player.Spawn → GetSpawnPoint`，**读的就是我们写的数组**。

### 1.2 真正的坑：不同模式读的数组不一样

`GameManager.AddPlayer`（`0x10AF9A90`）按 `GameManager.gameMode` 给进场玩家定队：

| gameMode | 模式 | 定队 | 重生读的数组 |
| --- | --- | --- | --- |
| 0 TeamDeath | 团队模式 | `ClientData.joinTeam`（0/1） | `SP_BL` / `SP_GR` |
| 1 DeathMatch | **个人竞技** | **全员 Neutral(2)** | **`SP_Netural`（当时根本改不到）** |
| 2 Special | 特殊战 | `ClientData.joinTeam` | `SP_BL` / `SP_GR` |
| 3-6 Nano* | 生化 / 剑客 / 终结者 | **全员 GlobalRisk(1)** | `SP_GR`（被感染后 BL 才用 `SP_BL`） |

- 旧版菜单只能加/删 **BL / GR**；个人竞技里游戏只读 `SP_Netural` → 加了点也**永远不会被用**。
- 生化里进场全员 GR：只加 BL 点同样没人用。
- 另外两个 `respawnType` 覆盖（改不动就说明模式本身不取点，不怪数组）：
  `ModeBase_Nano.RespawnPlayer` 设 2（敌方队）、`Mode_Nano4_Terminator.RespawnPlayer` 设 1（原地不取点）。

### 1.3 第二个坑：新增点排在末尾，轮不到

`MapManager.NewGameRoundStart`（`0x10AEBCB0`）每回合把 `SPID_BL/GR/Netural` 设成
`Random.Range(0, 数组长度)`，之后 `GetSpawnPoint` 顺序轮转。
旧版把新增点**追加在原生点后面**：一回合只重生若干次，常常轮不到新增点，玩家看到的就是"加了没用"。

## 2. 改了什么（src/editor.c）

| 改动 | 说明 |

| 三阵营 | `MT_SPAWN_NT=8`、`SPAWN_TEAMS=3`，状态数组扩到 3；`SPAWN_OFF={0x10,0x14,0x18}`；init 里多取 `SPID_Netural` |

## 2.1 高度：不准自己猜，跟原生点对齐（同日追加）

**用户反馈**：出生点高度太低，重生后直接往下坠（运输船平台下面是空的）。

原因：放置时 `wp_place` 用的是「准星地面 + 0.05 m」，而游戏自己的出生点比地面高一截
（`Player.Spawn` 直接把 `transform.position` 设成 `SpawnPoint.position`，原生点按游戏自己的
身高/胶囊基准摆的）。比地面低 → CharacterController 一出生就在地板里，直接穿下去。

修法（不写死数字，按本图原生点反推）：

- `ground_below()`：从点上方 1 m 向下打射线取脚下地面（层掩码 1，和准星/贴地同一条）。
- `spawn_height_gap()`：拿**本图原生出生点**逐个射线取地面，算 `原生 y - 地面 y`，
  过滤掉离谱值（-0.5 ~ 3 m）后取平均；量不到才退回 0.05 m。日志：
  `spawn: 高度基准 = 脚下地面 + N.NN m（按 K 个原生出生点测得）`。
- `spawn_fix_height()`：新增点一律抬到 `地面 + gap`；底下是空的就不动（不乱拽）。
- `spawn_fix_heights_all()`：原生点抓到后跑一次，把 markers 里**历史遗留的低点**一起改正
  （Ctrl+S 后落盘）。
- 预置虚线框也按同一高度摆，避免"框在脚下、建出来在半空"。

## 2.2 第一次出生：开局抢跑（同日再追加）

**用户反馈**：进房间第一波人机还是在**原生**出生点（连已经删掉的原生点也照样被用）；
把人机打死、复活之后才用改过的点。

原因：出生点数组以前只在 `editor_on_scene` 里套 —— 那是 navfix 的「场景通知」，
要先等 PointGraph 扫完（换图后常 1~3 s），而人机第一次出生早就过去了。
所以第一波出生读的是游戏刚 `MapManager.Awake` 拆出来的原生数组。

修法（不等场景通知）：

- `spawn_early_tick()`：在主线程高频 tick 里盯着 `MapManager` **实例**；
  一换实例（= 新的一局 / 换图）且 `SP_*` 已经非空（Awake 跑过），
  立刻只从 markers 里读 `spawn / spawndel` 两行并 `spawn_apply()` 写回数组。
- 调用点两处：navfix 的 hi-res `WM_TIMER`（≈15 ms 一跳，主力）+
  4 Hz 的 `editor_tick`（没拿到高精度定时器时兜底）。
- 其余标记（蹲守 / 守卫区 / 标签）仍等 `editor_on_scene`：它们要读场景组件，太早会崩。
- `spawn_parse_line()` 抽出来，`load_file` 和抢跑共用一份解析，格式只有一处。
- 数组被游戏重建（Awake 晚于我们）也靠同一 tick 自愈（`spawn_apply` 里指针比对）。

日志：`spawn: 开局抢跑 MapManager=0x… markers 出生点 新增 B+G+N / 删除 B+G+N`。

## 2.3 第一波人机：出生救援（同日第三轮）

**用户复测**：加了「开局抢跑」还是不行。日志证明抢跑是准时的：

```
10:07:34 [edit] scene: enter astar=...
10:07:34 [edit] spawn: 开局抢跑 MapManager=2237ee18 markers 出生点 新增 2+0+0 / 删除 6+0+0
10:07:34 [edit] spawn: team=BL 写回 新增 2 + 原生 8 - 删除 6 = 4 个 …
```

**结论**：人机是在**地图加载那一帧**就把位置定好的，我们的 tick 最早也只能下一跳
（≈15 ms，实际就是同一秒的下一帧）—— 怎么抢都抢不过。所以只能事后纠正：

- 数组写回成功后开一个 **12 s 窗口**（`spawn_rescue_tick`，跟着 ≈15 ms 的 tick 跑）。
- 每跳扫 `GameManager.allPlayers`（`GameManager` 实例 + 字段偏移 0x1C）：
  - 只看 `ClientData.isBot == 1`（`Player.clientData` +0x94 → `isBot` +0x1C），**不挪本地玩家**；
  - 位置还在**原生出生点 2 m 内**（包括已经被我们删掉的那些）才处理；
  - 已经站在生效点 2 m 内的跳过（不重复挪）；
  - 用 `Transform.set_position` 挪到本队生效点（`Player.team` +0x20；按人机序号轮流分配，避免全叠一处）；
  - 每个玩家只挪一次（`g_rescueMoved[]`）。
- 一次性诊断日志：`spawn: 救援诊断 allPlayers=N 人机=K 站在原生点=X 已在我们点=Y`；
  每个被挪的：`spawn: 第一次出生救援 人机#i team=BL (x y z) → (x y z)`；
  窗口结束：`spawn: 第一次出生救援窗口结束（共挪 N 个）`。

## 2.4 「救援」把游戏搞崩了 → 回退，并给出正确做法（同日第四轮）

**用户复测**："直接游戏闪退"。日志里的真异常只有一条：

```
spawn: 第一次出生救援窗口 12 s …
spawn: GameManager instance field=2d1152a8
!!! crash code=0xc0000005 at 6d89019d (UnityPlayer.dll+0x76019d)
!!! access read at 0xffffed80   reg edi=0xffffed6c
!!! stack+0x02c 6c212033 GameAssembly.dll+0x332033   ← Component.get_transform
!!! stack+0x038 65e5fde2 ucf_mod.dll+0x1fde2         ← 我们的救援代码
```

结论：**闪退是救援代码造成的** —— 在进房间的同一瞬间对 `GameManager.allPlayers` 里的 Player
调 `Component.get_transform`，拿到的是一个已经失效/还没就绪的对象（0xffffed80 这种地址就是
`this + 偏移` 时 base 是坏值）。**碰玩家对象这条路不安全，已整块删除**
（`spawn_rescue_tick` / `gm_inst` / 12 s 窗口 / 诊断全删），当前构建回到"三数组 + 高度 + 抢跑"。

### 评估：需求能做，但要换层次

- **写数组永远赢不了第一波**：日志证明抢跑和地图加载同秒，人机位置在**那一帧**就定了。
- **碰玩家对象不安全**：这次就是证据（对象生命周期不归我们管）。
- **正确层次：整函数替换 `MapManager.GetSpawnPoint`（RVA 0xAEB6E0，静态）**。
  - 它是游戏**唯一**的取点入口（只有 `Player.Spawn` 里两处调用），换掉它 = 所有出生（首波 + 复活）都走我们。
  - 签名已核实：`void GetSpawnPoint(SpawnPoint* ret, int team, const MethodInfo*)`（16 B 结构体 sret，
    调用方 `add esp, 0Ch` → cdecl）。
  - 不需要 trampoline：我们**完全接管**——用自己维护的"新增优先 + 原生去删除"列表 + 自己的轮转计数；
    某队没有编辑时按原逻辑复刻（读游戏 `SP_*` + 自身 SPID），行为与原生一致。
  - 数据来源：初始化时先把 markers 里的 `spawn / spawndel` 读进来（不依赖场景），
    钩子内首次调用时抓原生数组快照（字段 0x10/0x14/0x18，已有代码）。
  - 风险面小：只改一个函数入口 5 字节（`E9 rel32`）+ 一个纯计算函数；不碰 Player / Transform / GC。
  - 提供开关（`ucf_mod.json: spawn_hook`），出问题可一键回到原版。
- 评估工作量：约 150–200 行（集中在 `src/editor.c` 出生点段），实现 + 1~2 次实测。
- 备选（更慢但更"正统"）：离线改场景 `pointDic`（游戏自己 `Awake` 就带我们的点），
  代价是每张图做 IL2CPP 场景序列化，成本高，不推荐现在做。

## 2.5 取点钩子：整函数替换 `MapManager.GetSpawnPoint`（同日第五轮，最终方案）

**为什么非做钩子**：前四轮证明了两件事 ——
① 写数组永远赢不了"地图加载那一帧"（人机位置在那一帧就定）；
② 事后挪玩家对象不安全（第四轮直接闪退）。
所以只能换层次：**让游戏在"向谁要出生点"这一步就问我们**。

### 实现（src/editor.c）

| 项 | 内容 |
| --- | --- |
| 目标 | `MapManager.GetSpawnPoint`，RVA `0xAEB6E0`（游戏唯一取点入口，只有 `Player.Spawn` 两处调用） |
| 签名 | `void* __cdecl (SpawnPoint* ret, int team, const MethodInfo*)`；16 B 结构体 sret，**返回缓冲区指针必须放 EAX**（调用方 `call` 后是 `movups xmm0,[eax]`） |
| 打补丁 | 入口 5 字节 `E9 rel32`；先校验 `55 8B EC`（版本不符就放弃并写日志）；`VirtualProtect` → 写 → 还原保护 → `FlushInstructionCache` |
| 时机 | `editor_start` 里、场景还没加载时安装一次；`ucf_mod.json: "spawn_hook": false` 可整体关掉 |
| 数据 | 初始化时 `spawn_preload()` 先把 markers 的 `spawn / spawndel` 读进来（不依赖场景）；钩子里 `hook_sync()` 发现 `MapManager` 换实例就丢旧图数据、重读本图 markers、轮转清零 |
| 取点 | `hook_points(team)`：数组换了就重拍原生快照 → `spawn_effective`（新增优先 + 原生去删除）；`Neutral` 没数据时借用 BL/GR（和模式兜底一致）；自己维护 `g_hookId[]` 轮转（对应原 `SPID_*`） |
| 安全 | 不碰 Player / Transform / GC；没有数据时返回零点（原逻辑这条路径本来就会抛异常），并在日志里说明 |

### 验证要点（log\ucf_mod.log）

```
spawn: hook GetSpawnPoint @0x10AEB6E0 → 0x….（原字节 55 8B EC 83 EC）   ← 安装成功
spawn: 预读 markers 出生点 新增 2+0+0 / 删除 6+0+0
spawn: hook 换图 → 重读 markers 出生点 新增 2+0+0 / 删除 6+0+0        ← 进图
spawn: hook GetSpawnPoint team=0 → #0/4 (-58.36 -15.00 8.64)           ← 第一波就用我们的点
```

回滚：`ucf_mod.json` 里加 `"spawn_hook": false` → 完全不碰游戏代码，回到"写数组"的老行为。

## 2.6 钩子"没装上"：安装时机错了（同日第六轮，已修）

**用户复测**："还是不行"。**日志是决定性的**：10:54 那次只有

```
10:54:52 spawn: 预读 markers 出生点 新增 2+0+0 / 删除 6+0+0
```

**却没有** `spawn: hook GetSpawnPoint @…` 安装行，也没有任何 `hook GetSpawnPoint …` 调用行 ——
钩子根本没装。原因：安装写在 `editor_start` 里，而 `g_ga`（GameAssembly 基址）是
`ed_init` 才设置的；`RVA()` 依赖 `g_ga`，于是 `if (!g_ga) return 0;` **静默**返回。

修法：

- 安装点挪到 **`ed_init` 末尾**（g_ga 已就绪、还没进任何地图）；
- `editor_start` 只保留 `spawn_preload()`；
- hi-res tick 里加兜底：`if (!g_hookOn) spawn_hook_install();`（装不上会打一行原因，不会静默）；
- `spawn_hook_install` 增加 `tried` 标记：校验失败/改页失败只报一次，不刷屏。

### IDA 复核（2026-11-27，IDA MCP 已连）

- `MapManager.GetSpawnPoint` = `0x10AEB6E0`，签名 `(SpawnPoint* retstr, int team, MethodInfo*)` —— **sret 确认**。
- 它的代码 xref 只有 `Player$$_Spawn_g__MoveToRespawnPos_222_0`（`0x10B54574`）；而这个本地函数
  **没有代码调用者**（只有 metatable 的 data xref）→ 被编译器内联进 `Player.Spawn`。
  也就是说 `Player.Spawn` 里那条 `call GetSpawnPoint` 就是内联副本。
- `Player.Spawn`（`0x10B53760`）**没有直接代码调用者**（只有 vtable data xref）→ 只被
  `Player.Respawn` 的协程虚调用。
- `Player.Respawn` 的代码调用者：`Mode_DeathMatch$$DeathEvent`、`Mode_TeamDeath$$DeathEvent`
  （+ `ModeBase_Nano.RespawnPlayer`，字节扫描里也看到）→ 出生/复活都汇集到 `Player.Spawn → GetSpawnPoint`。
- IDB 的 md5 `fab04426db6a014c0129ef2001530908` 与游戏目录 `GameAssembly.dll` **完全一致**；
  `0xAEB6E0` 处字节 `55 8B EC 80 3D …`，和钩子里的入口校验一致。

## 4. 已知限制

- 生化 `Mode_Nano4_Terminator.RespawnPlayer` 自己把 `respawnType` 设成 Stay(1)：那条路径**不取点**，改数组也不会移动，属于游戏行为。

- 每回合 `SPID_*` 随机起头：新增点排前面 + 清零只能保证"刚加完的下一次重生"，几回合后仍会回到游戏的随机轮转。
