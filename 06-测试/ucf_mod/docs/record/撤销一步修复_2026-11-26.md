# 路点菜单「撤销一步」没撤回来（根因 + 修复）_2026-11-26

## 用户报障（原话）

> 为啥我用路点菜单，在游戏中，有的时候撤销上一步，就是没有撤销回来了，
> 是视觉上没有更新，还是实际上遇到了卡点没撤回呢，你检查一下，修复一下。

## 结论先说

**不是视觉没刷新，是撤销栈本身不忠实。** 每一次撤销都会 `nav_refresh()`（`g_visDirty=1`），
下一帧 `vis_rebuild()` 把点 / 边 / 跳链整体重画一遍 —— 日志里每次撤销后面都紧跟一行
`vis: nodes=… edges=…`，说明画面确实重画了，只是**该被撤掉的东西没被反做**（或反做了别的东西）。

## 证据（game 日志，2026-11-26 17:48:59 ~ 17:49:12）

```
17:48:59  naved: node disabled idx=101 at -19.92 6.12 22.34       ← 用户删了一个点
17:48:59  vis: nodes=142 edges=138                                ← 点数没变（软删），边少了 2 条
17:49:05  naved: undo -> 412 edits left (redo=1)
17:49:05  vis: nodes=142 edges=137                                ← 边少了 1，点还是 142（删掉的点没回来）
...      连续 18 次撤销，edges 138 → 128，nodes 142 → 138
```

**第一次撤销本该把 idx=101 那个点放回来（nodes 142 → 143），实际却去掉了别处的一条边。**
对照代码：`nav_del_here()` 删的是「本次会话里加的点」时走 `nav_drop_add()`，
后者把 `node add` 和相关边从清单里**直接摘掉、不压任何撤销记录** ——
于是「撤销一步」弹到的是更早的一条 `edge add`，用户看到的就是「撤销没反应 / 撤到了别处」。

## 七条根因

| # | 根因 | 现象 |
| --- | --- | --- |
| R1 | 删掉「自己加的点」时只摘清单、不压撤销记录（`nav_drop_add`） | 删完按撤销，删掉的点永远回不来，反而撤掉更早的一步 |
| R2 | 一次动作压多条记录：加点+自动连边=2 条，跳点=3 条（落点/边/jump add） | 按一次撤销只撤一半，看着像「没撤干净」 |
| R3 | `JADD` 撤销是**空操作**（注释写「组件删不掉」，实际只从清单摘） | 按下去屏幕上什么都没变，纯浪费一次撤销 |
| R4 | `NDEL` 撤销只写回坐标 + 可走，`nav_kill_node` 摘掉的连线不恢复 | 点回来了、线全没了 |
| R5 | 贴地（`nav_ground_here`）完全不进撤销栈 | 撤掉的是上一条别的编辑，贴过的点不动 |
| R6 | 蹲守点 / 守卫区 / 守卫点 / 标签 / 出生点的增删**根本不在栈里**（只管点图） | 放完标记按撤销：要么弹到很早的点图编辑，要么 `nothing to undo` |
| R7 | 边的撤销 `nav_conn_apply` 找不到端点时静默返回 0，仍然出栈并打「undo -> N edits left」 | 日志说撤了，图上一动不动 |

## 改动

**核心：撤销以「用户动作」为单位（`NAVED.grp` = `g_edStep` 步号），整组反做；
并且每条都如实报告「到底有没有在图上生效」。**

## 行为对照

| 动作 | 以前 | 现在 |
| --- | --- | --- |
| 加点（已选 A，自动连边） | 撤销一次只断边，点还在 | 一次撤销：边 + 点一起没 |
| 放跳点（落点+边+jump add） | 第一次撤销**什么都不变** | 一次撤销：跳链组件销毁 + 边断开 + 落点删掉 |
| 删点 | 撤销只放回点，连线全丢 | 点 + 底图连线一起回来，用户加的边按清单再校正 |
| 删「自己加的点」 | 撤销弹到更早一步，点回不来 | 点回来 + node add / 相关边补回清单 |
| 贴地 | 撤销撤的是上一条，点不动 | 撤销把 Y 写回旧值（会话级，不落盘） |
| 放 / 删蹲守点、守卫区、守卫点、标签、出生点 | 完全不进栈 | 按类型重建/销毁（守卫区连带点位按同一组） |
| 撤销失败（端点没了 / 槽位满了） | 静默出栈，日志照样说成功 | 日志写清原因，菜单提示「图上没有可反做的变化」 |

## 边界与取舍

1. **贴地 / 删自加点不落盘**：文件格式只认坐标（`node add/del`、`edge`），没有 move 记录；
   贴地本来就是会话级（旧日志里也写着 `session only`），删自加点只该少一条 `node add`。
   Ctrl+S 时会打印「本次会话的贴地/删自加点辅助条目不落盘」。
2. **标记重建 = 重新建一个对象**：不是把旧对象复活（游戏里 `Destroy` 之后没法救），
   走的是 `markers.txt` 读盘那套 `make_*`，所以结果和重进图一致；守卫区会重新占一个 aid。
3. **跳链落点没记录时不重建**：套包时建的跳链如果清单里没有 `jump add`（落点未知），
   撤销删除只能放弃，日志明说「重进图会按包文件重建」。
4. **撤销栈上限**：点图 4096 条（`NAV_ED_MAX`）、标记 96 个（`MKE_MAX`，满了丢最老的）。
5. **恢复栈会互相作废**：任何新编辑都会清空两套恢复栈（`nav_push` / `mke_push`；
   代码里仍叫 redo / `g_redoN`，菜单上叫「恢复」），和普通编辑器一致。

## 顺手修掉的一个格式串错位

同一份工作区里 2026-11-26 的「删旧守卫」改动把 `guard` 的计数删了，但导出 JSON 的
`fprintf` 格式串里还留着一个 `"guard": %d`，参数整体错位（`spawn/jump/tag` 全是脏值）。
改撤销时用 `-Wall` 编译发现，一并删掉那个 `%d`（[src/editor.c:3598](../../src/editor.c#L3598)）。

## 二次调整（2026-11-26，用户当场要求）

| 用户要求 | 落地 |
| --- | --- |
| 「重做一步」改名「恢复」并解释 | `WP_EDIT` 第 2 项 = `恢复（撤销的反操作）`；页内两行说明：`撤销 = 反做最近一步`、`恢复 = 把刚撤销的那一步放回来；做过新编辑就不能恢复` |
| 「重读并套用」去掉 | 第 4 项删除，撤销页只剩 3 项；`nav_reapply()` + 同次加的 `nav_grow_reconcile()/nav_grow_find()` 一并删除 |
| 想重读怎么办 | 控制台「重新应用 / 载入到游戏」（`cmd=reload` → `nav_cmd_set_pack`），那条路径连 `markers.txt` 一起重读 |

**为什么 `nav_grow_reconcile` 曾经需要存在**（留个知识，防以后又把这条路加回来）：
`nav_reapply()` 原来是「`nav_base_restore()` 还原原生底图 → 读盘 → `nav_apply_all()`」。
grow/keep 包的点是运行期 `PointGraph.AddNode` 新建的（nodeIndex 在快照范围之外）：

1. `nav_base_restore()` 会把 `[g_navBaseN, n)` 的节点全部 `walk=0` + 清连接（它认为那是"多余的 grow 点"）；
2. `nav_apply_grow()` 有「同一张图只建一次」的早退判据，重读时不会再建一遍。

结果就是：文件里明明有点，图上全灭（点还在原位、只是变成不可走的红点），人机站桩。
所以那天先用「按文件对账」兜住；用户随后说这个功能不要了，对账代码跟着一起删。
**如果以后要恢复"运行中重读点图"，别用底图还原，直接写按文件对账。**
