# 采样频率修复：为什么 10/20/30/60 Hz 全变成 4 Hz（2026-11-24）

> 用户反馈：控制台「开发者选项 → 原始轨迹采集」选 10 / 20 / 30 / 60 Hz，
> 采出来的 `data\navdata\dev\vis\trace\*.jsonl` 全是 4 Hz（`dt` 恒为 0.250）。
> 上一轮修的源码在工作区，但用户再测还是 4 Hz。本文是把这件事查到底的记录。

## 1. 结论（两件事叠在一起）

| # | 问题 | 位置 | 现象 |
| --- | --- | --- | --- |
| 1 | 采样只挂在 4 Hz 心跳上 | `src/navfix.c` / `src/editor.c` | 不管选几 Hz，实测都是 4.0 Hz |
| 2 | **修好的 DLL 没进用户在跑的那份游戏目录** | 部署流程 | 源码改了、重新编译了，用户测的仍是旧 DLL |

### 1.1 为什么天生只有 4 Hz

数学上的采样入口只有两个：

```
nav_worker 线程：Sleep(250) -> PostMessage(WM_UCF_TICK) -> nav_tick() -> editor_tick()
                                                              -> rec_tick() / trace_tick()
WM_TIMER 0xF3C1（10/16 ms）-> editor_rec_tick() -> rec_tick() / trace_tick()
```

第二条以前只在 `UCF_FREECAM=1`（车测自由视角）时才 `SetTimer`，所以正常游戏里
根本没有高频定时器 —— `trace_tick()` 每次都被 4 Hz 的心跳叫醒，QPC 闸门
（`g_trNextT += 1/60`）虽然是按档位排的时间表，但**机会只有 4 次/秒**，
于是 `dt` 恒等于 0.250 s。选 10/20/30/60 Hz 的差别只剩下「下一个采样点往前排
多远」，全都被 250 ms 的节拍卡住。

### 1.2 为什么「修了还是 4 Hz」

2026-11-24 15:35 改源码、15:36 重新编译并部署到
`D:\BaiduNetdiskDownload\UnityCrossFire1.7.1\...\ucf_mod`；
而 15:47~15:52 那三段 trace 日志是另一份游戏跑的 —— `ucf_mod.log` 首行写着：

```
15:47:38 log: dir=... mod=D:\BaiduNetdiskDownload\原始\UnityCrossFire1.7.1\UnityCrossFire1.7.1\ucf_mod
```

`原始\` 那份里的 `ucf_mod.dll` 还是 09:46:40 的旧版（含 `editor_rec_tick`，
但**不**含 `hires timer` 字符串），所以测的从来不是新代码。
`tools\deploy.json` 当时也确实指着 `原始\`，但编译产物落在了另一个目录。

验收方式（一眼定性）：`ucf_mod.log` 里没有 `[nav] hires: on ...` 这一行，
就说明跑的是旧 DLL 或者定时器没起来。

## 2. 这次的改法（都在工作区 `06-测试\ucf_mod\src`）

### 2.1 定时器（`navfix.c`）

- 保留 2026-11-24 的按需启停：`rec`/`trace` 开始 `+`1 引用，最后一个停了 `-`1，
  没人用就 `KillTimer`（不白耗 CPU）；`UCF_FREECAM=1` 仍然常驻。
- 周期从 16 ms 改成 **10 ms**（`UCF_HI_PERIOD_MS`，Windows 的 USER_TIMER_MINIMUM，
  再小也没用）。定时器只负责「给机会」，具体采哪一帧由 `editor.c` 的 QPC 闸门定，
  所以机会给得比样本密，档位才有意义。
- 启动时 `timeBeginPeriod(1)`（winmm 动态取地址，不给 `build.ps1` 加 `-lwinmm`）：
  不提精度的话默认 15.6 ms 系统量子，10 ms 定时器实际 ~15.6 ms 一跳。
- **数派发次数**：`g_hiTicks`（`navfix_hires_ticks()`）。「设了定时器」≠「它真的会来」，
  这是这次唯一能自证的指标。
- **自愈**：4 Hz 心跳里加 `navfix_hires_kick()` —— 万一 `acquire()` 比窗口钩子先到
  （`g_hwnd` 还是 0），250 ms 后补一次，不让一次错过的时序变成整场 4 Hz。
- 日志：`hires: on id=0xF3C1 period=10ms timer_res=1 refs=1 freecam=0` /
  `hires: SetTimer FAILED err=...` / `hires: off (ticks=N)`。

### 2.2 采样闸门（`editor.c`）

- `trace_tick()` 加 **25% 提前量**：`if (now + iv*0.25 < g_trNextT) return;`。
  时间表仍是绝对的（`g_trNextT += iv`），平均频率不跑偏；但 60 Hz 档配 60 fps 主循环时
  不会因为 ±1 帧抖动隔帧丢样本。用 `SetTimer(10ms)` + 模拟主循环实测对比：

  | 主循环 | 档位 | 只认「到点」 | 加 25% 提前量 |
  | --- | --- | --- | --- |
  | 60 fps | 30 Hz | 29.3 Hz | **30.3 Hz** |
  | 60 fps | 60 Hz | 51.0 Hz | **55.3 Hz** |
  | 120 fps | 60 Hz | 55.0 Hz | **59.5 Hz** |
  | 75 fps | 60 Hz | 50.0 Hz | **53.7 Hz** |
  | 任意 | 10/20 Hz | 10/20 Hz | 10/20 Hz |

  （表里低档位 +0.3 是 3 s 窗口里 t=0 那一帧算进去的量化误差，不是偏快。）
- `rec_tick()` 同一套提前量（整数毫秒，差 1/4 周期内也算到点）。
- `trace` 的 `end` 行和停止日志多一个 `ticks`（这次采集里定时器派发了几次），
  日志形如：`trace: stop (console) samples=1800 dur=30.0s avg=60.0Hz missed=0 ticks=1812`。
- 实测低于档位 75% 时直接告警（`hz_warn()`）：
  `trace: !!! 采样没跑满：档位 60 Hz，实测 4.0 Hz（定时器派发 0 次 = 0.0/s）...`

### 2.3 控制台（`app/tabs/dev/ucf_trace.py`）

- `starved(sm)`：实测 < 档位 75% 判定「没跑满」；`summary_text()` 末尾追加
  ` · !!! 没跑满档位（只有 7%）：插件采样定时器没起来 —— 确认跑的是新 ucf_mod.dll ...`。
- `summary()` 带上 `ticks`，命令行 `python app\tabs\dev\ucf_trace.py <文件>` 也会打印。

## 4. 怎么验证（用户侧，1 分钟）

1. 关掉游戏，重开（直接从控制台启动，DLL 才会加载新版）。
2. 「开发者选项」选 60 Hz → 开始采集 → 走两秒 → 停止。
3. 看三处：
   - 控制台状态条：`实测 xx Hz（档位 60 Hz）`，不该再是 4.x；
   - `06-测试\ucf_mod\log\ucf_mod.log`：应有
     `[nav] hires: on id=0xF3C1 period=10ms ...` 和 `[edit] trace: stop (...) avg=5x.xHz ... ticks=...`；
   - 轨迹文件最后一行：`{"end":1,...,"ticks":N}`，N ≈ 采样时长×定时器实际频率。
4. 如果还是 4 Hz：先看日志里有没有 `hires: on`。
   - 没有 → 跑的还是旧 DLL：核对游戏目录 `ucf_mod.dll` 的 sha256 是不是上面那个。
   - 有 `hires: on` 但 `ticks` 很小 → 游戏主循环没在泵消息（帧率极低/全屏独占异常），
     日志里的 `!!!` 那行会把档位和实测一起写出来。
