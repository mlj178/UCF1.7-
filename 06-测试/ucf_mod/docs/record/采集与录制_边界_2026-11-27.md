# 采集与录制的边界：一个采样器，两种会话（2026-11-27）

> 用户的问题：「开发调试的原始轨迹采集，还有录制，这两个是不是功能上有冲突？」
> 本文路径统一写成 /（Windows 上是同一个位置）。

结论：**目标不冲突，是上下游；实现冲突，已经收口。** 录制 = 采集 + 后处理（出点图），
采集 = 采集 + 报告（出证据）。现在两件事共用一套采样器、一份格式、一个读取器，
只是「会话类型」不同。

## 1. 两件事到底在做什么

| | 录制（控制台「录制」页） | 原始轨迹采集（「开发者选项」页） |
| --- | --- | --- |
| 给谁用 | 用户 / 人机：画完点图进游戏就能跑 | AI / 离线脚本：找判据、定阈值 |
| 产物 | 点图草稿：节点、双向边、跳链、单向落地边 | jsonl 原始日志（要报告就命令行跑 jump_stats.py） |
| 会不会改数据 | **会**：复盘 →「保存增量」→ 追加进草稿 | **不会**：只读、只出报告 |
| 绑不绑包 | 绑：要选图 + 选包（成品档只读，录不了） | 不绑：大厅、任意图、跨图都能采 |
| 频率 | 30 Hz（玩家） | 10 / 20 / 30 / 60 Hz 可选 |
| 默认采集对象 | 玩家（可选人机，用来看人机实际怎么走） | 玩家（可选人机，用来批量取证） |

一句话：**采集是原料，录制是原料 + 加工。** 所谓「冲突」其实来自三处实现重叠（§2）。

## 2. 以前为什么像冲突（2026-11-27 之前）

| 现象 | 证据（修复前） |
| --- | --- |
| 格式早就合并了，代码没合并 | 录制 v2 起 header 就是 schema=ucf-trace/2，字段和采集一模一样；rec_tick() 和 trace_sample() 几乎逐行相同（hz 闸门、里程、相机兜底、按键、跳结算各一份） |
| 双开会双写双结算 | editor_rec_tick() 每帧跑 rec_tick + rec_bot_tick + trace_tick；同一段路写两个文件、跳结算两个状态机。ucf_navcmd.txt 一次只承载一条命令，所以关控制台必须发 cmd=stopall |
| 人机采集挂错地方 | 「采集玩家、人机的行动数据」里的**人机**长在录制页（采集对象 + rec_bot_tick），真正的采集入口只采玩家、连 who 都没有 |
| 两个解析器互不认识 | ucf_trace.read_full() 只认 kind=="trace" 的 header，所以**录制文件喂给报告工具时 header 会被静默丢掉**；ucf_rec.parse_lines() 会排序去重、ucf_trace 不会 —— 同一份文件两个页面能给出不同的样本数 |

## 3. 现在长什么样

### 3.1 一个采样器（src/editor.c）

    cmd=rec     kind=rec      → 控制台「录制」页，结束复盘成点图
    cmd=trace   kind=trace    → 控制台「开发者选项」页，结束出日志 / 报告

- 两者都进 ss_begin() / ss_tick() / ss_stop()，**同一时刻只有一个写入者**：
  ss_begin() 会先把上一个会话收尾（写 end 行），所以 stopall 只剩兼容旧版控制台的用途。
- 采谁由 who=player|bots|all 决定，**和功能无关**：录制页和采集页都有「采集对象」。
  人机 10 Hz（SS_BOT_HZ），玩家按会话档位。
- 坐标是玩家脚底，g / vy 来自游戏自己的 isGrounded / velData；拿不到玩家对象就退回
  相机 + 眼高估算，header 写 src=camera。
- 跳事件在落地那一帧由插件结算（ev=jump：起跳点、落点、跳距、跳高、滞空、起跳速度、类型），
  两边的分析端都直接读它，不再各猜一次。
- 时间用 QPC；采样闸门保留 25% 提前量（60 Hz 档在 60 fps 主循环下不漏帧）。

### 3.2 一份格式（ucf-trace/3）

第一行 header：

    {"kind":"rec"|"trace","schema":"ucf-trace/3","who":"player|bots|all","hz":30,
     "t0":"2026-11-27 12:00:00","scene":"mp_x","map":"level1","label":"运输船",
     "pack":"...","fp":"...","src":"player",
     "fields":["t","dt","x","y","z","g","vy","sp","ct"],"notes":"...","kind_note":"..."}

- 玩家样本：t,dt,x,y,z,g,vy,sp,ct（键集合 = fields），**不带 k**。**录制和采集写出来的行完全一样**，
  所以录制日志可以直接拿去分析 —— 「忘了开采集」不用重录。
- 人机样本：k="b" + id / spd / j / en / act / tgt / njs / near / pts（10 Hz）。
  同一份 who=all 的日志靠 **玩家行没有 k、人机行有 k="b"** 区分；end 行 `bots` 是累计人机条数。
- 事件：ev=jump / ev=cam（换玩家对象，断段）/ ev=scene（场景名变了）；末行 end。
- 2 版（ucf-trace/2）和 1 版（ucf-trace/1）继续能读：样本行没变，只是 header 少了 who；
  1 版缺 g/vy，按缺省补，报告里标「估算」。

### 3.3 一个读取器（app/core/ucf_sample.py）

- ucf_trace.FIELDS / scan / read_full / read → 薄包装，指向 ucf_sample。
- ucf_rec.parse_lines / parse_events / parse_bots → 同一个实现。
- header 判定改成「有 kind（或 fields）且没有 x」，所以 **kind=rec 的文件也能读出
  header**（以前会被静默丢掉）。人机行不算进「样本数 / 实测 Hz」。

### 3.4 目录按生命周期，不按功能

| 目录 | 谁写 | 进 git | 说明 |
| --- | --- | --- | --- |
| data/maps/_inbox/rec/ | 录制会话 | 否 | 大（30 份约 30 MB），复盘时会被反复读 |
| data/maps/_inbox/trace/ | 采集会话 | 是 | 小，当「跳跃报告的原始证据」 |
| 跳跃报告_*.md | 报告工具 | 是 | 给人看的分析成品 |

命名：录制 <图>_<包>_<时间>.jsonl，采集 <图>_<时间>.jsonl；同一秒重复自动加 _2。

## 4. 控制台里的行为

- **两页都能开**：录制页的「采集对象」是给人机观察用的；采集页的「采集对象」是给批量取证用的。
  底层同一个 who。（原来录制页底部还有一个「人机验证 drive」面板，2026-11-27 已删除。）
  **两页各自记住上次的选择**：录制写 `rec.who`、采集写 `trace.who`，重开控制台各自恢复
  （见 `采集对象记忆_2026-11-27.md`）。两页现在都分开报玩家 / 人机计数；
  录制保存仍只写玩家路点，人机样本只观察（见 `录制_人机区分_2026-11-27.md`）。
- **互相接管**：录制进行中点「开始采集」，会先把那段录制收尾并进复盘（那一段照样能保存）；
  反过来一样。控制台会写一句状态提示，不会静默丢数据。
- **录制日志能直接出报告**：命令行 `python app/tools/data/jump_stats.py <jsonl|目录>`，
  指到 _inbox/rec/ 里的任意 jsonl 就行。
- **控制台只采不分析**（2026-11-27 用户要求）：原来「生成跳跃报告」「选文件出报告」两颗按钮
  是同一个动作的两个入口，已整块删掉；报告工具留在命令行。
- **暂停/继续**只做在录制页（act=pause|resume）；采集页没有这个按钮。

## 7. 已知边界

- 录制页仍**不推断路点**：怎么走、哪里跳由玩家决定；插件只负责原样记录 + 结算跳事件。
- 人机 id 是 Bot 指针，同一次会话内稳定，换图会变。
- src=camera 的日志有系统偏差（绝对高度有常数偏移），报告会标出来。
- 采集页没有「暂停」；需要断点就分成两份会话。
