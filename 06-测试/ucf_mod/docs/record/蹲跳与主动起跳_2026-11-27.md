# 蹲跳被吞 + 主动起跳判据（录制算法）2026-11-27

> 起因：18:02 在风暴录了一段，中间做了个「跳 + 空中蹲」，复盘里那一跳没有跳跃点，
> 空中是两个断开的节点。用户问「是不是录制算法漏了」。
> 结论：**没漏，是判类 + 两条阈值把它扔了，而且扔的时候一声不吭。**

## 1. 这局的真实数据

`data/maps/_inbox/rec/level9_10_Nano30_Storm__20261127-180246.jsonl`：615 个玩家样本 / 20.5 s。

    t=12.50  空格起跳（v0 = 9.5 m/s）
    t=12.54~13.27  空中 23 帧，滞空 0.73 s，跳高 1.925 m
    t=13.07  空中按蹲（ct=1），离落地还有 0.23 s
    t=13.30  落地 (11.813, 9.165, -39.032)，比起点 (4.880, 9.900, -39.055) **低 0.735 m**
    水平 6.93 m，3D 6.97 m

插件结算出来的事件是对的：`{"ev":"jump", a:[4.880,9.900,-39.055], b:[11.813,9.165,-39.032], h:6.933, rise:1.925, air:0.8, v0:9.5, run:8.2, kind:"down"}`。

## 2. 为什么消失（三刀，第三刀还是静默的）

| # | 规则 | 这一跳的下场 |
|---|---|---|
| 1 | 落点比起点低 0.5 m 以上 → `down` | dy = -0.735 → 记成「跳下」 |
| 2 | `down` 要落差 ≥ 2 m 才建单向边 | 0.735 < 2 → **什么都不建** |
| 3 | 跳链窗口 1.5~5.5 m | 6.97 > 5.5 → 就算判对也丢 |

第 2 条最坑：不建边、不写 issues，复盘里一句话都没有，看起来就像「压根没录到」。
这次落盘：+70 点 / +136 边 / **0 跳链**。

## 3. 改了什么

1. **主动起跳判据**（`editor.c jr_line` + `ucf_rec._kind`，两边同一套）：
   `v0 >= 9.0 且 air >= 0.3` → 是「跳」，落点低也按 `gap`，不记 `down`。
   判类顺序：hop（水平 < 0.5）→ mount（高 0.5 以上）→ **gap（主动起跳）** → down（低 0.5 以上）→ gap。
2. **down 落差 < 2 m 不再静默**：照样建 A->B 单向边，issues 里提一句「落差小，嫌多余就删」。
3. **跳事件带蹲**：`"ct":[c0,c1],"ctb":n`
   - `c0` = 空中第一次按蹲（相对起跳秒，-1 = 空中没蹲）
   - `c1` = 空中松开蹲（-1 = 蹲到落地）
   - `ctb` = 起跳那一帧是否已经蹲着
   落盘写进 `jump add` 的第 10~12 列；插件 `nav_load` 读得回来、游戏内保存也写得回去
   （不加这三列的旧文件照旧能用，读出来是 -1 = 未知）。
4. **跳链长度上限取消**：`LINK_MAX = inf`，只保留下限 1.5 m。
   删掉 `long_jump` 开关和「太长 —— 人机用不了」的提示（用户：要实测，别提示）。
5. **净下落的主动跳只留 A->B**：从高处跳下去能走，从低处「走」回高处不成立，不再写反向边。
6. 复盘重算 kind（不信文件里的 `kind`）：老录制是旧插件判的，重跑复盘也能按新规则建链。

## 4. 同一份录像的前后对比

| | 改之前 | 改之后 |
|---|---|---|
| 跳链 | 0 | **1**（6.97 m，只留 A->B） |
| 节点 | 两段断开 | 首尾由这条跳链接上 |
| issues | 无 | 一句「助跑 8.2 m/s，人机不会助跑」（见 §6） |
| jump add | 无 | `jump add 4.880 9.900 -39.055 11.813 9.165 -39.032 0.0 0.5 0 -1.00 -1.00 0` |

最后三个 `-1.00 -1.00 0` 是「老文件没有蹲信息」，不是「没蹲」。**用新 DLL 重录一次才有真值**
（这次应当是 `0.57 -1.00 0`：空中 0.57 s 起蹲，一直蹲到落地）。

### 8.4 这一轮补的：人机蹲跳驱动

`ct` 之前只是「记下来、写进包、日志里打一行」，没有任何代码用它 —— 游戏不会自己蹲。现在接上了：

- 进图 `nav_apply_jumps` 建跳链时，带 `jctb >= 0` 的那条把**起点节点**登记进 `g_cj[]`；
- `crouch_jump_tick()` 每 ~100 ms 扫一遍人机：**已经在空中**（`Player.isGrounded == 0`）
  且 `Bot.nextJumpStartNode` 正是登记的起点 → 把 `Bot.crouchEndTime` 顶到 `Time.time + 0.6`；
- 游戏自己的 `Bot.TryCrouch` 每帧算 `SetCrouchState(crouchEndTime > Time.time)`，于是蹲下。
  **不直接调 `SetCrouchState`**：那会和游戏每帧的判定打架，蹲住不放。
- 开关：`ucf_mod.json` 的 `"bot_crouchjump"`（默认开）。关掉就回到「只记录、不驱动」。

判据里特意加了「还在地面就先不蹲」——蹲着起跳可能跳不起来，等它离地再蹲。

构建：`ucf_mod-20261127-2003-d93ccaa50.dll`，462482 B，
SHA256 `4DC8D7EF1928983BDDB86CDA39E189A562384FA3084A748B50A8AE542C2C4461`。
（19:46 开的游戏占着 `run/build/ucf_mod.dll`，只更新到了 payload；关游戏后要再跑一次 build。）

## 11. 2026-11-27 20:30：加「前导点」让起跳推后（风暴那道缺口）

### 为什么人机在 4.36 就跳

那段台子上只有两个点：`3.400` 和跳链起点 `5.321`。游戏的触发是
`isArriveJumpStartNode` = 「最近节点 == 跳链起点节点」（**指针相等，不是距离**），
而最近节点在相邻两点**中点**就切换：

    中点 = (3.400 + 5.321) / 2 = 4.36

所以人机跑到 4.36 就跳，离起点还差 0.96 m、离台沿还差 ~0.5 m。
玩家是自己按空格，在 4.7~5.3 才跳 —— 这一段的差距到台沿大约是 0.5 m 高度。

### 改了什么（只动数据）

`data/maps/10_Nano30_Storm飓风危城/n0-0000000000000000.txt`（备份 `.bak-lead-20261127-2030`）：

    node add 4.680 9.900 -38.940          ← 新增前导点（3.400 与 5.321 之间，按直线插值）
    edge add 3.400 9.900 -39.056 4.680 9.900 -38.940   （双向，两条）
    edge add 4.680 9.900 -38.940 5.321 9.899 -38.882   （双向，两条）

触发点从 **4.36 → 5.00**（(4.68+5.321)/2），等于晚跳 0.64 m，
按 8.5 m/s、落体 ~10 m/s 算，到对面台沿高约 **0.7 m**。

台沿在 5.32 之后（19:49 那次录制玩家在 5.321 还是站在地上的），所以 5.00 起跳还有 ~0.3 m 余量。

### 校验

`python app/tools/data/check_jumps.py <包>`：路点 193 · 边 354 · 跳链 12；
结构问题（同点 / 缺路点 / 无连线 / 太短）**全 0**。那条 6.73 m 的蹲跳链还在。

### 没做的

- 没删 3.400 ↔ 5.321 的直连边：触发看的是「最近节点」，跟路径无关，留着不影响。
- 没动插件：这是纯数据改动，关掉 `bot_crouchjump` 也照样生效。
