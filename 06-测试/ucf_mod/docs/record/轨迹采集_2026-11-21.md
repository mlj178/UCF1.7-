# 原始轨迹采集：「开发者选项」页的「逐帧样本」采集（2026-11-21）

> 用户要求：在「录制」里加一个采集玩家行动轨迹坐标的功能 —— 频率要能分档，
> 日志名字和位置要显示在控制台里，日志文件夹要有一个快捷打开的按钮；
> 采到的数据直接发给 AI，用它来回答「自动识别到底该用什么数据、什么阈值」。
>
> 本文记录落地实现。**2026-11-21 当日后续调整**：这张卡片从「录制」页搬到了
> 新页签「开发者选项」（页签排最后），见 `开发者选项_2026-11-21.md`；采集流程没变。
>
> 相关：路点录制（重采样成节点/边）见
> `录制模式_2026-11-21.md`；两者共用 `ucf_navcmd.txt` 命令通道，但文件、频率、
> 关闭时机完全独立，可以同时开。

## 1. 它和「录制」的分工

| | 录制（已有） | 原始轨迹采集（新增） |
| --- | --- | --- |
| 目的 | 走一遍 → 生成路点/边，存进测试包 | 把每一帧原样记下来，给离线分析找识别规则 |
| 频率 | 固定 20 Hz | 10 / 20 / 30 / 60 Hz 四档 |
| 落盘 | `dev\vis\rec\<图>_<包>_<时间>.jsonl` | `dev\vis\trace\<图>_<时间>.jsonl` |
| 后处理 | 控制台按 2.5/4/6 m 重采样、识别跳跃/落下/岔路 | 不推断、不重采样；控制台只显示样本数/频率 |
| 写入者 | `editor.c` 的 `rec_tick()` | `editor.c` 的 `trace_tick()` |

为什么要分开：录制的 20 Hz + 重采样是「已经知道要什么」的产物；现在要回答的是
「短跳、蹲跳、上梯、电梯、贴墙卡住、传送」这些边界到底靠哪些信号区分，
所以需要**更高频、更多信号、不做任何推断**的原始数据。

## 2. 控制台怎么用（「开发者选项」页，页签排最后）

卡片：**原始轨迹采集（给 AI 分析用）**

- 频率档位：`10 Hz / 20 Hz / 30 Hz / 60 Hz`（写进 `ucf_mod.json` 的 `trace.hz`）。
  改档位对**下一份**日志生效。
- `开始采集`：先要求游戏在跑（插件只在游戏进程里写文件），然后写一条
  `cmd=trace act=start`，插件立刻建文件；人在大厅时显示「等待进图…」，
  进图后写第一条样本。
- `停止`：写 `act=stop`，插件写 `end` 行并关文件；控制台随后显示摘要
  （样本数 / 时长 / 实测频率 / 里程 / 空格次数 / 空中时间 / Ctrl 时间）。
- `打开日志文件夹`：直接打开 `dev\vis\trace\`。
- `打开日志` / `复制路径`：把当前这份日志用默认程序打开，或把绝对路径放进剪贴板
  （方便直接粘到 AI 对话里）。
- 卡片上常驻两行：**日志文件**（文件名）和 **日志目录**（完整路径）。
- 关控制台时如果采集还在跑，会发一条 `cmd=stopall`，把 rec 和 trace 一起收尾
  （`ucf_navcmd.txt` 只保留最后一条命令，分两次写会丢一条）。

## 3. 日志：目录、命名、档位

- 目录：`06-测试\ucf_mod\navdata\dev\vis\trace\`（和 `vis\rec\` 并排）。
- 命名：`<场景名>_<yyyyMMdd-HHmmss>.jsonl`，例如 `level1_20261121-150000.jsonl`。
  同一秒内重复开始会自动加 `_2`，不覆盖旧文件。
- 档位与体积（一行约 180~220 B）：

  | 档位 | 每小时样本 | 大约体积 |
  | --- | --- | --- |
  | 10 Hz | 3.6 万 | ~7 MB |
  | 20 Hz | 7.2 万 | ~14 MB |
  | 30 Hz | 10.8 万 | ~22 MB |
  | 60 Hz | 21.6 万 | ~43 MB |

  插件定时器是 16 ms，**60 Hz 是物理上限**（实测约 58~62 Hz）；控制台显示的
  「实测 Hz」是从 `t` 反算的，不是档位值。
- 文件不自动清理；确认没用了手动删（和 `vis\rec\` 一样）。

## 4. 数据格式（JSONL，UTF-8）

### 4.1 header（第一行，第一个样本落盘时才写）

```json
{"kind":"trace","schema":"ucf-trace/1","hz":20,
 "t0":"2026-11-21 15:00:00","scene":"mp_transport",
 "map":"level1","label":"运输船",
 "pack":"01_TransportShip运输船/TransportShip_20261121_140112",
 "fp":"n786-57a46e3465c847cb",
 "fields":["t","dt","x","y","z","gy","fx","fy","fz","sp","ct","sh","w","a","s","d"],
 "notes":"t/dt seconds; xyz camera; gy ground under camera (null = no hit); f* camera forward; keys 1/0"}
```

- `t0` 是**第一条样本**的本地墙钟时间；`t` 也从这条样本的 0 开始，
  所以 `t0 + t` 就是真实时间（在大厅等的时间不计入）。
- `scene` 是小地图贴图名（游戏里读到的，可能是空串）；`map`/`label`/`pack`/`fp`
  是控制台选中的图与包（人可能进错图，以 `scene` 为准）。
- `fields` 是字段表本身，`tests/test_trace.py` 用它和 `ucf_trace.FIELDS` 对钉。

### 4.2 样本行（每帧一行）

```json
{"t":0.017,"dt":0.017,"x":1.234,"y":-18.590,"z":-19.218,"gy":-20.140,
 "fx":0.1234,"fy":0.0,"fz":0.9923,"sp":0,"ct":0,"sh":0,"w":1,"a":0,"s":0,"d":0}
```

| 字段 | 含义 | 为什么要它 |
| --- | --- | --- |
| `t` | 相对第一条样本的秒数（QPC，3 位小数） | 60 Hz 下 `GetTickCount64` 的 1 ms 粒度不够 |
| `dt` | 距上一条样本的秒数 | 卡顿/掉帧时判断采样是否连续，不能被当成减速 |
| `x y z` | 相机（玩家眼睛）世界坐标 | 轨迹本身；y 的差分 = 垂直速度 |
| `gy` | 相机正下方 120 m 射线打到的地面高度；没打到 = `null` | 「眼睛离地高度」= `y-gy`：站立 ~1.6、蹲下 ~1.2、跳起 +0.8 |
| `fx fy fz` | 相机前向单位向量 | 朝向；转视角、回头、贴墙都靠它 |
| `sp` | 空格 | 起跳意图（和 `y-gy` 一起判断是「跳」还是「被顶上去」） |
| `ct` | Ctrl | 蹲行意图（和 `y-gy` 一起区分蹲跳/滑铲） |
| `sh` | Shift | 慢走/加速，用来解释速度异常 |
| `w a s d` | 方向键 | 「按键了但没位移」= 贴墙/卡住；「没按键却位移」= 电梯/传送/被推 |

### 4.3 事件行与结束行

```json
{"t":12.345,"ev":"cam"}
{"t":13.001,"ev":"scene","n":"mp_transport"}
{"end":1,"t":42.001,"n":1260,"dist":128.4,"missed":0}
```

- `ev=cam`：相机对象变了（换图 / 重开一局 / 重新载入）。轨迹在这之后断段。
- `ev=scene`：小地图场景名变了（每秒最多查一次），用来对齐「这是哪张图」。
- `end`：`n` 样本数、`dist` 水平里程（单帧 >20 m 不计，避免传送把里程拉爆）、
  `missed` 是调度落后 >0.5 s 的次数（游戏卡顿时会有）。

## 5. 命令协议（ucf_navcmd.txt）

```text
seq=<毫秒>
cmd=trace
pack=01_TransportShip运输船/TransportShip_20261121_140112
fp=n786-57a46e3465c847cb
act=start | stop
out=D:\...\navdata\dev\vis\trace\level1_20261121-150000.jsonl
hz=20
map=level1
label=运输船
```

- `cmd=trace` 不影响当前测试包；`pack`/`fp`/`map`/`label` 只写进 header。
- `cmd=stopall`：一条命令同时收掉 `rec` 和 `trace`（关控制台用）。
- 插件的 `nav_cmd_tick` 每 ~0.25 s 轮询一次；`trace_start` 先 `fopen` 建文件，
  **第一个样本落盘时才写 header**，所以大厅阶段文件是 0 字节，控制台显示「等待进图」。

## 7. 把这批日志发给 AI 时用的提示词（模板）

> 下面是 UnityCrossFire 1.7 的玩家轨迹原始日志（JSONL），采样 20 Hz，
> 字段含义见第一行 header 的 `fields` 和本文档第 4 节。请按运动捕捉数据处理：
>
> 1. 先按 `ev=cam` / `ev=scene` 和 `dt` 把轨迹切成连续段；
> 2. 对每段识别：走路 / 跳跃 / 跳下 / 蹲行 / 蹲跳 / 上梯 / 电梯或升降台 / 传送 / 贴墙卡住 / 静止；
> 3. 每一类给出**可计算的判据**：用哪些字段、时间窗口、阈值区间、要排除哪些干扰
>    （例如楼梯会让 `y` 连续变化，不能用 `y` 的突然变化当跳）；
> 4. 明确指出这份数据里**区分不了**的情况，以及下一版采集应该补什么字段；
> 5. 最后给一张「规则 → 伪代码 → 建议阈值」的表，阈值要和本文件里的实际数值对得上。
>
> 不要臆造没采到的字段；不确定的地方写「需要更多数据」并说明采什么。

配套命令：`python console/ucf_trace.py <日志>` 打印 header + 摘要；
`--csv <out.csv>` 导出 CSV（Excel 能开）。

## 8. 已知边界

- 相机是**眼睛**不是脚；落点/起跳点要靠 `gy` 或离线按 `y-gy` 反推。自由视角/车测的相机
  不跟玩家，采出来的不能当对局轨迹。
- 眼睛离地高度会随地图/角色模型略有差异（蹲下幅度也不完全一样），所以摘要里的
  `eye` 取的是中位数，识别时要用「相对这个中位数」而不是写死 1.6。
- `gy` 只打 120 m，且会打到**脚下最近的可碰撞体**（箱子、斜坡、电梯都算）；空中跨过
  矮墙时 `gy` 会突然换层，这是有用的信号，不要当噪声。
- 按键是 `GetAsyncKeyState` 轮询，短于 16 ms 的极短按键可能漏掉（正常起跳不会）。
- 没有记录血量/死亡/受击；死亡复活会表现为一次大位移（`ev=cam` 不一定触发），
  离线按「>8 m/帧」当传送处理。
