# 武器赋予脚本崩溃问题复盘与最终解决方案

> 项目背景：`UnityCrossFire.exe` IL2CPP 逆向，通过 Frida 注入脚本调用 `GameManager::GiveWeapon` 为玩家赋予武器。

---

## 一、目标复述

**目标**：在游戏进程中，通过 Frida RPC 调用 `GameAssembly.dll` 中的 `GameManager.GiveWeapon(Player player, int weaponIndex, bool autoGiveUp, bool autoSelect)`，实现“通过 ID 给玩家武器”。

**期望行为**：Python UI 发送武器 ID，JS 脚本同步执行函数，立即获得武器。

## 二、踩坑历程与版本演进

| 版本     | 尝试思路                                                     | 核心改动                                              | 结果 / 错误信息                                      |
| -------- | ------------------------------------------------------------ | ----------------------------------------------------- | ---------------------------------------------------- |
| v1-v2    | 直接 `NativeFunction` 调用，MethodInfo 传 `ptr(0)`           | 使用 Il2CppDumper 导出的 RVA 和函数签名               | `access violation accessing 0x8`                     |
| v2-fixed | 认为 MethodInfo 不能为 null，改用 `il2cpp_class_get_method_from_name` 获取有效指针 | 动态获取 `GiveWeapon` 的 `MethodInfo`                 | 依旧 `access violation accessing 0x8`                |
| v3       | 改用 `il2cpp_runtime_invoke`，希望 IL2CPP 运行时能正确处理   | 构造参数指针数组                                      | `access violation accessing 0x1`（指针数组格式错误） |
| v4       | 修正 `il2cpp_runtime_invoke` 参数为指针数组 + 直接调用增加调用约定 `'mscdecl'` | 值类型先分配缓冲区；ABI 改为 `mscdecl`                | 两种方式都 `access violation accessing 0x8`          |
| **v5**   | **识别线程问题，调度到游戏主线程**                           | Hook `ModeBase$$Update`，任务队列 + `send()` 异步通知 | ✅ 成功赋予武器                                       |

## 三、根因分析

### 3.1 为什么一直 `access violation accessing 0x8`？

- IL2CPP 对象内存布局：`[0x0] = Il2CppClass* klass; [0x4] = MonitorData* monitor; [0x8] = 第一个用户字段`
- 访问地址 `0x8` 意味着某个 **对象指针为 `null`**，代码试图访问其第一个字段（`obj + 0x8`），实际访问了地址 `0x8`。
- 这是典型的 **IL2CPP 空引用崩溃**。

### 3.2 为什么获取到的对象会是 null？

从 IDA 反汇编分析 `GiveWeapon` 内部流程：
1. 调用 `GameManager.GetWeapon(weaponIndex)` 获取武器预制体或已存在的武器对象。
2. `GetWeapon` 内部会调用 **`UnityEngine.Object.Instantiate<GameObject>()`** 和 **`GameObject.GetComponent<Weapon>()`**。
3. 这些 Unity API **具有线程亲和性，只能在主线程调用**。

### 3.3 线程问题的证据

- **Frida RPC** 回调运行在 Frida 自己的工作线程，**不是 Unity 主线程**。
- 在非主线程调用 `Instantiate` / `GetComponent` 会导致内部状态异常，返回 null 或无效指针。
- 后续代码访问该 null 指针的成员（偏移 0x8），触发 access violation。

**结论**：调用约定、MethodInfo、RVA 地址、参数格式等均正确，根本矛盾在于 **执行线程不匹配**。

---

## 四、最终解决方案（v5：主线程调度）

### 4.1 设计思路

将 `GiveWeapon` 的调用从 RPC 线程**转移到游戏主线程**执行：

1. **Hook 主线程频繁函数**：`ModeBase$$Update`（RVA `0xAF6A00`，每个逻辑帧在主线程调用）。
2. **任务队列**：RPC 请求到来时，将参数封装成任务推入队列，立即返回任务 ID。
3. **主线程执行**：Hook 的 `onEnter` 回调中，检查队列并取出任务，在主线程上下文中调用 `GiveWeapon`。
4. **异步结果通知**：通过 `send({type: 'giveWeaponResult', ...})` 将结果发回 Python 端。

### 4.2 关键代码片段（JS）

```javascript
// 任务结构
var _pendingTasks = [];

function installMainThreadHook() {
    var updateAddr = Module.findBaseAddress('GameAssembly.dll').add(0xAF6A00);
    Interceptor.attach(updateAddr, {
        onEnter: function(args) {
            while (_pendingTasks.length > 0) {
                var task = _pendingTasks.shift();
                var result = executeGiveWeaponOnMainThread(task.wpnId, task.giveUp, task.select);
                send({ type: 'giveWeaponResult', taskId: task.id, success: result });
            }
        }
    });
}

function giveWeapon(weaponIndex, autoGiveUp, autoSelect) {
    // ... 初始化、获取玩家、MethodInfo 等
    var taskId = ++_taskIdCounter;
    _pendingTasks.push({ id: taskId, wpnId: weaponIndex, giveUp: giveUpInt, select: selectInt });
    return 'pending:' + taskId;
}
```

**`executeGiveWeaponOnMainThread` 内部使用直接 `NativeFunction` 调用或 `il2cpp_runtime_invoke` 均可（因为已处于主线程）。**

## 五、经验与教训

### 5.1 调试技巧

- 在 IL2CPP 逆向中，`access violation accessing 0xN`（N 小）通常是空指针解引用。
- 必须使用 IDA 反汇编分析崩溃函数内部的**调用链**，确认是否涉及 Unity 托管对象操作。
- Frida 提供 `Process.getCurrentThreadId()` 和 Native 函数 `GetCurrentThreadId()` 可对比线程 ID。

### 5.2 关键知识点

| 问题类别                  | 注意事项                                                     |
| ------------------------- | ------------------------------------------------------------ |
| **调用约定**              | Windows x86 IL2CPP 使用 `__cdecl`，Frida 应使用 `'mscdecl'`  |
| **MethodInfo**            | IL2CPP 方法需要有效的 `MethodInfo` 指针，可用 `il2cpp_class_get_method_from_name` 动态获取，但多数静态函数可以传 `ptr(0)` |
| **il2cpp_runtime_invoke** | 参数 `void** params` 必须是指向每个参数值的指针数组，值类型需先分配内存 |
| **线程安全**              | Unity API（Instantiate、GetComponent、Transform 等）**必须主线程调用** |
| **RVA 验证**              | 使用多个来源（`dump.cs`、`script.json`、IDA）交叉验证地址    |

## 八、总结

这次调试的核心教训是：**IL2CPP 逆向不止是函数地址和参数匹配，还必须尊重 Unity 引擎的线程模型**。Frida RPC 的异步特性与 Unity 的主线程独占 API 天然冲突，必须通过 Hook 注入主循环实现调度。今后在类似场景（修改 Transform、实例化对象、调用涉及 GameObject 的方法）时，应第一时间考虑线程亲和性问题，避免在非主线程直接调用，从而节省大量排错时间。


## 1. `access violation accessing 0x8` 是如何解决的？

**崩溃直接原因**：某个对象的指针为 `null`，代码试图访问该对象的第一个字段（偏移 0x8），导致内存访问到地址 `0x8`（无效地址）。

**具体是哪个对象为 null？**  
`GiveWeapon` 内部先调用 `GameManager.GetWeapon(weaponIndex)` 获取一个 `Weapon` 对象。而这个 `GetWeapon` 方法内部会使用 Unity 引擎的 `Object.Instantiate`、`GetComponent` 等 API 来创建或查找武器对象。这些 API **必须在 Unity 主线程中调用**。

**为什么会在非主线程？**  
Frida 的 `rpc.exports` 函数是在 Frida 自己的工作线程中被调用的，不是 Unity 的主线程。

**所以**：从非主线程调用 `Instantiate`/`GetComponent` 导致 `GetWeapon` 返回了 `null`（或无效指针），后续代码访问 `null` 对象的成员 → 崩溃在 `0x8`。

**解决方案**：  
不再直接从 RPC 线程调用 `GiveWeapon`，而是改为**在游戏主线程上执行**。具体做法：

- Hook 了 `ModeBase.Update`（每帧都在主线程调用）。
- RPC 调用到来时，只把任务参数放入队列，然后立刻返回。
- 当 `Update` 触发时，在 Hook 回调中（主线程）取出任务并真正执行 `GiveWeapon`。
- 执行结果通过 `send()` 异步通知 Python 端。

这样 `GiveWeapon` 就运行在正确的线程中，`GetWeapon` 能正常返回武器对象，不再有空引用，崩溃解决。

## 2. 调用约定、MethodInfo、RVA、参数格式 分别参考什么？

### RVA 地址
**主要参考 `script.json`（Il2CppDumper 输出）**，其中记录的 `Address` 字段是相对于 `GameAssembly.dll` 基址的偏移，这是最准确的。  
也可以用 IDA 反汇编确认，但 IDA 中的地址与 `script.json` 是一致的（IDB 加载时已重定位）。  
`dump.cs` 中也会给出 `RVA` 属性值，可与 `script.json` 交叉验证。

### 调用约定
**只能从 IDA 反汇编中确认**。  
IDA 会在函数开头或结尾标注调用约定（如 `__cdecl`、`__stdcall`）。  
`dump.cs` 只有 C# 层签名，不包含底层调用约定信息。  
Windows 下 IL2CPP 的函数几乎都是 `__cdecl`，在 Frida 里对应 `'mscdecl'`。

### 参数格式
**结合 `dump.cs` 和 IDA**：
- `dump.cs` 给出参数类型（`Player`、`int`、`bool` 等），能判断是引用类型还是值类型。
- IDA 可以看清栈上参数布局、每个参数占多少字节（例如 `bool` 实际传递时通常占 4 字节）。
- 对于值类型（如 `int`、`bool`），在使用 `il2cpp_runtime_invoke` 时需要先分配内存，再把指针放入参数数组；引用类型（如 `Player`）直接传指针。
- 如果不使用 `il2cpp_runtime_invoke` 而用 `NativeFunction` 直接调用，则按 IDA 中看到的参数大小和顺序直接传值即可。

### MethodInfo 是什么？有什么作用？为什么需要？

**MethodInfo** 是 IL2CPP 运行时中一个方法的**元数据对象**，包含方法的名称、参数类型、返回类型、所在类等信息。  
在 IL2CPP 里，每个托管方法都有对应的 `MethodInfo` 结构体。

**作用**：主要用于**反射调用**（即 `il2cpp_runtime_invoke`）。  
`il2cpp_runtime_invoke` 的函数签名是：
```c
void* il2cpp_runtime_invoke(MethodInfo* method, void* obj, void** params, Il2CppException** exc);
```
它需要 `MethodInfo` 来知道该怎么解释参数、如何执行方法。

**为什么我们需要它？**  
虽然直接用 `NativeFunction` 调用不需要 `MethodInfo`（我们把函数地址强转成函数指针直接调用），但在我们的调试过程中：
- 早期我们试过 `il2cpp_runtime_invoke`，所以必须获取 `MethodInfo`。
- 即使最后用了直接 `NativeFunction` 调用，某些 IL2CPP 函数内部可能会访问自身的 `MethodInfo`（例如用于泛型方法、安全检查或日志），传 `ptr(0)` 可能导致内部崩溃。所以我们主动通过 `il2cpp_class_get_method_from_name` 获取了有效的 `MethodInfo`，并在直接调用时作为最后一个参数传入，这样更安全。

**如何获取**：使用 IL2CPP 导出的 `il2cpp_class_get_method_from_name` 函数，传入类指针、方法名字符串、参数个数，就能得到 `MethodInfo` 指针。

---

**总结**：
- RVA 地址 → 看 `script.json`（Il2CppDumper）
- 调用约定 → 看 IDA 反汇编
- 参数格式 → 综合 `dump.cs`（类型）和 IDA（内存布局）
- MethodInfo → 需要时通过 IL2CPP API 动态获取，用于反射调用或防止内部崩溃

## 1. IL2CPP API 与 Frida 直接调用对 MethodInfo 的需求区别

**Frida 直接调用（NativeFunction）**  
- 原理：Frida 将目标函数地址包装成一个可调用的 JavaScript 函数，使用 `NativeFunction(addr, retType, argTypes, abi)`。
- 调用过程：直接跳转到该地址，按照指定的调用约定传递参数，执行机器码。
- 对 `MethodInfo` 的需求：**通常不需要**。因为你只是调用一段已经编译好的原生函数，就像调用普通 C 函数一样，不需要运行时元数据。  
- 例外情况：有些 IL2CPP 函数内部可能会主动读取自己的 `MethodInfo`（例如用于堆栈跟踪、异常处理或某些安全检查），这时如果传入 `null` 就可能导致内部崩溃。但大多数情况下 `null` 也能工作。

**IL2CPP 反射 API（il2cpp_runtime_invoke）**  
- 原理：它是 IL2CPP 运行时提供的通用方法调用入口，类似于 .NET 的 `MethodBase.Invoke()`。
- 调用过程：运行时根据 `MethodInfo` 去解析参数类型、进行值类型装箱/拆箱、调用实际的托管方法、处理异常等。
- 对 `MethodInfo` 的需求：**必须提供**，因为它是描述方法的元数据，没有它反射调用无法工作。

**简单总结**：  
- 直接调用底层函数地址 → 可以不用 `MethodInfo`（传 `null` 通常 OK）。  
- 通过 IL2CPP 运行时反射调用 → 必须要有有效的 `MethodInfo`。

在我们的方案中，虽然最终采用了主线程 + 直接调用，但为了安全（避免内部访问崩溃），仍然动态获取了有效的 `MethodInfo` 并传入。

## 2. 调用约定（Calling Convention）详解

### 是什么？
调用约定是**函数调用时，调用者和被调用者之间关于如何传递参数、如何返回结果、谁来清理栈的约定**。不同的编译器、平台、ABI 有不同的默认约定。

### 为什么需要它？
如果不指定正确的调用约定，Frida 在生成调用代码时会用错误的方式传递参数或清理栈，导致：
- 参数值被放在错误的位置（寄存器/栈偏移不对），函数读到的是垃圾值。
- 栈指针在函数返回后未能正确恢复，后续代码直接崩溃。
- 非法内存访问（如 access violation）。

### 常见调用约定（Windows x86）

| 约定 | 参数传递 | 栈清理者 | 备注 |
|------|----------|----------|------|
| `__cdecl` | 全部压栈（从右到左） | 调用者 | C/C++ 默认，支持可变参数 |
| `__stdcall` | 全部压栈（从右到左） | 被调用者 | Win32 API 常用 |
| `__fastcall` | 前两个 DWORD 用 ECX/EDX，其余压栈 | 被调用者 | 性能优化 |
| `__thiscall` | this 指针用 ECX，其余压栈 | 被调用者 | C++ 成员函数 |

在 **IL2CPP（Windows）** 中，编译后的原生函数几乎都采用 **`__cdecl`**，因为它是统一生成代码的默认选择。

Frida 在 Windows 平台上的 ABI 名称：  
- `'mscdecl'` → 对应 `__cdecl`  
- `'stdcall'` → 对应 `__stdcall`

如果代码里写错（比如写 `'cdecl'` 而不是 `'mscdecl'`），Frida 会抛出 `invalid abi specified`。

### 在游戏修改器开发中的注意事项

1. **优先确认目标函数的调用约定**  
   使用 IDA 查看函数的开头或结尾注解（如 `; __cdecl`）。如果没有标注，可以通过函数末尾是否有 `retn 4` 等来推断（`retn N` 通常表示被调用者清理栈，即 `__stdcall`）。

2. **Frida 默认约定不可靠**  
   不同平台 Frida 的默认调用约定不同（Unix 默认 `cdecl`，Windows 默认 `stdcall`），不要依赖默认，**永远显式指定 ABI**。

3. **值类型参数的大小要匹配**  
   例如 `bool` 在 IL2CPP 中传递时通常占 4 字节（栈对齐），虽然 C# 中是 1 字节。通过 IDA 的 `push` / `[esp+...]` 可确认。错误的大小会导致后续参数全部错位。

4. **64 位与 32 位区别**  
   x64 下 Windows 统一使用 `Microsoft x64 calling convention`（前4个参数用 RCX/RDX/R8/R9，其余压栈），这时 Frida 应使用 `'win64'` ABI。

5. **测试验证**  
   如果出现 `access violation` 但地址不是 0x8 这类明显空指针，很可能是调用约定或参数大小错误导致栈被破坏。可以通过比较 Frida 调用前后的栈指针或参数值来诊断。

---

## 3. 综合经验总结

- **MethodInfo**：是 IL2CPP 反射调用的必需品；直接 NativeFunction 调用通常不需要，但为了安全可以传入有效值。
- **调用约定**：是 Frida 和原生函数之间的“通信协议”，必须显式指定为 `'mscdecl'`（Windows IL2CPP），否则参数错位、栈崩溃。
- **开发流程**：  
  1. 从 `script.json`/`dump.cs` 获取 RVA 和 C# 层签名。  
  2. 用 IDA 确认调用约定、参数个数与尺寸、获取 MethodInfo 的方式。  
  3. 在 Frida 中创建 `NativeFunction` 时指定正确的 `retType`、`argTypes`、`abi`。  
  4. 优先在主线程执行涉及 Unity 引擎 API 的调用，避免线程冲突。

这样就能避免绝大多数因元数据或 ABI 不匹配导致的崩溃。
