# 武器赋予脚本崩溃问题复盘与最终解决方案

> 项目背景：`UnityCrossFire.exe` IL2CPP 逆向，通过 Frida 注入脚本调用 `GameManager::GiveWeapon` 为玩家赋予武器。

---

## 一、目标复述

**目标**：在游戏进程中，通过 Frida RPC 调用 `GameAssembly.dll` 中的 `GameManager.GiveWeapon(Player player, int weaponIndex, bool autoGiveUp, bool autoSelect)`，实现“通过 ID 给玩家武器”。

**期望行为**：Python UI 发送武器 ID，JS 脚本同步执行函数，立即获得武器。

---

## 二、踩坑历程与版本演进

| 版本     | 尝试思路                                                     | 核心改动                                              | 结果 / 错误信息                                      |
| -------- | ------------------------------------------------------------ | ----------------------------------------------------- | ---------------------------------------------------- |
| v1-v2    | 直接 `NativeFunction` 调用，MethodInfo 传 `ptr(0)`           | 使用 Il2CppDumper 导出的 RVA 和函数签名               | `access violation accessing 0x8`                     |
| v2-fixed | 认为 MethodInfo 不能为 null，改用 `il2cpp_class_get_method_from_name` 获取有效指针 | 动态获取 `GiveWeapon` 的 `MethodInfo`                 | 依旧 `access violation accessing 0x8`                |
| v3       | 改用 `il2cpp_runtime_invoke`，希望 IL2CPP 运行时能正确处理   | 构造参数指针数组                                      | `access violation accessing 0x1`（指针数组格式错误） |
| v4       | 修正 `il2cpp_runtime_invoke` 参数为指针数组 + 直接调用增加调用约定 `'mscdecl'` | 值类型先分配缓冲区；ABI 改为 `mscdecl`                | 两种方式都 `access violation accessing 0x8`          |
| **v5**   | **识别线程问题，调度到游戏主线程**                           | Hook `ModeBase$$Update`，任务队列 + `send()` 异步通知 | ✅ 成功赋予武器                                       |

## 三、根因分析

### 3.1 为什么一直 `access violation accessing 0x8`？

- IL2CPP 对象内存布局：`[0x0] = Il2CppClass* klass; [0x4] = MonitorData* monitor; [0x8] = 第一个用户字段`
- 访问地址 `0x8` 意味着某个 **对象指针为 `null`**，代码试图访问其第一个字段（`obj + 0x8`），实际访问了地址 `0x8`。
- 这是典型的 **IL2CPP 空引用崩溃**。

### 3.2 为什么获取到的对象会是 null？

从 IDA 反汇编分析 `GiveWeapon` 内部流程：
1. 调用 `GameManager.GetWeapon(weaponIndex)` 获取武器预制体或已存在的武器对象。
2. `GetWeapon` 内部会调用 **`UnityEngine.Object.Instantiate<GameObject>()`** 和 **`GameObject.GetComponent<Weapon>()`**。
3. 这些 Unity API **具有线程亲和性，只能在主线程调用**。

### 3.3 线程问题的证据

- **Frida RPC** 回调运行在 Frida 自己的工作线程，**不是 Unity 主线程**。
- 在非主线程调用 `Instantiate` / `GetComponent` 会导致内部状态异常，返回 null 或无效指针。
- 后续代码访问该 null 指针的成员（偏移 0x8），触发 access violation。

**结论**：调用约定、MethodInfo、RVA 地址、参数格式等均正确，根本矛盾在于 **执行线程不匹配**。

## 四、最终解决方案（v5：主线程调度）

### 4.1 设计思路

将 `GiveWeapon` 的调用从 RPC 线程**转移到游戏主线程**执行：

1. **Hook 主线程频繁函数**：`ModeBase$$Update`（RVA `0xAF6A00`，每个逻辑帧在主线程调用）。
2. **任务队列**：RPC 请求到来时，将参数封装成任务推入队列，立即返回任务 ID。
3. **主线程执行**：Hook 的 `onEnter` 回调中，检查队列并取出任务，在主线程上下文中调用 `GiveWeapon`。
4. **异步结果通知**：通过 `send({type: 'giveWeaponResult', ...})` 将结果发回 Python 端。

### 4.2 关键代码片段（JS）

```javascript
// 任务结构
var _pendingTasks = [];

function installMainThreadHook() {
    var updateAddr = Module.findBaseAddress('GameAssembly.dll').add(0xAF6A00);
    Interceptor.attach(updateAddr, {
        onEnter: function(args) {
            while (_pendingTasks.length > 0) {
                var task = _pendingTasks.shift();
                var result = executeGiveWeaponOnMainThread(task.wpnId, task.giveUp, task.select);
                send({ type: 'giveWeaponResult', taskId: task.id, success: result });
            }
        }
    });
}

function giveWeapon(weaponIndex, autoGiveUp, autoSelect) {
    // ... 初始化、获取玩家、MethodInfo 等
    var taskId = ++_taskIdCounter;
    _pendingTasks.push({ id: taskId, wpnId: weaponIndex, giveUp: giveUpInt, select: selectInt });
    return 'pending:' + taskId;
}
```

**`executeGiveWeaponOnMainThread` 内部使用直接 `NativeFunction` 调用或 `il2cpp_runtime_invoke` 均可（因为已处于主线程）。**

### 4.3 Python 端适配

- `on_message` 监听 `giveWeaponResult` 消息，根据 `taskId` 显示结果。
- RPC 调用 `giveWeapon` 返回值是 `pending:taskId`，UI 可提示“任务已提交，等待主线程执行”。

## 五、经验与教训

### 5.1 调试技巧

- 在 IL2CPP 逆向中，`access violation accessing 0xN`（N 小）通常是空指针解引用。
- 必须使用 IDA 反汇编分析崩溃函数内部的调用链，确认是否涉及 Unity 托管对象操作。
- Frida 提供 `Process.getCurrentThreadId()` 和 Native 函数 `GetCurrentThreadId()` 可对比线程 ID。

### 5.2 关键知识点

| 问题类别                  | 注意事项                                                     |
| ------------------------- | ------------------------------------------------------------ |
| **调用约定**              | Windows x86 IL2CPP 使用 `__cdecl`，Frida 应使用 `'mscdecl'`  |
| **MethodInfo**            | IL2CPP 方法需要有效的 `MethodInfo` 指针，可用 `il2cpp_class_get_method_from_name` 动态获取，但多数静态函数可以传 `ptr(0)` |
| **il2cpp_runtime_invoke** | 参数 `void** params` 必须是指向每个参数值的指针数组，值类型需先分配内存 |
| **线程安全**              | Unity API（Instantiate、GetComponent、Transform 等）**必须主线程调用** |
| **RVA 验证**              | 使用多个来源（`dump.cs`、`script.json`、IDA）交叉验证地址    |

## 六、可能再次遇到的问题及预案

| 潜在问题                      | 可能原因                                                  | 解决方案                                                     |
| ----------------------------- | --------------------------------------------------------- | ------------------------------------------------------------ |
| Hook 未执行 / 任务不消费      | `ModeBase` 不是一直活跃的类，或游戏状态切换时 Update 暂停 | 1. 额外 Hook `UnityEngine.Object.DontDestroyOnLoad` 或更底层的 Unity 主循环 `PlayerLoop`。<br>2. 设置超时重试机制。 |
| 任务执行太慢或堆积            | Update 帧率低，处理大量任务导致卡顿                       | 限制每帧处理的任务数量（如每帧最多1个）。                    |
| `send()` 消息没被 Python 收到 | Python 端 `on_message` 未正确处理                         | 确保 `script.on('message', on_message)` 在脚本加载后立即绑定。 |
| 武器赋予后游戏崩溃            | 武器 ID 无效或玩家状态异常                                | 增加武器 ID 有效性检查（如从字典查询），捕获 C# 异常（通过 `il2cpp_runtime_invoke` 的 `exc` 参数）。 |
| 游戏更新后 RVA 变化           | DLL 重编译                                                | 使用特征码扫描或重新 dump，自动化更新偏移。                  |

## 八、总结

这次调试的核心教训是：**IL2CPP 逆向不止是函数地址和参数匹配，还必须尊重 Unity 引擎的线程模型**。Frida RPC 的异步特性与 Unity 的主线程独占 API 天然冲突，必须通过 Hook 注入主循环实现调度。今后在类似场景（修改 Transform、实例化对象、调用涉及 GameObject 的方法）时，应第一时间考虑线程亲和性问题，避免在非主线程直接调用，从而节省大量排错时间。
