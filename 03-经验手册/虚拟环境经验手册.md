# Python 虚拟环境经验手册

> 适用对象：刚接触 Python 虚拟环境的开发者，以及负责依赖管理、测试和打包的项目维护者。  
> 本文先解释通用原理，再结合本项目的 `.venv-build` 构建环境总结可复用经验。

## 1. 一句话理解虚拟环境

虚拟环境是一个项目专用的 Python 运行和依赖目录。

它让项目使用自己确定的 Python 解释器入口和第三方包，而不是直接依赖电脑中杂乱、随时可能变化的全局 Python 环境。

虚拟环境主要隔离：

- 通过 `pip` 安装的第三方 Python 包。
- 包的具体版本。
- `python`、`pip`、`pyinstaller` 等命令所指向的执行环境。
- 当前项目的依赖集合。

虚拟环境不会自动隔离：

- Windows 系统版本和系统组件。
- 显卡驱动、VC++ 运行库等系统级依赖。
- 项目源码、资源文件和配置文件。
- Python 基础解释器本身。创建虚拟环境的基础 Python 被删除后，原环境可能失效。
- 不同 CPU 架构。64 位 Python 创建的是 64 位环境。

因此，虚拟环境解决的是“Python 依赖环境一致性”，不是完整的操作系统虚拟化。

## 2. 虚拟环境由什么组成

Windows 下使用以下命令创建环境：

```powershell
py -3.12 -m venv .venv
```

常见结构如下：

```text
.venv/
├─ Include/
├─ Lib/
│  └─ site-packages/       # 第三方包安装位置
├─ Scripts/
│  ├─ python.exe           # 当前环境的 Python 入口
│  ├─ pip.exe
│  └─ pyinstaller.exe
└─ pyvenv.cfg              # 基础 Python 路径和环境配置
```

可以把它理解为下面这组关系：

```text
基础 Python
    ↓ 创建
虚拟环境 Python + 独立第三方包
    ↓ 运行
项目源码 / 测试 / 打包工具
    ↑ 依赖版本来源
requirements*.txt
```

其中：

- 虚拟环境保存“当前已经安装了什么”。
- `requirements*.txt` 保存“这个环境应当安装什么”。
- 前者是可重建的临时产物，后者才是应长期保存的项目依据。

## 3. 虚拟环境对本项目的作用

### 3.1 固定正式打包所用的工具

本项目使用 PyInstaller 将 Python 程序打包为 EXE。PyInstaller 会分析当前解释器环境中的模块、钩子和二进制扩展。

如果直接使用全局 Python 打包，全局环境中多装的包、旧版本包或测试包都可能影响分析结果。即使源码完全相同，两台电脑或两次打包也可能产生不同内容。

使用专用构建环境后，可以明确指定：

```powershell
& $buildPython -m PyInstaller --clean --noconfirm game_modifier.spec
```

这比仅输入 `pyinstaller` 更可靠，因为命令已经明确绑定到指定的 Python 环境。

### 3.2 防止全局包污染打包结果

本项目曾出现 EXE 启动时提示：

```text
Failed to extract PILavif.cp312-win_amd64.pyd:
decompression resulted in return code -1
```

这类报错发生在 PyInstaller 单文件程序解压内置文件阶段。它不等于“对方缺少 Python 包”，因为 Python 包已经被打入 EXE。

如果打包环境意外安装了项目并不需要的 `PILavif`，PyInstaller 可能把相应二进制扩展一起收集。专用虚拟环境配合受控依赖清单，可以减少无关包混入成品的风险。

需要注意：虚拟环境只能控制打包输入。成品损坏、杀毒软件拦截、磁盘或临时目录异常，也可能造成解压失败，仍需根据现场证据分别排查。

### 3.3 固定依赖版本

本项目各版本目录中的 `requirements-build.txt` 使用精确版本，例如：

```text
Pillow==12.1.1
PyInstaller==6.20.0
```

精确版本能够避免“今天安装到新版本，明天打包结果发生变化”。如果要升级，应主动修改清单、重建或更新环境，并重新完成正式版验证。

### 3.4 服务连续版本开发

本项目当前采用以下布局：

```text
04-正式发行版/
├─ .venv-build/                         # 共用的正式构建环境
├─ .gitignore
├─ 全功能整合包x.x/
│  └─ game_modifier/
│     ├─ requirements-build.txt         # 该版本的依赖依据
│     ├─ game_modifier.spec
│     └─ ...
└─ 虚拟环境经验手册.md
```

这样安排的目的：

- `.venv-build` 不跟随每个版本重复复制，节省磁盘空间和安装时间。
- 每个版本仍保留自己的依赖清单，能够表达该版本需要什么。
- 开发新版本时，可以继续使用同一个构建环境，但必须先按新版本的依赖清单校准。

共用环境只是本项目同一产品连续版本的工程选择，不代表无关项目也应该共用一个环境。

## 4. 主要优点

### 4.1 环境隔离

项目 A 安装 Pillow 12，不会迫使项目 B 放弃它需要的其他版本。不同项目之间的依赖冲突被限制在各自环境内。

### 4.2 可重复构建

基础 Python 版本、依赖清单和打包配置均固定时，更容易在以后重建接近一致的打包环境。

### 4.3 降低“我的电脑能运行”问题

开发者不再依赖自己全局环境中偶然存在的包。缺少依赖时，问题会更早暴露在环境安装或测试阶段。

### 4.4 便于排错

可以直接回答以下问题：

- 实际使用的是哪个 Python？
- 包安装到了哪里？
- PyInstaller 是哪个版本？
- 是否存在依赖冲突？
- 是否混入了清单之外的包？

### 4.5 便于清理和重建

环境损坏时，不必修补全局 Python。删除明确的虚拟环境目录并根据依赖清单重建即可。

### 4.6 减少重复工作

对于依赖兼容的连续版本，共用构建环境可以省去每个版本重新下载和安装全部依赖的时间。

它主要节省安装时间和磁盘空间，并不会直接减少 AI 对话的 Token。真正能够减少后续沟通成本的是清晰的文档、依赖清单和自动化命令。

## 5. 局限和容易产生的误解

### 5.1 虚拟环境不是发布成品

不要把 `.venv` 或 `.venv-build` 复制给最终用户，也不要将它放进发布压缩包。

对于本项目，交付的是打包后的 EXE 和所需资源，不是开发环境。

### 5.2 虚拟环境不是完整备份

仅保存虚拟环境目录并不能代替以下内容：

- 源码版本。
- `requirements-build.txt`。
- `.spec` 打包配置。
- Python 版本记录。
- 构建和验证说明。

### 5.3 激活环境不是必须步骤

激活的本质是临时修改当前终端的命令搜索路径。以下写法可以使用：

```powershell
.\.venv\Scripts\Activate.ps1
python -m pip check
```

但在正式打包或自动化流程中，更推荐显式调用解释器：

```powershell
& '.\.venv\Scripts\python.exe' -m pip check
```

显式路径不依赖终端是否已经激活，更不容易误用全局 Python。

### 5.4 共用环境可能产生版本残留

环境先服务旧版本、再服务新版本时，单纯执行：

```powershell
python -m pip install -r requirements-build.txt
```

会安装或调整清单中列出的包，但不会保证自动删除所有已经不再需要的旧包。

因此，正式发布前应检查实际包集合；当版本依赖变化较大或出现可疑残留时，直接重建环境最稳妥。

## 6. 本项目标准使用流程

以下命令假定当前终端位于目标版本的：

```text
全功能整合包x.x\game_modifier
```

版本号不写死，由当前文件夹位置自然确定。

### 6.1 定位共享构建环境

```powershell
$projectDir = (Get-Location).Path
$releaseRoot = Split-Path -Parent (Split-Path -Parent $projectDir)
$buildEnv = Join-Path $releaseRoot '.venv-build'
$buildPython = Join-Path $buildEnv 'Scripts\python.exe'
$requirementsFile = Join-Path $projectDir 'requirements-build.txt'
```

### 6.2 首次创建

```powershell
if (-not (Test-Path -LiteralPath $buildPython -PathType Leaf)) {
    py -3.12 -m venv $buildEnv
}
```

创建前应确认：

- 使用项目要求的 Python 版本。
- Python 位数符合项目要求，本项目为 Windows x64。
- 目录位置明确，不放入某个具体版本目录。

### 6.3 安装或校准依赖

```powershell
& $buildPython -m pip install --upgrade pip
& $buildPython -m pip install -r $requirementsFile
& $buildPython -m pip check
```

`pip check` 输出：

```text
No broken requirements found.
```

表示已安装包之间没有发现声明层面的依赖冲突，但它不能代替程序测试和 EXE 实机测试。

### 6.4 核对实际解释器

```powershell
& $buildPython -c "import sys; print(sys.version); print(sys.executable); print(sys.prefix); print(sys.base_prefix)"
```

重点检查：

- `sys.executable` 是否指向 `04-正式发行版\.venv-build\Scripts\python.exe`。
- `sys.prefix` 是否是 `.venv-build`。
- `sys.base_prefix` 是否指向创建环境时使用的基础 Python。

也可以核对工具版本：

```powershell
& $buildPython -m PyInstaller --version
& $buildPython -m pip list
```

### 6.5 正式打包

```powershell
& $buildPython -m PyInstaller --clean --noconfirm game_modifier.spec
```

正式版还应执行项目自己的发布前检查，包括：

- 确认使用正式版配置，而不是测试版配置。
- 检查调试日志开关是否关闭。
- 检查是否存在意外收集的第三方包或二进制扩展。
- 清理旧的 `build`、`dist` 或项目规定的构建输出后再打包。
- 在本机以外的干净环境验证 EXE。

### 6.6 切换到新的版本目录

进入新的 `全功能整合包x.x\game_modifier` 后，重新执行“定位环境”和“安装或校准依赖”步骤。

如果新旧版本的 Python 版本或依赖变化较大，建议重建 `.venv-build`，不要在旧环境上反复修补。

## 7. 依赖清单的管理原则

### 7.1 环境和清单各自负责什么

| 内容 | 是否提交版本管理 | 作用 |
|---|---:|---|
| `.venv-build/` | 否 | 本机可重建的构建环境 |
| `requirements-build.txt` | 是 | 正式构建依赖及版本依据 |
| `game_modifier.spec` | 是 | PyInstaller 收集和输出规则 |
| 构建说明文档 | 是 | 记录创建、验证和发布流程 |
| `build/`、`dist/` | 按项目规则 | 临时构建产物或交付产物 |

### 7.2 为什么要固定版本

正式发布项目推荐使用：

```text
package-name==确定版本
```

不建议正式构建长期依赖：

```text
package-name
package-name>=某版本
```

因为后两种写法会让不同时间安装到不同版本，降低可复现性。

### 7.3 修改依赖后的流程

1. 修改目标版本的 `requirements-build.txt`。
2. 在干净环境中安装。
3. 运行 `pip check`。
4. 运行源码测试。
5. 重新打包正式版。
6. 在干净电脑或虚拟机中测试 EXE。
7. 记录升级原因和验证结果。

不要先在环境中随意升级，最后才尝试猜测依赖清单应该写什么。

## 8. 重要经验：不要直接移动或复制 Windows 虚拟环境

### 8.1 本项目遇到的实际情况

本项目最初将 `.venv-build` 放在具体版本目录内。为了供后续版本复用，将目录移动到 `04-正式发行版` 根目录后发现：

- 环境内部分启动程序仍引用旧位置。
- `pip.exe`、`pyinstaller.exe` 等入口可能因旧绝对路径失效。
- 仅看到目录和包都还存在，不能证明环境可正常使用。

最终采用的可靠处理方式是在目标位置重新创建环境，再根据 `requirements-build.txt` 安装依赖并验证。

### 8.2 正确迁移方式

不要把旧环境目录当作普通资料直接搬家。正确流程是：

1. 确认依赖清单已经完整保存。
2. 在新位置创建新的虚拟环境。
3. 使用新环境的 Python 安装依赖。
4. 运行 `pip check`、测试和打包验证。
5. 确认新环境正常后，再处理旧环境。

通用示例：

```powershell
$newEnv = 'D:\projects\my-project\.venv'
py -3.12 -m venv $newEnv
& (Join-Path $newEnv 'Scripts\python.exe') -m pip install -r 'D:\projects\my-project\requirements.txt'
& (Join-Path $newEnv 'Scripts\python.exe') -m pip check
```

### 8.3 为什么“复制后暂时能用”仍不可靠

虚拟环境的配置文件、脚本和工具入口可能记录：

- 原基础 Python 的位置。
- 原虚拟环境的绝对路径。
- 创建环境时的 Python 版本。

部分功能能运行，只说明尚未触发失效入口，不能证明整个环境可迁移。

结论：**复制源码和依赖清单，重建虚拟环境；不要把虚拟环境本身作为可移植资产。**

## 9. 常见问题与排查

### 9.1 输入 `python` 后使用了错误环境

检查：

```powershell
Get-Command python
python -c "import sys; print(sys.executable)"
```

处理原则：正式命令直接使用虚拟环境中 `Scripts\python.exe` 的完整或已确认路径。

### 9.2 `pip` 安装到了全局 Python

容易出错的写法：

```powershell
pip install package-name
```

推荐写法：

```powershell
& $buildPython -m pip install package-name
```

`python -m pip` 能明确说明“使用哪个 Python，就给哪个 Python 安装包”。

### 9.3 `pip check` 正常，但程序仍不能运行

`pip check` 只检查已安装 Python 包声明的依赖关系。继续检查：

- 项目源码是否有运行时错误。
- 系统级 DLL 或运行库是否缺失。
- Python、包和系统的位数是否一致。
- 资源文件是否遗漏。
- PyInstaller 的隐藏导入、数据文件和二进制文件是否配置正确。
- 杀毒软件是否拦截或隔离文件。

### 9.4 打包结果混入不需要的包

检查环境中实际安装的内容：

```powershell
& $buildPython -m pip list
& $buildPython -m pip freeze
```

再检查 PyInstaller 构建警告、依赖分析结果和 `.spec` 配置。

如果环境来源不明或长期反复升级，优先根据依赖清单重建，而不是逐个猜测应该卸载哪些包。

### 9.5 环境损坏或工具仍指向旧路径

检查：

```powershell
& $buildPython -c "import sys; print(sys.executable); print(sys.prefix)"
& $buildPython -m pip --version
& $buildPython -m PyInstaller --version
```

只要仍出现旧目录、旧基础 Python 或入口无法启动，就应重建环境。

### 9.6 更换或删除了基础 Python

虚拟环境依赖创建它的基础 Python。升级 Python 的补丁版本后环境有时仍能工作，但正式构建不应依赖“看起来可以”。

处理原则：安装项目要求的基础 Python，重新创建虚拟环境并完成全套验证。

## 10. 什么时候应该重建环境

遇到以下任一情况，建议重建：

- 虚拟环境被移动、复制或改名。
- Python 主版本或次版本变化，例如从 3.11 改到 3.12。
- Python 位数或处理器架构变化。
- 依赖清单发生较大调整。
- 环境长期被手动安装、升级、卸载，实际状态难以说明。
- PyInstaller 意外收集不相关的模块。
- `pip`、PyInstaller 或其他入口仍引用旧路径。
- 出现无法稳定复现的打包差异。
- 准备进行重要正式发布，希望排除历史残留。

环境不是珍贵数据。只要依赖清单和构建说明完整，重建通常比修补更可靠。

## 11. 版本管理和发布规范

### 11.1 必须忽略虚拟环境

本项目根目录 `.gitignore` 应包含：

```gitignore
/.venv-build/
```

其他项目常用：

```gitignore
/.venv/
/.venv-build/
```

### 11.2 不要放入版本文件夹或发布包

本项目将 `.venv-build` 放在各 `全功能整合包x.x` 的外层，是为了：

- 避免复制新版本目录时把庞大的环境一起复制。
- 防止把环境误打入发布包。
- 明确它属于本机开发和构建基础设施。

### 11.3 发布依据必须可重建

一个可维护的 Python 项目至少应保存：

- 要求的 Python 版本和位数。
- 精确的依赖清单。
- 构建配置。
- 构建命令。
- 正式版和测试版的区分规则。
- 发布前测试清单。

## 12. 其他项目如何借鉴

### 12.1 默认建议：一个项目一个环境

对于互不相关的项目，推荐：

```text
project-a/
├─ .venv/
├─ requirements.txt
└─ src/

project-b/
├─ .venv/
├─ requirements.txt
└─ src/
```

优点是边界最清楚，项目之间不会互相影响。

### 12.2 何时可以考虑共用构建环境

只有同时满足以下条件时，才考虑像本项目一样在多个版本目录外共用环境：

- 它们是同一产品的连续版本。
- 使用相同的 Python 主次版本和架构。
- 依赖整体兼容。
- 每个版本都有自己的依赖清单。
- 切换版本时会重新安装、核对和测试。
- 维护者理解共用环境可能保留旧包。

如果不能确定，选择“一项目一环境”。

### 12.3 新项目推荐模板

```text
my-project/
├─ .venv/                    # 不提交
├─ src/
├─ tests/
├─ requirements.txt          # 运行依赖
├─ requirements-dev.txt      # 测试、格式化等开发依赖
├─ requirements-build.txt    # 打包依赖，可按项目需要设置
├─ .gitignore
└─ README.md
```

创建和验证：

```powershell
$projectRoot = (Get-Location).Path
$projectEnv = Join-Path $projectRoot '.venv'
$projectPython = Join-Path $projectEnv 'Scripts\python.exe'

if (-not (Test-Path -LiteralPath $projectPython -PathType Leaf)) {
    py -3.12 -m venv $projectEnv
}

& $projectPython -m pip install -r (Join-Path $projectRoot 'requirements.txt')
& $projectPython -m pip check
& $projectPython -m pytest
```

如果项目没有测试框架，可以删除最后一行，但正式项目最好逐步建立自动化测试。

## 15. 最终原则

1. 虚拟环境负责隔离依赖，依赖清单负责重建环境。
2. 正式操作显式调用虚拟环境的 Python，不依赖终端碰巧激活了什么。
3. 无关项目默认使用各自独立的虚拟环境。
4. 同一产品的连续版本可以谨慎共用构建环境，但切换版本必须重新校准和验证。
5. Windows 虚拟环境不要直接移动或复制，位置变化时按清单重建。
6. 虚拟环境不提交、不发布、不当作备份。
7. 重要正式版发布前，干净重建环境是排除历史污染的有效手段。
