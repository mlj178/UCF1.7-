# 获取**实例地址**的方法

### 1. Hook 实例方法的 `this` 指针（最常用）

**原理**：拦截该类的任何实例方法，在 `onEnter` 中通过 `args[0]` 拿到调用该方法的对象地址。

```
Interceptor.attach(addrUpdate, {   // addrUpdate = Player.Update 的 RVA
    onEnter: function(args) {
        let player = args[0];       // 这就是 Player 实例地址
    }
});
```

**优点**：几乎总能捕获到活跃实例，无需预先知道全局变量。
**缺点**：需要该类确实有被调用的方法；如果方法频率很低，可能需要等待。



### 2. 读取全局/静态变量

**原理**：游戏往往会把重要对象（如本地玩家、游戏管理器）存放在全局指针或静态字段中。找到该变量的内存地址（模块基址+偏移或通过特征码），直接读取指针。

```
let base = Module.findBaseAddress("GameAssembly.dll");
let globalPlayerPtr = base.add(0x123456).readPointer();  // 读取全局变量
```

**优点**：立即得到实例，无需等待调用。
**缺点**：需要事先分析出全局/静态变量位置（偏移或模式）。



### 5. 从其他已知对象链式读取

**原理**：如果已经持有另一个对象的地址，而该对象包含指向目标实例的字段（例如 `Player.playerSkills` 指向 `PlayerSkills` 实例），则可通过读偏移获得。

```
let player = ...;                 // 已获取的 Player 实例
let playerSkills = player.add(0xB0).readPointer();   // PlayerSkills 实例
```

**优点**：自然扩展，无需额外搜索。
**缺点**：需要先有一个“根”实例，且对象关系已知。





### 6. 通过构造函数 Hook

**原理**：Hook 该类的构造函数（`.ctor`），在对象刚创建时捕获其地址。

```
Interceptor.attach(base.add(0xCTOR_RVA), {
    onEnter: function(args) {
        let newInstance = args[0];    // .ctor 中 this 也是第一个参数
        console.log("新创建的实例:", newInstance);
    }
});
```



**优点**：能在对象生命周期最早点拿到地址。
**缺点**：仅适用于新创建的对象，无法拿到已存在的。

------

### 7. 通过静态方法/属性的返回值

**原理**：有些类提供静态方法返回单例（如 `GameManager.GetInstance()`）。Hook 该方法，从返回值获取实例。

```
Interceptor.attach(base.add(0xGET_INSTANCE_RVA), {
    onLeave: function(retval) {
        let instance = retval;
    }
});
```

**优点**：直接，几乎无偏移依赖。
**缺点**：需要知道该类有返回自身实例的静态方法。



# 方法对比总表

| 方法                    | 需要预知信息      | 是否主动获取     | 适用场景               |
| ----------------------- | ----------------- | ---------------- | ---------------------- |
| **Hook this 指针**      | 实例方法 RVA      | 被动（等待调用） | 任何有方法调用的类     |
| **读全局/静态变量**     | 变量地址/偏移     | 主动             | 存在全局指针的单例     |
| **链式读取**            | 根对象地址 + 偏移 | 主动（需先有根） | 已持有父对象           |
| **Hook 构造函数**       | .ctor RVA         | 被动             | 捕获新创建的实例       |
| **Hook 静态方法返回值** | 静态方法 RVA      | 被动             | 存在返回实例的静态方法 |

如果我的项目有两个功能都replace同一个方法，是两种不同的逻辑，请问应该怎么管理replace


Interceptor.replace 像"占座"——一个人坐了，另一个人坐上去，前面的人就被挤走了。

两个模块各自 replace 同一个地址 → 第二个覆盖第一个，功能A 的替换就没了。



解决方案：单点接管 + 注册表（最推荐）
