# 穿越火线单机版功能代码解读 HTML 生成规范

## 规范使用方式

本规范包含生成 `代码解读.html` 所需的完整要求，可以独立使用，不要求先读取其他规范。

相关文件：

- `代码解读HTML模板.html`：代码解读页面的布局参考。
- `HTML功能问答文档生成规范.md`：需要生成可持续提问和保存数据的 `功能问答.html` 时使用。
- `功能问答HTML模板.html`：功能问答页面的布局和持久化交互参考。
- `功能文档体系说明.md`：只说明各文件之间如何配合，不承载本规范的必需生成规则。
- `index.html`：功能文档总入口；新增或调整代码解读页面后必须检查对应功能的入口和链接。

代码解读和功能问答可以共用页面视觉与源码分段结构，但两份规范各自完整，不形成必须同时读取的强依赖。

## 1. 文档目的

为每个游戏修改功能生成独立的代码解读 HTML，让新接手项目的人能够快速理解：

- 该功能解决了穿越火线单机版中的什么问题。
- 修改了哪一段游戏流程或游戏规则。
- 涉及哪些 Unity、IL2CPP、线程、指针、Hook、玩家、Bot、武器、房间或模式逻辑。
- 修改了哪个类的哪个字段，调用或拦截了哪个方法。
- 代码读取了什么数据、写入了什么数据，以及使用什么 API 完成读写。
- 功能启用、关闭、进入房间、退出房间、死亡和复活时如何工作。

解读必须从“游戏修改如何实现”的角度出发，不能只解释 JavaScript、Python 或 C++ 的语法。

## 2. 目录与文件命名

功能编号和名称以 `05-正式功能` 下的目录为准。

```text
功能文档/
├─ index.html
├─ 01-无限子弹/
│  └─ 代码解读.html
├─ 02-无后座力/
│  └─ 代码解读.html
└─ XX-功能名称/
   └─ 代码解读.html
```

要求：

- 一个功能对应一个同编号、同名称的文件夹。
- 默认只生成 `代码解读.html`。
- 每次新增功能后更新 `功能文档/index.html`。
- 索引中的编号、名称、简介和超链接必须与实际目录一致。

## 3. 源码选择范围

### 3.1 当前整合包源码

优先读取：

```text
04-正式发行版/全功能整合包1.7-修复版/game_modifier/scripts/
```

展示当前正式整合包实际加载的功能脚本。

### 3.2 功能目录主方案

同时读取对应目录：

```text
05-正式功能/编号-功能名称/
```

选择规则：

- 优先选择名称正常、版本最新、实际可运行的主方案。
- 忽略带“副本”的重复文件。
- JS 负责游戏修改、Python 负责连接或界面时，根据功能理解需要决定是否同时展示。
- 与游戏修改无关的总结、日志、编译产物、第三方库和重复文件不收录。
- 一个功能存在多个关键源码时，使用多个源码标签页，不得截断关键实现。

### 3.3 ESP 功能的特殊规则

Universal ESP 盒子不要求展示整个工程，只展示主要功能代码，例如：

- 玩家和房间数据管理。
- IL2CPP 桥接和实例获取。
- Transform、世界坐标和碰撞盒读取。
- 世界坐标到屏幕坐标转换。
- ESP 方框和颜色绘制。
- 与上述流程直接相关的 Hook。

不收录 ImGui 第三方库源码、编译产物和无关的图形后端样板代码。

## 4. 源码展示要求

- 选中的源码文件必须完整展示，不能只摘录关键代码。
- 保留源码原有顺序、缩进、注释和行号。
- 不得为方便讲解而改写、格式化或修正源码。
- 每个源码文件单独一个标签页。
- 页面显示源码文件相对路径和总行数。
- 点击“复制源码”时，只复制当前标签页的完整源码。
- 解读分段必须从第一行连续覆盖到最后一行，不能遗漏中间代码。
- 07“完整代码导航”必须列出当前源码的全部代码段。
- 08“完整代码正文”必须把当前标签页的全部源码连续展示出来，不能只显示当前选中的代码段或关键代码摘录。
- 08 中每个代码段的“代码段名称 · 起止行号”必须使用独立标题框，样式参考“文件目标 · L1–2”：深色底、细边框、轻微圆角，标题与代码正文清楚分开。
- 点击某个代码段只改变选中状态和右侧解读，其他代码段仍然保持可见。

## 5. HTML 页面布局

页面以阅读代码方便为第一目标，不设计复杂的桌面端、移动端或营销式布局。

> 区域编号说明：本规范用 `01` 功能标题区、`02` 源码切换、`03` 快捷操作、`05` 源码档案、`06` 关键行图例、`07` 完整代码导航、`08` 完整代码正文、`09` 对应解读等编号指代页面各区域，**仅用于规范内部沟通**。正式生成的 HTML **不显示这些编号徽章**——不要出现 `.number` 编号方块，也不要在标题前加 `01`～`09` 数字标签，只保留各区域本身的内容与样式。`代码解读HTML模板.html` 中的编号是模板说明用途，迁移到正式文档时一律去掉。

固定布局：

- 顶部：功能名称、源码标签页、返回目录、复制源码。
- 顶部说明：一句话说明该功能解决的游戏问题。
- 左侧：07 完整代码导航和 08 完整代码正文，包含全部源码、行号、代码段标题和关键行高亮。
- 右侧：当前被点击代码段的业务逻辑解读。

交互要求：

- 01“功能标题区”、02“源码切换”和 03“快捷操作”位于同一顶部背景栏；页面向下滚动时，整个顶部栏固定在浏览器上方。
- 05“源码档案”和 06“关键行图例”随页面正常滚动，不固定在屏幕上方。
- 07“完整代码导航”在滚动到顶部栏下方后固定，始终位于 01-03 顶部栏的下面。
- 右侧解读区域固定时必须避开 01-03 顶部栏，不能被顶部栏覆盖。
- 只有点击左侧代码段时，右侧解读才允许改变。
- 鼠标滚轮和页面滚动不得自动切换右侧内容。
- 切换源码标签页后，默认选中该文件的第一段代码。
- 当前选中的代码段应有明显边框或背景反馈。
- 页面离线可用，不依赖网络资源或外部前端库。

## 6. 代码分段原则

代码分段应按真实职责划分，不能机械地按固定行数切割。

常见分段包括：

- RVA、字段偏移、配置和状态。
- GameAssembly 或 IL2CPP 初始化。
- 本地玩家、Bot、武器、模式实例或静态字段定位。
- Hook 安装、替换、监听和恢复。
- 指针链读取与有效性验证。
- 核心游戏逻辑修改。
- 主线程任务调度。
- 房间进入、退出、销毁、回合切换、死亡和复活处理。
- RPC、模块接口和状态同步。

每段必须有简洁、准确的标题，并标出对应的起止行号。

所有代码段必须在左侧连续展开。分段只用于定位和切换解读，不得把未选中的代码隐藏起来。

## 7. 右侧“业务流程对应”内容

右侧只展示当前代码段的“业务流程对应”。

每个代码段的业务流程必须包含：

### 游戏场景

使用穿越火线中的语言说明这段代码在什么时候发生，例如：

- 玩家按下开火键。
- 武器准备扣除弹匣子弹。
- 玩家死亡后等待复活。
- 进入多人生化回合。
- Bot 执行 Update。
- 游戏准备随机发放 BUFF。
- Unity 每帧更新模式逻辑。

### 原始游戏逻辑

说明没有修改器时，游戏原本如何处理。

### 修改后游戏逻辑

按执行顺序说明修改器做了什么。修改行为、关键结论和技术判断必须标注真实代码行号，例如 `L63` 或 `L63-L78`。

游戏背景、原始游戏规则和帮助理解的场景说明不必强行绑定代码行号。行号必须指向真正支持该结论的代码，不能为了满足格式随意引用附近行。

### 游戏表现

说明玩家在游戏中最终看到或感受到的结果，以及必要的限制或风险。

## 8. 必须分析的游戏修改信息

不能局限于预先给出的关键词，应根据实际代码主动分析以下内容。先判断当前功能实际涉及什么，再展开对应内容；不涉及线程、Bot、房间、武器或其他主题时，不得为了满足模板强行加入。

### 禁止模板化解读

- 每个代码段必须根据该段真实代码单独分析。
- 不能只替换代码段标题，重复使用相同的“原始逻辑、修改后逻辑、游戏表现”。
- 不同源码文件即使实现同一功能，也必须根据各自的实际实现解释差异。
- 右侧说明必须能回答“为什么这些代码行属于当前代码段”，不能使用与代码无关的通用描述。

### 区分代码性质

解读时应明确区分：

- 只负责配置、常量、日志或界面状态的代码。
- 负责定位 GameAssembly、IL2CPP 类、实例、字段或目标地址的代码。
- 负责安装、监听、替换、恢复或卸载 Hook 的代码。
- 负责读取游戏数据但不修改游戏行为的代码。
- 真正写入字段、替换返回值、修改参数或调用游戏方法的核心代码。

配置和生命周期辅助代码仍需完整展示，但只有在会影响功能行为时才独立展开，不应与真正的游戏修改混为一谈。

### 类、字段和方法

- 被修改或读取的 IL2CPP 类名称。
- 字段名称、字段偏移和字段类型。
- 方法名称、RVA 和函数签名。
- 静态字段、实例字段、数组、List、结构体之间的关系。
- 当继承关系会影响 Hook 覆盖范围、派生类特殊处理或遗漏类型时，应查阅 `dump.cs` 展示完整相关继承链，不能凭名称猜测。
- 不影响当前功能结论时，不必为所有功能机械展示完整继承树。

### 读取与写入

明确说明：

- 从哪个对象或静态区域开始读取。
- 经过怎样的指针链取得目标数据。
- 使用 `readPointer`、`readU8`、`readS32`、`readFloat` 或 C++ 安全读取等哪种方式。
- 使用 `writeU8`、`writeS32`、`writeFloat`、`retval.replace` 或原生函数调用等哪种方式修改。
- 写入前后是否验证指针、长度、内存权限或返回值。

### Hook 与原生调用

需要区分：

- `Interceptor.replace`：目标函数入口由新的 `NativeCallback` 接管，原逻辑是否执行由替换函数决定。
- `Interceptor.attach`：原函数仍执行；`onEnter` 在进入函数时运行，可以读取或修改参数；`onLeave` 在原函数返回后运行，可以读取或替换返回值。
- `NativeFunction`：不是 Hook，而是主动调用游戏内已有的原生函数。
- C++ Hook：说明使用的 Hook 库、目标函数和原函数保存方式。

不要把 Hook 简单描述成“替换 DLL”。应说明它修改的是目标函数入口、调用过程还是返回值。

### 线程

只有代码实际涉及线程、异步任务或 Unity 主线程限制时才展开本节。如果涉及 Unity API、GameManager、Instantiate、Transform 或对象创建，必须判断是否要求游戏主线程执行。

说明：

- 外部 Python 线程或 Frida RPC 线程负责什么。
- 为什么不能直接在线程中调用某些 Unity 方法。
- 如何借助 `ModeBase.Update` 等游戏主线程函数调度任务。
- 跨线程直接调用可能造成的游戏表现，例如无效对象、闪退或房间切换后崩溃。

### 玩家、Bot 与房间

只有当前功能涉及玩家对象、Bot 判断或房间生命周期时才展开。根据代码确认：

- 是否通过 `Player.get_isMyPlayer`、`GameManager.myPlayer` 或其他方法区分本地玩家。
- 是否会同时影响 Bot、队友、敌人或所有经过该函数的对象。
- 玩家死亡、复活、退出房间、进入新房间时指针是否失效。
- 是否清理缓存、Hook、定时器和旧房间对象。
- ESP 或聚怪功能如何确认玩家仍属于当前房间。

### 武器与模式

- 只有当前功能涉及武器、角色技能或游戏模式时才展开。
- 当继承关系决定功能覆盖范围时，根据 `dump.cs` 展示完整的相关继承关系，不只列当前代码直接使用的类。
- 游戏中的武器名称、模式名称和角色名称应结合穿越火线内容解释。
- 无法从代码确认具体武器映射时，必须明确写“代码无法证明”，不能强行对应。
- 特殊武器分支、普通枪械、近战、RPG、投掷物和技能武器应分别判断是否覆盖。

### 分析实现是否重复

当代码对基类、派生类或多个相邻方法安装 Hook 时，需要分析：

- 基类 Hook 是否已经覆盖派生类的调用路径。
- 派生类 Hook 是否仍有独立作用，还是与基类处理重复。
- 多个 Hook 是否会在一次游戏行为中重复执行。
- 不同功能模块是否修改同一函数、字段或对象，是否可能相互覆盖或冲突。
- 重复处理是必要兜底、特殊武器处理，还是可以被其他实现替代。

### 分析功能覆盖范围

根据对象来源、调用路径和判断条件确认：

- 修改影响 MyPlayer、Bot、队友、敌人，还是所有经过该方法的对象。
- 功能覆盖哪些武器、角色、技能、模式或回合状态。
- 哪些派生类、特殊分支或调用路径没有经过当前 Hook。
- 代码是否存在看似“全模式”或“全部武器”，实际只覆盖部分类型的情况。
- 不能从静态代码确认的覆盖范围，应标记为需要游戏内验证。

### 代码问题对应到游戏表现

发现风险或实现问题时，不能只写技术名称，还要说明可能出现的游戏表现，例如：

- Hook 没有成功卸载：关闭功能后修改仍然生效，或再次启用时重复触发。
- 旧房间指针没有清理：进入新房间后读取旧玩家、出现无效对象或闪退。
- 重复 Hook：一次开火、受伤、复活或回合事件被处理多次。
- 跨线程调用 Unity API：对象创建失败、状态不同步或游戏崩溃。
- 字段偏移或 RVA 错误：功能无效、修改错误对象或发生内存访问异常。

只描述代码能够支持的风险，不把“可能发生”写成“已经发生”。

### 比较整合版与主方案

同时存在整合版和功能目录主方案时，应比较：

- 当前正式整合版采用了主方案中的哪些核心逻辑。
- 哪些 Hook、字段、线程处理、校验或生命周期逻辑被新增、删除或修复。
- 两个版本的启用、关闭和游戏表现是否一致。
- 主方案中的调试代码、UI 代码或实验逻辑是否进入正式版。
- 如果两个版本实际相同，应直接说明，不为制造差异而牵强分析。

### 端到端调用链

只有功能实际涉及外部控制器、Frida 消息或多文件协作时才分析完整调用链：

- Python 如何发现并连接游戏进程。
- Frida 如何读取、拼接或加载脚本。
- UI 或 RPC 如何发出启用、关闭和参数消息。
- 游戏进程内的 JavaScript 或 DLL 如何接收请求。
- 状态消息由哪个文件、哪个处理函数接收。
- 最终在哪个游戏类、方法、字段或返回值上产生效果。

## 9. RVA 和关键代码标记

RVA 地址所在代码行后面应添加对应的类和方法名称，例如：

```text
base.add(0xB61140)    WPN_Gun.ConsumeAmmo
base.add(0xAF6A00)    ModeBase.Update
```

地址与类方法映射应优先依据：

1. 当前源码中的命名和注释。
2. `dump.cs` 中的方法、字段和继承关系。
3. 已确认的 IDA 或反编译结果。

不能确认时标注为待验证地址，不得虚构名称。

## 10. 关键行颜色规范

采用“整行淡色背景 + 左侧色条”的组合方式，高亮关键业务逻辑。

- 蓝色：RVA、偏移、函数地址和目标对象定位。
- 红色：安装、替换、监听、恢复或卸载 Hook。
- 绿色：真正改变游戏行为的读取、写入、返回值替换或原生调用。
- 橙色：风险、依赖、指针校验、异常处理、房间生命周期和兼容性问题。

点击代码段后，该段关键行的颜色应进一步增强。

不要把所有代码都高亮，只标记理解功能所必需的关键行。

## 11. enabled、Hook 生命周期和消息同步

如果功能存在 `enabled`、`enable()`、`disable()`、`sendStatus()` 或模块注册，需要结合对应文件说明：

- 游戏进程由哪个 Python 文件发现并连接 Frida。
- 所有 JS 由哪个文件读取、拼接和加载。
- 模块何时注册。
- Hook 是脚本加载时安装，还是用户启用功能时安装。
- `enable()` 是否安装 Hook、启动定时器或立即写入字段。
- `disable()` 是否真正 detach/revert Hook、停止定时器并恢复原值。
- `enabled=false` 是否只改变逻辑开关，而 Hook 仍留在函数入口。
- `sendStatus()` 通过 Frida `send()` 发给哪个 Python 文件，由谁接收并用于更新什么界面状态。

必须根据当前功能的真实调用链说明，不能套用统一结论。

## 12. 时间戳与源码变更识别

每个源码标签页必须显示：

- 文档生成时间。
- 源码最后修改时间。
- 源码文件大小。
- 源码 SHA-256。

页面说明：源码更新后 SHA-256 会变化，可据此判断当前 HTML 是否需要重新生成。

### 默认不重新读取源码

- **默认情况下不重新读取源码、不重算 SHA-256。** 迁移、改版或更新已有文档时，沿用现有 HTML 中记录的源码正文、修改时间、文件大小和哈希，避免无谓地推翻已校准的解读与行号。
- 只有在用户明确要求"重新读取源码""重算哈希""同步最新源码"，或确认源码已更新需要刷新时，才重新打开 `04-正式发行版` 与 `05-正式功能` 对应文件，重新嵌入正文并重新计算 SHA-256。
- 一旦重新读取，必须完整嵌入最新源码正文（逐字一致），并重新校准所有行号、代码段起止和行号引用，不得只换指纹而保留旧正文。

## 13. 表达方式

- 使用简洁、易懂的中文。
- 专业名词保留英文，例如 Hook、RVA、IL2CPP、NativeFunction、MyPlayer、Bot。
- 先说游戏中发生了什么，再解释代码如何实现。
- 把复杂指针链写成有顺序的流程。
- 每段说明都应针对当前代码，禁止套用其他功能的固定话术。
- 不堆砌泛泛的编程语法说明。
- 不加入与当前功能无关的背景知识。
