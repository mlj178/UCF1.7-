1. 这个功能解决了什么游戏问题？

它解决的是开火后弹药被游戏正常扣除的问题。

普通枪械通过替换 WPN_Gun.ConsumeAmmo 和 Weapon.ConsumeAmmo，让游戏收到“扣弹成功”的返回值，但不执行原来的扣弹代码。RPG/AT4 不走普通枪械的扣弹路径，所以在 WPN_RPG.Fire 进入前调用 WPN_RPG.FillAmmo。

2. 这些武器类和数据是什么关系？

最重要的区分：`WPN_*` 通常是房间中正在运行的武器对象；`WeaponData` / `WD_*` 是武器配置；另外几个是被对象持有的数据结构。

FAL CAMO、FN FAL 榴弹版和 Nano AT4 的区别

  • FAL CAMO：WPN_Gun → Weapon，数据类是 WeaponData_Gun。它属于普通枪械路径。
  • FN FAL 榴弹版：WPN_GrenadeGun → WPN_Gun → Weapon，数据类是 WD_GrenadeGun。普通射击仍属于枪械分支，但榴弹模式有独立状态和弹药数据；它不是 WPN_RPG。
  • Nano AT4：WPN_RPG → Weapon，数据类是 WD_RPG，不经过 WPN_Gun。

WPN_RPG.Fire 主要覆盖实例化为 WPN_RPG 的 RPG/AT4 家族，包括项目资料中提到的补给箱 RPG、AT4 和 Nano AT4；它不包含 FAL CAMO，也不包含 FN FAL 榴弹版。某把外观像发射器的武器是否受影响，最终取决于运行时类是不是 WPN_RPG。

问题：已经 Hook Weapon.ConsumeAmmo，WPN_Gun 的处理还有必要吗？

有必要，不能简单被基类 Hook 替代。

Weapon.ConsumeAmmo 是基类虚函数，WPN_Gun.ConsumeAmmo 是普通枪械自己的重写版本。WPN_Gun 实例通过虚函数分派时通常直接执行重写版本，不会先执行基类版本。

普通枪械 WPN_Gun → 调用 WPN_Gun.ConsumeAmmo（override） → 当前脚本必须 Hook 0xB61140 其他没有重写 ConsumeAmmo 的 Weapon 子类 → 可能调用 Weapon.ConsumeAmmo（基类） → 基类 Hook 0xB6C310 作为兜底

因此两者的职责是：WPN_Gun Hook 负责普通枪械，Weapon Hook 负责可能沿用基类实现的其他武器。如果只能保留一个，普通枪无限子弹应优先保留 WPN_Gun.ConsumeAmmo；基类 Hook 是否必需，可以通过逐类测试后再决定。

3. 普通枪械、基类兜底和 RPG 处理是否重复？覆盖全部武器吗？

有继承层面的重叠，但不是简单重复。

  • WPN_Gun.ConsumeAmmo 是普通枪械的主要扣弹入口。
  • Weapon.ConsumeAmmo 是基类函数，用于覆盖仍走基类实现的其他武器；一次开火不代表两个函数一定都会执行。
  • WPN_RPG : Weapon，不属于 WPN_Gun，并且在自己的 Fire 内处理弹药，所以需要单独处理。

不能仅凭当前脚本认定覆盖了全部武器。 `dump.cs` 里还有 WPN_Throw、WPN_Arcane、WPN_SentryGun、WPN_Disposable、WPN_Rope 等直接继承 Weapon 的类型。它们只有在实际调用被替换的基类 ConsumeAmmo 时才会生效；如果像 RPG 一样自己扣弹，就需要继续分析各自的开火函数。

4. 当前方案是否区分 MyPlayer 和 Bot？

没有显式区分。当前 plan4 没有调用 Weapon.get_isMyWeapon，也没有读取 owner 后判断 Player.get_isMyPlayer。

它替换的是全局 Native 函数地址。因此，只要玩家武器或 Bot 武器执行同一个 WPN_Gun.ConsumeAmmo、Weapon.ConsumeAmmo 或 WPN_RPG.Fire，都会进入 Hook。

这表示“代码没有过滤 Bot”，但不能只靠静态脚本断言每一种 Bot 武器一定受到影响；还要确认 Bot 的实际射击逻辑是否调用这些函数。

如果需要只修改 MyPlayer，怎么实现？

  1. 把 Weapon.get_isMyWeapon（RVA 0xB6E1D0）包装为 NativeFunction。
  2. 每次进入扣弹或开火回调时，把当前武器的 thisPtr 传给它。
  3. 返回 true 才执行“不扣弹/补弹”；返回 false 时必须执行游戏原逻辑，不能直接返回 true。
普通枪 / Weapon 基类： if (isMyWeapon(thisPtr, ptr(0))) return true; // 本地玩家不扣弹 else return original(...); // Bot 和其他玩家走原扣弹逻辑 RPG / AT4： onEnter(args) { if (isMyWeapon(args[0], ptr(0))) FillAmmo(args[0], ptr(0)); }

当前脚本使用 Interceptor.replace，要让非玩家安全调用原函数，需要保存可靠的原函数入口，例如使用 Frida 支持的原实现 trampoline；另一种更稳的现有思路是采用 plan1_memory_lock.js：只在 isMyWeapon 为 true 时缓存并回写玩家武器的 AmmoData。

5. enabled 如何控制功能开关？何时安装 Hook？

是的：在这个模块里，enable() 就是安装 Hook，disable() 就是尝试恢复或卸载 Hook。

  • enable() 调用 Interceptor.replace 和 Interceptor.attach，把拦截逻辑安装到目标函数地址。
  • disable() 调用 Interceptor.revert 和 listener 的 detach()，让函数恢复原逻辑或移除旁路监听。
  • enabled 本身不会修改游戏；它只是记录模块认为自己当前是否已安装 Hook，并阻止重复启用。

enabled 主要是模块内部的重复启用保护：已经为 true 时再次调用 enable() 会直接返回，避免重复 Hook。

正常情况下，检测到进程只会加载和注册脚本，不会立即启用无限子弹。点击开关后才安装 Hook。不过，如果修改器保存了“上次希望保持开启”的状态，重新连接游戏后可能自动重发开启消息，此时表现为连接后自动 Hook。

“加载/注册脚本”和“安装 Hook”有什么区别？

加载/注册只是让 Frida JS 知道存在 modules.ammo，并准备好 enable/disable 方法；此时原游戏函数尚未被替换。安装 Hook发生在 enable() 中，会真正改变 GameAssembly.dll 函数的执行路径。

Hook 是不是替换 DLL 中的函数？

要分 Hook 类型。它们都针对游戏进程内已经加载的 GameAssembly.dll，改变的是运行时内存和函数执行路径，不会直接修改硬盘上的 DLL 文件。

  • Interceptor.replace：把目标函数入口交给新的 NativeCallback。本功能用它替换 ConsumeAmmo，因此原扣弹函数不再执行。
  • Interceptor.attach：不替换原函数，只在进入 onEnter 或返回 onLeave 时插入额外逻辑。本功能用它在 WPN_RPG.Fire 开始前补弹，之后原 Fire 仍继续执行。
  • Interceptor.revert：撤销 replace，恢复原函数入口。
  • listener.detach()：移除 attach 注册的监听，不再执行额外回调。

你的 replace / attach 理解是否正确？

你的理解：replace 可以接管参数、返回值和内部逻辑；attach 用于监听，可以在 onEnter 修改参数、在 onLeave 修改返回值，但默认不会替换原函数内部逻辑。

结论：基本正确。attach 虽然保留原函数，但修改参数、内存或返回值后，仍能改变最终游戏行为。

onEnter：进入原函数之前

调用者刚准备进入目标函数时触发。这里可以读取或修改 args，所以原函数会看到修改后的参数；也可以提前修改对象内存、调用其他函数。

当前无限子弹脚本就在 WPN_RPG.Fire 的 onEnter 中调用 FillAmmo，然后才让原 Fire 继续。

onLeave：原函数执行结束之后

原函数已经算出结果，但结果还没有返回给调用者时触发。这里可以读取返回值，并通过 retval.replace(...) 改成另一个返回值。

当前 RPG Hook 没有使用 onLeave；它只使用了 onEnter。

replace 会用新回调整体接管函数：可以使用传入参数、自己执行新逻辑并决定返回值，原函数内部逻辑默认不再运行。attach 默认保留原函数内部逻辑，但可以通过改参数、改对象内存、调用额外函数或改返回值，显著改变最终行为；它只是不会像 replace 那样直接用一套新函数体取代原函数。

RPG listener 没有正确保存，会有什么游戏表现？

点击关闭后，普通枪的 replace 会恢复，所以普通枪重新扣弹；但 RPG/AT4 的 attach 可能仍然存在，开火前继续执行 FillAmmo，表现为界面显示“无限子弹已关闭”，RPG/AT4 却仍然近似无限弹。再次开启还可能叠加新的 listener，使一次开火触发多次补弹回调，增加额外开销和不稳定风险。

6. sendStatus('ammo', true) 发给谁？为什么要发？

它通过 Frida 的 send() 从游戏进程内的 JavaScript 发给外部 Python 修改器：

scripts/01-unlimited_ammo.js → 调用 scripts/_common.js 的 sendStatus('ammo', true) → Frida send({ type: 'status', feature: 'ammo', enabled: true }) → core/frida_manager.py 的 FridaManager._on_message() 接收 → EventBus.emit('feature_status_changed', feature='ammo', enabled=true) → ui/app.py 的 _on_feature_status() 接收事件 → 更新 self._features['ammo'] 和 ammo_switch
文件职责
scripts/_common.js定义 sendStatus()，把状态包装为 Frida 消息。
core/frida_manager.py_on_message() 是 Python 端直接接收者；识别 type='status' 后发出事件总线消息。
ui/app.py订阅 feature_status_changed，由 _on_feature_status() 更新内部状态和界面开关。

发送它是为了让界面显示脚本实际执行后的状态，而不只是用户刚才点了什么。这样重新连接、启用失败、脚本主动关闭时，UI 与游戏内 Hook 状态更容易保持一致。
