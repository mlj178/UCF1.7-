## 最终可靠方案：回归内存写入 + 暂停无限时间模块





在dump.cs中，如何分析类？

一、 为什么直接调用 GameRoundEnd() 会失败？

在 IL2CPP 游戏中，一个函数（比如结束回合）通常不是孤立存在的，它依赖于“调用栈”和“对象状态”。

缺少前置状态（前置条件未满足）：
    函数内部可能有判断 if (currentState != GamePlaying) return;。如果你直接调用，对象可能处于 GameInit 状态，函数直接返回了。
缺少前置函数（环境未初始化）：
    正常流程是 OnBeforeRoundEnd() -> GameRoundEnd()。OnBeforeRoundEnd() 可能设置了某些标志位，如果你跳过它直接调 GameRoundEnd()，它会因为标志位不对而崩溃。
参数伪造困难：
    有些函数需要传入 RoundResult 对象。在 Native 层，你很难构造一个合法的托管对象（Managed Object）指针传进去。

二、 解决方案：从“调用函数”改为“修改状态”

这是最稳的方案。既然调用函数容易死（Crash），那我们就模仿函数执行后的结果。

针对 GameRoundEnd() 的“状态覆盖法”
不要去调用 GameRoundEnd()，而是去找控制游戏状态的那个变量（通常是 enum GameState 或 int state）。

操作步骤：
    用 Cheat Engine 搜当前的“游戏状态”数值（比如游戏中是 2，结束是 3）。
    找到这个状态变量的内存地址（通常在 GameManager 或 ModeBase 里）。
    直接写内存：把状态从 2 (Playing) 改成 3 (End)。
    游戏的主循环（Main Loop）每帧都会检查这个状态，下一帧它看到状态变成了 End，就会自动跳转场景。

对比：
   你的旧代码（失败）：试图直接调用 GameRoundEnd() -> 缺少参数/环境 -> 崩溃。
   状态覆盖法（推荐）：把“开关”拨到结束档位 -> 游戏自己检测到开关变了 -> 游戏自己安全地执行结束流程。


操作：不要去调用 ResetRound()，直接用 Interceptor 或 setInterval 把 restGameTime 强制写为 0。
结果：游戏逻辑认为时间到了，自然触发回合结束，完美绕过复杂的主动调用。



“Hook 验证”大法
当你不确定是 ClassA 还是 ClassB 时，写一个简单的 Hook 去验证。

// 假设你不确定是 0xA 还是 0xB 偏移
Interceptor.attach(base.add(可疑地址), {
    onEnter: function(args) {
        console.log("疑似命中: ", args[0]); // 打印 this 指针
        // 然后去内存里看这个指针 +0x34 是不是血量
    }
});

通过打印日志，看哪个类在运行时确实被调用了，这就是你要找的“活人”。

四、 总结建议

针对你的情况，建议采取以下策略：

放弃直接调用复杂逻辑函数：像 GameRoundEnd 这种大函数，依赖太多，外部强行调用极易报错。
改用“内存修改”模拟行为：
    想结束回合？把时间改成 0 或 把状态改成 End。
    想无限子弹？把弹匣数值改成 999 或 拦截消耗函数返回 false（像你代码里那样）。
利用“偏移量”而非“类名”：在 dump.cs 里找到关键变量的偏移（Offset），然后直接通过 ptr + offset 去读写，这样最稳定，不管类叫什么名字。

你之前的 无限时间 模块（直接写内存时间）其实是最正确的写法，比试图去调用 SkipRound() 函数要稳健得多。建议把这种思路推广到其他功能上。















# 跳过回合实现逻辑与经验总结（基于 `skip_round.js`）

## 一、核心原理

**直接修改 `ModeBase` 对象的回合剩余时间字段为 `0:00`**，触发游戏原生回合结束流程（无需模式判断，全模式通用）。

- 字段偏移：`ModeBase + 0x34`（分钟，int32）、`+0x38`（秒，int32）
- 关键 Hook 点：
  - `ModeBase.UpdateTimeUI`（`0xAF6930`）→ 捕获 `ModeBase` 实例
  - `GameManager.GameRoundEnd`（`0xAFAA40`）→ 回合结束清理
  - `ModeBase.OnTimeOut`（`0xAF1920`）→ 超时监控

## 二、关键逻辑框图

```
RPC install()
    ↓
installHooks()
    ├─ UpdateTimeUI Hook → 每帧捕获/更新 modeBaseInstance
    ├─ GameRoundEnd Hook → 清空实例、标记 roundActive=false
    └─ OnTimeOut Hook → 标记 roundActive=false
    ↓
RPC skipround() → skipRound()
    ├─ 防重入检查 (skipGuard)
    ├─ 实例有效性检查 (isValidInstance)
    ├─ 读取当前时间，若已是 0:00 则跳过
    ├─ 写入 0 到分钟/秒字段
    ├─ 增加 skipCount，发送 UI 通知
    └─ 返回结果
```

## 三、核心实现要点

### 3.1 实例捕获与生命周期管理
```javascript
// UpdateTimeUI Hook 中获取实例
if (!state.modeBaseInstance || !instance.equals(state.modeBaseInstance)) {
    state.modeBaseInstance = instance;
    state.roundActive = true;
}

// GameRoundEnd / OnTimeOut 中清空
state.modeBaseInstance = null;
state.roundActive = false;
```

### 3.2 有效性检查（避免崩溃）
```javascript
function isValidInstance(instance) {
    if (!instance || instance.isNull()) return false;
    if (instance.compare(ptr(0x10000)) < 0) return false;
    instance.readU8();       // 探针
    return true;
}
```

### 3.3 防重入保护
- `state.inHook`：防止 Hook 回调内嵌套触发自身。
- `state.skipGuard`：防止 `skipRound()` 被并发调用（如用户快速点击）。

### 3.4 写入操作
```javascript
instance.add(0x34).writeS32(0);   // 分钟归零
instance.add(0x38).writeS32(0);   // 秒归零
```

## 四、经验总结

| 经验点               | 说明                                                         |
| -------------------- | ------------------------------------------------------------ |
| **通用性优先**       | 不依赖模式判断，统一将时间设为零即可触发任何模式的回合结束。 |
| **实例动态捕获**     | 通过 `UpdateTimeUI` 每帧刷新实例，应对房间切换/回合重置。    |
| **严格的空指针检查** | 偏移量访问前必须验证指针范围（`>0x10000`）+ 探针读。         |
| **防重入机制**       | Hook 回调和 RPC 函数都要设置标志位，避免递归或并发导致状态错乱。 |
| **状态重置**         | 在 `GameRoundEnd` 和 `OnTimeOut` 中主动清空缓存实例，避免使用过期指针。 |
| **RPC 封装**         | 提供 `install`、`skipround`、`getstatus`、`reset` 接口，与 UI 解耦。 |
| **日志与计数**       | 记录跳过次数、错误次数、各 Hook 触发次数，便于调试。         |

## 五、可迁移方法

若要将此逻辑应用到其他 Unity 游戏：
1. 使用 **Il2CppDumper** 或 **IDA** 找到 `ModeBase` 类中的 **剩余时间字段**（通常是两个 int32）。
2. 找到每帧更新 UI 的函数（类似 `UpdateTimeUI`）以捕获实例。
3. 找到回合结束/超时的回调函数，用于重置状态。
4. 关键偏移可能不同，但**写零触发结束**的思路适用于大多数带倒计时模式的游戏。
