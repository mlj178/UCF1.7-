## 为什么 `time_freeze_nano6_modify_memory.js` 只在有人类被感染时才修改时间？

### 1. 核心原因：Hook 错了触发点

你的脚本把 **获取并修改时间** 的主要逻辑挂在了 `ModeBase_Nano.CheckRoundOver` 上。  
这个方法**不是每帧调用的**，它只在生化模式检查“是否应该结束当前回合”时触发，而 **有人类被感染** 正是最常见触发回合检查的事件之一。

**原始代码片段（问题所在）：**
```javascript
// Hook ModeBase_Nano.CheckRoundOver
var checkRoundOver = base.add(0xAEF8A0);
Interceptor.attach(checkRoundOver, {
    onEnter: function(args) {
        // 这里才去获取实例、修改时间
        modeBaseInstance = newInstance;
        safeModifyTime(modeBaseInstance, 99, 59);
    }
});
```
- 如果一整局都没人感染（例如僵尸被秒杀、时间耗尽），回合检查可能更晚触发，甚至不触发这条路径，你的时间修改就迟迟不生效。
- 一旦有人类被感染，游戏立刻调用 `CheckRoundOver` 检查是否人类全灭，你的脚本就“恰好”在这个时候获取到实例、修改内存，所以给你一种“感染才生效”的错觉。

**所以不是“感染导致生效”，而是“感染触发了脚本唯一能拿到实例的机会”。**

---

### 2. 类继承关系与调用时机

```
ModeBase (基类)
├── Mode_TeamDeath (团队竞技)   —— 没有 CheckRoundOver 的特殊逻辑
├── Mode_DeathMatch (个人竞技)  —— 同上
└── ModeBase_Nano (生化基类)
    ├── Mode_Nano4 (终结者模式)
    └── Mode_Nano6 (多人生化)   —— 你主要测试的模式
```

- `ModeBase_Nano.CheckRoundOver` **只存在于生化模式及其子类**。
- `ModeBase.UpdateTimeUI` 才是**所有模式共有**的刷新显示时间的方法。  
  要全模式生效，必须 Hook 这个通用方法，而不能只依赖生化专属的 `CheckRoundOver`。

## 无限时间脚本的核心代码逻辑

### 你的脚本做了三件事：

1. **获取 `modeBaseInstance` 实例地址**  
   通过 Hook 某一函数（如 `CheckRoundOver` 或 `UpdateTimeUI`）拿到 `this` 指针（即游戏模式对象的基址）。

2. **直接修改内存中的时间值**  
   已知字段偏移：
   ```
   实例地址 + 0x34 → 分钟数 (restGameTime_minute)
   实例地址 + 0x38 → 秒钟数 (restGameTime_second)
   ```
   每次检查如果时间少于 90 分钟，就把这两个位置写成 `99` 和 `59`。

3. **定时器保底**  
   `setInterval` 每 1000 毫秒用保存的实例地址再写一次，防止游戏逻辑又把时间改回去。

### 为什么之前会“暂停所有动作”？

因为你修改的是 **游戏剩余倒计时**，而某些模式中倒计时归零会直接触发 **回合结束/时间耗尽事件**。  
如果一直把时间保持在 99:59，那“时间耗尽”的条件就永远不满足，导致：
- 生化模式时间永远不会结束，但杀敌/感染胜利条件可能也卡住（取决于你的修改是否影响了其它逻辑）。
- 某些模式下，游戏帧逻辑可能与倒计时同步，强行锁定时间可能会阻塞角色移动更新（极少见，但可能与特定版本的反作弊或协程有关）。

## 涉及函数、类名与字段偏移的整理

### 表1：Hook 的关键函数

| 方法名           | 所属类          | 中文作用             | RVA (相对偏移) | VA (实际地址)               | 备注                                                 |
| ---------------- | --------------- | -------------------- | -------------- | --------------------------- | ---------------------------------------------------- |
| `UpdateTimeUI`   | `ModeBase`      | 刷新显示倒计时UI     | 0xAF6930       | GameAssembly.dll + 0xAF6930 | **所有模式都会调用，是全模式修改时间的最佳 Hook 点** |
| `CheckRoundOver` | `ModeBase_Nano` | 检查生化回合是否结束 | 0xAEF8A0       | GameAssembly.dll + 0xAEF8A0 | 仅生化模式调用，触发不稳定                           |
| `OnTimeOut`      | `ModeBase_Nano` | 时间耗尽处理         | 0xAF1920       | GameAssembly.dll + 0xAF1920 | 仅生化模式，用于重置实例                             |
| `GameRoundEnd`   | `GameManager`   | 任意模式回合结束     | 0xAFAA40       | GameAssembly.dll + 0xAFAA40 | 用于在回合真正结束时清理实例                         |

> 注：VA 地址 = 基址 + RVA，基址会随 ASLR 变化，但 RVA 固定。

### 表2：关键内存字段偏移

| 字段                  | 所属类     | 中文含义           | 偏移    | 修改值     |
| --------------------- | ---------- | ------------------ | ------- | ---------- |
| `restGameTime` (分钟) | `ModeBase` | 剩余游戏时间(分钟) | `+0x34` | `99` (S32) |
| `restGameTime` (秒钟) | `ModeBase` | 剩余游戏时间(秒钟) | `+0x38` | `59` (S32) |

这两个偏移在 `ModeBase` 中定义，因此**所有继承自 ModeBase 的模式都可以通过 +0x34/+0x38 修改时间**。  
你需要的就是正确获取那个 `ModeBase` 实例地址。

## 结合你的个人总结：概念混淆与解决方案

### 1. 游戏概念澄清
- **房间**：整个游戏房间，从开局到返回大厅。
- **回合**：在房间内的一场对局。团队竞技通常只打一个回合，生化模式会打多个回合（达到胜利分数或回合数结束）。
- **回合结束条件**：
  - **团队模式**：某方阵营分数达到上限 → 回合结束 → 直接结束房间。
  - **生化模式**：某方阵营胜利（人类存活到最后 / 僵尸感染全部人类）**或者** 时间耗尽 → 进入下一回合或结束房间。
- **你的脚本一直在阻止时间耗尽**，从而导致生化模式永远不会因时间结束回合，只能靠感染胜负强制推进。

### 2. 目标到底是什么？
你的标题和代码都显示目标是 **无限时间**，即让一局游戏永不超时。  
但潜意识里你也在纠结“能不能无限刷分/锁分”。这是两个不同的目标：
- 无限时间 → 修改 `restGameTime`，但必须小心避免卡死回合结束逻辑。
- 锁分/改分 → 需要找胜利条件计分器（例如击杀数、感染数），那个偏移不在这两个字段。

### 3. 为什么暂停了角色移动？
锁定时间不会直接让角色不能动，但可能的副作用：
- 游戏服务端/客户端同步校验时，发现本机时间与服务器严重不符，强制停止动作数据。
- 如果你修改的时间值导致某个内部状态机卡死在“等待时间结束”的循环里，就可能造成移动失效。
解决办法：将时间锁在一个较大的值（如 99:59）但不要完全阻止它流动，或者只修改 UI 显示（动静更小，但实际时间仍在走）。

## 改进版脚本的整体适配思路

1. **Hook `ModeBase.UpdateTimeUI`** 作为主要的实例获取和修改点（全模式通用）。
2. **在第一次调用时保存实例地址**，后续持续写入 `99:59`。
3. **同时 Hook `GameRoundEnd`** 清空保存的实例，防止下一回合拿到旧实例。
4. 如果想完全避开“时间耗尽结束回合”，你需要额外 Hook 判断时间归零的恢复逻辑，而不仅仅是锁时间——不过无限时间本身就意味着永远不因时间耗尽结束，这可能会导致回合无法正常结束（需要靠击杀等条件）。
5. **使用安全写入**：检查实例地址合法性，避免访问野指针导致崩溃。
