## 二、V6 的核心技术方案详解

> V6 本质上采用的是**方案1变体（内存锁定）+ isMyWeapon 过滤 + ObscuredInt 明智处理**。
> **对应脚本**: `plan1_memory_lock.js`

**工作流程：**
1. Hook 4个开火函数，第一次见到新武器指针时：
   - 先检查黑名单（notMine）→ 已知非玩家 → 跳过
   - 再检查白名单（wpnData）→ 已知玩家 → 跳过（定时器锁定）
   - 都不是 → 调用 `isMyWeapon()` 判断
   - 是玩家武器 → 读取当前加密值（`+0x0C` 和 `+0x20`）→ 存入 wpnData
   - 不是 → 加入 notMine 黑名单
2. 定时器每2秒遍历 wpnData，将加密值原样写回
3. 3个 room hook 在切房间时清空全部缓存

**使用的 ObscuredInt 偏移：**

```javascript
// 这是 ObscuredInt.hiddenValue 的偏移，不是 plain int！
ammoDataPtr.add(0x0C) = clip.hiddenValue  // 加密弹药值
ammoDataPtr.add(0x20) = ammo.hiddenValue  // 加密备弹值
```

### 2.2 V6 已经解决的问题

| 问题 | 解决方法 |
|------|----------|
| ObscuredInt 加密 | 读取并原样写回加密值(hiddenValue)，不写裸数字 |
| 玩家武器识别 | `isMyWeapon()` + 黑名单缓存 |
| 全武器支持 | 不设数量上限，动态收集所有指针 |
| 房间切换闪退 | 3个 room hook 清空缓存 + 定时器写入失败自动删除 |
| Bot卡顿 | 热路径快操作(toString+dict查找)，慢操作(process.findRange)仅首次 |
| 模式切换卡死 | 写入失败时自动从 wpnData 删除（兜底） |

### 2.3 V6 的潜在风险（已证实存在但已兜底）

| 风险 | 现象 | V6的兜底 |
|------|------|----------|
| AmmoData 被回收 | 定时器写入失败 | catch → delete wpnData |
| 切枪后旧指针失效 | 新的 WPN_Gun 实例使用新地址 | fire hook 自动发现新武器 |
| 模式切换时 AmmoSetting 重初始化 | AmmoData 被重新创建 | 新 AmmoData 地址不同,fire hook 重新收集 |
| 定时器 2000ms 可能漏过 | 2秒内弹药可能变空 | 实际测试没问题（V5用500ms也没事） |

## 三、ObscuredInt 加密的解析与应对

### 3.1 ObscuredInt 结构（从 dump.cs + IDA 反编译验证）

```
ObscuredInt (16 字节):
  offset 0x00: currentCryptoKey  — 加密密钥（uint）
  offset 0x04: hiddenValue       — 加密后的真实弹药值（XOR后）
  offset 0x08: inited            — 是否已初始化（byte）
  offset 0x0C: fakeValue         — 伪装值（给内存扫描器看的假值）
  offset 0x10: fakeValueActive   — 伪装值是否激活（byte）

AmmoData 对象:
  +0x08: clip.currentCryptoKey   ← ObscuredInt 起始
  +0x0C: clip.hiddenValue        ← 弹药加密值！V6 锁定这里
  +0x10: clip.inited             ← 固定为 1
  +0x14: clip.fakeValue          ← 伪装值（和 hiddenValue 同步）
  +0x18: clip.fakeValueActive    ← 固定为 1
  +0x1C: ammo.currentCryptoKey   ← 备用弹药 ObscuredInt 起始
  +0x20: ammo.hiddenValue        ← 备弹加密值！V6 锁定这里
  +0x24: ammo.inited
  +0x28: ammo.fakeValue
  +0x2C: ammo.fakeValueActive
  +0x30: maxClip (ObscuredInt 16字节)
  +0x44: maxAmmo (ObscuredInt 16字节)
  +0x58: isBuff (bool)
```

### 3.2 枚举 ObscuredInt 加密/解密公式

```
加密: hiddenValue = realValue XOR currentCryptoKey
解密: realValue = hiddenValue XOR currentCryptoKey
验证: fakeValue 必须和 hiddenValue 保持一致（游戏内部同步）
```

**反编译证据**：在 `ConsumeAmmo (0x10B61140)` 中：
```c
// line 70: 读取 clip 的加密值 → 解密
sub_107FEBB0(v7)  // ObscuredInt.get_Value(clip) → 返回真实弹药值

// line 84-88: 减1后写回加密值
v13 = sub_107FE9A0(v24, v10, v11);  // ObscuredInt.op_Subtract → 返回新的 hiddenValue
*(_OWORD*)(v9+8) = *v13;            // 写回 clip.hiddenValue（偏移 +0x0C）
*(_DWORD*)(v9+24) = v15;            // 更新 fakeValue（偏移 +0x14）
```

### 3.3 为什么不能写 9999

```
用户写入 9999 →
hiddenValue 变成 9999 →
但 currentCryptoKey 没变 →
解密: 9999 XOR key = 乱码 → 游戏读到乱码 →
验证 fakeValue 和 hiddenValue 不匹配 →
触发反作弊 → 画面卡死
```

### 3.4 正确做法：锁定加密值

```javascript
// ✅ 正确：记录加密值，每次原样写回
var encryptedClip = ammoDataPtr.add(0x0C).readInt();  // 读 hiddenValue
var encryptedAmmo = ammoDataPtr.add(0x20).readInt();  // 读 hiddenValue

// 每次锁定
ammoDataPtr.add(0x0C).writeInt(encryptedClip);  // 写回相同加密值
ammoDataPtr.add(0x20).writeInt(encryptedAmmo);  // 写回相同加密值
```

**原理**：游戏在扣弹药时改变 `hiddenValue`，但 `fakeValue` 和 `hiddenValue` 始终同步。我们锁定 `hiddenValue` 后，游戏扣减无效，且 `fakeValue`= `hiddenValue` 一致 → 不触发校验。

### 3.5 重要注意事项

**⚠️ `+0x0C` 锁定的是 `clip.hiddenValue`，不是 `clip.fakeValue`！**

```
AmmoData 的 ObscuredInt 布局（32位 IL2CPP）：
  +0x08 → currentCryptoKey  ← 不要动！
  +0x0C → hiddenValue       ← 锁定这个！（V6 正确）
  +0x10 → inited            ← 不要动！
  +0x14 → fakeValue         ← 自动同步，不需要锁
```

**验证**: V6 代码使用 `+0x0C` 和 `+0x20`，这是 ObscuredInt 的 `hiddenValue` 偏移。而如果写 `+0x14` 和 `+0x28` 则只改了 `fakeValue`（伪装值），游戏内部真实值 `hiddenValue` 仍在被扣 → 画面显示"9999"但实际打不出去。

## 四、地址动态变化与 isMyWeapon 机制

### 4.1 AmmoData 地址变化的原因

```
每次以下操作都会创建新的 WPN_Gun 实例 → 新的 AmmoData：
  ① 切枪（主武器 → 副武器 → 主武器）→ 旧实例回收，新实例创建
  ② 死亡复活 → 旧武器销毁，重生时重新 Init
  ③ 捡地上的枪 → 创建新武器实例
  ④ Nano 模式变身/切换 → 新武器实例
  ⑤ 房间切换 → 全部对象销毁重建
```

### 4.2 isMyWeapon 的工作原理

```javascript
var isMyWeapon = new NativeFunction(
    base.add(0xB6E1D0),  // Weapon.get_isMyWeapon
    "bool", ["pointer", "pointer"]
);
```

**C# 层逻辑（还原）**：
```csharp
// Weapon.get_isMyWeapon (RVA: 0xB6E1D0)
public bool get_isMyWeapon() {
    if (this.owner != null && this.owner == GameManager.myPlayer)
        return true;
    return false;
}
```

**继承链**：
```
WPN_Gun → Weapon → CFAnimator → Model → RecyclableObject → MonoBehaviour
                                                    ↑
                                          owner: Player
```

**为什么 V6 必须用 isMyWeapon**：
- 游戏中有 16 个 Bot，每人 1-2 把枪 → 总计 16-32 个武器实例
- 如果不过滤，定时器要给 30+ 把枪写弹药 → 掉帧 + 卡顿
- `isMyWeapon()` 是游戏内建的判断方法，准确性 100%

### 4.3 黑名单缓存加速

```javascript
// 快速路径（每次开火都走这里）
var k = wpn.toString();      // 0.02μs 纯JS字符串
if (wpnData[k]) return;      // 已知玩家 → 跳过（定时器会锁）
if (notMine[k]) return;      // 已知Bot → 直接跳过

// 慢速路径（只有全新指针才执行，每个指针一生只执行一次）
if (!readable(wpn)) return;  // Process.findRangeByAddress ~5μs
if (checkIsMyWeapon(wpn)) {  // NativeFunction 调用 ~3μs
    wpnData[k] = {...};  // 加入白名单
} else {
    notMine[k] = true;   // 加入黑名单
}
```

## 五、模式切换卡死的根本原因

### 5.1 你在历史版本中遇到的卡死场景

根据你的经验总结，以下场景会卡死：

| 场景 | 原因 |
|------|------|
| Nano 模式切换（普通→Nano→普通） | AmmoSetting 重初始化 AmmoData，旧指针失效 |
| 切房间 | 所有对象被回收，缓存的指针变悬垂 |
| 死亡复活 | 武器被销毁重建，AmmoData 地址变化 |
| 拾取新枪 | 旧枪被回收，新枪新地址 |

### 5.2 V6 如何解决（三重保险）

```
保险1（主）：GameRoundEnd → 清空 wpnData + notMine
保险2（辅）：OnStartNewGameRound / NanoOnStartNewGameRound → 清空
保险3（兜底）：定时器写入失败 → catch → 自动 delete
```

### 5.3 依然可能卡死的边缘场景

| 场景 | V6是否处理 | 风险 |
|------|-----------|------|
| Nano模式中切换武器 | fire hook重新发现 ✅ | 低 |
| Nano模式切换到普通模式 | room hook触发 ✅ | 低 |
| **同一房间内Nano模式变身后立即开枪** | fire hook 发现新武器 ✅ | 极低 |
| 主武器和副武器同一个AmmoData地址 | 去重机制(toString) ✅ | 无 |

**唯一残留风险**：如果 `AmmoSetting` 在非 room switch 场景下重新创建 AmmoData（如在 Nano 变身过程中），旧的 AmmoData 指针失效，但 V6 的定时器会在写入失败时自动删除旧条目。风险已在兜底中处理。

### 5.4 你的历史错误：没有清理悬垂指针

```
V1-V4 的问题：
  缓存 playerGun = thisPtr;
  切房间 → playerGun 指向已释放内存
  定时器继续往已释放内存写数据 → Access Violation → 闪退

V5 的旧 Bug：
  MAX_WPN = 4 限制了新武器发现
  但旧武器指针未清理 → 死亡复活后新枪识别不了
```

## 六、clip_Nano / ammo_Nano 分析

### 6.1 Nano 弹药系统架构

```
WeaponData_Gun (ScriptableObject, 静态配置)
  ├─ +0xB8: clip       = 30   (普通模式弹匣容量)
  ├─ +0xBC: ammo       = 90   (普通模式备用弹药)
  ├─ +0xC0: clip_Nano  = 45   (Nano模式弹匣容量)
  └─ +0xC4: ammo_Nano  = 150  (Nano模式备用弹药)

AmmoSetting() 函数根据 isNanoMode 选择使用哪组数据初始化 AmmoData

AmmoData (运行时实例)
  ├─ +0x0C: clip.hiddenValue  ← 运行时弹匣弹药（加密）
  └─ +0x20: ammo.hiddenValue  ← 运行时备用弹药（加密）
```

### 6.2 AmmoSetting 的反编译分析 (0x10B604C0)

```c
// 伪代码还原
void WPN_Gun.AmmoSetting() {
    var realData = this.realData;  // WeaponData_Gun* at WPN_Gun+0xEC
    var ammoData = this.ammoData;  // AmmoData* at WPN_Gun+0xF4
    bool isNano = CheckIfNanoMode();  // 读取某个全局状态

    if (isNano) {
        // 使用 Nano 弹药配置
        clipValue = realData.clip_Nano;    // WeaponData_Gun+0xC0  = 0x?8+192
        ammoValue = realData.ammo_Nano;    // WeaponData_Gun+0xC4  = 0x?8+196
    } else {
        // 使用普通弹药配置
        clipValue = realData.clip;         // WeaponData_Gun+0xB8  = 0x?8+184
        ammoValue = realData.ammo;         // WeaponData_Gun+0xBC  = 0x?8+188
    }

    // 初始化 AmmoData
    ammoData.clip = new ObscuredInt(clipValue);
    ammoData.ammo = new ObscuredInt(ammoValue);
    // ...
}
```

### 6.3 Nano 弹药的关键结论

**✅ V6 方案天然支持 Nano 弹药！**

原因：
1. V6 锁定的是 `AmmoData.clip.hiddenValue`（+0x0C）和 `AmmoData.ammo.hiddenValue`（+0x20）
2. `AmmoData` 是运行时实例，`AmmoSetting()` 初始化后，其中的值就是当前模式（普通或Nano）的值
3. V6 锁定的就是当前模式下的弹药值 — 不管普通模式还是 Nano 模式，锁的都是同一个 AmmoData 对象

**⚠️ 唯一需要注意的点**：
- 从 Nano 切换到普通模式（或反之）时，`AmmoSetting()` 会重新创建 AmmoData
- 旧 AmmoData 失效 → V6 定时器写入失败 → 自动 delete ✅
- 新 AmmoData 被 fire hook 重新发现 → 自动加入 wpnData ✅
- 完全由 V6 的兜底机制覆盖，无需额外处理

**🎯 对于单独写 Nano 弹药锁定：无需特殊处理。**
V6 的锁定逻辑对普通和 Nano 模式一视同仁。

### 14.1 方案1（内存锁定）实测反馈 — `plan1_memory_lock.js`

#### 已确认的问题

| 问题 | 现象 | 原因 |
|------|------|------|
| **子弹恢复太慢** | 射速快时弹药还是会见底 | 定时器每2秒才写回一次，高射速武器在2秒内可能打完一个弹匣 |
| **捡来的武器无法恢复** | 地上捡起的枪弹药不锁定 | 捡枪时创建新 WPN_Gun 实例，但此时不触发开火函数，fire hook 无法发现新武器 |

> ⚠️ **方案1不做修改，保留现状。** 如果后续需要方案1支持更高射速，只需要把定时器间隔从 2000ms 降到 300ms 即可。

#### 方案1的实现思路（精简版）

```
思路：锁定 AmmoData 中的 ObscuredInt 加密值
原理：不是阻止消耗，而是每2秒把弹药加密值"恢复"回去

1. Hook 4个开火函数
2. 开火时检查是否是玩家的武器（isMyWeapon）
3. 是玩家武器 → 记录 AmmoData 地址 + 当前加密值(clip+ammo)
4. 不是玩家武器 → 加入黑名单，下次跳过
5. 定时器(2秒)遍历记录 → 把加密值原样写回
6. 切房间 → 清空所有记录（防闪退）

为什么锁加密值而不是写9999：
  ObscuredInt = 真实值 XOR 密钥
  写9999 → 密钥没变 → 游戏解密出乱码 → 校验失败 → 卡死
  写原始加密值 → 游戏解密出正确数值 → 校验通过
```

### 14.2 方案2（NOP ConsumeAmmo）实测反馈 ✅ — `plan2_nop_consume.js`

**结论：完美可用。**

#### 关于多人生化箱子中的道具

用户发现多人生化模式中佣兵捡箱子后获得的**枪和火箭筒，无限子弹无效**。

从 dump.cs 和 IDA 分析：

```
SupplyBox（箱子）— 不是武器，是 RecyclableObject
  └─ OnTriggerStay → CanPickUp → OnPlayerPickUpSupplyBox
      └─ 给玩家发放武器/道具

箱子中的武器：
  WPN_RPG : Weapon（rocket launcher，继承自 Weapon，不是 WPN_Gun）
      私有字段：WPN_Gun.AmmoData ammo;  // 0xEC（偏移和 WPN_Gun 不同！）

  WPN_Missile : RecyclableObject（missile/grenade 基类，不是 Weapon）
      这根本不是武器类！是抛射体
```

**结论**：
- 箱子发放的武器可能走完全独立的弹药管理系统
- `WPN_RPG` 虽然继承自 `Weapon`，但它的 `ammo` 偏移是 `0xEC`，不同于 `WPN_Gun` 的 `0xF4`
- 箱子中的枪和火箭筒属于**特殊道具类别**，不走常规 `ConsumeAmmo` 流程
- **无限子弹方案对该类道具无效属于正常现象，不做额外处理**

#### 方案2脚本关闭后依旧生效的原因

**核心原因：方案2是修改 `.text` 段的字节，属于永久性修改。**

```
Frida 的 Memory.protect + writeByteArray 流程：
  1. Memory.protect(addr, 6, 'rwx')  → 将代码页设为可写
  2. addr.writeByteArray(patchBytes) → 将 B8 01 00 00 00 C3 写入内存
  3. Ctrl+C 关闭 Frida → Frida 进程退出
  4. 但游戏进程继续运行 → 内存中已修改的字节仍然存在！
  5. 之后每次调用 ConsumeAmmo → 跳转到 0xB61140 → 执行的是我们写入的 ret true
```

**对比 JavaScript 其他方式的持久性**：

| 方式 | 原理 | 关闭后是否失效 |
|------|------|:---:|
| `Interceptor.attach` | Frida 在函数入口插入跳板（trampoline），Frida 管理 | ✅ **是**（Frida 退出时清理） |
| `Interceptor.replace` | Frida 替换函数入口，通过 JIT stub 执行 | ✅ **是**（Frida 退出时还原） |
| **`Memory.protect + writeByteArray`** | **直接修改游戏内存中的原始字节** | **❌ 否**（字节已永久修改） |
| `Memory.write*` / `setInterval` | 持续写入数据（非代码段） | ✅ **是**（停止写入后游戏恢复） |

> **大白话**：方案2相当于用笔在游戏代码上直接涂改，你关了Frida，墨迹还在上面。
> 方案4就像是戴了一副眼镜看代码，你摘掉眼镜（关Frida），代码恢复原样。

### 14.3 方案3（Buff_InfinityAmmo）实测反馈 ❌ — `plan3_buff_infinity.js`【已作废】

**结论：完全无效，作废。**

方案3设置了 `Player.Buff_InfinityAmmo = true`（Player+0x128），但弹药照样消耗。这和之前 IDA 分析结论一致——`ConsumeAmmo` 的反编译代码中没有直接检查 `Buff_InfinityAmmo` 字段。

**推测**：`Buff_InfinityAmmo` 可能是通过 Buff 系统的 `AddAmmo/Recover` 回调在弹药消耗后才恢复，而不是阻止消耗。或者该字段仅用于客户端显示逻辑（HUD上的无限符号），并不影响实际消耗。

> ❌ **方案3脚本丢弃，不再维护。**

### 14.4 方案2 vs 方案4 对比 — `plan2_nop_consume.js` vs `plan4_replace_consume.js`

两者都能完美实现无限子弹，核心区别在于**关闭脚本后的行为**：

| 维度 | 方案2 `plan2_nop_consume.js` (NOP Patch) | 方案4 `plan4_replace_consume.js` (Interceptor.replace) |
|------|:---:|:---:|
| **关闭后效果** | ❌ **继续生效**（字节已永久修改） | ✅ **立即消失**（Frida 退出时还原） |
| **实现方式** | `Memory.protect + writeByteArray` | `Interceptor.replace` |
| **修改位置** | 游戏 `.text` 段 | Frida JS 引擎层 |
| **恢复方法** | 需要重新 patch 回原始字节 | 直接 Ctrl+C 关闭即可 |
| **反外挂检测** | ⚠️ 可能被 CRC 检测 | ✅ 不易被检测 |
| **适用场景** | 想"一劳永逸"不想反复注入 | 想随时开关，控制灵活 |

**使用建议**：

- 如果你想要"注入一次永久有效" → 用 `plan2_nop_consume.js`
- 如果你想要"随时能关" → 用 `plan4_replace_consume.js`
- 如果担心反外挂检测 → 用 `plan4_replace_consume.js`

#### 方案2恢复原始代码的方法

如果用了方案2后想恢复，重启游戏最简单。或者用以下恢复脚本：

```javascript

```

## 十五、最终结论

```
方案4 `plan4_replace_consume.js` (Interceptor.replace)  🥇 — 最推荐，随时可关闭，安全性最高
方案2 `plan2_nop_consume.js` (NOP Patch)           🥈 — 完美可用，但关闭后不恢复，适合"一劳永逸"
方案1 `plan1_memory_lock.js` (内存锁定)            🥉 — 可用但有限制（射速/捡枪），保留不修改
方案3 `plan3_buff_infinity.js` (Buff激活)            ❌ — 无效，已作废
```

> **现状**：`plan2_nop_consume.js` 和 `plan4_replace_consume.js` 均已通过实测，`plan2` 保留代码不改，`plan4` 推荐日常使用。
