## 二、行为变化（需要实机确认）

1. **自瞄（11）**：写入由"JS 线程 16ms 定时器"改为"主线程相机钩子内 16ms 节流"。若某个场景下相机钩子不触发（纯菜单/特殊观战），自瞄不会写入 —— 属预期。
2. **轻重力（09）**：loop 由主线程每帧驱动 + 50ms 节流，等价于原来的 20Hz。
3. **亮度（32）**：apply/reset 变为**异步**（结果通过下一次 status 轮询反映）；关闭功能时恢复会在主线程执行，若当时不在房间内（ModeBase.Update 不跑），恢复会推迟到回到房间。
4. **极速枪托（23）**：强制解锁由主线程执行，可能比原来晚 1 帧。
5. **无限时间（03）**：多了 1 个 hook（GameManager.OnDestroy）。

## 二之七、终结者/爪击连招无限重播（用户实测反馈后，本轮修复）

> 触发：用户实测——「从人类变身成终结者，终结者攻击到人类，就会不断有攻击动画；即使进入下一局、变身成人类，还有终结者的攻击动画」（附游戏内截图：终结者爪 + M4A1 枪神，爪痕/雷电特效持续叠加）。
> 结论：**二之五 那次"左键防卡死"的兜底钩子写在 Hook 的 `onEnter` 里，而它挂钩的函数体本身就是"把 `fireBtnPressed` 置 1"，所以写进去的 0 被本体立刻覆盖 —— 该保护从上线起从未生效**。因此只要游戏侧左键状态卡住（或 Unity `Input.GetKey(Mouse0)` 卡住），`WPN_Knife` 的连招循环就会一直自我重播；卡住的是**武器对象上的字段**（人类刀与终结者爪同属 `WPN_Knife` 族、对象池复用），所以会跨"变身"和"下一局"继续。
>
> ⚠ **后续更正（见 二之八）**：onEnter/onLeave 只是第一道坑。即使改成 onLeave，这道兜底**依然一次都执行不到** —— 它的第一道门 `physicalLeftDown()` 里 `new NativeFunction(fn,'short',...)` 在 Frida 17 直接抛异常被吞掉，恒返回 null。二之七的改动是必要条件，不是充分条件。

## 二之八、真凶：Frida 17 不接受 `'short'`，左键兜底恒判"读不到"（用户第二次实测反馈后，本轮修复）

### 1. 根因（探针实测，非推断）

`06-测试/frida-revert-probe/probe_async_keystate.py`（在 32 位 ia32 进程里跑，与游戏同架构）：

```
retType_matrix     = short=THROW(invalid type specified) | int16=OK(raw=1,down=false) | uint16=OK | int=OK | BOOL=THROW
physicalLeftDown_old = null      ← 旧写法：恒 null（异常被 catch 吞掉）
physicalLeftDown_new = false     ← 新写法：正确读到"已松开"
guard_first_gate     = 旧: 拦住(永不撤销 fireBtnPressed) | 新: 放行(会撤销)
```

链式推理，一步不缺：

1. 兜底的第一道门是 `if (physicalLeftDown() !== false) return false;`（"真按着"或"读不到"都不动）。
2. `physicalLeftDown()` 内部 `asyncKeyStateFn = new NativeFunction(fn, 'short', ['int'])`。
3. **Frida 17 里 `'short'` 不是合法类型名**（`'int16'`/`'uint16'` 才是），构造即抛 `invalid type specified`。
4. 该异常被 `catch (e) { return null; }` 吞掉，且 `asyncKeyStateFn` 始终为 null ⇒ 每次调用都抛 ⇒ **恒返回 null**。
5. ⇒ 第一道门永远成立 ⇒ `clearStuckFireBtn` 从上线起**一次都没有执行到写 0 那一行**。

旁证：包内另两个用 `GetAsyncKeyState` 的功能（`25_free_camera`、`28_wall_noclip`）用的都是 `'int16'`，所以它们正常；**只有快刀和极速枪托这两个"出问题的"用了 `'short'`**。

## 二之九、游戏"停止响应"（用户第三次实测：变身终结者用轻击后卡死）+ 连招循环的真凶另有其人

### 3. 卡死当时到底开了哪些功能（回答"是不是别的功能"）

`ActionRouter.restore_enabled()`（`ui/controllers/action_router.py:126`）在**连上游戏时**会把上次保存为"开启"的功能全部 `enable` 一遍 —— "我没开"不等于"它没在跑"。13:12:02 一连串日志里被自动开启的有：

按"对游戏的侵入面"排序，卡死嫌疑人里排在前面的并不是快刀/枪托：

- **时间加速 3.6x**：它不去 Hook 游戏逻辑，而是**直接改写引擎全局 `Time.timeScale`**（从 `get_timeScale` 机器码里 `fld [eax+0xEC]` 反推出变量地址）。全局 3.6 倍速会同时放大动画、协程、物理；而**它的"关闭=恢复 1.0"也是靠主线程 Hook 执行的**（`script.js:620` 只置 `_pendingSpeed = 1.0`）⇒ 一旦主线程卡住/退出，`timeScale` 就**留在 3.6 不还原**——这就是"功能关了还在影响游戏"的现成例子。
- **手雷模式**：45 个 Hook + 6 个 `Interceptor.replace`，其中"保护武器不被 Remove 删除"直接压在最敏感的换武器路径上，而且**在变身那一刻真的失败过**。
- **Nano4T**：多人生化特性系统（20 条属性，就是截图里"攻击力提升 240%"的来源），只在终结者模式生效，正好是出问题的场景。

## 二之十、【已定位并修复】终结者"重击动画不断重现"：`WPN_Knife.OnSpecialBtnDown` 是唯一入口且没有状态位

> 触发：用户二分测试 —— 「快刀、极速枪托单独测都没问题，两个一块开也没问题；**再加上手雷模式里面的功能**，终结者的攻击动画就会不断重现」。
> 日志 + IDA 双边对上，根因确定。

### 1. 根因（IDA 反汇编 0x10B64240 全文 0x70 字节）

```c
void WPN_Knife__OnSpecialBtnDown(WPN_Knife_o *this) {
  if ( Weapon__get_isUsing(this)                                    // ① 武器在用
       && System_String__op_Equality(this->_currentAnimTag, string.Empty) )   // ② 且当前无动画
  {
    this->klass->vtable.PlayKnifeAttackAnim(this, 3, ...);          // ③ 播重击（combo3）
  }
}
```
**函数体里没有状态位、没有冷却、没有"是否已按下"的判据** —— 谁调它、只要武器空闲就立刻起一次重击。

而它的调用者（`PlayerController.UseWeapon` 0x10B13450 反编译）是：

```c
if (wpns->inUse) {
    if (Input.GetKeyDown(324)) inUse->OnSpecialBtnDown();   // 324 = 鼠标右键
    if (Input.GetKey(324))     inUse->OnSpecialBtnDown();   // ← 按住时每帧都调
    else                       inUse->OnSpecialBtnUp();
    ...
}
```
⇒ 只要游戏侧"右键按下"这个状态卡住，重击就会**一击接一击无限重播**（节奏 = 重击 clip 时长 ≈1.1s），
且因为整段逻辑包在 `if (wpns->inUse)` 里，切武器/换角色期间状态不会刷新 —— 于是**跨变身、跨回合都能继续**。

日志实证（调用者对上了）：
```

13:58:08.955  combo=3 由 GameAssembly.dll+0xb642a1 触发（weapon=0x49f84c98，fireBtn=0）
```
`0xb642a1` 正是 `WPN_Knife.OnSpecialBtnDown`(0x10B64240) 里 `call PlayKnifeAttackAnim` 之后的返回地址

## 二之十一、【真凶抓到并已修复】手雷模式：`Interceptor.replace` 吞掉了游戏自己的托管异常，人类→终结者变身时发枪/收枪被静默中断

用户第 5 次实测反馈：**只有加上"手雷强化"三个选项就会复现** —— 人类变身终结者后轻击/重击动作卡住、无法攻击。

### 1. 根因（本轮有 Frida 内部证据 + 日志实证，不是推断）

**证据链三层，逐层对上：**

**第 1 层：日志把失败点钉在"武器切换"两个函数上**（本次实测会话 14:13，`logs/game_modifier.log`）：

```
14:13:27.401 手雷模式：全部 Hook/Replace 已安装 | hooks=45, replacements=6
                       （config: lock999_enabled=false，只有 enable_damage/range/shoot_speed=true）
14:13:49.287 快刀诊断 心跳: role=9 human=0 using=1 tag=select            ← 已经变身成终结者
14:13:51.070 手雷模式 异常：PlayerWeapons.Remove.replacement  | Error: system error
14:13:51.070 手雷模式 异常：GameManager.GiveWeapon.replacement | Error: system error
14:13:51.071 手雷模式 异常：PlayerWeapons.Remove.replacement  | Error: system error
14:13:51.071 手雷模式 异常：GameManager.GiveWeapon.original_after_error | Error: system error
14:13:52.300 快刀诊断 心跳: role=9 fireBtn=1 using=0 tag=KnifeAtk anim=combo_1  ← 动作卡住：武器不再 inUse
```

- 时间点：**恰好是变身/换武器那一刻**；本次会话里**没有任何一颗手雷被捕获、没有任何一次数值改写**
  （日志里没有"已捕获 WPN_Throw 生成的 missile"/"已修改手雷 missile"行）——也就是说
  **"手雷强化"本身什么都没改，它只是让脚本跑起来并把 45 个 Hook + 6 个 Replace 全装上了。**
- 结果状态：`using=0`（`Weapon.get_isUsing()` 为假）、`fireBtn=1`、`animTag=KnifeAtk`、`anim=combo_1`
  —— 这就是"轻击/重击动作卡住、无法攻击"，而且因为是武器对象状态残留，**会跨回合、跨变身继续**。

**第 2 层：`Error: system error` 到底是什么**（在 Frida 17.9.1 二进制里直接查出来的）：

在 `_frida.pyd` 的异常类型字符串表里，`system error` 与
`arithmetic error` / `breakpoint triggered` / `single-step triggered` **排在同一张表里**，
紧跟着的是 `access violation accessing 0x%x`：

```
..arithmetic error....breakpoint triggered....single-step triggered...system error.... accessing 0x%x
```

即：`Error: system error` = **Frida 的异常处理器抓到了一次"系统类"CPU 异常**
（Windows 上就是 C++ EH 的 `0xE06D7363`，il2cpp 正是用它来抛托管异常），
而不是访问违例、不是算错。Frida 在自己的调用边界把它转成了 JS 异常。

**第 3 层：为什么会吞掉 —— `Interceptor.replace` + `NativeFunction` 回call 的模式**

手雷模式把 `PlayerWeapons.Remove` / `GameManager.GiveWeapon` 换成 JS 回调，回调里再用
`NativeFunction` 回call原函数。这时原函数内部的托管异常**先被 Frida 抓到**（因为它就在我们的
调用边界内），游戏自己的异常处理帧**永远收不到这个异常**；我们的 `catch` 记完日志再回call一次
（于是又出现 `original_after_error`），最后 `return ptr(0)`。
净效果：**发枪/收枪被静默中断**，终结者手里根本没有一把"正常 inUse"的武器 → 动作卡死。

> 补充（IDA 佐证，为什么偏偏在变身时抛）：这两个函数**本来就带"抛托管异常"的出口**，
> 而变身瞬间武器/模型正在销毁，正好会走到那里：
>
> | 函数 | 地址 | 抛异常出口 | 触发条件（反汇编出来的空判） |
> |---|---|---|---|
> | `GameManager.GiveWeapon` | 0x10AFB390 | `loc_10AFB4A4: call sub_10167D60`（0x10AFB4A4） | `player`/`weapon`/`weapon->data(0x68)`/`player->wpns(0xA0)` 任一为空 |
> | `PlayerWeapons.Remove` | 0x10B15FD0 | `sub_10167D60`（0x10B164BA） | `weapon` 已被销毁、`this->owner`、`owner._modelInfo`、`weapon->data`、`current` 等空判 break 到这里 |
>
> `sub_10167D60` → `jmp sub_101401B0`（0x18 字节，构造异常对象后跳 `sub_10140190`）
> = il2cpp 的抛异常辅助函数，**不是普通返回**。
> 也就是说：`GiveWeapon` 在变身时抛异常是**原版就会发生的事**（游戏自己的异常帧接住它），
> 而我们的 `replace` 让 Frida 抢先把这次 `0xE06D7363` 变成了 JS 的 `system error`。

### 5. 复现时怎么一眼定性（本轮新增的判据）

1. 日志里有 `[game_modifier.App] UI 已就绪（PID: …），开始恢复功能开关` → 连接链路正常；**没有这一行**就是链路被吞（现在会同时留下 `TkCallback` 异常或 `由心跳补投` 的证据）。
2. `UI 回调滞留后由心跳补投 N 条` → 命中过 (b) 竞态，功能已自动恢复（无需重启）。
3. `<功能> 未执行：插件 RPC 客户端不可用（…）` → 命中过 (d)。
4. `事件队列已满，已丢弃事件 connection_status …` → 命中过 (a)。
