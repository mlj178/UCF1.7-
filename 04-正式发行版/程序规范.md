# 程序规范

这份文档是给以后开发和 AI 修改代码时用的。内容以我自己的描述为主，语言尽量口语化、简洁化，不追求长篇解释。

它的作用很简单：记录这个程序原本的分区、功能、UI 设计和一些特殊处理。以后 AI 改功能时，不能把这些原本的设计偷偷改偏；改完以后也要拿这份文档检查一遍。

## 0. 概念绑定表

以后文档和代码沟通时，统一用“英文 ID（中文名）”来称呼同一个东西，不要一会儿叫这个、一会儿叫那个。中文是给人看的，英文 ID 是给代码和 AI 对照用的。

基础界面：

- `APP_TITLE`（程序名称）：`全功能整合包 v1.8`。
- `main_window`（主窗口）：程序启动后的完整窗口。
- `collapsed_window`（折叠窗口）：折叠后只剩顶部状态栏的窗口。
- `status_bar`（顶部状态栏）：最上方状态区域。
- `status_dot`（状态圆点）：左侧圆点，必须用 `text_color` 显示颜色。
- `status_label`（状态文字）：状态圆点右侧的连接状态文字。
- `pid_label`（PID 文字）：右侧显示游戏 PID 的文字。
- `hint_label`（提示条文字）：状态栏下面提示用户下一步该做什么。
- `tab_view`（功能分页）：主功能分页容器。
- `connect_button`（连接游戏按钮）：备用手动连接按钮。
- `log_box`（用户日志框）：界面底部给用户看的日志。
- `dev_log`（程序员日志）：保存到 `logs/game_modifier.log` 的详细日志。
- `settings_window`（设置窗口）：点击设置后弹出的窗口。

布局和卡片：

- `feature_card`（通用功能卡片）：普通开关类功能使用的卡片。
- `simple_feature_card`（简洁功能卡片）：一行两个、各占一半宽度的功能卡片。
- `wide_feature_card`（宽功能卡片）：占满一整行的功能卡片。
- `grid_columnconfigure`（列宽权重）：控制一行有几列、每列怎么分宽度。
- `columnspan`（跨列数）：控制一个卡片占几列。`columnspan=1` 是半行，`columnspan=2` 是整行。
- `switch`（开关）：功能启用/关闭控件。
- `slider`（滑块）：倍率或数值调节控件。
- `button`（按钮）：一次性动作控件。
- `combo_box`（下拉框）：选择模式、特性或快捷键的控件。

功能分页：

- `weapon_tab`（武器页）：枪械、近战、射速等功能。
- `player_tab`（人物属性页）：速度、时间、重力、无敌、技能冷却等功能。
- `other_tab`（其他页）：聚怪、天机傀儡、回合跳过、方框透视、时间加速等功能。
- `nano4t_tab`（多人生化 Buff 选择页）：多人生化特性和决战回合。
- `weapon_giver_tab`（赋予武器页）：武器赋予、复活自动赋予、武器快捷键。

功能 ID：

- `knife`（快刀）、`recoil`（无后座力）、`ammo`（无限子弹）、`ammoplus`（快速换弹）、`range`（剑气化丝）、`aim`（自瞄）、`speedgun`（射速变快 / 连狙）。
- `movespeed`（滑板鞋）、`time`（无限时间）、`gravity`（轻重力 / 高跳）、`godmode`（金刚不坏）、`skillcd`（技能无冷却）。
- `gather`（聚怪）、`isbot`（天机傀儡）、`roundskip`（回合跳过）、`esp_box`（方框透视）、`timescale`（时间加速）。
- `nano4t`（多人生化特性）、`battle_round`（决战回合）、`weapon_giver`（赋予武器）。

快捷键：

- `HOTKEY_POSITIONS`（功能快捷键位）：`Ctrl+1` 到 `Ctrl+5`、`F1` 到 `F3`、`Alt+1` 到 `Alt+3`。
- `WEAPON_HOTKEY_POSITIONS`（武器快捷键位）：`Ctrl+Z`、`Ctrl+X`、`Ctrl+C`。
- `save_and_apply`（关闭保存流程）：关闭设置窗口时，把快捷键写入文件，并重新注册快捷键。

## 1. 主窗口和折叠规则

- 程序名称统一叫 `全功能整合包 v1.8` 这种格式。以后版本变化时，只改后面的版本号，不再使用 `游戏修改器控制台` 这个旧名字。
- 程序启动后的**主界面**尺寸是 `610x700+10+10`，**最小尺寸**是 `610x400`。
- 主窗口**允许调整大小**，窗口**置顶**（始终 Pin 在游戏界面之上，不仅仅是设置窗口置顶），**透明度**大概是 `0.92`。
- 折叠后的界面尺寸是 `400x62`，**最小尺寸**也是 `400x62`。
- 折叠时只保留 `status_bar`（顶部状态栏），也就是只保留 `status_dot`（状态圆点）、`status_label`（状态文字）、`pid_label`（PID 文字）、折叠/展开按钮、设置按钮。`hint_label`（提示条文字）、`tab_view`（功能分页）、`connect_button`（连接游戏按钮）和 `log_box`（用户日志框）都不显示。
- 折叠和展开时，窗口位置不要变。只能改宽高，不能把窗口强行移动到屏幕左上角，也不要固定回 `+10+10`。
- 展开时恢复折叠前保存的完整窗口尺寸和位置。









## 2. status_bar（顶部状态栏）

顶部状态栏是整个程序最重要的状态提示区，位置在窗口最上方。

- `status_dot`（状态圆点）：在左侧，用圆点颜色表示连接状态。绿色是已连接，黄色是等待或处理中，红色是断开，灰色是空闲或未知。这里必须设置 `text_color`，不能只换圆点字符，不然程序里看起来就没有颜色。
- `status_label`（状态文字）：在圆点右侧，用文字说明当前状态，比如等待游戏启动、正在连接、已连接、连接断开。
- `pid_label`（PID 文字）：在右侧，显示当前连接到的游戏 PID。没连上时可以为空。
- `折叠界面` 按钮：在右侧，用来折叠或展开主界面。折叠后按钮文字变成展开界面。
- `设置` 按钮：在右侧，打开设置弹窗。

状态栏背景是深灰色，整体要紧凑，不要做得太高。

## 3. hint_label（提示条文字）

`hint_label`（提示条文字）在 `status_bar`（顶部状态栏）下面，专门给用户看当前应该怎么做。

- 未连接时：提示用户先启动游戏、进入模式、打开工具、再开启功能。
- 已连接时：提示已经连接，可以点击功能按钮开启修改。
- 断开时：提示连接断开，正在重连。

提示条颜色跟状态走：绿色表示可用，黄色表示等待，红色表示异常或断开。

## 4. tab_view（功能分页）分区

主功能都放在 `tab_view`（功能分页）里，分页不要随便改名、换顺序或合并。

- `weapon_tab`（武器页）：放和枪械、近战攻击相关的 `feature_card`（通用功能卡片）。
- `player_tab`（人物属性页）：放角色属性类功能，比如速度、时间、重力、无敌、技能冷却。
- `other_tab`（其他页）：放聚怪、天机傀儡、回合跳过、方框透视、时间加速等杂项功能。
- `nano4t_tab`（多人生化 Buff 选择页）：专门放多人生化特性选择和决战回合。
- `weapon_giver_tab`（赋予武器页）：专门放武器赋予、复活自动赋予、武器快捷键绑定。

每个 tab 里面都是可滚动区域，内容多的时候靠滚动解决，不要压缩到看不清。

## 5. feature_card（通用功能卡片）设计

`feature_card`（通用功能卡片）要保持现在这种紧凑风格。

- `simple_feature_card`（简洁功能卡片）一行放两个，各占一半宽度。这个不是 `spawn` 控制的，是由 `grid_columnconfigure`（列宽权重）把页面分成两列，再由 `columnspan=1`（跨列数为 1）决定卡片占半行。
- `wide_feature_card`（宽功能卡片）可以占满一整行，比如攻击范围、轻重力这类需要更多控件的卡片。整行由 `columnspan=2` 控制。
- 卡片宽度跟窗口自适应，高度根据内容自适应。
- **卡片背景**以深灰为主，圆角小一点，边框细一点，不要做成很夸张的大卡片。
- **卡片标题**一般是**图标**加名称，字体是微软雅黑加粗，**说明文字**用**浅灰色**。
- 卡片**右侧**一般是开关；需要调数值的功能，标题区域里可以放滑块和数值标签。
- `feature_card`（通用功能卡片）不做“点卡片任意区域就切换”的设计。功能开关交给 `switch`（开关）处理，一次性动作交给 `button`（按钮）处理，数值交给 `slider`（滑块）处理。

常见控件：

- `switch`（开关）：控制功能启用和关闭。
- `slider`（滑块）：控制倍率或范围，比如快刀、滑板鞋、剑气化丝、重力、高跳、时间加速。部分修改涉及数值修改，滑块可以在区间内连续调节，比输入框更直观，比预设档位更自由。
- `button`（按钮）：用于一次性动作，比如聚怪、回合跳过、赋予武器。
- `combo_box`（下拉框）：用于选择模式或快捷键。

- 方框透视：显示敌人方框。
- 时间加速：调整 Unity 时间倍率。

## 6.1 上次开启状态恢复规则

`data/user_config.json` 会记录上一次程序运行时各功能的 `enabled` 状态。简单说，用户上次把某个普通功能开着，程序下次启动时就能知道这个功能之前是开着的。

程序启动时，会先读取 `feature_state.json`，再用 `user_config.json` 覆盖需要同步的功能状态。连接游戏后，`restore_enabled()` 会根据这些状态恢复功能。

这里要分清楚：不是所有功能都应该按“上一次开启状态”自动恢复。普通开关功能可以这样做，但特殊页、特殊控制器、DLL 功能、预约/一次性状态功能，不要强行套普通恢复逻辑。

这些功能的 `sync_enabled_from_config` 是 `false`，这是合理设计：

- `nano4t`（多人生化特性 / Nano4T）
- `weapon_giver`（赋予武器 / Weapon Giver）
- `esp_box`（方框透视 / ESP Box）
- `battle_round`（强制决战回合 / Battle Round）

以后新增功能时，先判断它是不是普通持续开关。是普通持续开关，就让 `user_config.json` 记录并恢复 `enabled`。如果是特殊页、预约功能、一次性按钮、DLL 控制功能，就不要硬改成 `sync_enabled_from_config=true`，要在 manifest 或文档里写清楚为什么不走普通恢复。

## 7. ESP 方框透视流程

ESP 功能采用"成熟常驻方案"，核心原则是：**功能开关 ≠ DLL 卸载，关闭修改器 ≠ 卸载 ESP DLL，关闭游戏 = ESP DLL 自然释放**。DLL 进入游戏后，尽量不在游戏运行中 FreeLibrary，只控制 ESP 显示状态。

### 开启 ESP
用户打开 ESP → 修改器检查游戏进程 → `try_connect_existing(pid)` 连接旧 DLL → 如果没有旧 DLL，注入 `Universal-ImGui-Hook.dll` → 连接 pipe → `set_esp_box(True)` → DLL 开始画方框。

代码中 `_connect_universal_for_esp()` 实现先连接旧 DLL，连接不到才注入新 DLL。

### 关闭 ESP 功能（不关闭修改器）
用户关闭 ESP 开关 → `set_esp_box(False)` → DLL 停止绘制方框 → pipe 仍连接 → DLL 仍留在游戏进程里。

此时 DLL 不卸载，属于正常状态。

### 关闭修改器程序
关闭修改器 → `set_esp_box(False)` → 等 300ms → `UniversalHookManager.disconnect()` 断开 pipe → `FridaManager.disconnect()` → 修改器退出。

**关键**：只断开 pipe，DLL 仍留在游戏进程里，游戏继续运行不闪退。

### 修改器关闭后游戏继续运行
ESP DLL 变成"后台待机"状态：
- `Universal-ImGui-Hook.dll` 仍存在
- D3D Hook 仍存在
- `ESPState.boxEnabled = false`
- 不绘制 ESP 方框
- pipe server 等待下次连接

### 重新打开修改器（游戏未关）
重新打开修改器 → 找到游戏进程 → 用户开 ESP → `try_connect_existing(pid)` 连接旧 DLL → 不重复注入 → `set_esp_box(True)` → 方框重新出现。

**关键**：复用旧 DLL，不重复注入。

### 关闭游戏
用户关闭游戏 → 游戏进程退出 → Windows 自动释放游戏进程所有 DLL → ESP DLL 自然释放 → 所有 Hook / ImGui / pipe 随进程销毁。

这是最安全的 DLL 释放方式。

### 重新启动游戏
旧游戏进程结束 → 旧 ESP DLL 已自然释放 → 新游戏进程启动 → 修改器检测新 pid → 用户开启 ESP → 注入新 DLL → 连接 pipe → 开始绘制。

新游戏进程是干净环境，需要重新注入 DLL。

## 8. nano4t_tab（多人生化 Buff 选择页）

这个页面是专门给多人生化用的，状态设计不要改乱。

- 顶部有自己的 `nano4t_status_dot`（多人生化状态圆点）和 `nano4t_status_label`（多人生化状态文字），显示多人生化系统是否就绪。
- 还有当前回合提示，告诉用户现在是不是在多人生化房间、当前回合是什么状态。
- 幽灵方特性和人类方特性各占一半宽度。
- 幽灵方卡片偏红色，人类方卡片偏蓝色。
- 每边都有一个下拉框，下面显示当前选中特性的说明。
- **状态标签**有 `[未激活]` 和 `[已激活]`。未激活是灰色，已激活是绿色。
- 点击 `应用` 后，把当前选择写进游戏，两个状态都变成已激活，并提示当前配置下一回合生效。
- 没有进入多人生化房间时，`应用` 按钮不能点；如果用户操作不对，要用提示告诉他应该先进入多人生化模式房间。
- 退出房间后，按钮禁用，状态回到未激活。

这个页面的重点不是让用户猜状态，而是要告诉用户下一步该做什么。

## 9. 决战回合

决战回合放在多人生化 Buff 页面里。

- 功能作用是每局强制触发决战回合，也就是多人生化最后 30 秒触发希望 buff 的那种保底局。
- 设计巧思是：玩家即使还没进入多人生化房间，也可以在房间外提前预约。
- 如果游戏还没连接，状态显示已预约，等待连接游戏。
- 如果已经连接但还没进多人生化，状态显示已预约，等待多人生化。
- 进入多人生化房间后，预约状态自动激活，显示已启用，下回合生效。
- 运行中会根据实际回合显示决战回合、普通回合或读取中。

不要把它改成只有进房间后才能开。提前预约是这个功能的重点。

## 10. weapon_giver_tab（赋予武器页）

赋予武器是单独的 tab，不要塞进普通武器功能里。

- 顶部有标题、复活自动装备武器勾选框、当前武器提示。
- 武器很多，所以不能用一个超长下拉框。现在的设计是每个武器一个卡片。
- 武器按类型分组，每组里面卡片一行放 3 个，不要改成 4 个。4 个会太窄。
- 武器卡片宽度自适应，三列等宽。
- 每个武器卡片里有武器名称、`赋予` 按钮、快捷键绑定按钮。
- 普通武器卡片偏深蓝，英雄或特殊类型武器可以用更醒目的颜色区分。

特殊武器处理：

- 有些**特殊武器**第一次赋予时，需要赋予两次。
- 这样做是为了让特殊武器的射速变快能正常生效，类似需要切枪或 deploy 两次。
- 这个逻辑不能删，尤其是首次进入房间后的特殊武器赋予。

复活自动赋予：

- 勾选复活自动装备武器后，玩家点击某个武器赋予时，会把这个武器记为复活后自动赋予的武器。
- 玩家死亡复活后，程序会自动再赋予这个武器。

武器快捷键：

- 武器快捷键是 `Ctrl+Z`、`Ctrl+X`、`Ctrl+C`，一共 3 个。
- 以前试过 `Shift+1/2/3` 或数字键，但游戏里数字键经常切主武器、副武器、刀，所以改成了 Z/X/C。
- 每个快捷键只能绑定一个武器，绑定了一个就少一个可选项。
- 绑定入口在武器卡片上，点击后弹出绑定快捷键的小窗口。
- 如果要删除快捷键，点武器卡片右上角的快捷键小标签里的删除按钮即可。

## 11. connect_button（连接游戏按钮）和日志

`connect_button`（连接游戏按钮）在 `tab_view`（功能分页）下面，但平时很少用。

- 程序后台会自动检测游戏进程。
- 检测到游戏进程后自动连接。
- 游戏进程断开后自动断开，并进入重连或等待状态。
- 连接按钮主要是备用手动触发，不是主要操作路径。

日志分两种：

- `log_box`（用户日志框）：显示在界面底部，给用户看，内容要简洁，说明当前发生了什么。
- `dev_log`（程序员日志）：持久化保存到 `logs/game_modifier.log`，信息更详细，用来排查问题。

不要把大量调试细节直接刷到用户日志里。用户只需要知道结果、状态和下一步。

## 12. settings_window（设置窗口）

点击顶部 `设置` 会打开一个新弹窗。

- 设置窗口尺寸是 `500x650`。
- 设置窗口置顶，不允许随便拉伸。
- 里面有两个 tab：`快捷键` 和 `关于`。

快捷键页：

- 功能快捷键用下拉框绑定。
- 绑定规则是互斥绑定：一个功能绑定后，其他下拉框里就少一个。
- 功能快捷键主要保留 `Ctrl+1` 到 `Ctrl+5`，因为 `Ctrl+6` 到 `Ctrl+0` 太远，用户不好按。
- 还保留 `F1` 到 `F3`、`Alt+1` 到 `Alt+3`。
- `多人生化特性`、`赋予武器`、`方框透视` 不走普通功能快捷键绑定。
- 武器快捷键这里主要做显示，真正绑定在赋予武器的武器卡片弹窗里完成。

关于页：

- 展示程序名称、版本号、作者名、QQ群。
- 有 B 站链接。
- 有历代版本更新说明链接，打开的是 GitHub Pages 上的 HTML。
- 有微信赞赏码图片。

`settings_window`（设置窗口）没有 `保存并应用` 按钮。功能快捷键下拉框变化时，只是先改内存里的绑定和刷新可选项；真正写入快捷键文件、重新注册全局快捷键，是关闭设置窗口时通过 `save_and_apply`（关闭保存流程）自动完成。

## 13. AI 修改后的检查清单

以后 AI 改完代码，至少要按这些点检查：

- 主窗口启动尺寸、折叠尺寸、折叠位置没有被改偏。
- 程序名称仍然是 `全功能整合包 vxx`，不要再出现 `游戏修改器控制台`。
- 顶部状态栏、提示条、连接按钮、日志框的位置没有乱。
- `status_dot` 有真实 `text_color`，绿色、黄色、红色、灰色都能看出来。
- tab 名称和分区没有乱。
- 普通功能卡片仍然是一行两个，宽功能才占满一行。
- `simple_feature_card`（简洁功能卡片）的一行两个由 `grid_columnconfigure` + `columnspan=1` 控制，不要写成其他概念。
- `feature_card`（通用功能卡片）不要加入"点击卡片四处都能触发开关"的额外绑定。用户通过 `switch`（开关）、`button`（按钮）、`slider`（滑块）等明确控件操作。
- 赋予武器仍然是一行 3 个武器卡片，不要变成 4 个。
- 多人生化没进房间时不能点应用，并且要提示用户该怎么做。
- 决战回合仍然支持房间外提前预约。
- 特殊武器首次赋予两次的逻辑还在。
- ESP 功能关闭时不卸载 DLL，只停止绘制。
- 关闭修改器时只断开 pipe，不 FreeLibrary ESP DLL。
- 重新打开修改器时复用旧 DLL，不重复注入。
- 复活自动赋予武器还在。
- 武器快捷键仍然是 `Ctrl+Z`、`Ctrl+X`、`Ctrl+C`，并且互斥绑定。
- `settings_window`（设置窗口）的快捷键不是下拉框一改就落盘，必须保留关闭窗口时的 `save_and_apply`（关闭保存流程）。不要再加回 `保存并应用` 按钮。
- 用户日志和程序员日志不要混在一起。
- 设置窗口的快捷键页和关于页不要被删。

## 14. 天机傀儡（isbot）状态流转

天机傀儡功能有特殊的状态流转逻辑，状态显示必须清晰告诉用户当前发生了什么。

### 状态分类

- **已关闭**：功能开关未开启，状态标签显示灰色 `#888888`。
- **已预约，等待进房**：功能开关已开启，但用户还没进入游戏房间。状态标签显示黄色 `#f39c12`。
- **已预约，等待重进房间生效**：功能开关已开启，用户在房间内开启功能，但需要退出房间重新进入才能生效。状态标签显示黄色 `#f39c12`。
- **已生效**：功能已成功写入游戏，玩家已被标记为 Bot。状态标签显示绿色 `#2ecc71`。

### 状态流转场景

1. **初始状态**：
   - 功能开关关闭 → 显示 "状态: 已关闭"

2. **开启功能但未进房间**：
   - 用户打开开关 → 游戏未连接或未在房间 → 显示 "状态: 已预约，等待进房"

3. **房间内首次开启**：
   - 用户在房间内打开开关 → 功能立即写入 → 显示 "状态: 已生效"

4. **房间内开启后退出房间**：
   - 用户在房间内已生效 → 退出房间 → 状态清空 → 显示 "状态: 已预约，等待重进房间生效"

5. **重新进入房间**：
   - 用户重新进入房间 → 功能自动重新写入 → 显示 "状态: 已生效"

6. **关闭功能**：
   - 用户关闭开关 → 状态回到 → 显示 "状态: 已关闭"

### 状态标签设计

- **字体**：Microsoft YaHei，11号
- **位置**：在开关下方，独占一行
- **颜色**：
  - 灰色 `#888888`：已关闭
  - 黄色 `#f39c12`：等待中（等待进房、等待重进）
  - 绿色 `#2ecc71`：已生效


## 15. 统一编码规范

### 15.1 正式发行版编码要求

正式发行版所有文本文件统一 UTF-8。

UI 文本、功能名称、按钮文字、提示文字、日志文字、manifest 中文字段、README 文档全部必须 UTF-8。

程序标题、tab 名称、卡片名称、卡片说明、状态栏文字、设置窗口文字不能出现乱码。

### 15.2 manifest 编码要求

插件 `manifest.json` 中的以下字段必须 UTF-8：

- `display_name` 功能显示名
- `icon` 图标
- `desc` 功能描述
- `controls.label` 控件标签
- `display_values` 显示值

### 15.3 新增功能编码要求

新增功能时，如果出现中文或 emoji，必须先确认文件编码是 UTF-8。

文档文件 `.md` 也必须使用 UTF-8，不允许用 ANSI / GBK 保存。

### 15.4 打包迁移要求

打包、复制、迁移版本时，不能破坏 UTF-8 编码。

不允许把正常中文替换成 Unicode 乱码、问号或不可读字符。

不允许把中文转成错误编码后提交。
