# 正式发行版功能接入规范

这份规范用于 `04-正式发行版/`，当前重点适配：

```text
04-正式发行版/全功能整合包2.1/game_modifier/
```

目标是让 `05-正式功能/XX-功能名/` 里的单功能成果，按正式发行版插件架构低成本接入 `全功能整合包2.1`。

正式发行版接入原则：

```text
只接验证过的功能成果
优先完整复制单功能 JS
不重写游戏核心逻辑
不把多个功能合并成一个大 JS
不为单个功能修改中心架构
只做插件壳、manifest、UI、RPC、配置、生命周期适配
```

一句话：正式版接入不是重新开发功能，而是把已经验证过的 JS 能力装进 2.1 的插件体系。

------

## 1. 适配范围

### 1.1 2.1 当前架构

`全功能整合包2.1` 使用插件式功能目录：

```text
04-正式发行版/全功能整合包2.1/game_modifier/
├── core/
│   ├── plugin/
│   │   ├── manifest_loader.py
│   │   ├── plugin_registry.py
│   │   └── plugin_base.py
│   ├── frida_runtime/
│   │   ├── script_manager.py
│   │   └── rpc_client.py
│   └── frida_manager.py
├── features/
│   ├── _template/
│   └── <feature_dir>/
│       ├── __init__.py
│       ├── manifest.json
│       ├── feature.py
│       ├── panel.py
│       ├── script.js
│       └── events.py
├── ui/
├── data/
└── tools/
    └── check_architecture.py
```

2.1 不再使用旧式接入路径：

```text
scripts/feature_id.js
features/feature_id.py
ui/panels/feature_id_panel.py
data/features.json
core/feature_registry.py
```

因此，2.1 接入新功能时，不能照旧规范把 JS 放进 `scripts/`，也不能为了注册功能去恢复旧注册表。

### 1.2 历史单功能工具的接入方式

如果 `05-正式功能/XX-功能名/` 里只有独立 JS 和独立 UI，例如：

```text
AAAAA-bot_pause_min.js
AAAAA-bot_pause_ui.py
free_camera_v1_3.js
free_camera_ui_v1_3.py
```

则按以下原则处理：

```text
完整复制原 JS 到 2.1 插件 script.js
独立 UI 不直接接入正式版
从 features/_template/ 复制插件壳
补齐 manifest.json / feature.py / panel.py / events.py
只做 2.1 所需的接口、配置、生命周期适配
不重写 JS 中已经验证过的游戏读写、Hook、偏移、算法逻辑
```

## 2. 接入前置条件

一个功能进入正式发行版前，至少要满足：

```text
JS 文件存在，且功能逻辑已经单功能验证
JS 提供 rpc.exports
JS 至少提供 enable / disable / status / cleanup
cleanup 可以重复调用
退出或关闭时能恢复游戏状态
单功能说明或经验总结存在
关键偏移、字段、Hook 点来源清楚
功能边界和失败条件清楚
```

如果源功能已经是标准功能包，还应满足：

```text
manifest.json 存在
manifest.json 中 status = release_ready
Python Feature 文件存在
UI Panel 或 UI 描述存在
RPC 接口完整
生命周期说明完整
单功能测试通过
```

如果源功能不是标准包，不允许因为缺少标准文件而重写功能逻辑。正确做法是：保留原 JS 核心，补齐 2.1 插件壳。

## 3. 2.1 标准插件目录

每个功能必须独立放在一个插件目录中：

```text
game_modifier/features/<feature_dir>/
├── __init__.py
├── manifest.json
├── feature.py
├── panel.py
├── script.js
└── events.py
```

要求：

```text
每个功能一个目录
每个功能一个 manifest.json
每个功能一个 script.js
script.js 必须自包含
feature.py 继承 PluginFeatureBase
panel.py 只通过通用 callbacks 调用功能
events.py 只处理本功能事件，没有事件也保留空处理
```

目录命名建议：

```text
24-人机暂停       -> 24_bot_pause
25-自由视角       -> 25_free_camera
```

`feature_id` 使用稳定英文标识，不能随意改名。例如：

```text
bot_pause
free_camera
```


## 5. JS 接入规范

### 5.1 完整复制优先

从 `05-正式功能` 接入时，JS 处理顺序必须是：

```text
1. 先完整复制原 JS 到 features/<feature_dir>/script.js
2. 保留原偏移、Hook、字段读写、算法和状态机
3. 再补 2.1 所需 RPC 别名、配置入口、cleanup 参数兼容
4. 最后只删除明显无关的独立 UI 启动代码或测试代码
```

不允许：

```text
为了风格统一重写 JS
把功能核心逻辑改成另一个实现
把多个功能的 JS 合并
把 JS 放进中心 dispatcher
让 JS 依赖全局 modules.xxx
让 JS import / require 外部 helper
```

### 5.2 RPC 标准

2.1 通过 `RpcClient` 和 `ScriptManager` 调用插件 JS。标准 RPC：

```text
enable
disable
setConfig
setconfig
status
cleanup
```

要求：

```text
enable 开启功能
disable 关闭功能
status 返回结构化状态
cleanup 负责恢复游戏状态和释放 Hook/timer
setConfig/setconfig 用于接收 UI 配置
```

如果原 JS 已经使用其他配置接口，例如：

```text
configure(input)
```

可以保留原函数，并增加别名：

```javascript
rpc.exports.setConfig = rpc.exports.configure;
rpc.exports.setconfig = rpc.exports.configure;
```

这属于 2.1 接口适配，不属于重写游戏逻辑。

### 5.3 cleanup 参数兼容

2.1 cleanup 可能传入原因参数：

```javascript
cleanup({ reason: "shutdown" })
```

如果原 JS 的 cleanup 不接收参数，可以只做兼容，不改变功能逻辑：

```javascript
cleanup: function (payload) {
  // payload 可忽略，但函数必须能接收。
  return cleanupOriginal();
}
```

## 6. Python Feature 规范

`feature.py` 必须继承 `PluginFeatureBase`：

```python
from core.plugin.plugin_base import PluginFeatureBase


class PluginFeature(PluginFeatureBase):
    feature_id = "bot_pause"
    js_filename = "script.js"
    name = "人机暂停"
    category = "other"
    desc = "暂停或恢复所有人机。"
```

要求：

```text
不使用旧 FeatureBase
不使用 register_feature
不 import core.feature_registry
不自己 attach Frida
不自己管理 session
RPC 调用只通过 PluginFeatureBase / feature_service / rpc_client
```

如果功能需要特殊 action，可以在 `PluginFeature` 内封装，但仍然必须走通用 RPC 客户端。

## 7. UI Panel 规范

`panel.py` 只能负责显示和触发通用回调。

允许：

```text
显示开关
显示滑块
显示下拉框
显示状态文字
callbacks["toggle"](feature_id)
callbacks["set_config"](feature_id, key, value)
callbacks["action"](feature_id, action)
```

禁止：

```text
panel.py 直接 import FridaManager
panel.py 直接调用 script.exports.xxx
panel.py 直接写 RVA / 偏移 / Hook 地址
panel.py 访问 app._xxx 私有字段
panel.py 使用 context._app / context.legacy
panel.py 使用 get_state / set_state / get_handle / set_handle
panel.py 为某个功能改 ui/app.py
```

如果需要完整页面，必须在 manifest 里声明：

```json
"ui": {
  "mode": "special_page",
  "tab_title": "功能页名称",
  "tab_order": 60,
  "lazy_build": true
}
```

不要为了一个功能在 `ui/app.py` 中写特殊页面分支。

## 8. 配置规范

配置必须属于本功能 manifest：

```json
"config": {
  "moveSpeed": 18.0,
  "lockPlayerMove": true
}
```

要求：

```text
UI 修改配置后走 callbacks["set_config"]
Python Feature 负责把配置传给 JS
JS 不直接读取 data/user_config.json
JS 只接收 RPC 传入的配置
配置字段命名要与 JS 接口一致
```

如果原 JS 使用驼峰字段，例如 `moveSpeed`，正式版 manifest 和 panel 也优先保持 `moveSpeed`，不要无意义改成 `move_speed`。

## 9. 生命周期规范

每个功能的生命周期需求写入 manifest：

```json
"lifecycle": {
  "cleanup": true,
  "restore": true,
  "requires_room_reset": false,
  "uses_cached_pointer": false
}
```

要求：

```text
游戏连接成功后按需加载 script.js
功能开启调用 enable
功能关闭调用 disable
配置变更调用 setConfig/setconfig
游戏断开调用 cleanup
UI 退出调用 cleanup
重新 attach 后按配置恢复
切房间可能失效的缓存必须能刷新或清理
```

如果 JS 缓存了玩家、武器、房间、相机、Bot 静态字段等指针，必须在以下场景考虑清理：

```text
切房间
GameManager 销毁
游戏断开
cleanup
重新 attach
```

### 9.1 UI 已开启但进房后未生效的接入要求

2.1 的 `restore_enabled()` 触发点是“Frida 连接成功后按配置恢复”，但连接成功不等于游戏房间、玩家、Bot、相机、回合对象已经全部就绪。

如果功能依赖房间内对象、相机 Hook、Bot 静态字段、玩家实例、GameManager、回合实例等运行态对象，只写 `lifecycle.restore = true` 还不够。否则会出现：

```text
程序未进游戏前 UI 已经开启
连接成功时 restore_enabled 提前调用 enable
enable 当时找不到房间对象或 Hook 写入点
进入游戏后 UI 仍显示开启，但运行态没有重新 apply
必须手动关闭再开启才生效
```

这类功能必须在文档和 manifest 中明确“需要房间就绪后再次应用”：

```json
"lifecycle": {
  "cleanup": true,
  "restore": true,
  "requires_room_ready_reapply": true,
  "room_ready_retry": true
}
```

接入步骤必须写清楚：

```text
1. enable 只能表示用户意愿已开启，不能假设房间对象一定存在。
2. enable 时先保存 enabled=true，再尝试 apply 当前运行态。
3. 如果运行态对象未就绪，JS 必须进入 pendingApply/pendingEnable 状态，而不是只返回失败。
4. 进入房间、捕获到 GameManager/玩家/Bot/相机对象、或收到生命周期 Hook 后，必须再次执行 applyEnabledState。
5. 重新 apply 时只按当前配置补写运行态，不要反复切 UI 开关。
6. disable/cleanup/断开连接必须清理 pendingApply、定时器、临时 Hook、缓存指针。
7. status 必须返回 enabled、applied、pendingApply 或 pendingEnable、lastApplyReason，方便日志和测试判断。
```

这条规范默认适用于所有依赖“游戏运行态对象”的功能，尤其是：

```text
玩家实例 / myPlayer / allPlayers
Bot 静态字段或 Bot 列表
GameManager / ModeBase / GameRound
CameraManager / CinemachineBrain / Unity Camera
武器实例 / 当前武器 / HUD 运行态对象
房间内才创建或切房间会销毁的对象
```

如果后续开发的功能不需要这套机制，必须在功能接入说明或 manifest 中写清楚“不适用原因”。例如：

```json
"lifecycle": {
  "cleanup": true,
  "restore": true,
  "requires_room_ready_reapply": false,
  "room_ready_retry": false,
  "room_ready_reapply_exempt_reason": "只安装固定 RVA Hook，不依赖房间内对象；Hook 命中时自然按 enabled 状态生效"
}
```

判断标准：

```text
能在连接后一次性安装固定地址 Hook，且 Hook 命中时会读取 enabled 状态再执行：
可以不做 pendingApply，但必须写 exempt_reason。

enable 会立即写玩家、Bot、相机、武器、房间对象字段：
必须做 pendingApply 或 pendingEnable。

功能依赖定时扫描：
扫描循环本身可以承担 room_ready_retry，但 status 仍要暴露 pending/applied。

功能是一次性按钮动作，例如跳过当前回合：
通常不应该 restore，manifest.lifecycle.restore 应为 false。
```

房间就绪触发源要按功能依赖来选，不要固定只认一种 Hook：

```text
GameManager.Awake / GameManager.OnDestroy：
适合判断房间或场景的创建、销毁。需要注意 GameManager 可能早于具体玩家、相机、武器对象出现。

ModeBase.Update / ModeBase.ExitGame：
适合判断当前模式实例已经进入主循环。很多需要主线程执行、需要房间稳定后再写入的功能，可以用它做 room_ready 触发。

模式专属函数，例如 OnStartNewGameRound、OnTimeOut、ChooseTrait：
适合只在特定模式里生效的功能。不要把模式专属 Hook 当成所有模式通用房间就绪信号。

玩家、武器、Bot、相机、HUD 等对象自己的 Hook：
适合对象出现后才 apply 的功能。比如依赖玩家实例，就在玩家相关函数命中后 apply；依赖最终相机，就在相机链路命中后 apply。

短周期 retry：
只能作为兜底。retry 必须能停止，必须有次数/日志节流，disable、cleanup、断开连接时必须清理。
```

推荐实现顺序：

```text
1. enable 保存用户意愿：enabled = true。
2. 尝试立即 apply 一次。
3. 如果对象未就绪，设置 pendingApply = true，不要把 UI 状态改回关闭。
4. 安装或复用本功能自己的 room_ready 触发源。
5. room_ready 触发后检查 enabled 是否仍为 true。
6. enabled 仍为 true 时执行 applyEnabledState。
7. apply 成功后设置 applied = true、pendingApply = false。
8. disable/cleanup/断开连接时清理 pending、applied、timer、hook、缓存指针。
```

可行性判断：

```text
用 GameManager 或 GameMode/ModeBase Hook 监听房间开启是可行的，而且通常比单纯等 Frida 连接更可靠。

但它不是唯一答案，也不能写成全局中心逻辑。每个功能要在自己的 features/<feature_dir>/script.js 里选择最稳定的触发点。

如果功能只需要知道“进房了”，优先考虑 GameManager.Awake + GameManager.OnDestroy 或 ModeBase.Update + ModeBase.ExitGame。

如果功能需要具体对象已经存在，例如玩家、相机、武器、Bot 静态字段，就必须等对应对象的 Hook 或可写地址出现后再 apply。

中心 UI 只负责保存 enabled 和连接后调用 restore_enabled；真正的房间就绪二次应用，应该留在功能插件自己的 JS 状态机里完成。
```



交付测试必须覆盖：

```text
1. 未进入游戏前开启功能
2. 再连接或进入游戏房间
3. 不手动关闭再开启，功能也能自动生效
4. 退出房间再进入，功能能再次按 UI 开关状态恢复
5. UI 关闭时 pendingApply 不会继续生效
```

## 10. 中心文件禁止事项

2.1 中心文件只做通用架构，不允许出现具体新功能分支。

中心文件包括：

```text
core/frida_manager.py
core/frida_runtime/script_manager.py
core/frida_runtime/rpc_client.py
core/plugin/manifest_loader.py
core/plugin/plugin_registry.py
ui/app.py
ui/views/plugin_tab_builder.py
ui/controllers/app_event_controller.py
ui/controllers/feature_action_controller.py
ui/controllers/action_router.py
core/state/app_state.py
core/config.py
```

禁止：

```text
if feature_id == "bot_pause"
if feature_id == "free_camera"
switch(feature_id) case "xxx"
为了新功能新增中心 controller
为了新功能新增中心 service
为了新功能修改 app.py 主流程
为了新功能恢复 core/feature_registry.py
为了新功能恢复 scripts/ 旧入口
```

如果某功能确实需要特殊事件处理，放在本功能目录：

```text
features/<feature_dir>/events.py
features/<feature_dir>/controller.py
features/<feature_dir>/service.py
```

## 11. 2.1 正式版接入流程

每次从 `05-正式功能` 接一个功能到 `全功能整合包x.x`，按这个顺序：

```text
1. 阅读单功能 JS、说明文档、经验总结
2. 确认原 JS 的 enable / disable / status / cleanup 行为
3. 从 game_modifier/features/_template/ 复制新插件目录
4. 将原 JS 完整复制为 features/<feature_dir>/script.js
5. 补齐或兼容 setConfig / setconfig / cleanup(payload)
6. 编写 manifest.json，声明 tab、config、rpc、lifecycle、state
7. 编写 feature.py，继承 PluginFeatureBase
8. 编写 panel.py，只使用通用 callbacks
9. 如有 JS 事件，编写 events.py
10. 不修改 ui/app.py、core/frida_manager.py 等中心文件
11. 运行 JS 语法检查
12. 运行 Python 编译检查
13. 运行 tools/check_architecture.py
14. 运行插件架构相关测试
15. 启动正式版 UI，测试开启/关闭/status/cleanup
16. 测试退出 UI、游戏断开、重开游戏、切房间
17. 更新发行版 CHANGELOG 或接入记录
```

## 14. 硬规则

```text
正式版不是功能试验田。
2.1 新功能必须走插件目录。
JS 核心逻辑先完整复制，再做最小适配。
中心文件不能出现具体功能 ID 分支。
独立单功能 UI 不能直接接入正式版。
能通过插件壳、manifest、配置、UI、RPC、生命周期完成接入，才说明功能适合进入正式版。
```
