# 程序文档

## 运行时文件与版本控制

本项目使用 `git rm --cached` 将运行时生成的数据文件（`data/*.json`）和日志文件（`inject_log.txt`、`esp_dllmain_test.txt` 等）从版本控制中移除。

这些文件由程序在运行期间动态生成或修改，每个用户的本地内容不同，不应纳入 Git 管理。

移除后，本地文件继续保留，但 Git 不再跟踪其变更；配合 `.gitignore` 规则，后续新生成的同类文件也不会被误提交。

执行 `git push` 后，远程仓库中对应的文件会被清理。

## 2026-06-20 连接性能与决战回合交互优化

### 修改文件

- `game_modifier/scripts/19-battle_round.js`
  - 删除开启时写入 `isBattleRound=1` 和关闭时写入 `isBattleRound=0` 的立即操作。
  - Frida连接后仅安装新回合与模式销毁生命周期Hook。
  - 新回合触发时先验证实例类指针必须等于 `Mode_Nano4_Terminator`，验证通过且用户开关为开启时才写入字段。
  - 主动发送进入模式、回合状态和退出模式事件。

- `game_modifier/scripts/15-buff_selector.js`
  - `ModeBase.Update` 调度Hook改为按需安装，有主线程请求时处理一帧，完成后立即解除。
  - 新回合事件只在需要时初始化或读取当前Buff，不再依靠持续轮询。

- `game_modifier/core/frida_manager.py`
  - 增加决战回合生命周期消息到Python事件总线的转发。

- `game_modifier/ui/app.py`
  - 决战回合开关始终可以操作，状态区分“已关闭、等待连接、等待多人生化、已启用、决战回合”。
  - 未连接或未进入模式时打开开关只保存用户意愿，不写游戏字段。
  - 删除每1秒决战状态查询、每2秒模式健康查询和每5秒Buff查询。
  - 基础状态栏建立后立即启动游戏进程检测，不再等待完整功能页面构建。
  - 全局快捷键延后到窗口显示后注册；JSON配置仍同步读取。

- `game_modifier/core/game_session_manager.py`
  - 核心连接顺序改为：检测进程 → 稳定确认 → Frida → 普通功能就绪。
  - 成功状态转换立即进入下一步，删除每一步固定2秒等待。
  - 未发现游戏时每0.8秒检测一次，连接后每3秒执行一次健康检查。
  - ESP关闭时不连接或注入Universal DLL；ESP开启后才在Frida就绪的后台阶段处理DLL。
  - 失败重试采用非阻塞退避，保留手动立即重连。

### 用户可见效果

- 程序打开后更早开始检测游戏，普通功能不再等待ESP DLL完成。
- ESP关闭时不会注入DLL；打开ESP后独立连接，普通功能保持可用。
- 决战回合可以在未进入多人生化、甚至未连接游戏时提前开启。
- 未进入多人生化时显示“已预约”，不会读取或写入 `isBattleRound`。
- 进入多人生化后，新回合事件自动激活；只有类指针验证通过时才写入 `isBattleRound=1`。
- 回合中途开启时从下一回合生效；关闭后停止后续回合写入，不强行改动当前回合。
- 退出多人生化后回到“已预约”状态，用户开关选择继续保留。

### 性能说明

- 取消Python端1秒、2秒、5秒定时RPC轮询。
- 多人生化主线程Update Hook不再永久存在，无任务时不会每帧空跑。
- 保留的新回合和销毁Hook只在对应生命周期触发，平时没有持续查询。
- 本次未实现Frida合并脚本缓存，也没有生成新的缓存文件。
