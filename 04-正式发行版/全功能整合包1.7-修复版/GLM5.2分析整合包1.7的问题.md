## 渐进式重构方案（4 个阶段，每阶段都有可验证产出）

### 阶段 0：止血 + 可观测性（半天，零结构改动）

**目标**：先让软件"能用、能查问题"，不碰结构。

- 把 `battle_round_always.enabled` 默认改 `false`（闪退止血）
- 把 ESP DLL 改成**条件注入**（只有用户开方框透视才注入）+ 轮询加指数退避（卡顿止血）
- 引入 Python 标准 `logging`，日志**落盘**到 `logs/` 文件，加 `trace_id` 贯穿一次操作

**产出验证**：用户反馈卡顿/闪退消失；日志文件能定位到具体崩溃前的最后一步。

### 阶段 1：建安全网——真假测试 + Fake 游戏环境（1-2 天，最关键）

**目标**：在动结构之前，先有能兜底的真测试。这是整个方案的重心。

- 写一个 `FakeFrida`（假的 frida 后端，记录所有 `call_export`/`send_toggle` 调用，不连真游戏）
- 把假测试（字符串断言）全部改写成**行为测试**：给定输入 → 断言 FakeFrida 收到了正确的调用序列
- 重点覆盖：连接/断连/重连状态机、feature 开关、nano4t 模式守卫、持久化读写

**产出验证**：`pytest --cov` 能跑出覆盖率；故意改坏一个 feature 的逻辑，测试会红。

### 阶段 2：拆黑盒——三层分离（3-5 天，渐进推进）

**目标**：把上帝类拆成清晰的三层，每层可独立测试。

```
UI层(app.py，只管渲染和事件) 
    ↓ 调用
Feature层(每个feature自己封装逻辑+模式守卫，不再旁路) 
    ↓ 调用
Service层(FridaService/DllService/SessionService，可注入Fake)
```

做法是 **Strangler Fig（绞杀者模式）**：不一次性重写 app.py，而是**一个 feature 一个 feature 地迁移**——每迁一个，先补行为测试，再动代码。迁完一个就验证一次，随时能停。

**关键**：消灭"假 feature 系统"——让 `FeatureRegistry` 成为唯一真相源，UI 自动从它生成开关（不再硬编码 switch_map）。

**产出验证**：每迁移一个 feature，`pytest` 全绿 + 真机手动验证一次；app.py 从 1818 行降到 < 800 行。

### 阶段 3：治理单例与并发（2-3 天，最后做）

**目标**：消除偶发 bug 的温床。

- 把"方法内 `get_instance()`"改成**构造函数依赖注入**（Service 层从外部传入，测试时传 Fake）
- 事件总线改成**同步 emit + 主线程派发**（用队列代替每事件开新线程）
- App 共享状态加锁或迁到单线程

**产出验证**：压测（快速开关/重连/切房间）跑 50 次无偶发崩溃。

## 为什么是这个顺序，不能乱

```
阶段0 止血   → 先让软件能用、能查（否则用户还在骂，你也没动力）
阶段1 测试网 → 必须在动结构之前！没网就别拆黑盒
阶段2 拆分层 → 有了网，才敢一个一个迁移 feature
阶段3 治并发 → 最难，放最后，且要靠前面的测试网兜底
```

**核心原则：测试先行，每步可验证，随时可停。** 这样即使中途你放弃重构，前面每一阶段都已经留下了独立价值（止血的软件、落盘的日志、能跑的行为测试）。

## 给你的一个关键建议

你说"一直用AI编程导致黑盒"——AI 适合写**有明确边界、能被测试**的小单元。它不擅长写 1818 行的上帝类，因为没人能 review 那么长的上下文。所以这次重构的本质是：**把大黑盒切成小盒子，每个小盒子都有测试兜着**。重构完成后，你反而可以更安全地继续用 AI——因为每个 feature 都是小而独立、可测的。
