📊 项目概览

🎯 项目简介

这是一个穿越火线游戏修改器，使用 Python + Frida + JavaScript + C++ DLL 技术栈开发。程序通过注入代码到游戏进程，实现各种游戏功能修改。

通俗理解：想象你有一个遥控器，可以控制游戏里的各种参数（比如移动速度、武器威力等）。这个项目就是制作这个遥控器的工具。

💡 设计巧思

1. 单例模式 - 全局唯一实例

👑 什么是单例？

通俗解释：单例就是"一个国家只有一个总统"。程序中的某些管理器（比如EventBus、FridaManager）只能有一个实例，不能创建多个。

单例模式代码：
class EventBus:
    _instance = None  # 类变量，保存唯一实例
    _lock = threading.Lock()  # 线程锁
    
    @classmethod
    def get_instance(cls):
        if cls._instance is None:  # 如果还没有实例
            with cls._lock:  # 加锁（防止多线程同时创建）
                if cls._instance is None:
                    cls._instance = cls()  # 创建实例
        return cls._instance  # 返回唯一实例

为什么使用单例？因为EventBus是"广播站"，如果有多个广播站，消息就会混乱。FridaManager是"注入管理器"，如果有多个，就会重复注入导致游戏崩溃。

有多例吗？有！比如功能模块（knife.py, movespeed.py等）就不是单例，每个功能都是独立的实例，可以同时存在多个功能。

2. 事件总线 - 模块间通信

📡 模块间的广播站

通俗解释：EventBus就像一个广播站，一个模块发送消息，所有订阅了该消息的模块都能收到。比如UI层发送"游戏已连接"消息，日志模块、音效模块都能收到并做出反应。

事件总线使用：
# 订阅消息（收听广播）
bus = EventBus.get_instance()
bus.subscribe('connection_status', self._on_connection_changed)

# 发送消息（广播）
bus.emit('connection_status', status='connected', pid=1234)

# 处理消息（收到广播后执行）
def _on_connection_changed(self, status, pid):
    if status == 'connected':
        print(f"游戏已连接，PID: {pid}")

3. 功能注册表 - 统一管理功能

📋 功能的花名册

通俗解释：FeatureRegistry就像一个花名册，记录了所有功能模块。程序启动时，所有功能模块自动注册到花名册中，方便统一管理。

❌ 没有功能注册表
  • ❌ 需要手动创建每个功能实例
  • ❌ 需要手动管理功能列表
  • ❌ 新增功能需要修改多处代码
  • ❌ 容易遗漏或重复
  • ❌ 难以统一查询和遍历
✅ 有功能注册表
  • ✅ 自动注册，无需手动创建
  • ✅ 统一管理，一处查询所有功能
  • ✅ 新增功能只需加装饰器
  • ✅ 不会遗漏或重复
  • ✅ 方便遍历和查询
使用装饰器自动注册：
# 定义功能模块时，加一个装饰器就自动注册了
@register_feature  # 这个装饰器会自动把功能注册到FeatureRegistry
class KnifeFeature(FeatureBase):
    feature_id = 'knife'
    name = '快刀'
    # ...

# 程序启动后，可以这样获取所有功能
registry = FeatureRegistry.get_instance()
all_features = registry.get_all()  # 获取所有功能
knife_feature = registry.get('knife')  # 获取特定功能

这里收集了新手常见问题，用通俗易懂的语言解答。如果你有其他问题，欢迎提问！

❓ 问题1：业务逻辑层是什么意思，为什么都是py代码，业务逻辑不应该是js代码吗？

答：这是一个很好的问题！让我用游戏修改的思维来解释：

通俗理解：想象你在玩一个遥控车。Python代码就是遥控器，JavaScript代码就是遥控车里的接收器。你在遥控器上按按钮（Python），遥控器发送信号给接收器（JavaScript），接收器控制遥控车移动。

为什么业务逻辑用Python？

  • Python是主程序：负责界面显示、用户交互、功能管理等"指挥"工作
  • JavaScript是注入代码：负责修改游戏内存、Hook函数等"执行"工作
  • 分工明确：Python负责"做什么"，JavaScript负责"怎么做"

举个例子：

Python（业务逻辑层）：
# knife.py - 快刀功能的业务逻辑
class KnifeFeature(FeatureBase):
    def enable(self):
        # 告诉注入层：请开启快刀功能
        FridaManager.get_instance().send_toggle('knife', True)
    
    def disable(self):
        # 告诉注入层：请关闭快刀功能
        FridaManager.get_instance().send_toggle('knife', False)
JavaScript（注入层）：
// knife.js - 快刀功能的注入代码
var knifeModule = {
    enable: function() {
        // 修改游戏内存，提升挥刀速度
        Memory.writeFloat(speedAddress, 10.0);
    },
    disable: function() {
        // 恢复游戏内存，还原挥刀速度
        Memory.writeFloat(speedAddress, 1.0);
    }
};

总结：Python是"指挥官"，JavaScript是"士兵"。指挥官发号施令，士兵执行任务。所以业务逻辑在Python中，注入代码在JavaScript中。

❓ 问题2：业务逻辑和注入层是如何联系的？

答：业务逻辑层和注入层通过Frida工具进行通信。让我详细解释这个联系过程：

1
用户点击开关
用户在Python界面点击"快刀"开关
⬇️
2
业务逻辑层处理
knife.py 调用 FridaManager.send_toggle('knife', True)
⬇️
3
Frida发送消息
FridaManager 通过Frida的IPC机制发送消息到游戏进程
⬇️
4
注入层接收消息
游戏内的JavaScript代码接收到消息
⬇️
5
修改游戏内存
JavaScript代码修改游戏的内存地址，实现快刀功能
FridaManager 发送消息的代码：
# frida_manager.py
def send_toggle(self, feature_id, enabled):
    """发送功能开关消息到注入层"""
    if self._script:
        # 通过Frida的script.send()发送消息
        self._script.post({
            'type': 'toggle',
            'feature': feature_id,
            'enable': enabled
        })
注入层接收消息的代码：
// _common.js
// 监听来自Python的消息
recv('toggle', function(data) {
    var featureName = data.feature;
    var enable = data.enable;
    
    // 根据功能名调用对应的模块
    if (featureName === 'knife') {
        if (enable) {
            modules.knife.enable();  // 开启快刀
        } else {
            modules.knife.disable(); // 关闭快刀
        }
    }
});

通俗理解：Frida就像一个"翻译官"，把Python的指令翻译成JavaScript能理解的消息，然后发送到游戏内部。JavaScript收到消息后，执行对应的操作。

❓ 问题3：核心管理层里面的文件都做了什么事情？

答：核心管理层是程序的"大脑"，负责协调各个模块的工作。让我结合代码详细解释每个文件的作用：

1. game_session_manager.py - 游戏会话管理器

作用：检测游戏是否运行，自动连接/断开，管理整个游戏会话的生命周期。

核心代码解析：
class GameSessionManager:
    def _worker_loop(self):
        """后台线程，每2秒执行一次状态机"""
        while not self._stop_event.is_set():
            self._state_machine_step()  # 执行状态机的一步
            time.sleep(2)
    
    def _step_no_game(self):
        """步骤1：没有检测到游戏"""
        pid, create_time = self._find_game_process()  # 查找游戏进程
        if pid is None:
            return  # 没找到，继续等待
        
        # 找到了，进入下一步
        self._state = SessionState.WAITING_GAME_READY
        self._bus.emit('log_message', message=f'检测到游戏进程 PID:{pid}')
    
    def _step_waiting_game_ready(self):
        """步骤2：等待游戏稳定"""
        # 等待0.5秒，确保游戏进程稳定
        time.sleep(self._stability_wait)
        
        # 检查进程是否还在运行
        if not self._is_process_stable(pid):
            self._state = SessionState.NO_GAME  # 进程不稳定，重新检测
            return
        
        # 进程稳定，进入下一步
        self._state = SessionState.CONNECTING_EXISTING_DLL

游戏修改思维：就像你等朋友上线玩游戏，先看他在不在线（检测进程），然后等他准备好（等待稳定），最后开始游戏（连接注入）。

class EventBus:
    def subscribe(self, event_type, callback):
        """订阅消息（收听广播）"""
        self._subscribers[event_type].append(callback)
    
    def emit(self, event_type, **kwargs):
        """发送消息（广播）"""
        for callback in self._subscribers[event_type]:
            # 在新线程中执行回调，避免阻塞
            threading.Thread(target=callback, kwargs=kwargs).start()

def _find_game_process(self):
    """查找游戏进程"""
    for proc in psutil.process_iter(['pid', 'name', 'create_time']):
        try:
            # 检查进程名是否是游戏进程
            if proc.info['name'] == 'crossfire.exe':  # 游戏进程名

检测游戏是否关闭的逻辑

代码位置：game_session_manager.py 第 152-180 行
def _step_waiting_game_ready(self):
    """状态机步骤：等待游戏稳定"""
    pid, create_time = self._find_game_process()
    
    # 检查PID是否变化（游戏重启了）
    if pid != self._pid or create_time != self._pid_create_time:
        # PID变了，说明游戏重启了，重新检测
        self._pid = pid
        self._pid_create_time = create_time
        return
    
    # 检查进程是否还在运行
    if not self._is_process_stable(pid):
        # 进程不在了，游戏已关闭
        with self._lock:
            self._state = SessionState.NO_GAME  # 回到初始状态
            self._pid = None
            self._pid_create_time = None
        self._bus.emit('log_message', level='warning',
                       message='游戏进程不稳定，重新检测')
        return

def _is_process_stable(self, pid):
    """检查进程是否稳定（是否还在运行）"""
    try:
        proc = psutil.Process(pid)
        return proc.is_running()  # 进程还在运行返回True
    except psutil.NoSuchProcess:
        return False  # 进程不存在，游戏已关闭

通俗解释：程序会持续检查进程是否还在运行。如果进程不存在了（游戏关闭），就回到"没有游戏"状态，重新等待游戏启动。

❓ 问题7：初始化管理器（单例模式）是什么意思？什么是单例，为什么使用单例？还有多例吗？

答：让我用游戏修改的思维来解释单例模式：

什么是单例？

通俗解释：单例就是"一个国家只有一个总统"。在程序中，某些管理器只能有一个实例，不能创建多个。

游戏修改思维：想象你在玩游戏，如果游戏里有多个"系统设置"窗口，你会很困惑：到底该改哪一个？单例模式就是确保只有一个"系统设置"窗口，避免混乱。

为什么使用单例？

❌ 不使用单例（多例）
  • ❌ 可能创建多个EventBus实例
  • ❌ 消息发送到不同的EventBus，接收方收不到
  • ❌ 可能创建多个FridaManager实例
  • ❌ 重复注入导致游戏崩溃
  • ❌ 资源浪费，状态混乱
✅ 使用单例
  • ✅ 全局只有一个EventBus实例
  • ✅ 所有模块通过同一个EventBus通信
  • ✅ 全局只有一个FridaManager实例
  • ✅ 避免重复注入，游戏稳定
  • ✅ 节省资源，状态统一

哪些是单例？哪些是多例？

类型 类名 为什么
单例 EventBus 全局消息广播站，只能有一个
FridaManager 注入管理器，重复注入会导致崩溃
GameSessionManager 游戏会话管理，只能有一个游戏连接
FeatureRegistry 功能注册表，统一管理所有功能
UniversalHookManager DLL注入管理，避免重复注入
多例 KnifeFeature 快刀功能，每个功能都是独立实例
MovespeedFeature 移动速度功能，每个功能都是独立实例
GravityFeature 重力修改功能，每个功能都是独立实例
单例模式的实现：
class EventBus:
    _instance = None  # 类变量，保存唯一实例
    _lock = threading.Lock()  # 线程锁
    
    @classmethod
    def get_instance(cls):
        """获取单例实例"""
        if cls._instance is None:  # 第一次调用
            with cls._lock:  # 加锁（防止多线程同时创建）
                if cls._instance is None:
                    cls._instance = cls()  # 创建实例
        return cls._instance  # 返回唯一实例

# 使用方法
bus1 = EventBus.get_instance()
bus2 = EventBus.get_instance()
# bus1 和 bus2 是同一个对象！

❌ 不支持持久化的功能（1个）

功能ID 功能名称 为什么不同
esp_box ESP透视 通过DLL实现，状态管理方式不同

为什么ESP功能不同？ESP透视功能是通过DLL注入实现的（高性能需求），而其他大部分功能是通过Frida的JavaScript注入实现的。DLL的状态管理与JavaScript注入的功能不同，所以使用了不同的持久化文件（desired_states.json）。

总结：95%的功能都支持持久化，只有ESP透视功能使用了不同的持久化方式。这样的设计既保证了大部分功能的用户体验，又满足了特殊功能的需求。
