# 单功能开发-生命周期规范

这份规范用于所有 `05-正式功能/XX-功能名/` 下的单功能脚本。

## 0. 本文档职责

本文档只规定 JS 运行期怎么安全管理 Hook、指针、定时器、状态、cleanup、切房间和进房后二次应用。

它不重复维护单功能目录结构，也不重复维护 2.1 manifest 字段：

```text
单功能目录和交付物：看《01-单功能开发规范：面向正式发行版.md》
单功能开发顺序：看《单功能开发-可复用流程.md》
整合包2.1接入字段：看 04-正式发行版/00-正式发行版功能接入规范.md
```

如果某个功能将来进入 2.1，本规范里的运行期状态机仍然适用；具体 manifest 写法以正式接入规范为准。

目标是解决这些问题：

```text
切房间后旧指针还在用
退出房间后继续写旧对象
死亡/重生后玩家对象变化
切武器后武器指针失效
关闭功能后定时器还在跑
UI 退出后 Frida 脚本没有清理
异常后功能状态和真实状态不一致
```

一句话原则：

```text
Hook 可以长期存在，指针不能长期相信。
状态可以保存，游戏对象指针必须随房间/玩家/武器变化重新确认。
cleanup 必须可以重复调用，重复调用不能崩。
```

---

## 1. 成熟方案的核心思路

成熟的修改器/插件系统一般不是“拿到一个指针一直用”。

成熟做法是：

```text
静态信息长期保存
运行期指针短期使用
对象每次使用前验证
房间/模式/死亡/重生时清空缓存
功能开关只改 enabled 状态
cleanup 统一释放定时器、Hook 句柄、缓存、原值记录
```

也就是把数据分成两类：

### 1.1 可以长期保存的东西

这些可以长期保存：

```text
GameAssembly.dll 基址
RVA
函数地址
字段偏移
NativeFunction 对象
Hook 句柄
功能配置
日志计数器
```

这些东西和当前房间无关，通常不用因为切房间清理。

### 1.2 不能长期相信的东西

这些不能长期保存：

```text
Player*
Weapon*
PlayerWeapons*
Camera*
Transform*
当前武器 data 指针
当前房间对象
当前模式对象
当前 UI 对象
从游戏对象里读出来的子对象指针
```

这些指针只在当前场景、当前房间、当前生命周期内可信。

一旦出现下面情况，必须认为旧指针可能失效：

```text
进入房间
退出房间
切换地图
切换模式
死亡
重生
换武器
返回大厅
重新开始一局
游戏进程重启
Frida 重新 attach
```

### 1.3 不是指针但仍然不能跨生命周期复用的状态

有些数据本身不是指针，但它们依赖当前房间、地图、模式或玩家对象，也不能跨生命周期长期复用。

典型例子：

```text
当前房间保存的坐标点
当前地图里的目标位置
当前玩家身上的临时标记
等待下一帧执行的 pending save / pending teleport
依赖当前武器/玩家/模式算出来的派生值
只对当前 generation 有意义的功能应用状态
```

规则：

```text
resetRuntime(reason) 必须同时清理缓存指针和这些生命周期绑定状态。
如果某个状态只在当前房间、当前玩家、当前武器或当前模式里有意义，就必须挂到 generation 上。
跨房间可以保留用户配置，但不能保留运行态点位、运行态目标、pending 动作和旧对象派生值。
```

## 2. 每个单功能必须有统一 Runtime 状态

每个 JS 单功能都必须有一个统一的运行期对象。

推荐名字：

```js
const Runtime = {
    name: "功能名",
    enabled: false,
    initialized: false,

    // 当前生命周期编号
    generation: 0,

    // Hook 句柄
    hooks: [],

    // 定时器句柄
    timers: [],

    // 当前缓存指针
    cache: {
        localPlayer: ptr(0),
        currentWeapon: ptr(0),
        playerWeapons: ptr(0),
        lastRoomObject: ptr(0)
    },

    // 原值记录，只记录当前 generation 内的原值
    originals: {},

    // 只对当前 generation 有意义的挂起动作和运行态状态
    pending: {},
    transient: {},

    // 统计和日志
    stats: {
        hookHits: 0,
        skippedNull: 0,
        skippedInvalid: 0,
        cleanupCount: 0,
        errorCount: 0,
        lastReason: ""
    }
};
```

要求：

```text
所有状态都放 Runtime 里。
不要到处散落 enabled、timerId、playerPtr。
不要用全局变量乱存当前 Player/Weapon。
```

## 3. generation 机制

每个功能必须有 `generation` 概念。

它的作用是区分“旧房间的数据”和“新房间的数据”。

规则：

```text
脚本加载时 generation = 0
每次 resetRuntime(reason) 时 generation += 1
缓存指针、原值记录、临时状态都只属于当前 generation
发现 generation 不一致，直接丢弃旧数据
```

推荐实现：

```js
function resetRuntime(reason) {
    Runtime.generation += 1;

    Runtime.cache.localPlayer = ptr(0);
    Runtime.cache.currentWeapon = ptr(0);
    Runtime.cache.playerWeapons = ptr(0);
    Runtime.cache.lastRoomObject = ptr(0);

    Runtime.originals = {};
    Runtime.pending = {};
    Runtime.transient = {};
    Runtime.stats.lastReason = reason || "unknown";

    logOnce("reset", "runtime reset, reason=" + reason + ", gen=" + Runtime.generation);
}
```

如果功能有明确的运行态字段，也要在 `resetRuntime` 里逐项清理，不要只清指针：

```js
function resetRuntime(reason) {
    Runtime.generation += 1;

    Runtime.cache.localPlayer = ptr(0);
    Runtime.cache.currentWeapon = ptr(0);

    Runtime.savedPoint = null;
    Runtime.pending.save = false;
    Runtime.pending.teleport = false;
    Runtime.pendingApply = Runtime.enabled;

    Runtime.originals = {};
    Runtime.stats.lastReason = reason || "unknown";
}
```

什么时候调用：

```text
disable()
cleanup()
检测到玩家对象变化
检测到房间对象变化
检测到武器 owner 变化
检测到连续异常
UI 断开
游戏进程退出
```

## 4. 指针使用规则

### 4.1 不允许裸用缓存指针

错误写法：

```js
Runtime.cache.localPlayer.add(0x20).readS32();
```

原因：

```text
localPlayer 可能已经是上一局的对象。
退出房间后这个地址可能被释放或复用。
```

正确写法：

```js
const player = getValidLocalPlayer();
if (player.isNull()) return;
```

---

### 4.2 每次使用前必须验证

至少验证：

```text
指针不是 NULL
指针可读
对象归属是本地玩家
字段读取没有异常
必要时重新通过游戏逻辑确认
```

推荐封装：

```js
function isReadablePtr(p) {
    try {
        if (!p || p.isNull()) return false;
        p.readPointer();
        return true;
    } catch (e) {
        return false;
    }
}

function safeReadPointer(base, offset) {
    try {
        if (!isReadablePtr(base)) return ptr(0);
        const p = base.add(offset).readPointer();
        if (!isReadablePtr(p)) return ptr(0);
        return p;
    } catch (e) {
        Runtime.stats.skippedInvalid++;
        return ptr(0);
    }
}
```

### 4.3 RPC 不能直接写运行态游戏对象

UI 调用 JS RPC 时，RPC 运行在 Frida 调用链里，不等同于游戏自己的 `Update`、`Tick`、物理或角色逻辑线程。

因此 RPC 不应该直接做这些事情：

```text
直接调用会修改 Unity / 游戏对象状态的 NativeFunction
直接写 Player、Weapon、Transform、CharacterController、Camera 等运行态对象
直接用缓存 Player* 执行瞬移、移动、开火、换武器、相机切换等动作
直接在 RPC 里执行依赖当前帧游戏状态的重逻辑
```

正确做法：

```text
RPC 只表达用户意愿：设置 pending 标记、更新配置、返回 status。
真正读写游戏对象的逻辑，放到游戏自己的 Hook 点里执行。
优先选择 Player.Update、Weapon.Update、CharacterController.Move、ModeBase.Update、Camera 更新点等和功能对象一致的 Hook。
Hook 里拿当次参数或当帧重新确认的对象，执行一次 pending 动作后立即清掉 pending。
resetRuntime / disable / cleanup 必须清掉所有 pending 动作。
```

最小示例：

```js
function requestTeleport() {
    if (!Runtime.savedPoint) return false;
    Runtime.pending.teleport = true;
    return true;
}

function onPlayerUpdate(player) {
    if (!Runtime.enabled) return;
    if (!captureLocalPlayer(player, "Player.Update")) return;

    if (Runtime.pending.teleport) {
        Runtime.pending.teleport = false;
        native.playerSetPos(player, Runtime.savedPoint.x, Runtime.savedPoint.y, Runtime.savedPoint.z, ptr(0));
    }
}

rpc.exports = {
    teleport() {
        requestTeleport();
        return buildStatus();
    }
};
```

例外情况必须写明理由：

```text
只读 status / config 可以直接在 RPC 里做。
纯 JS 状态更新可以直接在 RPC 里做。
如果必须在 RPC 里调用 NativeFunction，必须确认该函数不依赖 Unity 当前帧、不写运行态对象、不触发物理/场景/对象生命周期变化，并在简要说明里记录理由。
```

## 5. Hook 安装和功能开关分离

成熟做法：

```text
Hook 尽量只安装一次。
enable() 只设置 Runtime.enabled = true。
disable() 只设置 Runtime.enabled = false，并清理运行期缓存。
cleanup() 才真正释放 Hook、定时器、缓存。
```

不要每次开关都重复 attach。

推荐：

```js
function installHooks() {
    if (Runtime.initialized) return;

    const h = Interceptor.attach(addrTarget, {
        onEnter(args) {
            Runtime.stats.hookHits++;

            if (!Runtime.enabled) return;

            try {
                // 功能逻辑
            } catch (e) {
                Runtime.stats.errorCount++;
                if (Runtime.stats.errorCount >= 5) {
                    Runtime.enabled = false;
                    resetRuntime("too many errors");
                }
            }
        }
    });

    Runtime.hooks.push(h);
    Runtime.initialized = true;
}
```

## 6. Interceptor.attach 和 Interceptor.replace 的规范

### 6.1 优先使用 attach

适合场景：

```text
只想观察参数
只想临时改字段
只想在原函数前后补逻辑
需要保留原游戏逻辑
```

优点：

```text
风险低
容易 detach
不破坏原函数
适合单功能测试
```

---

### 6.2 replace 必须写明理由

只有这些情况才建议 replace：

```text
原函数本身就是限制点
原函数执行后一定会覆盖你的修改
原函数有明确返回值，替换后逻辑更简单
已经确认不会破坏房间/模式状态
```

使用 replace 必须记录：

```text
原函数 RVA
原函数作用
替换返回值
为什么不能用 attach
如何恢复
```

cleanup 里必须处理：

```js
function cleanupHooks() {
    for (const h of Runtime.hooks) {
        try {
            if (h && h.detach) h.detach();
        } catch (e) {}
    }

    Runtime.hooks = [];

    // 如果用了 Interceptor.replace，要在这里 revert
    // Interceptor.revert(addrTarget);
    // Interceptor.flush();

    Runtime.initialized = false;
}
```

---

### 6.3 生命周期 Hook 与指针缓存清理

有缓存游戏对象指针的功能，必须覆盖对应生命周期清理场景。

可以按功能需要组合使用：

```text
GameRoundEnd
NewGameRoundStart
ModeBase.ExitGame
GameManager.OnDestroy
Player.OnDestroy
cleanup
disable
游戏断开 / 重新 attach
```

规则：

```text
多个功能可以同时使用 Interceptor.attach 监听同一个生命周期函数。
禁止使用 Interceptor.replace 覆盖生命周期函数。
生命周期 Hook 内只做 resetRuntime / clear cache / set flag，不做重逻辑。
禁止在生命周期 Hook 内主动调用 GameRoundEnd / ResetRound 等游戏状态机函数。
每个 Hook 回调必须 try/catch。
Hook handle 必须保存，cleanup 时必须 detach。
同一个功能内部必须有 initialized 保护，避免重复安装 Hook。
调用游戏 NativeFunction 前，必须先判断指针是否为空、是否可读。
```

按钮、滑块、RPC 的保留规则：

```text
正式版要给用户使用的入口：保留，并写入 manifest / panel / JS / 测试。
单功能调试用、正式版暂不接入的入口：可以留在 05 单功能 UI，但必须在说明里标注“仅单功能调试使用，正式版是否接入待定”。
已经确认废弃或不对用户开放的入口：同步清理 JS RPC、单功能 UI、正式版 manifest/panel 和测试。
```

判断标准：

```text
缓存的指针可能跨回合复用：
必须在 GameRoundEnd / NewGameRoundStart 或等价回合边界清空。

缓存的指针可能跨房间复用：
必须在 ModeBase.ExitGame / GameManager.OnDestroy 或等价房间边界清空。

依赖本地玩家、武器、相机、Bot 等运行态对象：
必须等对象重新出现后重新捕获，不允许长期使用旧指针。
```

## 7. 定时器规范

默认不推荐高频 `setInterval` 硬写内存。

优先级：

```text
优先 Hook 游戏自己的 Update / Tick / 关键方法
其次低频定时检查状态
最后才考虑高频写内存
```

如果必须用定时器：

```text
必须保存 timerId
必须在 disable/cleanup 清理
频率必须写明理由
日志必须限频
定时器里不能直接相信旧指针
```

推荐：

```js
function addTimer(fn, intervalMs) {
    const id = setInterval(() => {
        try {
            fn();
        } catch (e) {
            Runtime.stats.errorCount++;
        }
    }, intervalMs);

    Runtime.timers.push(id);
    return id;
}

function cleanupTimers() {
    for (const id of Runtime.timers) {
        try {
            clearInterval(id);
        } catch (e) {}
    }

    Runtime.timers = [];
}
```

建议频率：

```text
状态检测：500ms - 1000ms
普通功能维护：100ms - 250ms
相机/视角类：优先 Hook Update，不建议普通定时器硬刷
```

## 8. 原值恢复规范

如果功能修改了字段，必须考虑恢复。

但是恢复不能乱写旧指针。

规则：

```text
只恢复当前 generation 内记录的原值
恢复前必须验证指针仍然有效
如果指针已经失效，宁可放弃恢复，也不要写旧地址
退出房间后的旧对象不要强行恢复
```

推荐原值结构：

```js
function rememberOriginal(ptrObj, offset, value) {
    const key = Runtime.generation + ":" + ptrObj.toString() + ":" + offset;
    if (!(key in Runtime.originals)) {
        Runtime.originals[key] = {
            ptr: ptrObj,
            offset: offset,
            value: value,
            generation: Runtime.generation
        };
    }
}
```

恢复：

```js
function restoreOriginals() {
    for (const key in Runtime.originals) {
        const item = Runtime.originals[key];

        if (item.generation !== Runtime.generation) continue;
        if (!isReadablePtr(item.ptr)) continue;

        try {
            item.ptr.add(item.offset).writeFloat(item.value);
        } catch (e) {
            Runtime.stats.skippedInvalid++;
        }
    }

    Runtime.originals = {};
}
```

注意：

```text
退出房间、切图、重生后，不要强行恢复旧对象。
因为旧地址可能已经被释放或变成别的对象。
```

## 9. 房间/模式切换处理

每个功能都要有“房间边界意识”。

### 9.1 最低要求

如果暂时没有找到准确的房间生命周期函数，至少做到：

```text
发现 localPlayer 从有效变成 NULL，resetRuntime("player lost")
发现 localPlayer 地址变化，resetRuntime("player changed")
发现 currentWeapon 地址变化，清理武器缓存
发现连续 N 次读取失败，resetRuntime("invalid pointers")
```

---

### 9.2 推荐方案

找到游戏里的房间/模式生命周期函数后，优先 Hook：

```text
进入房间
退出房间
模式开始
模式结束
玩家创建
玩家销毁
玩家重生
武器切换
```

Hook 到这些函数时：

```text
不要在里面做重逻辑
只做标记和 resetRuntime
真正功能逻辑仍在自己的 Hook 点里执行
```

---

### 9.3 UI 已开启但进房后未生效

这是所有依赖房间运行态对象的功能都要处理的问题。

常见原因：

```text
程序启动时 UI 已经是开启状态
连接游戏后 restore/enable 被调用
enable 当时游戏还没进入房间
玩家、Bot、相机、武器、GameManager、ModeBase 等对象还没创建
enable 尝试 apply 失败后没有等待下一次房间就绪
进房后 UI 仍显示开启，但真实游戏逻辑没有生效
必须手动关一次再开一次
```

正确做法：

```text
enable 只代表用户意愿：Runtime.enabled = true
apply 成功才代表运行态已生效：Runtime.applied = true
对象未就绪时进入等待：Runtime.pendingApply = true
房间、模式、相机、玩家、Bot、武器等触发源命中后再次 apply
disable/cleanup 时清理 pendingApply、applied、timer、缓存指针
status 必须暴露 enabled、applied、pendingApply、lastApplyReason
```

推荐状态字段：

```js
const Runtime = {
    enabled: false,
    applied: false,
    pendingApply: false,
    generation: 0,
    lastApplyReason: "",
    timers: [],
    hooks: []
};
```

推荐流程：

```text
1. enable 设置 enabled=true。
2. 立即尝试 applyEnabledState("enable")。
3. 如果对象未就绪，设置 pendingApply=true。
4. 安装或复用自己的 room-ready 触发源。
5. 触发源命中后，如果 enabled 仍为 true，再执行 applyEnabledState("room_ready")。
6. apply 成功后设置 applied=true、pendingApply=false。
7. disable/cleanup 时清理 pending、applied、timer、缓存。
```

room-ready 触发源要按功能依赖选择：

```text
只需要知道进房：GameManager.Awake、ModeBase.Update、ModeBase.ExitGame、GameManager.OnDestroy
依赖玩家：Player 相关 Hook 或 localPlayer 捕获点
依赖武器：Weapon / PlayerWeapons 相关 Hook
依赖 Bot：Bot.Update 或 Bot 静态字段可写时
依赖相机：CameraManager.Awake、CinemachineBrain、Unity Camera 更新点
```

不要把这件事写成全局中心逻辑。中心 UI 只负责保存开关状态和连接后恢复；真正的进房后二次应用，应该由每个功能自己的 JS 状态机完成。

## 10. 死亡、重生、换武器处理

玩家死亡和重生通常会导致对象状态变化。

要求：

```text
不要假设 Player 指针永远不变
不要假设 Weapon 指针永远不变
不要假设 PlayerWeapons 永远不变
```

推荐处理：

```text
玩家死亡：停止写玩家状态类字段
玩家重生：重新获取 localPlayer
切武器：清空 currentWeapon 缓存
武器 owner 变化：重新判断 get_isMyWeapon
```

武器类功能必须每次确认：

```text
Weapon 指针有效
Weapon 属于本地玩家
Weapon.data 有效
需要时 owner/playerWeapons 有效
```

## 11. UI 和 JS 的 RPC 规范

每个单功能 JS 必须导出：

```js
rpc.exports = {
    enable() {},
    disable() {},
    status() {},
    cleanup() {}
};
```

推荐额外导出：

```js
reset(reason) {}
```

语义：

```text
enable：开启功能，不重复安装 Hook
disable：关闭功能，恢复能恢复的值，清理运行期缓存
status：返回当前状态、命中次数、错误次数、generation
cleanup：UI 退出/脚本卸载时调用，释放所有资源
reset：手动清理缓存，用于排查切房间问题
```

RPC 分工要求：

```text
RPC 可以改用户配置。
RPC 可以设置 Runtime.enabled。
RPC 可以设置 pending 动作。
RPC 可以返回 status。
RPC 不直接写当前 Player/Weapon/Camera/Transform 等运行态对象。
RPC 不直接调用会改变当前房间对象状态的 NativeFunction。
```

对于按钮触发型功能，比如“保存当前位置”“瞬移到保存点”“立即应用一次”，推荐统一写成：

```text
按钮 RPC：只设置 Runtime.pending.xxx = true。
游戏 Hook：在下一次 Update / Move / Tick 命中时执行 pending 动作。
执行后：立即清掉 pending，记录成功/失败原因。
resetRuntime：清掉 pending，避免切房间后执行旧动作。
status：暴露 pending_xxx，方便 UI 和日志排查。
```

UI 侧要求：

```text
CustomTkinter UI 启动后自动等待并连接 UnityCrossFire.exe
游戏进程重启或断开后，UI 必须停止轮询旧脚本状态，并等待下一次连接
重新 attach 后必须重新加载 JS，并按用户当前 UI 开关状态重新调用 setConfig / enable
窗口退出时必须调用 cleanup；cleanup 失败也不能阻塞 UI 关闭
```

## 12. enable / disable / cleanup 标准行为

### 12.1 enable()

必须做：

```text
安装 Hook，如果已经安装就跳过
设置 enabled = true
清空错误计数
记录日志
```

不应该做：

```text
不要缓存当前 Player 后一直用
不要启动多个重复定时器
不要重复 attach 同一个 Hook
```

---

### 12.2 disable()

必须做：

```text
enabled = false
恢复当前 generation 内可安全恢复的原值
清理运行期缓存
清理普通定时器
保留 Hook 也可以，但 Hook 内必须判断 enabled
```

推荐：

```js
function disableFeature() {
    Runtime.enabled = false;
    restoreOriginals();
    cleanupTimers();
    resetRuntime("disable");
}
```

---

### 12.3 cleanup()

必须做：

```text
enabled = false
清理定时器
清理 Hook
恢复可安全恢复的原值
清空缓存
清空原值记录
initialized = false
```

要求：

```text
cleanup 可以调用多次
cleanup 不能因为某个 Hook 已经释放而报错
cleanup 不能依赖 UI 状态
```

推荐：

```js
function cleanupFeature() {
    Runtime.enabled = false;
    Runtime.stats.cleanupCount++;

    try { restoreOriginals(); } catch (e) {}
    try { cleanupTimers(); } catch (e) {}
    try { cleanupHooks(); } catch (e) {}

    resetRuntime("cleanup");

    Runtime.initialized = false;
}
```

## 13. 日志规范

日志必须能看出生命周期变化。

必须记录：

```text
Hook 安装成功
enable
disable
cleanup
resetRuntime 原因
localPlayer 变化
currentWeapon 变化
连续异常
指针无效
原值恢复成功/跳过
```

日志不要刷屏。

推荐限频：

```js
const LogLimiter = {};

function logOnce(key, msg, intervalMs = 1000) {
    const now = Date.now();
    if (!LogLimiter[key] || now - LogLimiter[key] > intervalMs) {
        console.log("[" + Runtime.name + "] " + msg);
        LogLimiter[key] = now;
    }
}
```

## 15. 不同类型功能的特殊要求

### 15.1 武器类功能

比如：

```text
无限子弹
射速
换弹速度
无后座力
极速枪托
```

要求：

```text
每次使用前确认 Weapon 属于本地玩家
不要长期保存 Weapon*
切武器必须清空武器缓存
武器 data 指针只当次使用
优先 Hook 武器自身方法，而不是定时扫所有武器
```

---

### 15.2 玩家状态类功能

比如：

```text
移动速度
跳高
无敌
第三人称相关玩家状态
```

要求：

```text
每次确认 Player 是本地玩家
死亡/重生后重新获取 Player
不要对 BOT 生效，除非功能明确要求
写字段前记录原值
退出房间不强行恢复旧 Player
```

---

### 15.3 相机/视角类功能

比如：

```text
第三人称
视角拉远
开镜视角
相机偏移
```

要求：

```text
优先使用游戏 Update 或相机更新点
不要用过高频 setInterval 硬刷
开镜、死亡、观战、切房间要单独处理
缓存 Camera/Transform 前必须验证
开镜时要允许原游戏相机接管，避免覆盖游戏自己的两段开镜逻辑
```

---

### 15.4 模式/回合类功能

比如：

```text
无限时间
跳过回合
模式状态修改
```

要求：

```text
必须确认当前模式对象有效
切模式必须 resetRuntime
不要跨模式复用旧模式对象
不要在大厅写模式对象
```

## 16. 单功能验收标准

一个功能想进入正式发行版，必须通过：

```text
1. 启动 UI，连接游戏，开启功能正常
2. 关闭功能，不再继续改游戏
3. 反复开关 5 次，不重复 Hook，不重复定时器
4. 进入房间后生效
5. 退出房间后不再写旧指针
6. 再进新房间后能重新生效
7. 死亡/重生后不崩
8. 切武器后不崩
9. 退出游戏后 UI 不报大量异常
10. 关闭 UI 时 cleanup 被调用
11. 日志能看到 enable/disable/cleanup/reset 原因
12. 如果 UI 在进房前已开启，进房后不手动关开也能生效
13. status 能看出 enabled、applied、pendingApply、lastApplyReason
14. 按钮型 RPC 不直接写 Player/Weapon/Camera/Transform 等运行态对象，只设置 pending
15. resetRuntime 会清理缓存指针、原值、pending 动作和当前房间派生状态
```

---

## 17. 禁止事项

禁止：

```text
长期保存 Player*、Weapon* 后一直使用
setInterval 高频硬写内存但不清理
disable 只改 enabled，不恢复、不清缓存
cleanup 里不 detach Hook、不 clearInterval
退出房间后继续写旧对象
没有本地玩家判断就改武器/玩家
没有 try/catch 就读写指针
没有日志就说功能稳定
为了整合方便顺手重构旧功能
在 RPC 里直接调用会修改当前房间运行态对象的 NativeFunction
切房间后保留旧 savedPoint、pendingTeleport、pendingSave 这类当前 generation 动作状态
```

## 18. 推荐最小 JS 骨架

```js
"use strict";

const Runtime = {
    name: "功能名",
    enabled: false,
    initialized: false,
    generation: 0,
    hooks: [],
    timers: [],
    cache: {
        localPlayer: ptr(0),
        currentWeapon: ptr(0)
    },
    originals: {},
    stats: {
        hookHits: 0,
        skippedNull: 0,
        skippedInvalid: 0,
        cleanupCount: 0,
        errorCount: 0,
        lastReason: ""
    }
};

function log(msg) {
    console.log("[" + Runtime.name + "] " + msg);
}

function isReadablePtr(p) {
    try {
        if (!p || p.isNull()) return false;
        p.readPointer();
        return true;
    } catch (e) {
        return false;
    }
}

function resetRuntime(reason) {
    Runtime.generation += 1;
    Runtime.cache.localPlayer = ptr(0);
    Runtime.cache.currentWeapon = ptr(0);
    Runtime.originals = {};
    Runtime.stats.lastReason = reason || "unknown";
    log("resetRuntime: " + reason + ", gen=" + Runtime.generation);
}

function installHooks() {
    if (Runtime.initialized) return;

    // 在这里安装 Hook
    // const h = Interceptor.attach(addrTarget, { ... });
    // Runtime.hooks.push(h);

    Runtime.initialized = true;
    log("hooks installed");
}

function cleanupHooks() {
    for (const h of Runtime.hooks) {
        try {
            if (h && h.detach) h.detach();
        } catch (e) {}
    }

    Runtime.hooks = [];
    Runtime.initialized = false;
}

function cleanupTimers() {
    for (const id of Runtime.timers) {
        try {
            clearInterval(id);
        } catch (e) {}
    }

    Runtime.timers = [];
}

function enableFeature() {
    installHooks();
    Runtime.enabled = true;
    Runtime.stats.errorCount = 0;
    log("enabled");
}

function disableFeature() {
    Runtime.enabled = false;
    cleanupTimers();
    resetRuntime("disable");
    log("disabled");
}

function cleanupFeature() {
    Runtime.enabled = false;
    Runtime.stats.cleanupCount++;

    try { cleanupTimers(); } catch (e) {}
    try { cleanupHooks(); } catch (e) {}

    resetRuntime("cleanup");
    log("cleanup done");
}

rpc.exports = {
    enable() {
        enableFeature();
        return true;
    },

    disable() {
        disableFeature();
        return true;
    },

    status() {
        return {
            name: Runtime.name,
            enabled: Runtime.enabled,
            initialized: Runtime.initialized,
            generation: Runtime.generation,
            stats: Runtime.stats
        };
    },

    cleanup() {
        cleanupFeature();
        return true;
    },

    reset(reason) {
        resetRuntime(reason || "manual");
        return true;
    }
};
```

## 19. 一句话总结

```text
单功能不要只管“能不能生效”，还要管“什么时候停止生效、什么时候清掉旧指针、什么时候重新识别对象、什么时候安全恢复”。
成熟方案不是相信指针，而是用状态机、generation、指针验证、统一 cleanup 来控制生命周期。
```
