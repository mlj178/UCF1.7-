# 18｜方框透视（ESP Box）

**来源**：`features/18_esp_box/`（script.js，标准 RPC 适配）+ `plugins/universal_hook/`（本体 `Universal-ImGui-Hook.dll`）+ 开发素材 `05-正式功能/18-Universal-ESP盒子/Universal-Dear-ImGui-Hook/`（C++ 源码 + 失败经历.md + 问答总结.md + ESP空跑优化修改记录.md）

## 核心原理

- **一句话**：本体是注入的 C++ DLL（非 Frida JS），Hook D3D11 `Present`，在每一帧用 ImGui DrawList 把敌人/全体玩家的世界坐标经 `Camera.WorldToScreenPoint_Injected` 投影成屏幕方框并绘制，本质是“就地读取 + 覆盖渲染帧”类方案。
- **手段归类**：DLL 注入 + D3D11 Present Hook + MinHook 函数 Hook + ImGui 覆盖层绘制；script.js 只是 RPC 开关适配层，真正逻辑在 C++。

**特殊处理**：
- **安全读内存** `SafeReadMemory`：`VirtualQuery` 查 MEM_COMMIT、非 NOACCESS/GUARD、跨区越界检查，再 SEH `__try/__except` 包裹 memcpy（防 GC/回收对象崩溃）。
- **每玩家独立 SEH 保护**：`SafeDrawPlayer` 对单个玩家包 `__try`，一个坏实体不拖垮整帧。
- **位置合理性过滤** `IsSanePosition`：近零、超 ±1000、离参考点过远都丢弃。
- **Box 尺寸/宽高比钳制**：宽 ≤300、高 ≤600、宽高比 0.15–5.0、高 <4px 丢弃；过窄框补宽到 0.4×高。
- **Bot 缓存生命周期**：Bot.Update 存入 `s_BotPlayers`，带 epoch + 超时（BOT_ENTRY_TIMEOUT_MS）+ 回合冷却（ROUND_CHANGE_COOLDOWN_MS），只收当前房间内玩家、过期/跨回合/失效即剔除。
- **会话封锁** `s_BlockSessionRefresh`：GameManager.OnDestroy 先置 1 再清缓存，防止渲染线程在 scene teardown 瞬间重拾旧静态指针；到真正新回合 OnStartNewGameRound 才解封。
- **GameManager 实例缓存 + 可见性重查**：非每帧都查单例，房间外低频重试（问答建议 0.5–1s），进房缓存、回合/销毁事件驱动刷新；重开局后自动恢复方框。
- **渲染开关空跑优化**：ESP 关闭时不建 ImGui Frame、不遍历玩家、不查坐标（保留一次 D3D/ImGui 初始化以建立命名管道与 Hook）。
- **模块地址核对**：Hook 回调每次动态取 `getGameAssembly().base` 与缓存 base 比较，防 ASLR 后地址漂移。
- **命名管道外部控制**：`esp_box` 开关状态由外部修改器经命名管道下发，DLL 不内置菜单输入。

## 作用范围

全局无区分的“所有玩家 + Bot”，绘制目标是全部可见的存活玩家。数据源是 `GameManager` 静态/实例字段（玩家列表全局共享），故可枚举房间内所有玩家，且按 `team` 相对本地玩家着敌我色。Bot 由 `Bot.Update` 单例补充，未在存活列表中的不重复绘制。

## 开发历程（重点）

### 踩过的坑

1. **DLL 架构不匹配导致注入失败**
   - 一开始没考虑到：VS 编译目标平台。
   - 出问题：1.7 修复版重编译后注入失败，`LoadLibraryW` 返回 NULL；远程线程是能创建的。
   - 怎么发现：`dumpbin /headers` 显示新 DLL 是 `8664 machine (x64)`，游戏进程是 32 位（`14C machine`）。
   - 怎么修：VS 切到 `Release + Win32(x86)` 重编译，用 `dumpbin /headers` 确认 `14C` 后再注入。

2. **ESP 未开启时仍每帧空跑 ImGui**
   - 一开始没考虑到：DLL 无条件每帧建 ImGui Frame + Present Hook，即使方框关着也在跑。
   - 出问题：白耗 CPU，占用持续存在。
   - 怎么修：`Render()` 开头先查 `ESPState::IsBoxEnabled()`，关闭直接 return；再关掉 F10/内置菜单/鼠标输入 Hook 路径（源码保留），仅保留首次初始化、Present Hook、命名管道与低频 ping。

3. **GameManager 查询频率不当**
   - 一开始没考虑到：一帧内可能重复查多次单例（Render 的 RefreshSession + GetAllPlayers 各一次）。
   - 出问题：房间外每帧 `SingletonGet` 无效空查；完全不查又会导致进房后找不到新 GameManager、切房后沿用旧对象、重开局方框不恢复。
   - 怎么修：存在则缓存实例不重复查、不存在则低频重试、回合/销毁事件驱动刷新（配合 `s_BlockSessionRefresh` 防止 teardown 期间误拾旧指针）。

4. **退出房间后仅部分模式能恢复方框**
   - 一开始没考虑到：普通模式与 Nano 生化使用不同的新回合入口；早期只 Hook `ModeBase.OnStartNewGameRound`（+0xAF5B30），而 Nano 调用 `ModeBase_Nano.OnStartNewGameRound`（+0xAF15D0），不会经过普通入口。
   - 出问题：退出房间时 `GameManager.OnDestroy` 会封锁会话刷新并清除旧缓存；团队/个人竞技重开后能从普通入口解除封锁并恢复方框，但生化系列仍处于封锁状态，无法重新获取新房间的 GameManager 和玩家。
   - 原因：早期只有普通模式的新回合入口能解除 `s_BlockSessionRefresh`，Nano 生化的新回合路径无法解除封锁，后续渲染刷新也就不能重新获取新房间数据。
   - 怎么修：同时 Hook 普通与 Nano 两个新回合入口，任一真实新回合到来都解除封锁、更新 epoch 并清除旧 Bot 缓存，从而允许后续渲染路径的 `RefreshSession` 重新获取新 GameManager，再由 `GetLocalPlayer` / `GetAllPlayers` 读取当前玩家，覆盖团队、个人竞技和生化模式。

### 方案迭代

- **最初（纯 Hook 拿玩家）**：只从 `GameManager.allPlayers`（+0x1C）数组枚举。问题：个别玩家/Bot 不在数组或为空，方框断。
- **中间（Bot.Update 补充）**：再加 Hook `Bot.Update`(0xB33370) 把 Bot 也缓存进 `s_BotPlayers` 作为补充数据源，与存活列表去重合并。
- **边界框从“命中箱 Transform”到“CharacterController Bounds”**：先用命中箱 Transform[]（CM_*）+ 颈/脊/头盔补充点；后新增主法 `Collider.get_bounds_Injected`(+0x2C) 直接取 AABB 8 角投影，失败再回退命中箱法（method 1 / 2 标记）。
- **最终**：主法 Bounds + 后备命中箱，全部走 SEH 保护 + 位置/尺寸合理性过滤，配生命周期会话管理。

### 一开始没考虑到的点

- 32 位 vs 64 位编译目标——架构选错直接导致 DLL 无法注入（纯编译层面，非代码问题）。
- Unity `WorldToScreenPoint` 原点在左下，ImGui 覆盖层原点是左上，需 `screenY = clientH - screenY` 翻转；且不能用 `ScreenToClient`。
- 相机可能在初始化时取不到（进房后才创建），需每帧 `GetMainCamera()` 重试而非只初始化一次。
- GameManager 的静态指针在 OnDestroy 与真正新回合之间处于“残留”状态，渲染线程抢在 teardown 前重拾旧指针有崩溃风险，必须用封锁位。

### 经验教训

- 注入类方案先核验**目标进程位数 vs 编译架构**，注入失败先 `dumpbin /headers`。
- 只读大量 IL2CPP 对象指针时，务必**安全读（SEH + VirtualQuery）+ 合理值过滤**，把“一个坏指针拖垮整帧”变成“丢弃该实体”。
- 渲染/绘制类功能要把**开关判定前置**，关闭时不建帧、不遍历、不投影，避免空跑。
- 会话类对象（GameManager）要做**实例缓存 + 事件驱动刷新 + teardown 封锁**，别每帧重复查，也别完全依赖单点获取。

## 一句话总结

用注入的 C++ DLL Hook D3D11 Present，通过 IL2CPP 桥接读取玩家/Bot 集合并投影成屏幕方框（主法 CharacterController Bounds、后备命中箱），靠 SEH 安全读、位置/尺寸过滤与回合级会话管理压住崩溃与空跑；最难的是注入后 32/64 位架构不匹配与 GameManager 生命周期/刷新节奏，最终用架构核对 + 事件驱动会话缓存解决。
