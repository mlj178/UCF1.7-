# 03｜无限时间（Infinite Time / Time Freeze 全模式）

来源：`features/03_time/`（script.js）。开发素材：`05-正式功能\03-全模式-无限时间\` 下的 `AAAAA-time_freeze_all_modes_modify_memory.js`（全模式改内存）。

---

## 核心原理

**一句话**：在事件触发点把 `ModeBase` 的 `restGameTime` 改写成 **99 分 59 秒**（直接清零式的"反向"：往大钳制，而非归零），事件漏跑时再由每秒定时器兜底重写，回合结束/切房重置实例指针。

**手段归类**：定时器轮询 + 写内存（事件 Hook 即时钳制，定时器兜底），即"持续状态反复钳制一个值"。

## 关键 Hook 表（GameAssembly.dll）

| RVA | 函数 | 手段 | 作用 |
|---|---|---|---|
| +0xAF6930 | `ModeBase.UpdateTimeUI` | Interceptor.attach | 全模式，每次刷新时间 UI 时把 restGameTime 钳到 99:59，并捕获 ModeBase 实例 |
| +0xAFAA40 | `GameManager.GameRoundEnd` | Interceptor.attach | 回合结束，重置 `modeBaseInstance`（防陈旧指针） |
| +0xAEF8A0 | `ModeBase_Nano.CheckRoundOver` | Interceptor.attach | 生化模式，进入时钳制时间 + 捕获新实例 |
| +0xAF1920 | `ModeBase_Nano.OnTimeOut` | Interceptor.attach | 生化模式超时，重置实例 |
| — | `setInterval` | 定时器（每秒） | 兜底：只要 `modeBaseInstance` 存在且时间 < 90 分就重写为 99:59 |

## 修改的关键字段

| 偏移 | 字段 | 值 |
|---|---|---|
| `restGameTime+0x34` | minute | 写 **99** |
| `restGameTime+0x38` | second | 写 **59** |

**特殊处理（具体到逻辑）**：
- **数值合法性校验**：`safeModifyTime` 要求 `instance>0x10000`（地址自理范围判据）才写；`readCurrentTime` 要求 `minute∈[0,200]`、`second∈[0,59]` 才认为有效，否则返回 null。
- **钳制条件**：仅当 `minute < 90` 才改写（若已是 99:59 或更大则跳过，避免无谓写）。
- **防陈旧写（生命周期）**：`GameRoundEnd`(+0xAFAA40) 与 `OnTimeOut`(+0xAF1920) 把 `modeBaseInstance` 置 null；读时间失败（null）也置 null 以便下次重新捕获。
- **新实例检测**：`UpdateTimeUI`/`CheckRoundOver` 用 `!instance.equals(modeBaseInstance)` 判断是新实例并更新捕获。
- **日志限流**：定时器每秒至多输出 1 条（`lastModifyTime` 时间窗）。
- **多模块协同**：`pauseFor(ms)` RPC 设置 `pauseUntil = Date.now()+ms`，在暂停窗口内**不钳制**，供「10-回合跳过」把时间改写为 0:00 触发超时（见开发历程）。
- **可逆卸载**：hooks `detach` + `clearInterval`。

## 作用范围

**全局无区分**：`restGameTime` 是公共类 `ModeBase`/`ModeBase_Nano` 的实例字段，属于**全局共享**的对局状态（不区分玩家/bot/人类）。全模式覆盖：团队、特殊战、个人竞技、终结者(Nano4)、生化剑客、多人终结者(Nano6)。

## 产品设计巧思

- **全模式开箱即用**：用基类 `ModeBase` + 子类 `ModeBase_Nano` 分层铺 point，团队/生化/特殊战等全模式统一生效，用户进任何模式都无需再手动开启。
- **与「10-回合跳过」自动协同**：暴雷 `pauseFor(ms)` 提供"暂停钳制"窗口，两个功能同开不打架（多模块协调），用户同时开无限时间与回合跳过也不会互相抵消。
- **切房/超时自动重置**：实例指针失效自动置空、下一回合自动重捕，用户换房后无需重开功能。

## 开发历程（重点）

### 踩过的坑（问题 → 原因 → 解决）

1. **最初只支持单一模式，切模式/切房就失效**
   - 问题：早期版本只 Hook 单一模式的某个回调，进其他模式时间照走。
   - 原因：不同模式用不同的模式类/回调，Hook 点没覆盖全会话。
   - 解决：参照 `no_recoil_v4_fix.js` 的**全模式适配思路**，铺两层——基类 `ModeBase.UpdateTimeUI`/`GameRoundEnd`（全模式通用）+ `ModeBase_Nano.CheckRoundOver`/`OnTimeOut`（生化专属）。

2. **盲写时间导致写到错误实例 / 异常值**
   - 问题：不校验直接 `writeS32`，可能改到无效指针或把错误对象当时间对象写，造成数值怪异。
   - 原因：`restGameTime` 的实例指针需在运行中捕获，且内存可含非法对象。
   - 解决：`safeModifyTime` 做**地址范围校验**（`>0x10000`），`readCurrentTime` 做**数值合理性校验**（分/秒范围），不满足就返回 null 并重置实例。

3. **回合结束/超时后旧实例指针陈旧，持续写会崩**
   - 问题：上一回合的 `modeBaseInstance` 在下回合被重建/释放，定时器仍对着旧地址写。
   - 原因：对象生命周期由游戏管理，跨回合重建。
   - 解决：`GameRoundEnd`/`OnTimeOut` 触发时把 `modeBaseInstance=null`；读时间失败也置 null（防陈旧写）。

4. **每秒定时器+事件双重刷新会刷屏/空转**
   - 问题：每秒都可能写，日志每条都打非常吵。
   - 解决：日志限流（1 秒 1 条）；钳制条件 `minute<90` 提前跳过已达标实例，减少无谓写。

5. **与「10-回合跳过」时序冲突**
   - 问题：回合跳过要把时间改 0:00 触发超时，但无限时间会立刻把它钳回 99:59，导致跳过失效。
   - 原因：两个模块争抢同一字段（`restGameTime`），无时序协调。
   - 解决：03_time 暴露 `pauseFor(ms)` RPC，设置 `pauseUntil`；10_roundskip 面板先 RPC 调 `pauseFor(2000)` 暂停钳制 2 秒，再执行回合跳过改 0:00（多模块时序协调）。

### 方案迭代

1. **单模式版本（早期）**：只 Hook 一个模式回调，模式覆盖不全 → 进出模式失效。
2. **基类 + 子类分层铺点（中期）**：`ModeBase.UpdateTimeUI`（全模式）+ `ModeBase_Nano` 生化专属，覆盖所有模式 → 全模式成立。
3. **事件 + 定时器双保险 + 安全校验（定稿）**：事件触发即时钳制，1s 定时器兜底，配地址/数值校验、切房/超时重置、日志限流、`pauseFor` 协同 → 稳定全模式无限时间。

### 一开始没考虑到的点

- **模式覆盖不全**：只有基类 Hook 不够，需按 `ModeBase`/`ModeBase_Nano` 分层铺点。
- **写内存要校验地址与数值合理性**：先判断"对象对不对、值合不合理"再改。
- **跨回合/切房对象重建**：缓存实例必须配生命周期清理（回合结束/超时置 null）。
- **与其他改同一字段的模块存在时序冲突**：需要跨模块协调，而不是各自为政。

### 经验教训

- **持续状态（倒计时）用"事件即时钳制 + 定时器兜底"双层保障**，单靠事件可能漏、单靠定时器有延迟。
- **凡持指针反复写内存，必须带生命周期清理**（切房/回合/超时重置），否则陈旧指针持续写会崩。
- **多模块改同一字段要显式时序协调**（`pauseFor` 暂停窗口），不能默认互不干扰。
- **写外挂内存前先做"对象/值合法性校验"**再写，可规避大量无效对象与错误写。

## 一句话总结

在 `ModeBase.UpdateTimeUI`(+0xAF6930，全模式) 与 `ModeBase_Nano.CheckRoundOver`(+0xAEF8A0，生化) 把 `restGameTime`(+0x34/+0x38) 钳成 99:59，1s 定时器兜底，`GameRoundEnd`/`OnTimeOut`(+0xAFAA40/+0xAF1920) 重置实例防陈旧写；从"单模式"迭代到"基类+子类分层铺点+校验+多模块 pauseFor 协同"，才实现全模式稳定无限时间。
