# 22｜无限背包（Unlimited Bag）

**来源**：`features/22_unlimited_bag/`（script.js）+ 开发素材 `05-正式功能/22-无限背包/经验总结.md`、`无限背包-最小实现步骤.md`、`AAAAA-unlimited_bag_min.js`

## 核心原理

- **一句话**：不重写背包逻辑也不主动发武器，只在 `Player.SelectWeaponBag` 执行前把 `WeaponBag.disabled` 和 `WeaponBag.tooFarFromSpawnPos` 两个 `ObscuredBool` 加密写为 false，让游戏自己的 `HUD_Bag.SelectBag → Player.SelectWeaponBag → GameManager.GiveWeaponByBag` 流程照常走通，本质是“就地改写限制字段”类方案。
- **手段归类**：Hook 换包函数（onEnter 清限制）+ 辅助 Hook 每帧兜底清限制 + 调用 `ObscuredBool.Encrypt` 加密写。

## 关键 Hook 表（GameAssembly.dll）

| RVA | 符号 | 手段 | 作用 |
|---|---|---|---|
| 0xB52830 | Player.SelectWeaponBag(int index) | Interceptor.attach(onEnter) | 换包前清 disabled / tooFarFromSpawnPos |
| 0xB00360 | HUD_Bag.Update | attach(onEnter) | 每帧兜底清背包限制（防实时更新） |
| 0xAFB6F0 | GameManager.OnDestroy | attach(onEnter) | 场景销毁清玩家/背包缓存 |
| 0x7F93D0 | ObscuredBool.Encrypt(bool value, byte key) | NativeFunction 调用 | 生成加密后的 hiddenValue |

## 修改的关键字段

| 偏移 | 字段 | 值/说明 |
|---|---|---|
| Player +0xA4 | weaponBag | 读取本地玩家背包对象 |
| WeaponBag +0x8 | disabled（ObscuredBool） | 加密写 false |
| WeaponBag +0x14 | tooFarFromSpawnPos（ObscuredBool） | 加密写 false |
| HUD_Bag +0x2C | bag | 读取 HUD 当前绑定的 WeaponBag |
| WeaponBag +0x20 / +0x24 / +0x28 | available / weaponID / currentBagID | 只读（定位其它限制点） |
| ObscuredBool +0x0/+0x4/+0x8/+0x9/+0xA | currentCryptoKey / hiddenValue / inited / fakeValue / fakeValueActive | Encrypt 后写 hiddenValue，置 inited=1、fake=0、fakeActive=0 |

**特殊处理**：
- **ObscuredBool 加密写**：`disabled`/`tooFarFromSpawnPos` 是 `ObscuredBool`（非普通 bool），不能直接写 0；先读 `currentCryptoKey`，调 `ObscuredBool.Encrypt(false, key)` 得 hiddenValue 写入，同时 inited=1、fakeValue=0、fakeValueActive=0。
- **身份双重校验**：本地玩家用 `GameManager.myPlayer` 缓存 + 实例 `equals` 对照（`isLocalPlayer`），不处理 Bot；背包对象也做 `isKnownLocalWeaponBag` 校验（缓存 + 已见集合）。
- **兜底双保险**：`SelectWeaponBag`（点击瞬间）+ `HUD_Bag.Update`（每帧实时）两路清限制，防“离出生点太远”这类实时更新限制。
- **生命周期清理**：GameManager.OnDestroy / disable / cleanup 清空 myPlayer/weaponBag 缓存与已见集合；disable 不强行恢复字段（保持最小侵入）。
- **日志限流**：每模块上限（`MAX_LOGS_PER_MODULE=3`），`HUD_Bag.Update` 每 600 帧才报一次。
- **探测式排查**：onLeave 记录 SelectWeaponBag 返回值，false 提示还有其它限制层（available/UI/射击状态），不盲目 replace。

## 作用范围

仅本地玩家。所有清限制只针对 `isLocalPlayer` 的玩家及其 `weaponBag`；`HUD_Bag.Update` 兜底也只处理 `isKnownLocalWeaponBag`（本地背包）。不触碰人机与其他玩家。

## 产品设计巧思

- 一键开关，自动连接游戏，不用手动配置。
- “随时能换包”：离开出生点、甚至边开枪边切背包都照常生效（靠持续兜底清限制）。
- 关闭脚本后游戏恢复正常限制，不影响正常游玩。

## 开发历程（重点）

### 踩过的坑

1. **`WeaponBag.disabled` 是 `ObscuredBool`，直接写 0 无效/不可靠**
   - 一开始没考虑到：该字段不是普通 bool，而是加密布尔（`currentCryptoKey` + `hiddenValue`）。
   - 出问题：把字段 +0x0 直接写 0 不会真正清掉禁用状态（或用错偏移读到假值）。
   - 怎么修：读当前 `currentCryptoKey`，调用 `ObscuredBool.Encrypt(false, key)` 得到加密 hiddenValue 写回，并同步置 inited/fakeValue/fakeValueActive。

2. **清一次不够，远离出生点/实时限制会再回来**
   - 一开始没考虑到：`tooFarFromSpawnPos` 由游戏实时计算，点击时清一次后可能马上又被写回 true。
   - 出问题：只在 `SelectWeaponBag` 清，走远后切包仍被拦。
   - 怎么修：加 `HUD_Bag.Update` 每帧兜底清（只对已知本地背包），用低频日志防刷屏。

3. **`SelectWeaponBag` 返回 false 但不知卡在哪层**
   - 一开始没考虑到：清掉两个字段后仍可能因 `available`/`weaponID`/UI 焦点/射击状态失败。
   - 怎么修：onLeave 记录返回值并提示下一层排查方向，先探测后修改，不轻易 `replace` 整函数。

### 方案迭代

- **方案 A（Hook SelectWeaponBag 清限制）**：改动最小、风险最低，只清限制字段后走原函数。缺点：实时限制会被游戏再写回。
- **方案 B（Hook HUD_Bag.Update 持续清）**：补充 A 的不足，每帧压住距离限制。缺点：每帧执行需限流。
- **最终（A+B 组合）**：点击瞬间 + 每帧兜底两路清，稳定“任何位置可切包”；`replace` 整函数作为备选（需重写游戏背包逻辑、风险高）未采用。

### 一开始没考虑到的点

- 字段是 `ObscuredBool`，逆向时需识别加密布尔结构（offset 0/4/8/9/A）。
- 游戏限制是“实时计算”而非“一次性开关”，需要持续兜底。
- 换包失败可能发生在多个层级（字段/数组/UI/射击状态），排查要按层推进。

### 经验教训

- **改限制字段优于重写逻辑**：借用游戏自己的流程（SelectWeaponBag→GiveWeaponByBag），只把“闸门”打开，风险最低。
- 遇到加密字段（`ObscuredBool`/`ObscuredInt` 等）务必走游戏自身的 Encrypt 逻辑，不要硬写。
- 持续性限制需要**事件触发 + 周期兜底**双保险，并做好日志限流。

## 一句话总结

通过 Hook `Player.SelectWeaponBag` 用 `ObscuredBool.Encrypt(false,key)` 把 `disabled/tooFarFromSpawnPos` 加密写 false，再叠加 `HUD_Bag.Update` 每帧兜底清限制，实现任意位置、任意状态（含开枪时）都能切包；踩坑集中在 ObscuredBool 不能直写 0、限制实时更新需持续兜底，最终保持最小侵入不重写游戏逻辑。
