# 33｜玩家信息修改（Player Profile Editor）

**来源**：`05-正式功能/33-玩家信息修改器/`（player_profile_service.py + AAAAA-player_profile_editor_ui.py + test_player_profile_service.py + 玩家信息修改器-简要说明.md）

## 核心原理

- **一句话**：不注入游戏、不连 Frida，纯 Python 直接读写 UnityCrossFire 本地 `PlayerData.dat`（INI 格式）：定位 `[Player]` 节，把 `NickName / Level / VipLevel` 三个键改写为目标值；文件里没有 `[Player]` 时把该节插入到 `[Inven]` 之前，本质是“文本级 INI 编辑”类方案。
- **手段归类**：无 Hook、无内存操作。路径定位（%USERPROFILE%\AppData\LocalLow\Alexander_GaGa\UnityCrossFire\PlayerData.dat）+ 正则找节 + 文本重写 + 自动备份 + CustomTkinter UI。

## 关键 Hook 表

**无**（本功能不 Hook GameAssembly.dll，不连接 Frida，纯 Python 文件编辑）。这是 21-33 中唯一一个完全不依赖游戏进程的功能。

## 修改的关键字段

| 键名（INI） | 说明 | 值/来源 |
|---|---|---|
| `[Player] NickName` | 玩家昵称 | 用户输入（中文显示） |
| `[Player] Level` | 玩家等级 | 用户输入（≥0） |
| `[Player] VipLevel` | VIP 等级 | 用户输入（≥0） |

**特殊处理**：
- **节定位三种情况**：已有 `[Player]` → 只更新该节；没有但有 `[Inven]` → 插到 `[Inven]` 前；都没有 → 追加到文件尾。用正则按行头匹配 `[Section]`，避免误匹配键值里的字符串。
- **换行归一化**：读入时把 `\r\n / \r` 统一为 `\n`，写出固定 `\n`（`newline="\n"`），避免 Windows/Linux 混行导致游戏读键错乱。
- **自动备份递增**：保存前 `shutil.copy2` 备份到 `.bak`；已存在则 `.bak.1 / .bak.2 …` 递增，绝不覆盖旧备份。
- **校验前置**：昵称非空、不含换行；等级/VIP ≥0；全部通过才写文件，失败抛异常由 UI 弹窗提示。
- **保存即反馈**：`SaveResult` 返回 path / backup_path / created_file，UI 日志展示“已备份到 X、已写入 Y”。
- **文件不存在自动建目录**：`mkdir(parents=True)` 创建 LocalLow 路径，首次保存也能成功。

## 作用范围

本地单机玩家数据文件，对所有玩家/账号的存档文件生效（改哪个文件改哪个账号）。不修改游戏运行内存、不改其他玩家、不进游戏内同步；改动在下次启动/读取时生效。

## 产品设计巧思

- 独立小工具（CustomTkinter 桌面窗口 + 可打包 exe），不动游戏本体，改完即走。
- 中文界面（昵称/等级/VIP等级）+ 英文键名（NickName/Level/VipLevel），人看得懂、游戏读得对。
- 文件路径动态取当前 Windows 用户目录，不写死 `C:\Users\17242`，换账号/换机器也能用，还支持手动选文件。
- 打开工具自动“读取现有 [Player]”回填输入框，所见即所得。
- 自动备份 + 递增备份名，改错了可随时回滚。
- 提供独立测试用例（路径/插入/更新/备份四类），为后续整合包 2.3 复用同一读写规则打底。

## 开发历程（重点）

### 踩过的坑

1. **改错节导致游戏读不到昵称/等级**
   - 一开始没考虑到：`[Player]` 节的位置可能变、换行可能是 `\r\n`、也可能根本没有该节；用简单字符串拼接容易把节插错位置或漏写键。
   - 出问题：保存后游戏读不到修改，或把 `[Inven]` 顶掉。
   - 怎么修：用正则 `^\[Player\]\s*$` 精确找节、`^\[[^\]]+\]$` 找下一节头切分区间；换行归一化后统一 `\n` 写出。

2. **键名大小写/中英文混淆**
   - 一开始没考虑到：界面显示中文但文件里游戏按英文键读，若直接写中文键名游戏不认。
   - 出问题：UI 显示正常但游戏内没生效。
   - 怎么修：固定英文键名（NickName/Level/VipLevel）写文件，仅界面层做中英映射。

3. **覆盖写坏原文件无法恢复**
   - 一开始没考虑到：直接覆写没有回退手段，改错全丢。
   - 出问题：改坏后连原昵称都找不回。
   - 怎么修：保存前自动备份（.bak/.bak.1/…递增），改错可回滚。

4. **游戏运行中保存被覆盖**
   - 一开始没考虑到：游戏运行时它自己会周期写 PlayerData.dat，外部修改会被游戏内存里的值覆盖。
   - 出问题：刚改完进游戏又变回原值。
   - 怎么修：UI 与说明文档明确提示“先关闭游戏再保存”；工具本身不改游戏进程行为。

5. **写死用户目录不可移植**
   - 一开始没考虑到：路径写死某用户目录，换机器/账号就失效。
   - 出问题：在别的电脑上找不到文件。
   - 怎么修：`Path.home()` 动态取当前用户目录，UI 支持手动选择文件。

### 方案迭代

- **早期（手改 INI / 简单替换）**：手动编辑或一次性替换。缺点：易错、无回退、位置错乱。
- **最终（Service 分层 + 备份 + 测试）**：`player_profile_service.py` 独立核心（路径/读节/更新/备份），`AAAAA-player_profile_editor_ui.py` 只做 UI，`test_player_profile_service.py` 覆盖四类场景；为整合包 2.3 复用同一套读写规则打底。

### 一开始没考虑到的点

- INI 节的位置与换行格式不固定，必须正则找节 + 换行归一化。
- 游戏按英文键读数据，中英键名要分离（UI 中文 / 文件英文）。
- 需要自动备份递增机制，防覆盖写坏无法回滚。
- 游戏运行中会覆盖外部修改，要先关游戏再保存。
- 路径不能写死用户目录，要动态取 `Path.home()`。

### 经验教训

- 文件编辑类功能**先备份再写**是底线，递增备份比单备份更稳。
- 读写规则要**独立成 service 并配测试**，后续整合进整合包时直接复用，避免两套逻辑漂移。
- 面向用户的显示名与文件内键名要分离，别让 UI 文案影响文件格式。
- 与游戏进程共享的文件，要告知用户“关游戏再改”的运行前提。

## 一句话总结

纯 Python 文本级编辑 `PlayerData.dat` 的 `[Player]` 节（NickName/Level/VipLevel），正则定位节 + 换行归一化 + 三种插入策略，保存前递增备份；不 Hook、不连 Frida，独立 CustomTkinter UI + 自动测试，为整合包 2.3 复用统一读写规则；踩坑集中在“节位置/换行格式不固定”“中英键名混淆”“覆盖无回退”“游戏运行中覆盖修改”，最终以 Service 分层 + 备份递增 + 测试兜底收尾。
