# 08｜聚怪（Gather / 聚集 Bot / Gather Enemies）

来源：`features/08_gather/`（script.js + manifest.json + panel.py + events.py）。开发素材：`AAAAA-bot_to_spawn_v24.js`（独立版）与整合包内聚怪模块，及 `bot_to_spawn-聚怪经验总结.md`。

---

## 核心原理

**一句话**：开启后通过 9 个 attach Hook 维护玩家列表与 Bot 缓存，点"一键聚怪"时经 RPC 置 `ntp` 标志，下一帧 `Player.Update` onEnter 触发 `executeTeleport()`：对每个活着的 Bot 执行 `CC.disable → set_position → CC.enable`，拉到出生点 spawn=(13.6, 14.1, 0.1) —— 属于"**调用游戏函数 + 写内存（传送）**"，本质是**主动传送敌方 Bot（不是改数值）**。

**手段归类**：9 个 attach Hook + 7 个 NativeFunction 直调游戏函数，RPC `gather` → `ntp=true` → `Player.Update` 触发传送。

## 关键 Hook 表与 NativeFunction（GameAssembly.dll）

| RVA | 符号 | 手段 | 用途 |
|---|---|---|---|

| +0xAEBB70 | `MatchManager.MapGun` | attach | 捕获 MM 单例 |
| +0xB551D0 | `Player.Update` | attach | onEnter 检测 `ntp` 标志并触发传送 |
| +0xB33370 | `Bot.Update` | attach | onEnter 缓存最近见过的 Bot（补路径，`Bot+0x24` thisPlayer） |
| +0xAF6930 | `ModeBase.UpdateTimeUI` | attach | 跟踪 modeBase，判断房间切换 |
| +0xAEE850 / +0xAFAA40 / +0xAEBCB0 / +0xAFB6F0 | ExitGame / GameRoundEnd / NewGameRoundStart / OnDestroy | attach | 房间/回合生命周期清空缓存 |
| +0xB55FD0 | `Player.isMyPlayer` | NativeFunction | 排除自己 |
| +0xB400E0 | `Enemy.isDead` | NativeFunction | 排除已死 Bot |
| +0x1CF180 | `Enemy.get_CharacterController` | NativeFunction | 取 CC |

数据偏移：`GM+0x1C`=allPlayers 列表；`Player+0x94`=clientData，`clientData+0x1C`=isBot（U8，1=Bot），`clientData+0x18`=team；`Bot+0x24`=Bot 指向的玩家；`Player+0x58`=charContainer（回退取 Transform 用）；`Transform+0x10`=nativeTransform，其 `+0x38/0x3C/0x40`=坐标 x/y/z。

## Bot 判定（双路径扫描）

1. **主路径（全局列表）**：`GM+0x1C`（allPlayers 列表）→ `+0xC` 读总数（上限 64）→ 逐个 `+0x10+i*8` 取玩家指针。
2. **补路径（Bot 缓存）**：`Bot.Update` onEnter 缓存 `Bot+0x24`（Bot_thisPlayer）指向的玩家，5 秒内有效，补全主列表遗漏。
3. **Bot 判定**：`player+0x94`（clientData）→ `+0x1C` 读 U8，`1=Bot`；用 `isMy(+0xB55FD0)` 排除自己、`isDead(+0xB400E0)` 排除死 Bot。

## 传送细节与防崩兜底

| 处理 | 实现 |
|---|---|
| 碰撞体临时禁用 | 传送前 `CC.set_enabled(0)`，写完坐标后 `set_enabled(1)`，避免卡墙/掉地 |
| 双路径传送兜底 | 首选 `Player.set_position`(+0xB534C0)；失败回退 `get_transform`(+0x32CF40) → `Transform.set_position`(+0x3F4810, posBuf) + 手动写 `np+0x38/0x3C/0x40` |
| 数量上限 | allPlayers 最多扫 64；Bot 缓存最多 64（超限告警） |
| 帧预算 | 每次执行总耗时上限 12ms（`GATHER_FRAME_BUDGET_MS`），三阶段均检查，用尽即停，防掉帧 |
| Bot 缓存 TTL | 缓存条目超过 5000ms 不再使用，防过期/已销毁对象 |
| 房间状态自动清理 | 退出/回合结束/新回合/销毁 4 类 Hook 均 `clearRoomState()` |
| 事件回报 | 传送完成发 `plugin_event {event:'done', n, bots, fail}` 给面板回显 |
| 可逆卸载 | `disable()` 停诊断定时器 + 逐一 detach 9 个 Hook + 清空缓存 |

## 作用范围

**只作用于 Bot（人机），明确排除自己与真人**——这是反过来的设计（其余 04~07 都只作用于自己，聚怪只作用于 Bot）。`isMy(pp)` 命中跳过自己；`isHuman(pp)`（clientData+0x1C==0）跳过真人；`isDead(pp)` 跳过已死 Bot；其余活的 Bot 传送。作用对象是玩家实体（Player/Bot），无武器特判。

## 产品设计巧思

- **一键聚怪 + 结果回显**："一键聚怪"按钮触发，传送完成后事件上报数量/失败数给面板回显，用户一眼知道聚到几只。
- **聚怪不卡顿**：帧预算 12ms + 数量上限 64，高密度 Bot 场景也不掉帧。
- **只聚 Bot、不误伤**：明确排除自己/真人/已死 Bot，只把敌方人机拉到出生点，不打扰队友与真人。
- **生命周期自动清理**：退出/回合结束/新回合/销毁自动清空缓存，不至于在错误房间残留。

## 开发历程（重点）

### 踩过的坑（问题 → 原因 → 解决）

1. **`GameManager.allPlayers` 只能找到约 14 个 Bot（实际 30 个）**
   - 问题：常规路径只能收集到约 14 个 Bot，聚不全。
   - 原因：`allPlayers` 是动态数组，只含已**注册**到 GameManager 的玩家；Nano（生化）模式有**独立 Bot 创建系统**，Bot 延迟注册/分批加载，大量 Bot 不进数组。
   - 解决：加**补路径**——Hook `Bot.Update`(+0xB33370)，Unity 每帧必调每个 Bot 组件的 Update，无论是否注册都能捕获，经 `Bot.thisPlayer`(+0x24) 取到 Player。
2. **`allPlayers` 数组存在 `null` 槽位**
   - 问题：数组里有些槽位是 null，不是 Player 实例，访问 `transform` 直接报错/崩溃。
   - 解决：指针有效性校验（读首字段探针 `isValid`），null/无效槽位跳过。
3. **Bot 身份判断不能只靠 `isBot` 标志**
   - 问题：部分 Bot 的 `clientData=null`，`isBot` 读不到，判断漏人。
   - 原因：`ClientData.isBot`(clientData+0x1C) 是服务器下发的标记，但 clientData 可能为 null。
   - 解决：**双路径收集**（allPlayers + Bot.Update）+ 能读到的用 `isBot==1` 确认，配合排除自己/真人/已死，不漏不死。
4. **直接改 `Transform.position` 会卡墙/掉地/乱套**
   - 问题：直接写坐标，传送后物理引擎不同步。
   - 原因：角色控制器（CharacterController）与物理引擎冲突，位置改了物理没跟上。
   - 解决：**Unity 标准传送三步法**——`CC.set_enabled(false)` → 写坐标 → `CC.set_enabled(true)`，禁用物理控制期间再写位置。
5. **持久化追踪野指针崩溃（v24 独立版教训）**
   - 问题：`trackedPlayers`/`trackedBots` 永久保存所有捕获指针，对局越久集合越大；玩家退房/销毁后指针失效仍被访问 → 访问违规崩溃。
   - 解决（整合版 v1.3）：改为**按需扫描 + 临时缓存**——每次传送前从 `GM.allPlayers` 重新扫描，`recentBotPlayers` 只保留 5 秒内新鲜 Bot，**传送后立即清空**，指针不再长期持有。
6. **进房后 `GameManager` 还没被捕获，功能不生效**
   - 问题：只靠 `AddPlayer` 事件捕获 GM，进房后事件没触发时 GM 为空。
   - 解决：脚本**主动扫描内存单例**——`singletonGetter`(+0x4A8170) 读 GM 单例 MethodInfo(0xE1CE64)/MM(0xE1D9E8) 兜底，不依赖事件时序。

### 方案迭代

1. **思路演进**：先想"isbot/cam/cd 判断人机"→ 再想"判断非玩家"→ 发现 allPlayers 不全 + 有 null 槽位 → 确定"主路径 allPlayers + 补路径 Bot.Update 缓存"双路径。
2. **v24（独立版）**：持久化追踪 `trackedPlayers` + `trackedBots`，RPC `teleport()` 置 `ntp`，`Player.Update` 驱动。缺点：集合无限增长、野指针风险高。
3. **整合版（v1.3+，最终）**：改为**双路径动态扫描 + 临时缓存 + 时效过滤 + 及时清理**——`GM.allPlayers` 主扫 + `recentBotPlayers`（Bot.Update 注入、5 秒有效）补漏，传送后立即清空；Unity 标准传送公式；帧预算 12ms / 数量上限 64 防掉帧；4 类生命周期 Hook 自动清理房间状态。

### 一开始没考虑到的点

- **动态数组覆盖不全**：Nano 模式 Bot 独立创建、延迟注册，`allPlayers` 兜不住全部。
- **数组有 null 槽位**：不是 Player 实例，必须探针校验。
- **传送要"先禁 CC 再写坐标再启用"**：直接写坐标会卡墙/掉地。
- **单例捕获要主动扫描兜底**：不能只靠事件时序（进房后 AddPlayer 未必触发）。
- **长期持有指针必炸**：要"按需扫描 + 时效缓存 + 用后即清"。
- **开发过程通用反例**（该功能经验文档重点）：频繁创建新文件导致上下文混乱、逻辑/数据错乱、日志反复变化；AI 改代码（js 转 py、整合进大包）会"悄悄改逻辑和数值"导致卡退——都要对比差异、指定参考文件、减少新文件。

### 经验教训

- 收集对象列表用"**按需扫描 + 时效缓存 + 及时清理**"，不要持久持有指针。
- 身份判断要**多路径兜底**，别迷信单一标志位。
- 传送类修改必须走 **Unity 标准流程**（禁 CC → 写坐标 → 启 CC）。
- 单例/实例获取要有"**事件捕获 + 主动兜底扫描**"双保险。
- 做复杂功能时**控制对话轮次与新文件数量**，指定参考文件和代码，防止 AI 迷失目标、悄悄改数值。

## 一句话总结

9 个 attach Hook（`GameManager.AddPlayer`+0xAF9A90、`Bot.Update`+0xB33370、`Player.Update`+0xB551D0 等）维护 GM/MM/玩家列表与 Bot 缓存，双路径（allPlayers + Bot.Update 临时缓存）收集活的 Bot，`CC.disable → set_position → CC.enable` 传送到出生点 (13.6, 14.1, 0.1)，明确排除自己/真人/已死 Bot，带帧预算 12ms、数量上限 64、缓存 TTL 5s、房间状态自动清理；开发核心教训是"allPlayers 覆盖不全 → 补 Bot.Update 路径"、"直接写坐标卡墙 → Unity 标准传送三步法"、"持久持指针必崩 → 按需扫描+用后即清"。
