# 31｜定点瞬移（Fixed Point Teleport）

**来源**：`features/31_fixed_point_teleport/`（script.js）+ 开发素材 `05-正式功能/31-定点瞬移/定点瞬移-简要说明.md`

## 核心原理

- **一句话**：Hook `Player.Update` 捕获当前本地 Player，保存时读其 `Transform.position` 存为单个点，瞬移时调用原游戏 `Player.SetPos(Vector3)`（由原版处理碰撞器禁用/恢复），RPC 只置 pending 动作、真正的保存/瞬移在下次 `Player.Update` 内执行，本质是“调原游戏接口 + 事件驱动消费命令”类方案。
- **手段归类**：Hook 玩家生命周期（Player.Update 捕获/执行）+ NativeFunction 调用 `Player.SetPos` + Transform get_position + 生命周期 Hook 清点。

## 关键 Hook 表（GameAssembly.dll）

| RVA | 符号 | 手段 | 作用 |
|---|---|---|---|
| 0xB551D0 | Player.Update | Interceptor.attach | 捕获本地 Player、消费 pending 保存/瞬移动作 |
| 0xB55FD0 | Player.get_isMyPlayer | NativeFunction | 本地玩家判断 |
| 0xB534C0 | Player.SetPos | NativeFunction | 原游戏瞬移接口（处理 Collider.enabled） |
| 0x32CF40 | Component.get_transform | NativeFunction | 取玩家 Transform |
| 0x3F4280 | Transform.get_position_Injected | NativeFunction | 读取当前坐标用于保存 |
| 0xAF6930 | ModeBase.UpdateTimeUI | attach | 捕获模式实例 / 房间就绪信号 |
| 0xAFAA40 / 0xAEBCB0 / 0xAEBD40 | GameManager.GameRoundEnd / NewGameRoundStart / OnDestroy | attach | 回合结束/新回合/房间销毁清空保存点 |

## 修改的关键字段

| 偏移 | 字段 | 值/说明 |
|---|---|---|
| Player +0x2C | characterController | 供 Player.SetPos 内部读取（不动） |
| （运行时）savedPoints[1/2] | Vector3 坐标 | 脚本自维护的保存点 |
| Player Transform.position | 由 SetPos 改写 | 瞬移目标位置 |

**特殊处理**：
- **RPC 只置 pending**：`savepoint()/teleporttopoint()` 不直接操作，只在下一帧 `Player.Update` 内消费，保证与游戏主线程同步、避免非主线程写游戏对象。
- **绑定 roomGeneration**：保存点绑定当前局/房间 generation，回合结束、新回合、房间销毁、模式实例变化时自动清空，切房后旧点不可用。
- **本地玩家捕获带缓存时效**：缓存 localPlayer + 3000ms 年龄上限，过期或失效重新捕获，不写陈旧指针。
- **只处理本地玩家**：不处理人机/其他玩家/多保存点；死亡/重生后重新捕获。
- **可逆卸载**：disable 时 detach hooks、清 savedPoints/pending 与缓存。

## 作用范围

仅本地玩家（单保存点/双槽位可选，当前实现 2 槽）。不自动找地面、不修正高度；只做“当前位置 ↔ 保存点”往返，不改 Bot/他人坐标。

## 产品设计巧思

- 一键“保存当前位置 / 瞬移到保存点”（按钮或 Alt+1 / Alt+2 快捷键），探图/跑图超方便。
- 瞬移走原游戏 `Player.SetPos`，碰撞器自动处理，不会卡墙或坠落穿模。
- 切房/新回合自动清空旧点，避免跨局“瞬移到上一局的坐标”这种诡异体验。

## 开发历程（重点）

### 踩过的坑

1. **直接写 Transform 瞬移风险高**
   - 一开始没考虑到：直接 `Transform.set_position` 会绕过 CharacterController 的碰撞器禁用/恢复逻辑。
   - 出问题：瞬移可能卡进墙里、碰撞状态残留。
   - 怎么修：改调原游戏 `Player.SetPos(Vector3)`——IDA 汇编确认它先关碰撞器、再设位置、最后恢复碰撞器，风险最低。

2. **RPC 非主线程操作游戏对象**
   - 一开始没考虑到：Frida RPC 回调可能不在游戏主线程，直接改坐标/存指针不稳。
   - 出问题：偶发瞬移失败或指针读取异常。
   - 怎么修：RPC 只写 pending（saveSlot/teleportSlot），真正执行放到下一帧 `Player.Update` 主线程内。

3. **切房/新回合后旧点失效**
   - 一开始没考虑到：保存点跨局/跨房仍被复用，会瞬移到不存在的旧坐标。
   - 出问题：新局瞬移回上一局的点。
   - 怎么修：保存点绑定 `roomGeneration`，GameRoundEnd/NewGameRoundStart/OnDestroy 时清空，死亡/重生重新捕获本地玩家。

### 方案迭代

- **早期（直接写 Transform）**：读当前位置、set_position 瞬移。缺点：绕过碰撞器处理，易卡墙。
- **最终（原游戏 SetPos + pending 消费）**：Hook `Player.Update` 消费 pending，调 `Player.SetPos` 瞬移，保存点绑定 roomGeneration。缺点：不做多点列表/自动找地（设计边界明确）。

### 一开始没考虑到的点

- 瞬移接口要**复用原版 SetPos**，自己处理碰撞器开关容易遗漏状态。
- RPC 回调与游戏主线程的关系要先确认，动作要延迟到主线程执行。
- 保存点是“局级/房级”数据，必须绑定生命周期并在切房/新回合清空。

### 经验教训

- 位移类功能优先**调用游戏自身移动接口**，而不是绕过它直接改 Transform。
- 跨线程的命令一律**置 pending + 主线程消费**，避免竞态。
- 任何保存的状态都要想清楚“何时失效”，绑定房间/回合生命周期比全局常驻安全。

## 一句话总结

Hook `Player.Update` 捕获本地玩家并消费 pending 动作，保存时读 `Transform.position` 存单点、瞬移时调原游戏 `Player.SetPos`（碰撞器由原版处理），保存点绑定 roomGeneration 并在切房/新回合清空；踩坑集中在“直接改 Transform 卡墙”“RPC 非主线程操作”“旧点跨局复用”，最终以复用原版 SetPos + pending 消费 + 生命周期清点收尾。
