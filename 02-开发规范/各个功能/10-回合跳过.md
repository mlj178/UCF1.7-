# 10｜回合跳过（Round Skip / 结束当前回合）

来源：`features/10_roundskip/`（script.js + manifest.json + panel.py + events.py + monitor.py）。开发素材：`AAAAA-skip_round.js`（独立版）与整合版。

---

## 核心原理

**一句话**：attach 挂住 `ModeBase.UpdateTimeUI` 捕获 ModeBase 实例并记录"房间代号"，点"跳过"按钮时经 RPC 对实例的 `restGameTime` 字段（分/秒）**直接写 0:00**，游戏检测到时间归零即自然结束回合。

**手段归类**：主动写内存（条件式清零）—— 不调用任何回合结束函数，靠游戏原生"时间到"逻辑结束回合。

| 项目 | 值 |
|---|---|
| 手段 | 5 个 attach Hook 维护实例 + RPC 触发写内存 |
| 本质 | `ModeBase.restGameTime` 直接写 0:00（分钟 +0x34、秒 +0x38） |
| 触发方式 | RPC `skip_round`（按钮），首次需先 enable 再点（"第一次跳过需要点击两次"） |
| 防呆 | 已为 0:00 不重复写（`already_zero`）；`skipGuard` 防重入 |

## 关键 Hook 表（GameAssembly.dll）

| RVA | 符号 | 手段 | 作用 |
|---|---|---|---|
| +0xAF6930 | ModeBase.UpdateTimeUI | attach | onEnter 捕获 ModeBase 实例、记录回合号 |
| +0xAFAA40 | GameManager.GameRoundEnd | attach | 回合结束清空实例 |
| +0xAF1920 | ModeBase.Nano.OnTimeOut | attach | 超时回调时置 `roundActive=false` |
| +0xAEE850 | ModeBase.ExitGame | attach | 退出时清空实例并递增房间代号 |
| +0xAFB6F0 | GameManager.OnDestroy | attach | 销毁时清空实例并递增房间代号 |

## 修改的关键字段（ModeBase 实例）

| 偏移 | 字段 | 值 |
|---|---|---|
| +0x34 | 剩余分钟（S32） | 写 0 |
| +0x38 | 剩余秒（S32） | 写 0 |
| +0x14 | 当前回合号（S32） | 只读，用于状态显示 |

**防陈旧写**：`modeBaseGeneration` 与 `roomGeneration` 比对，不一致拒绝写（`stale_room_generation`），防止写到旧房间实例；`isValidInstance`（非空、地址 >0x10000、可读一字节）三重校验；`skipGuard` 防重入；`skipCount`/`skipErrorCount`/`currentRound`/`restGameTime` 状态统计供 status 查询。

## 与无限时间（03_time）的协同（关键机制）

"无限时间"开启时会把 `restGameTime`(+0x34/+0x38) 在分钟 <90 时钳回 99:59（见 [03-无限时间.md](file:///d:/trae_project/ucf1.7-modifier/02-开发规范/各个功能/03-无限时间.md)）。若不处理，回合跳过写的 0:00 会被立刻弹回 99:59，等于无效。解决方式是 **UI 面板层先暂停无限时间、再写 0:00**：

1. `run_skip_round`（panel.py）在线程里先检测 `is_enabled("time")`，若无限时间开启则先调 `time.pauseFor({"ms": 2000})`（暂停 2 秒），随后才调 `skip_round` 写 0:00。**注意：JS 脚本本身不调 pauseFor，协调完全发生在 UI 面板（Python）层。**
2. 效果：2 秒暂停窗口内无限时间不反弹，游戏能检测到 0:00 并正常结束回合；窗口自然过期后无限时间自动恢复继续钳制，无需显式恢复。

## 作用范围

**全局无区分（回合计时是全局共享数据）**。回合倒计时属于整个房间共有的 ModeBase 状态，清零立即结束当前回合，对人类和 bot 一视同仁 —— 作用于全场，不存在玩家私有数据概念。

## 产品设计巧思

- **与「无限时间」自动协同（核心）**：UI 面板层先 `time.pauseFor(2000)` 暂停无限时间钳制、再写 0:00──两个功能同开也不互相抵消，用户无需手动关掉一个来用另一个（协调放在面板，JS 纯净）。
- **按钮防呆提示**：首启需先 enable 再 skip，按钮上明确提示"第一次跳过需要点击两次"，避免用户困惑。
- **防重复写**：`already_zero` 拦截已为 0:00 的场景，防止用户反复点击无效操作；`skipGuard` 防重入。
- **跨房间不写错**：`generation` 防陈旧写，切房后不会把旧房间误当新房间处理。

## 开发历程（重点）

### 踩过的坑（问题 → 原因 → 解决）

1. **直接写回合时间 0 → 被无限时间弹回**
   - 问题：一开始的方案就是"把回合时间写 0"，但时灵时不灵——开着"无限时间"时写 0 完全不生效。
   - 原因：无限时间模块会在分钟 <90 时把 `restGameTime`(+0x34/+0x38) **钳回 99:59**，回合跳过写的 0:00 被立刻弹回，等于白写。
   - 解决：**UI 面板层先暂停无限时间、再写 0:00**——`run_skip_round`（panel.py）在线程里先检测 `is_enabled("time")`，开启则先调 `time.pauseFor({"ms":2000})`（暂停 2 秒）再调 `skip_round`；2 秒窗口内游戏检测到时间归零自然结束回合，窗口过期后无限时间自动恢复钳制。
2. **调 `GameManager.GameRoundEnd()` → 只是个广播通知**
   - 问题：尝试直接调用结束回合，结果没有真正结束/流程不完整。
   - 原因：该函数是"广播通知"性质，不是完整的状态机切换入口，外部强行调用缺少配套流程。
   - 解决：放弃调用，回归"改内存模拟结果"。
3. **调 `ResetRound()` 静态方法 → 失败**：同样依赖大量前置状态，放弃。
4. **IDA 反编译读到"不可读内容"，卡了半天**
   - 问题：在 IDA 里啃回合结束相关函数，读到的内容不可读/看不懂，分析陷入僵局。
   - 原因：反编译对象没找对，或真正需要的是"变量偏移"而不是函数逻辑。
   - 解决：改用 **"Hook 验证"大法**——不确定类/偏移时，随手写个 `Interceptor.attach` 打印 onEnter 的 `args[0]`（this 指针），看哪个函数在运行时真的被调用、再拿指针去内存验证字段，找到"活人"再下结论。
5. **强行调 `refreshNextRound()` → 立即闪崩**
   - 问题：想调用推进到下一回合，结果**直接闪崩**。
   - 原因：该成员只在正常流程"回合结束时"才被正确初始化；提前强行调用时内部还是空的，一访问空对象就崩。
   - 解决：**彻底放弃调用任何游戏内部状态机函数**，改为"写 0:00 触发游戏原生时间到逻辑"。
6. **房间切换后旧实例残留 → 写到旧房间**
   - 问题：整合时发现回合切换/退房后，`modeBaseInstance` 仍指向旧房间的 ModeBase，跳过可能写到已失效/旧实例上。
   - 解决：引入**房间代号 generation 防陈旧写**——`modeBaseGeneration` 与 `roomGeneration` 比对，不一致直接拒绝（`stale_room_generation`）；`ExitGame`/`OnDestroy` 时递增 `roomGeneration` 并清实例。

### 方案迭代

1. **第一版**：写回合时间 0 → 能触发结束，但与无限时间冲突时无效（被钳回 99:59）。
2. **第二版思路**：调 `GameManager.GameRoundEnd()` → 只是广播通知，不完整，失败。
3. **第三版尝试**：调静态 `ResetRound()` → 失败。
4. **IDA 反编译** → 读到不可读内容卡住 → 换"Hook 验证大法"定位真实现象。
5. **尝试 `refreshNextRound()`** → 前置状态未初始化，**闪崩**。
6. **结论：游戏内部状态机函数依赖大量前置条件，不适合外部强行调用** → **回归写内存**：把 `ModeBase.restGameTime` 写 0:00，让游戏"时间到"原生逻辑自然结束回合（`skip_round.js` 全模式通用版，3 个 Hook：UpdateTimeUI 捕实例 / GameRoundEnd 清实例 / OnTimeOut 监控）。
7. **解决无限时间冲突（关键转折）**：JS 脚本本身不调 pauseFor，协调完全放在 **UI 面板（Python）层**——先 `time.pauseFor(2000ms)` 再写 0:00，功能即可稳定使用。
8. **整合版（最终）**：5 个 Hook；加 `modeBaseGeneration` vs `roomGeneration` 防陈旧写、`isValidInstance` 三重校验、`skipGuard` 防重入、`already_zero` 防重复写、enable/disable 可逆卸载；`events.py`/`monitor.py` 把"跳过结果/回合状态"回传 UI 日志；按钮文案提示"第一次跳过需要点击两次"（先 enable 再 skip 的防呆）。

### 一开始没考虑到的点

- **功能间协同**：无限时间模块会把时间钳回 99:59——写 0 之前没想到别家模块正在"罩着"这个字段，多模块同时改同一地址必须考虑时序。
- **GameRoundEnd 只是广播通知**，不是完整的结束入口。
- **状态机函数强行调用依赖前置条件**（refreshNextRound 的初始化时机），会闪崩——外部调函数远没有"改内存模拟结果"稳。
- **防陈旧写**：房间切换后旧 ModeBase 指针要用 generation 比对拦截，光靠"清空实例"不够。
- **"第一次跳过需要点击两次"**：首次需先 enable 再 skip，按钮上要提示用户防呆。

### 经验教训

- 宁可"**改内存模拟结果**"，不要强行调游戏状态机函数（用偏移而非类名/函数，最稳）——写 0:00 让游戏自己走"时间到"流程，比硬调 GameRoundEnd/ResetRound/refreshNextRound 可靠得多。
- 不确定函数/字段时用 **Hook 打印验证"活人"**，别在 IDA 里硬啃不可读内容。
- **多模块协同要在 UI 层编排时序**：暂停别人的钳制（pauseFor）→ 动手写 0 → 窗口过期自动恢复，JS 层保持纯净不掺协作逻辑。
- 写操作要有**防陈旧写 + 防重入 + 实例校验**三件套，配合房间生命周期清理。

## 一句话总结

5 个 attach Hook 维护 ModeBase 实例 + 房间代号（`modeBaseGeneration` vs `roomGeneration`）防陈旧写，按钮 RPC 触发对 `restGameTime`（+0x34/+0x38）条件式清零（0:00）；与无限时间协同由**面板层**先 `pauseFor(2000ms)` 再写 0:00（JS 不调 pauseFor），全局生效不分 bot/人类，带重入保护、状态统计与可逆卸载；开发核心教训是"调游戏状态机函数全翻车 → 改内存写 0:00 模拟结果"、"refreshNextRound 闪崩 → 放弃调函数"、"多模块同改一字段 → UI 层编排时序"。
