# 16｜赋予武器（Weapon Giver）

**来源**：`features/16_weapon_giver/`（script.js）+ 开发素材 `05-正式功能/16-赋予武器-全模式/经验总结.md`、`weapon-hero-giver-fixed-v2.js`、`weapon_hero_ui_v2.py`

## 核心原理

- **一句话**：不 Hook 游戏消耗逻辑，而是直接调用 `GameManager.GiveWeapon` 主动造武器；关键是把 `GiveWeapon` 从 Frida RPC 线程迁移到游戏主线程 `ModeBase.Update` 执行，本质是“主动注入返回值”类方案，解决 Unity 线程亲和性崩溃。
- **手段归类**：Hook 主线程函数 + 任务队列排队 + 延迟到主线程直接 `NativeFunction` 调用。

## 关键 Hook 表（GameAssembly.dll）

| RVA | 符号 | 手段 | 作用 |
|---|---|---|---|
| 0xAF6A00 | ModeBase.Update | Interceptor.attach | 主线程调度：消费任务队列、执行 GiveWeapon、复活检测 |
| 0xAFAA40 | GameManager.GameRoundEnd | attach | 回合结束仅清空任务与玩家缓存 |
| 0xAEE850 | ModeBase.ExitGame | attach | 退出房间立即封锁旧指针与新任务 |
| 0xAFB6F0 | GameManager.OnDestroy | attach | 场景销毁最终保险 |
| 0xB51210 | Player.OnEntityDeath | attach | 识别本地玩家死亡状态 |
| 0xB511C0 | Player.OnDestroy | attach | 本地玩家销毁时清空缓存 |
| 0xB53760 | Player.Spawn | attach(onLeave) | 复活后触发自动赋予武器 |

## 修改的关键字段

| 偏移 | 字段 | 值/说明 |
|---|---|---|
| `GameManager_TypeInfo` 0x0E2933C → klass → static_fields(+0x5C) → `myPlayer`(+0x00) | 本地玩家指针 | 只读，用于定位 myPlayer |
| Player.wpns（+0xA0） | 武器列表 | 校验玩家有效性 |
| PlayerWeapons.inUse（+0x18） | 当前武器 | 读取当前使用武器 |
| 静态 `GiveWeapon`(0xAFB390) 调用参数 | player, weaponId, autoGiveUp=0, autoSelect, NULL | 与游戏内部 HUD_Cheat 调用一致 |

**特殊处理**：
- **任务队列**：RPC 只入队（带 `expiresAt` 5s TTL），不在 RPC 线程直接调用；每帧最多消费 1 个任务。
- **原生调用冷却**：相邻两次 `GiveWeapon` 至少间隔 250ms（`_nativeCallCooldownMs`）。
- **房间活动窗口**：`_roomActiveWindowMs=1200`，切房宽限 `_modeSwitchGraceMs=800`，非稳定房间直接丢弃任务。
- **双重身份校验**：以 `GameManager.myPlayer == this` 对照（`isMyPlayer`），必要时再校验 isBot（注释明言 get_isMyPlayer 在 isBot 功能改写 isBot=1 时不可靠，以 myPlayer 为准）。
- **玩家实例合法性校验** `isPlayerValid`：地址 > 0x10000、可读、`wpns(+0xA0)` 非空、`get_isDead` 非死亡。
- **可逆卸载**：enable/disable 时 detach 全部 hooks、清空队列与缓存、重置 NativeFunction。
- **复活自动赋予**：死亡→存活状态翻转时（Spawn onLeave）重放入队武器。
- **特殊武器二次赋予**：`weaponId ∈ {2978, 3494}`（AT4/FN FAL 榴弹版）首次进入房间连入队 2 次，第二次 select=1 进入 Deploy，才真正应用效果；`_firstRoomSpecialGiveDoneByWeaponId` 保证仅首页触发一次。
- **日志限流**：每模块上限处理（如 80 条）避免刷屏。

## 作用范围

仅本地玩家。数据源是 `GameManager.myPlayer`（玩家私有静态字段），只对该玩家实例调用 GiveWeapon；不触碰其他玩家或 Bot。

## 产品设计巧思

- **特殊武器自动补一枪**：AT4 / FN FAL 榴弹版这类武器第一次赋予只“拿在手上”不生效，功能自动再补一次赋予让武器进入 Deploy 状态，用户只需点一次，效果立刻到位。
- **复活自动再给**：设好想要的武器后，角色死亡复活会自动重新赋予，用户不用每局/每次死亡都手动点。
- **给一次就好，切房自动收手**：退出房间/回合结束自动清空待办，不会把上一局的武器请求拖到下一局误发。
- **点一下就有回执**：点击赋予后 UI 会收到成功/失败结果，失败会提示原因（没进房/已死亡/还没就绪），不会“点了没反应”。
- **乱点时兜底**：没进房间、玩家已死亡、游戏还没就绪时直接拦截并给出提示，避免在错误时机执行导致卡顿或崩溃。
- **换武器自动继承**：切换武器后按一次即可沿用，配合复活自动赋予形成“配一次、全场有效”的体验。

## 开发历程（重点）

### 踩过的坑

1. **`access violation accessing 0x8`（空指针）**
   - 一开始没考虑到：直接从 Frida RPC 回调线程调用 `GiveWeapon`。
   - 出问题：反复崩溃在地址 0x8。
   - 怎么发现：用 IDA 反汇编 `GiveWeapon` 内部链，发现它先调 `GameManager.GetWeapon(weaponIndex)`，内部走 `Object.Instantiate<GameObject>()` + `GameObject.GetComponent<Weapon>()`，这些 Unity API 有线程亲和性（只能主线程调用）。
   - 怎么修：Frida RPC 线程调用导致 `GetWeapon` 返回 null，后面访问 null 对象第一个字段（+0x8）崩溃。把调用迁移到主线程即解决。

2. **`il2cpp_runtime_invoke` 参数格式错误（`accessing 0x1`）**
   - 一开始没考虑到：反射调用参数数组格式。
   - 出问题：`void** params` 需指向每个参数值，值类型要预先分配缓冲区；写错指针数组导致崩溃在 0x1。
   - 怎么修：改用 `NativeFunction` 直接调用（同时动态获取有效 MethodInfo 作为最后一个参数，避免 IL2CPP 内部访问自身 MethodInfo 崩溃），并显式 `'mscdecl'`。

3. **调用约定错误**
   - 一开始没考虑到：Windows x86 IL2CPP 用 `__cdecl`，Frida 里对应 `'mscdecl'`；写 `'cdecl'` 会 `invalid abi specified`。
   - 出问题：参数/栈错位崩溃。
   - 怎么修：从 IDA 确认约定，始终显式指定 ABI，不信任 Frida 默认（Windows 默认 stdcall 会错）。

4. **武器页控件过多导致启动和滚动卡顿**
   - 一开始没考虑到：大量 CustomTkinter 武器卡片一次性构建会拖慢主窗口，`CTkScrollableFrame` 滚动时还会反复重排大量控件。
   - 出问题：先尝试延迟构建；随后改成虚拟网格动态创建/销毁卡片，反而出现滚动延迟、残影和首次切换空白，其中空白的直接原因之一是 `place()` 不支持 `height` 参数。
   - 怎么修：撤销虚拟网格，完整列表改用 `after_idle / after` 分批创建，滚动过程中不再动态销毁或重新定位卡片；当前又改为程序启动后自动预构建，不再等首次点击页签才创建，但仍通过分批调度避免一次阻塞；同时把每行 4 个改为 3 个。当前实现为 `WEAPON_COLUMNS = 3`、`ROW_BUILD_BATCH_SIZE = 2`，`_render_batch()` 通过 `after(1, ...)` 调度下一批。

5. **复活自动装备勾选在 UI 未就绪或未连接时异常**
   - 一开始没考虑到：App 尚未绑定复活选项变量时，勾选回调仍可能被触发；未连接游戏时又没有 RPC 可下发。
   - 出问题：页面构建时序可能让回调读取未就绪变量并报错，用户离线勾选的意愿也可能因没有 RPC 而丢失。
   - 怎么修：`CTkCheckBox` 把当前 bool 值直接传给控制器；控制器先更新 `state.respawn_enabled` 并持久化。启用勾选时只保存意愿，之后由用户选择并赋予武器时再设置复活武器；取消勾选且已连接时立即下发 clear RPC。这样绑定时序不再报错，离线意愿也能保存。

6. **快捷键下拉框显示已被其他武器占用的按键**
   - 一开始没考虑到：旧弹窗把全部快捷键都列为候选，没有按 `WeaponHotkeyManager` 的互斥绑定状态过滤。
   - 出问题：用户选完并确认后才发现快捷键已被其他武器占用。
   - 怎么修：候选只列 `get_available_hotkeys()`，当前武器自己的已绑定键可以补回，其他武器占用的键不显示；没有可用键时禁用选项和确认按钮并提示。这样在选择阶段就排除了冲突。

### 方案迭代

| 版本 | 思路 | 结果 |
|---|---|---|
| v1-v2 | 直接 NativeFunction 调用 + MethodInfo 传 ptr(0) | 崩溃 0x8 |
| v2-fixed | 改用 `il2cpp_class_get_method_from_name` 取有效 MethodInfo | 依然崩溃 0x8 |
| v3 | 改用 `il2cpp_runtime_invoke`，构造参数指针数组 | 崩溃 0x1（数组格式错） |
| v4 | 修正参数为指针数组 + ABI 改 mscdecl | 仍 0x8 |
| **v5** | **识别线程问题，Hook ModeBase.Update 任务队列 + send 异步通知** | ✅ 成功 |

### 一开始没考虑到的点

- Unity 引擎的**线程亲和性**：RPC 工作线程 ≠ 主线程，凡涉及 Instantiate/GetComponent/Transform 的调用都必须在主线程。
- MethodInfo 对直接调用非必需，但部分 IL2CPP 函数内部会访问自身 MethodInfo，传 null 可能崩。
- bool 在 IL2CPP x86 栈上传递占 4 字节（非 C# 的 1 字节）。
- 切房/回合结束/玩家销毁后，旧玩家指针和未完成任务都会失效，必须做生命周期清理，否则 `GiveWeapon` 会作用到已销毁对象。

### 经验教训

- IL2CPP 逆向不止地址+参数，还必须**尊重 Unity 线程模型**：凡涉及 GameObject/Transform 的方法，第一时间考虑主线程调度，别在非主线程直调。
- `access violation accessing 0x8`（小地址）≈ 空指针解引用，用 IDA 看内部调用链定位是哪个对象为 null。
- 异步 UI（Frida RPC + Python）与游戏内部、一次性就要结果的调用，用**任务队列 + 主线程消费 + send 异步回执** 来解耦。
- 对一次性、强线程依赖的调用，调度到 `ModeBase.Update`（每逻辑帧主线程）比 `setInterval` 定时器更契合游戏生命周期。

## 一句话总结

通过 Hook `ModeBase.Update` 把原本在 Frida RPC 线程执行的 `GiveWeapon` 迁移到主线程任务队列，一举解决 Unity 线程亲和导致的一连串空指针崩溃（v1–v4 全栽在线程问题上），最终配合同步 ID、房间生命周期清理与特殊武器二次赋予落地。
