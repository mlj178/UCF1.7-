# UCF 修改器打包与发布须知

本文档适用于 `全功能整合包x.x/game_modifier/game_modifier.spec`，说明 Windows 发布版的构建环境、版本识别规则、打包规则、检查流程和常见故障。

> 当前状态：现有 `spec` 仍有若干待修正项，包括输出名称使用固定字符串。完成本文“发布前阻断项”之前，不应把新生成的 EXE 作为正式版发布。

## 一、当前打包方式

- 打包工具：PyInstaller
- 主入口：`game_modifier/main.py`
- 配置文件：`game_modifier/game_modifier.spec`
- 目标平台：Windows 64 位
- Python：CPython 3.12 64 位
- 窗口模式：`console=False`
- 权限：`uac_admin=True`
- UPX：`upx=False`
- 当前输出形式：onedir（目录形态）
- 安装器：Inno Setup，见 `packaging/installer.iss`
- 构建脚本：`packaging/build_release_non_destructive.ps1`
- 用户数据目录：`%LOCALAPPDATA%\UCFModifier\<版本>\data`（例如 2.6）
- 版本号：从 `全功能整合包x.x` 目录名自动识别，经 `/DAppVersion=` 传入 Inno Setup

PyInstaller 成品包含 Python 解释器和已收集的依赖。用户不需要另外安装 Python，也不应把“缺少本机 Python”作为 EXE 启动失败的排查方向。

## 三、发布环境标准

### 1. 必须使用专用虚拟环境

正式构建不得继续直接使用装有大量其他工具的全局 Python。应为发布构建建立独立虚拟环境，只安装项目直接需要的包及其锁定依赖。

所有版本共用的构建环境固定放在：

```text
04-正式发行版/.venv-build/
```

不得再在 `全功能整合包x.x` 或其 `game_modifier` 目录内创建、复制 `.venv-build`。开发新版本时保留发布根目录下的共享环境，只复制源码和依赖清单。虚拟环境由各版本自己的 `game_modifier/requirements-build.txt` 校准；每次切换版本打包前都必须重新执行安装和 `pip check`。

从目标版本的 `game_modifier` 目录执行：

```powershell
$projectDir = (Get-Location).Path
$releaseRoot = Split-Path -Parent (Split-Path -Parent $projectDir)
$buildEnv = Join-Path $releaseRoot '.venv-build'
$buildPython = Join-Path $buildEnv 'Scripts\python.exe'

if (-not (Test-Path -LiteralPath $buildPython -PathType Leaf)) {
  py -3.12 -m venv $buildEnv
}

& $buildPython -m pip install -r (Join-Path $projectDir 'requirements-build.txt')
& $buildPython -m pip check
```

不要求激活虚拟环境，后续命令统一通过 `$buildPython` 调用，避免误用全局Python。不要在正式构建前无条件升级依赖。需要升级 Python、PyInstaller、Pillow 或其他包时，必须先更新目标版本的 `requirements-build.txt`，再执行完整测试并生成新的正式版。如果Python大版本或次版本发生变化，应重新创建共享环境，不要直接沿用旧环境。

### 2. 必须锁定版本

不要继续使用只有 `>=` 下限的旧依赖清单。Python、PyInstaller、hooks和运行依赖都应记录确切版本；升级任何一项后必须重新完成全套发布测试。

项目直接依赖应至少包括：

- PyInstaller
- pyinstaller-hooks-contrib
- customtkinter
- frida
- psutil
- keyboard
- pygame
- Pillow

当前源码没有使用 `frida_tools` 和 `pynput`，不应继续作为正式打包依赖。`pygame` 在声音管理器中动态导入，必须保留；Pillow被设置界面使用，也必须保留。

### 3. 不要安装外部 AVIF 插件

项目不使用 AVIF 图片，不需要 `pillow-avif-plugin`。旧成品中出现 `PILavif.cp312-win_amd64.pyd`，说明当时的构建环境与当前环境不同，并且把可选扩展收进了EXE。

当前 Pillow 已自带自己的 AVIF 支持。不要为了处理旧报错重新安装 `pillow-avif-plugin`；该报错发生在单文件自解压写入阶段，不是缺少该插件。

## 四、版本号与构建类型规则

### 1. 版本号只能从整合包文件夹名称解析

不得在 `spec`、构建命令或发布检查命令中写死版本号。`spec` 所在目录的上一级文件夹必须采用以下格式：

```text
全功能整合包x.x
```

其中 `x.x` 是实际版本号。构建时必须严格匹配文件夹名称，提取其中的数字，并据此生成正式版文件名 `UCF<版本号>修改器.exe`。如果目录名不符合规则，构建必须直接终止，不能使用默认版本号或旧版本号兜底。

`spec` 应采用以下逻辑：

```python
import os
import re

current_dir = os.path.dirname(os.path.abspath(SPEC))
package_dir_name = os.path.basename(os.path.dirname(current_dir))
version_match = re.fullmatch(
    r"全功能整合包(?P<version>\d+(?:\.\d+)+)",
    package_dir_name,
)
if version_match is None:
    raise ValueError(
        f"整合包目录名不符合规则：{package_dir_name}；应为：全功能整合包x.x"
    )

package_version = version_match.group("version")
app_name = f"UCF{package_version}修改器"
```

在 `EXE(...)` 中统一使用：

```python
name=app_name
```

每次复制整合包目录并修改版本号后，`spec` 无需再手工修改输出名称。界面中显示的版本号如果来自其他文件，也必须在发布检查中确认与目录版本一致。

### 2. 未特别说明时一律构建正式版

收到“打包”“重新打包”“生成EXE”或“生成发布包”等请求，只要没有明确要求测试版或诊断版，就一律按正式版构建和验收。

正式版必须满足：

- 文件名由整合包目录版本动态生成
- `console=False`
- `debug=False`
- `upx=False`
- 不包含测试模块、开发日志和开发者个人配置
- 输出到 `dist_release`，并完成本文全部正式发布检查

只有用户明确说“打包测试版”或“打包诊断版”时，才允许生成对应版本。测试版或诊断版必须带明确后缀、使用独立输出目录，不得覆盖或冒充正式版。

## 五、发布前阻断项

以下问题必须先修正，再生成新的正式版：

### 1. 改为动态输出文件名

当前 `spec` 的 `name` 仍使用固定字符串，不符合上面的版本规则。正式构建前必须加入目录版本解析逻辑，并将 `EXE(...)` 的 `name` 改为 `app_name`。

### 2. 删除 `data` 目录打包逻辑

当前规则会把以下本机运行状态打进单文件包：

- `desired_states.json`
- `hotkeys.json`
- `weapon_hotkeys.json`
- `universal_revision.json`

程序运行时实际读取的是EXE同目录下的 `data`，不是 `_MEI/data`，因此这些文件打进EXE没有运行价值，还会暴露测试状态。应删除整个 `data` 收集段，不应只增加排除名单。

首次运行时，由程序在EXE同目录按需创建 `data` 目录及配置文件。正式发布目录不得附带开发者自己的JSON状态。

### 3. 排除缓存、测试和旧模块

当前UI资源收集会把 `ui/**/__pycache__/*.pyc` 当作数据文件打包；当前宽泛的 `collect_submodules()` 还会分析功能测试、`features._template` 和 `core._legacy_archive`。

必须做到：

- 所有目录排除 `__pycache__`、`.pyc`、`.pyo`
- 排除名称以 `test_` 开头或以 `_test` 结尾的模块
- 排除 `features._template`
- 排除 `core._legacy_archive`
- 不收集 `tools` 目录

### 4. 删除无用隐藏导入

从 `hiddenimports` 删除：

- `frida_tools`
- `pynput`

保留 `pygame`，因为它在函数内部动态导入。功能插件通过 `importlib.import_module()` 动态加载，因此仍需显式收集，但必须使用过滤后的收集规则。

### 5. 必需文件缺失时必须终止构建

以下文件缺少任意一个都应直接报错，不得静默跳过并继续生成残缺EXE：

- `plugins/universal_hook/inject.exe`
- `plugins/universal_hook/Universal-ImGui-Hook.dll`
- `plugins/universal_hook/universal_hook.json`
- `资源/微信赞赏码.png`
- `资源/音效1.MP3`
- `_tkinter.pyd`
- `tcl86t.dll`
- `tk86t.dll`
- Tcl 的 `init.tcl`
- Tk 的 `tk.tcl`

### 6. 清理旧式无效配置

后续可以从 `spec` 清理这些旧模板字段：

- `block_cipher = None`
- `cipher=block_cipher`
- `win_no_prefer_redirects=False`
- `win_private_assemblies=False`
- 仅对 macOS 有意义的空参数

这些内容目前多数不会导致失败，但会增加维护成本，并可能在未来PyInstaller版本中变成错误。

## 六、UPX规则

发布版保持：

```python
upx=False
```

不要按照旧说明改回 `upx=True`，原因如下：

- 当前电脑没有配置UPX程序
- 单文件内部归档本身已经压缩
- UPX会进一步处理 `.dll`、`.pyd` 等二进制文件
- 某些二进制经过UPX后可能损坏
- 对注入器类程序，额外二进制压缩不利于杀毒软件信誉判断

除非以后单独完成兼容性和杀毒软件测试，否则不启用UPX。

## 七、Tcl/Tk规则

当前 `spec` 会从本机 Python 安装目录复制 Tcl/Tk 到临时暂存目录，并设置：

```text
TCL_LIBRARY
TK_LIBRARY
```

当前暂存位置是：

```text
game_modifier/build/_tcltk_staging/
```

即使构建命令指定 `--workpath build_release`，这个Tcl/Tk暂存目录仍位于 `build/`，这是当前 `spec` 自己定义的行为。

构建日志出现以下任一情况时禁止发布：

- `tkinter installation is broken`
- 找不到 `hook-_tkinter.py`
- 找不到 `pyi_rth__tkinter.py`
- 缺少 `_tkinter.pyd`
- 缺少 `tcl86t.dll` 或 `tk86t.dll`
- 启动界面时报 Tcl/Tk 初始化错误

不要在没有完整回归测试的情况下升级到不同的大版本Python；当前Tcl/Tk路径和DLL名称与Python 3.12环境绑定。

## 八、正式构建命令

在完成“发布前阻断项”并建立专用虚拟环境后，从 `game_modifier` 目录执行：

```powershell
& $buildPython -m PyInstaller `
  --clean `
  --noconfirm `
  --workpath build_release `
  --distpath dist_release `
  game_modifier.spec
```

构建完成后，按目录名计算预期成品路径并确认文件存在：

```powershell
$projectDir = (Get-Location).Path
$packageFolder = Split-Path -Leaf (Split-Path -Parent $projectDir)
$versionMatch = [regex]::Match(
  $packageFolder,
  '^全功能整合包(?<version>\d+(?:\.\d+)+)$'
)
if (-not $versionMatch.Success) {
  throw "整合包目录名不符合规则：$packageFolder"
}
$packageVersion = $versionMatch.Groups['version'].Value
$exePath = Join-Path 'dist_release' "UCF$packageVersion修改器.exe"
if (-not (Test-Path -LiteralPath $exePath -PathType Leaf)) {
  throw "未找到预期的正式版：$exePath"
}
Write-Output $exePath
```

如果只生成了名称与目录版本不一致的EXE，必须停止发布。不能靠手工改名掩盖 `spec` 中的版本错误。

## 九、构建结果检查

以下检查命令沿用上一节计算得到的 `$exePath`。如果重新打开了 PowerShell，请先重新执行上一节的成品路径计算代码。

### 1. 检查警告和依赖图

每次构建必须检查：

```text
build_release/**/warn-*.txt
build_release/**/xref-*.html
```

重点搜索：

- `PILavif`
- `pillow_avif`
- `test_`
- `_template`
- `_legacy_archive`
- `pynput`
- `frida_tools`
- `ModuleNotFoundError`
- `tkinter installation is broken`

警告文件不为空不代表构建失败，但所有与本项目直接依赖有关的缺失模块都必须解释清楚。

### 2. 检查EXE内容

使用PyInstaller自带的归档查看工具检查成品：

```powershell
& $buildPython -m PyInstaller.utils.cliutils.archive_viewer -l $exePath
```

成品中不应出现：

- 外部 `PILavif` 插件
- 项目测试模块
- `__pycache__`
- 开发日志
- 开发者个人JSON状态
- `_template` 和 `_legacy_archive`

### 3. 生成SHA256

```powershell
Get-FileHash -LiteralPath $exePath -Algorithm SHA256
```

发布时同时保存并公布SHA256。用户报告“只有他的电脑打不开”时，先比较双方哈希；哈希不同则先重新下载，不进入程序兼容性排查。

### 4. 检查数字签名

当前 `inject.exe` 和 `Universal-ImGui-Hook.dll` 均未签名。正式长期分发建议依次签名：

1. `inject.exe`
2. `Universal-ImGui-Hook.dll`
3. 最终主EXE

签名不能保证杀毒软件不报，但能建立发布者身份和文件完整性，降低未知程序信誉问题。

## 十一、正式版、测试版与诊断版

### 正式版

- 所有未注明构建类型的打包请求均默认生成此版本
- `console=False`
- `debug=False`
- `upx=False`
- 不包含测试和开发日志
- 所有由Python或功能模块控制的文件日志开关必须关闭；当前必须确认 `features/11_aim/events.py` 中 `AIM_DEBUG_LOG_ENABLED = False`
- 输出到 `dist_release`
- 用于正常分发

### 测试版

只有收到明确的“打包测试版”要求时才生成：

- 文件名必须带“测试版”后缀
- 输出到独立目录，例如 `dist_test`
- 可包含本次测试明确需要的开关或资源
- 不得覆盖、替换或作为正式版发布
- 测试结束后如需发布，必须重新按正式版规则构建，不能直接给测试版改名

### 诊断版

用户出现无法复现的启动或导入问题时，应单独构建诊断版：

- `console=True`
- 根据需要启用PyInstaller导入调试
- 输出可回传的启动日志
- 文件名明确带“诊断版”
- 输出到独立目录，例如 `dist_diagnostic`
- 不得覆盖或作为正式版发布

当前冻结环境下的 `core/log_manager.py` 使用 `NullHandler`，正式版也没有控制台，因此常规Python日志不会写入文件。不要再在说明中声称“打包后保留控制台日志”。如果后续需要远程排错，应单独设计安全、可轮转、可由用户主动发送的诊断日志。

`console=False` 和 `debug=False` 不能阻止业务代码主动创建日志文件。正式构建前必须检查所有Python及功能模块的文件日志开关；正式版必须保持关闭，只有明确要求测试版或诊断版时才允许打开。

构建后的检查不能只确认EXE中没有打包旧日志，还必须运行正式版并触发相关功能，然后确认EXE目录没有新增以下主程序日志：

```text
logs/aim_debug.log
logs/game_modifier.log
```

发现上述文件时必须停止发布，先关闭对应日志开关并重新构建，不能只删除生成的日志后继续发布。

## 十二、单文件版的限制

单文件EXE启动时必须先把 `.pyd`、DLL和资源写入系统临时目录。以下因素都可能导致解压失败：

- 杀毒软件或EDR拦截新写出的二进制文件
- `%TEMP%` 权限或安全策略异常
- 系统盘空间不足
- 磁盘配额或文件系统错误
- EXE下载不完整

典型报错：

```text
Failed to extract xxx.pyd: decompression resulted in return code -1
```

该错误发生在写临时文件阶段，不等同于缺少VC++运行库，也不等同于 `.pyd` 本身不兼容。

由于程序同时使用单文件、自解压、管理员权限、注入器和DLL，建议后续增加 `onedir` 目录版作为兼容备用。目录版不需要每次启动自解压，也更便于确认缺少了哪个文件。



## 十三、发布目录内容

单文件正式版发布时只提供：

```text
UCF<目录版本号>修改器.exe
UCF<目录版本号>修改器.exe.sha256.txt
必要的使用说明
```

不得发布：

- `build/`
- `build_release/`
- 开发环境 `data/`
- `logs/`
- `__pycache__/`
- 测试文件
- `inject_log.txt`
- `esp_debug.log`
- `esp_dllmain_test.txt`

如果以后提供目录版，必须压缩并分发整个目录，不能只取出其中的主EXE。
