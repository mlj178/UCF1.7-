# 从本项目提炼的 Agent 协作与工程控制经验

## 一、新 Agent 会话使用固定入口

不要让新 Agent 每次从整个项目盲目搜索。项目应提供一份固定的入口文档，并根据任务类型规定最小阅读顺序。

推荐顺序：

```text
项目入口与背景
→ 当前任务对应的权威规范
→ 同类成功功能或模板
→ 当前正式版本代码
→ 与本任务直接相关的问题记录
```

Agent 不需要一次读完整个项目，而应按任务角色读取“完成当前任务所需的最小充分上下文”。这样既能减少无关信息干扰，也能避免误用旧版本目录、旧接口和已经废弃的实现方式。

## 二、一个主题只保留一个唯一权威来源

生命周期、编码、状态恢复、插件接入、打包发布等主题，应分别指定唯一权威文档。其他文档只引用权威文档，不重复复制整套规则。

推荐规则：

```text
一个主题 = 一份权威文档
其他文档 = 只写链接、摘要或适用场景
发生冲突 = 以指定的权威文档为准
规则变化 = 只修改权威文档并补更新记录
```

这样可以避免多份文档长期演化后互相冲突，也可以让 Agent 明确应该相信哪一份规则。

## 三、给出多个方案，由用户审批后再执行

当一个需求存在不同实现路径时，Agent 不应直接替用户选择并开始修改。应先提供几个真正可执行的方案，说明各自的范围、优点、缺点、风险和推荐理由，再等待用户审批。

推荐格式：

```text
方案 A：最小修改
- 修改范围：
- 优点：
- 缺点或限制：

方案 B：标准实现
- 修改范围：
- 优点：
- 缺点或限制：

方案 C：长期治理
- 修改范围：
- 优点：
- 缺点或限制：

推荐方案：B
推荐理由：……

请确认选择哪个方案；确认后再执行。
```

方案必须有实际差异，不能只是换一种说法。用户没有确认前，不修改代码、不新增文件、不顺手重构。

## 四、修改前先提交“变更说明清单”

即使实现方案已经基本确定，Agent 在执行前仍应明确告诉用户本次准备改什么。

至少列出：

```text
1. 涉及哪些文件。
2. 每个文件准备修改哪个位置或模块。
3. 每处修改解决什么问题。
4. 哪些相关文件明确不修改。
5. Agent 推荐采用什么方案，以及推荐理由。
6. 修改后准备怎样验收。
```

推荐格式：

```text
计划修改文件：
- path/a.py：修改 XXX 方法，增加……
- path/b.js：修改 XXX Hook，调整……
- path/c.md：补充本次行为说明。

明确不修改：
- ui/app.py
- 与本功能无关的其他插件

推荐方案：……
验收方式：……

请确认；确认后开始执行。
```

如果执行过程中发现必须增加新的文件或扩大修改范围，应暂停并重新说明原因，不能把新增范围隐藏在最终结果里。

## 五、把成熟做法固化为可直接套用的模板

对于重复出现的功能类型，不要每次都让 Agent 从零思考目录、接口、状态和接入方式。应提供一套经过验证的模板，让后续开发以“复制模板、填写差异”为主。

模板应固定：

```text
目录结构
文件职责
稳定的功能 ID
manifest 字段
标准 RPC
生命周期入口
UI 调用边界
日志格式
配置和状态字段
必要的检查项
禁止修改的中心文件
```

模板的目的不是限制合理实现，而是给 Agent 划定稳定扩展点。新增普通功能时，优先只在自己的功能目录内完成，使用通用回调、通用事件和标准接口，不因每加一个功能就修改一次主程序。

模板应同时写明：

- 哪些内容必须保留，不能自行删除或改名。
- 哪些占位内容必须替换。
- 哪些部分允许按功能差异扩展。
- 什么情况必须跳出模板并重新向用户申请方案确认。

这样可以减少 Agent 自行添加内容、改变接口或把业务逻辑堆进中心文件，也能降低功能数量增加后主程序持续膨胀的风险。

## 七、区分用户意图、保存参数和实际运行状态

程序中的状态不能只用一个“开启/关闭”概念表示。至少应区分：

```text
用户保存的参数
用户希望下次继续使用的意图
UI 当前显示状态
功能当前是否已经真正生效
需要用户手动触发的一次性动作
可以自动恢复的持续功能
只能预约、不能立即生效的功能
```

基本原则：

```text
保存了参数 ≠ 启动时自动执行动作
UI 开关打开 ≠ 游戏内已经生效
用户希望开启 ≠ 当前具备生效条件
上次执行过一次性动作 ≠ 下次启动可以自动重放
```

### 多人生化 Buff 选择示例

多人生化 Buff 选择适合把“参数保存”和“动作执行”分开：

- 幽灵方、人类方选择属于配置参数，可以在用户修改后保存。
- 程序下次启动时可以恢复两个下拉框的选择，方便用户继续使用。
- 恢复下拉框不等于自动把 Buff 写入游戏。
- 真正应用 Buff 是一次用户动作，必须由用户进入正确模式后手动点击“应用”。
- 未连接游戏、未进入多人生化房间或运行对象尚未就绪时，界面应显示当前条件不足，不能把已保存的选择误报成“已经生效”。
- 离开房间后，应重新判断实际生效状态，但不需要删除用户保存的两个选择。

这个例子说明：配置可以跨会话保留，用户动作不能被擅自重放，实际运行状态必须根据外部环境重新确认。

## 八、生命周期必须作为独立设计维度

只验证“功能开启后有效”是不够的。凡是持有外部对象、指针、Hook、线程、计时器、任务队列或延迟动作的功能，都应单独说明生命周期。

开发前至少回答：

```text
运行对象什么时候获取？
对象什么时候可能失效？
切回合是否保留？
换房间是否清理并重新获取？
断线重连如何处理？
关闭功能如何恢复？
程序退出时如何 cleanup？
尚未执行的延迟动作能否跨回合或跨房间继续执行？
```

不能只依赖某个可能已经错过的事件被动获取对象。也不能在场景变化后继续使用旧指针、旧实例或旧任务。生命周期边界发生变化时，应明确哪些状态保留、哪些状态清空、哪些动作需要取消。

## 九、采用渐进式架构治理

架构治理应围绕真实需求逐步进行，不要让 Agent 为了减少行数或追求“更先进的架构”主动发起大范围重构。

推荐做法：

- 修改某个功能时，只治理与该功能直接相关的职责边界。
- 页面布局放视图层，用户操作编排放控制器，业务动作放服务层，配置读写放仓库层，外部事件转换放适配层。
- 主程序只负责接线、生命周期入口和少量跨模块协调，不继续堆放具体业务逻辑。
- 功能尚未稳定、边界没有想清楚时，先不要抽象公共层。
- 不创建只有一层简单转发、没有独立职责的空壳模块。
- 小修复不扩展成全项目重构；确实需要重构时，重新给出方案和文件范围供用户确认。

判断是否值得拆分，应看职责是否清晰、是否便于独立验证、是否减少重复和耦合，而不是只看文件行数。

## 十、日志按照受众分层

新增或修改日志前，先判断日志是给普通用户看，还是给开发者排查问题使用。

```text
用户日志：说明发生了什么，以及用户下一步可以怎么做。
开发日志：记录模块、方法、Hook、地址、指针、异常、关键 ID 和重试次数。
双通道日志：用户看到简短提示，开发者保留完整技术细节。
```

要求：

- 不把 RVA、指针、Hook 名称和内部任务细节直接显示给普通用户。
- 用户操作失败时，应给出重连、进入房间或稍后重试等可执行建议。
- 高频循环、扫描和 Hook 回调日志只能进入开发日志，不能刷 UI。
- 开发日志必须包含足够的定位信息，不能只写“失败了”。
- 正式版、测试版和诊断版的日志策略必须分开，正式版不能默认遗留大量调试日志。

## 十一、发布过程必须可重复、可审计

发布不能只看“成功生成了 EXE”。推荐把流程固定为：

```text
源码与配置验证
→ 构建环境验证
→ 清理旧产物
→ 执行构建
→ 校验产物结构和版本号
→ 启动与功能验证
→ 检查日志、个人状态和开发文件污染
→ 生成哈希
→ 标记正式发布
```

工程控制要求：

- 使用固定或专用构建环境，避免依赖开发者机器上的偶然状态。
- 版本号应有唯一来源，目录名、程序名、界面和发布说明保持一致。
- 正式版、测试版、诊断版输出到不同目录，不能互相改名代替。
- 正式包不得携带开发者个人配置、功能开关状态、缓存、测试文件和调试日志。
- 构建脚本遇到缺失依赖、错误目录或缺失产物时应立即停止。
- 产物生成后仍需实际启动和检查，打包成功不等于发布完成。
- 发布文件生成 SHA-256，便于确认文件完整性和版本一致性。

## 十二、失败记录形成“原始仓库—复盘—规范升级”闭环

开发过程中可以先把问题、现象和失败尝试随手记录到原始问题仓库，不要求立即整理得很完整。问题解决后，再把有价值的内容整理为结构化复盘。

推荐复盘字段：

```text
表面现象
当时的错误真正根因
关键定位过程
最终修复
```

复盘完成后再判断是否升级：

- 只影响单个功能的细节，保留在该功能经验文档。
- 反复出现、影响较大或 Agent 很容易再次犯的问题，升级为通用规范。
- 可以自动检查的问题，尽量固化为测试或构建检查。
- 已经失效的规则及时标记或清理，避免 Agent 继续照搬旧经验。

这样既能持续积累反例，又不会把所有偶发问题都堆进全局规范，导致规范越来越难读。
