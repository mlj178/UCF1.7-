# 功能生命周期统一管理设计

## 背景

当前程序退出后，偶尔会在重新启动程序并重新连接同一个游戏进程时导致游戏闪退。

日志显示，Python 侧 `GameSessionManager.stop()`、`FridaManager.disconnect()`、JS 侧 `cleanupAll()` 大多数情况下已经执行完成，但这并不代表所有游戏效果都真正恢复干净。

核心问题是：现在很多模块把“用户手动关闭功能”和“程序退出时强制清理运行效果”混在一起了。部分模块的 `disable()` 只是改 JS 状态、清 Hook，或者等待游戏主线程下一帧恢复；程序退出时马上 `script.unload()`，这些延迟恢复动作可能来不及真正执行。

## 设计目标

程序需要把两类状态分开管理：

1. 用户想开启什么
2. 当前这次注入到游戏里的实际效果

这两件事不能互相污染。

用户想开启什么，应该保存在 JSON 里。比如用户上次开启了射速、无后座、快刀，下次程序启动后界面仍然显示开启，并且连接游戏后自动恢复这些功能。

当前这次注入到游戏里的实际效果，只在当前 Frida 会话里有效。程序退出、断开连接、重新注入前，必须全部卸载、恢复、清空。这个过程不能把 JSON 里的用户选择改成关闭。

## 生命周期规则

### 程序启动

程序启动时读取 JSON，恢复界面上的用户选择。

这一步只恢复“用户想开启什么”，不代表游戏里已经生效。

### 连接游戏成功

Frida 连接成功、脚本加载完成后，由统一管理器按 JSON 里的开启状态逐个加载功能。

加载功能时需要按顺序执行，避免大量功能同时装 Hook、解析地址、写内存，导致启动卡顿或状态竞争。

### 用户手动开关功能

用户手动开启功能时，更新 JSON，并调用模块的 `enable()`。

用户手动关闭功能时，更新 JSON，并调用模块的 `disable()`。

这里的 `disable()` 表示“用户不想继续用这个功能了”，可以保留配置，但必须尽量恢复这个功能造成的游戏效果。

### 程序退出或断开连接

程序退出前进入 `shutdown` 状态。

进入 `shutdown` 后：

- 不再把运行期的 `status=false` 写回 JSON。
- 不再接受新的功能开启请求。
- 不再把清理动作当作用户手动关闭。

然后统一执行所有模块的 `cleanup()`。

`cleanup()` 表示“当前 Frida 会话要结束了，必须强制收尾”。它不关心 JSON 里这个功能是不是开启，只负责把本次注入留下的运行效果清干净。

所有模块 `cleanup()` 完成后，再执行：

1. `script.unload()`
2. `session.detach()`
3. Python 管理器状态清空

## enable、disable、cleanup 的区别

### enable()

启用功能。

典型动作：

- 安装 Hook
- 创建 NativeFunction
- 启动定时器
- 写入必要的运行状态
- 标记模块 enabled

### disable()

用户手动关闭功能。

典型动作：

- 停止这个功能继续生效
- 尽量恢复功能修改过的游戏状态
- 关闭状态上报给 UI
- 保留用户配置，比如倍速、快捷键、武器配置

### cleanup()

程序退出、断开连接、重新注入前的强制清理。

典型动作：

- 卸载所有 Hook
- 清除所有定时器
- 清空缓存指针
- 清空 NativeFunction 引用
- 停止排队任务
- 恢复已经写入的游戏内存
- 禁止延迟任务继续运行
- 不能依赖下一帧一定会执行
- 多次调用也不能报错

`cleanup()` 应该是安全、强制、幂等的。

## 统一管理方式

JS 侧建立统一的模块生命周期协议。

每个模块尽量提供：

```js
enable()
disable()
cleanup()
isEnabled()
```

Python 侧退出时不再只调用普通 `disable()`，而是通过 RPC 调用 JS 的统一 `cleanupAll()`。

`cleanupAll()` 负责遍历所有模块：

1. 优先调用 `module.cleanup("shutdown")`
2. 如果模块暂时没有 `cleanup()`，再兼容调用 `module.disable()`
3. 记录每个模块是否清理成功
4. 返回完整清理结果给 Python 日志

长期目标是所有模块都实现自己的 `cleanup()`，最终不再依赖 `disable()` 做退出清理。

## 特别注意 BattleRound

`BattleRound` 当前在 JS 文件加载时就自动执行 `startMonitor()`。

这意味着只要 Frida 脚本加载，它就会自动装 Hook，即使用户没有真正开启对应功能。

最后一次异常日志显示，新程序重启后停在 `BattleRound [INSTALL] GameAssembly base=...` 附近，没有继续打印正常的 `Hook 已安装` 和 `Agent 已加载`。

因此这类“脚本一加载就自动 Hook”的行为风险很高，应该改成由统一生命周期管理器决定何时安装和卸载。

建议：

- JS 文件加载时只注册模块，不自动安装 Hook。
- 连接成功后，由恢复逻辑按 JSON 状态决定是否开启。
- 如果确实需要低频监听，也要明确纳入统一 lifecycle，而不是文件加载时偷偷启动。

## 改造原则

不建议继续只修某一个功能。

更合理的方向是：

- 保留 JSON 里的用户选择
- 清空当前 Frida 会话里的运行效果
- 统一启用顺序
- 统一退出清理
- 区分用户关闭和程序退出

这样既能保留“重启自动恢复功能”的体验，也能避免旧 Hook、旧指针、旧内存状态残留到下一次注入。

## 成功标准

改造完成后，需要满足：

- 程序退出后，JSON 里的开启状态不被清理流程改成关闭。
- 程序重启后，界面仍按 JSON 自动恢复用户选择。
- 连接游戏成功后，按统一顺序恢复开启功能。
- 程序退出时，每个模块都有清理日志。
- `script.unload()` 前已经完成所有模块的 `cleanup()`。
- 同一个游戏进程不重启的情况下，连续打开程序、连接、退出、重开，不应导致游戏闪退。
- 如果某个模块清理失败，日志能明确指出模块名和失败原因。
